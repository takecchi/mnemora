## ⚠⚠ 重要な食い違い: eval-undated-c1-seat-floor-reinforced

段3a（切り分け、temperature=0、20回）では eventAwareFreshness の gradeAnswer
正答数が **0/20** だった。今回の「本評価の取り直し」（temperature=0、同じ
ケース定義、trials=5）では **5/5（全問正解）**——真逆の結果である。

**検索順位そのものは、両方の実行で完全に一致している**（contextDiagnostics
を直接比較した）:
- old-seat-undated（古い予定、occurredAt/validFrom/validUntil無し）は、
  eventAwareFreshness では5 trialすべてで rank=1・enteredContext=true・
  total=0.8031002918516041（5 trial ともビット単位で同一の値）。
- legacy では5 trialすべてで rank=2・enteredContext=false・
  total=0.0007842776287613322。
- 実際の回答生成に使った recall()（診断用ではない1回目）でも、
  eventAwareFreshness は毎回 recallMemoryCount=2（両方の記憶が文脈に入って
  いる）——段3aの構造的な指摘（古い予定が常に rank1・文脈入りする）は
  この回でも100%再現している。

⟹ **検索順位（recall()のスコアリング）は temperature/実行に関係なく完全に
決定的で、常に古い予定を rank1・文脈入りさせる。** ここは段3aの結論と
1バイトも違わない。**variance があるのは、その後の LLM の回答テキスト
そのもの**である——同一のプロンプト（同じ記憶・同じ質問・同じ
system文・temperature=0）を投げても、実行のタイミング（別の日・別の
API呼び出しセッション）によって回答が変わりうる。これは OpenAI が
文書で認めている既知の制約（temperature=0 は「決定的に近づける」だけで、
ビット単位の再現を保証しない）と整合する。

⟹ **「eventAwareFreshness が legacy より劣る」という結論を、gradeAnswer の
正答数だけから断定しない。** 断定できるのは「eventAwareFreshness は
occurredAt/validFrom/validUntilを持たない古い予定を、reinforce済みなら
常に文脈の最上位へ持ち上げる」という検索側の事実であり、それが最終的な
誤答に繋がるかどうかは、LLM側の頑健さに依存し実行ごとに変わりうる。

## 🔴 段3c 追記: 上の「variance は LLM 側」という説明は誤りだった（実 API 無しで訂正）

段3a と段3b-1 の間に、このブランチが `origin/main`（Issue #691 / PR #698「回答プロンプトで
記憶の由来・話者・主題・矛盾関係を保持する」）を取り込んでおり、`mnemora-path.ts` の
`buildMnemoraPrompt` が変わっていた。段3a は取り込み前の書式（`- content` のみ、
`inputChars=81`）、段3b-1 は取り込み後の書式（`- [由来:...] [主題:...] [記録順:N]
[出来事時刻:...] content`、`inputChars=185`）で走っていた——**同じケースなのに
LLM へ渡ったプロンプトの文字数からして違っていた。**

両方の実際のプロンプト・回答を実 API 無しで確認した（旧書式の根拠は段3aの生データ
`answer-time-weighting-stage3a-isolation.json`、新書式の根拠はカセット
`answer-time-weighting.json` の再生。カセットは新書式しか含まない）:
- 旧書式（段3a、生データ）: `eventAwareFreshness` の回答は「分かりません。」——`accept`
  （`5階`）も`reject`（`3階`）も含まないため`fail`（古い方を選んだのではなく、
  答えなかった）。
- 新書式（段3b-1相当、カセット再生）: 各行に `[出来事時刻:不明]`（古い予定側）/
  `[出来事時刻:2026-07-26T09:00:00.000Z]`（現行の予定側）が付き、`eventAwareFreshness`
  の回答は「5階です。」——`pass`。

⟹ `[出来事時刻:不明]` というタグが、`occurredAt` の有無という `eventAwareFreshness` の
判断材料そのものを回答生成モデルにも見せていた。variance は LLM/temperature の非決定性
ではなく、**プロンプトの書式が段3aと段3b-1で実際に違っていたこと**が原因だった。
検索側の事実（古い予定が常にrank1・文脈入りする）は変わらず成り立つ——動くのは
「それが最終的な誤答に繋がるかどうか」のほうで、回答プロンプトの書式に依存する。
