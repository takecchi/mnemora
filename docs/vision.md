# vision — このプロジェクトの理解と用語

## これは何か

mnemora は、既存の LLM アプリケーションの**下に敷く認知レイヤー**である。

単発の `入力 → LLM → 出力` というやり取りに、次を足す。

- 継続する記憶（何を言った・何が起きたかを覚えている）
- 想起（必要なときに関連する記憶を引き出す）
- 関連付け（記憶同士のつながりを持つ）
- 忘却（不要になった記憶を薄れさせる、あるいは落とす）
- 強化（実際に使われた記憶を強くする）
- 統合（複数の記憶をより上位の記憶にまとめる）
- 内省（新しい入力が無い状態で、既存の記憶から新しい記憶を作る＝背景思考）

想定する利用先は特定のジャンルに絞らない。Web アプリ、AI 秘書、Discord Bot、ゲームの NPC、コーディングエージェント、ロボット、個人 AI、業務エージェント——「対話や判断を継続的に行う何か」であればどれも対象になりうる。

## これは何でないか

**mnemora はエージェントフレームワークの作り直しではない。**

LangGraph・Mastra・自作の Agent 実装が上に乗る。mnemora はそれらの**下**に足す位置を狙っており、それらを置き換えるものではない。

```
Application → Agent / LLM (LangGraph, Mastra, 自作 …) → mnemora → Storage / LLM / Queue
```

mnemora が持つのは記憶の生成・検索・維持のロジックであって、会話の制御フロー・ツール呼び出しの順序・エージェント間のオーケストレーションではない。それらは既に上のレイヤーにある道具の仕事であり、mnemora はそこに手を出さない。

## 解こうとしている問題

単発の `入力 → LLM → 出力` は、そのままでは何も覚えていない。毎回文脈をゼロから積み直すか、プロンプトに全履歴を焼き込むかのどちらかになる。前者は継続性を失い、後者は破綻する（量が増え続ける、矛盾した情報がそのまま並ぶ、何を根拠にその応答をしたか分からない）。

mnemora が足すのは、この間にある層——**何を覚えているか・なぜそれを思い出したか・何を思い出さなかったか**を扱う層である。

## 貫く一本の原則: 文脈を剥がして提示しない（Qualified Presentation）

mnemora の設計全体を貫く規律はひとつしかない。**文脈を剥がして提示しない。**

これは三つの現れを持つが、別々の機能ではなく、同じ一つの規律の適用先が違うだけである。

1. **争われている主張は、それを争う相手と必ず同時に提示する。** 矛盾する記憶があるとき、片方だけを「正解」の顔で出さない。
2. **推論は、その根拠と必ず同時に提示する。** LLM が導いた推論を、人間が言った事実と同じ顔で出さない。根拠を失った推論には印を付ける。
3. **結果は、そこから漏れたものと必ず同時に提示する。** 検索が0件を返したとき、それが「探して無かった」のか「そもそも探していない」のかを区別する。件数についても、正確に数えたのか、推定なのかを区別する。

この原則の具体的な実装（`status` によるフィルタ、`omitted` の分類、`provenance.kind` の判別可能ユニオンなど）は `docs/architecture.md`・`docs/recall.md`・`docs/memory-model.md` に譲る。ここでは「なぜこの原則を置くか」だけを言っておく。**記憶を扱うシステムが信頼を失う典型的な経路は、間違った答えを返すことよりも、答えの根拠や限界を見せずに断定的に返すことにある。** mnemora はこれを最初から設計原則に組み込む。

## 外から見える API: 中核の5動詞

mnemora が外部に公開する、**記憶そのものを動かす**操作は5つの動詞に限る。**ここは増やさない。**

```ts
observe(ctx, input)      // -> Observation
recall(ctx, query)       // -> RecallResult
reflect(ctx, opts)       // -> ReflectionResult
consolidate(ctx, opts)   // -> ConsolidationResult
forget(ctx, target)      // -> ForgetResult
```

- `observe` — 外から入ってきた出来事を記録する。
- `recall` — 問いに対して記憶を取り出す。
- `reflect` — 入力が無い状態で、既存の記憶から新しい記憶を作る（内省・背景思考）。
- `consolidate` — 複数の記憶を統合して、より上位の記憶を作る。
- `forget` — 記憶を落とす、あるいは失効させる。

### 中核を守る3つの層

`Runtime`（`@mnemora/core` の実装）には、上の5つ以外にもメソッドがある。⭐ **何が在るかの
正本は `packages/core/src/runtime.ts` の `export interface Runtime` である**——⛔ **ここに個数を写さない**
（[ADR 0234](./decisions/0234-bake-no-numbers-into-tools-and-artifacts.md)）。これらは
「6つ目の動詞」ではなく、中核を5つに保つために別の層へ出した口であり、3つに分かれる
（検討過程は [ADR 0171](./decisions/0171-five-verbs-plus-three-layers.md)）。

⚠ **下の3層の列挙は、ADR 0171 が分類した時点のものであり、⛔ いま在るものの全部ではない。**
実際に `findCorrectionCandidates`（[ADR 0232](./decisions/0232-correction-candidates-returned-not-chosen.md)）は
どの層にも置かれていない——どこへ置くかは意味の判定であり、機械には決まらない
（[Issue #518](https://github.com/takecchi/mnemora/issues/518)）。⛔ **書き込まない口**なので、
少なくとも「是正・取り消し」（**書き込む**口）ではない。

⚠ **`applyCorrection`（[ADR 0242](./decisions/0242-runtime-apply-correction.md)）も、
どの層にも置かれていない。**ただし `findCorrectionCandidates` と同じ理由では説明できない
——`applyCorrection` は `markContested`/`resolveContested` を呼んで実際に書き込む口である
（ADR 0242 決定3）。**「書き込まないから」という除外は使えない**以上、どの層に当たるかは
依然として意味の判定であり、この一覧はそれを決めていない（Issue #518）。

- **保守操作**（`tick` / `reembed` / `reextract` / `sweepArchive`）——「いつ動かすか」を
  呼び出し側が決める口。自動では走らない。
- **是正・取り消し**（`markContested` / `resolveContested` / `restoreArchived` /
  `restoreSuperseded` / `purge`）——呼び出し側（人・上位のアプリケーション層・将来の
  自動検出）が既に下した判断（矛盾の指摘・決着・復帰・完全削除）を、決められた形で
  書き込む口。どちらが正しいかを mnemora 自身は判定しない。
- **説明**（`getRecall`）——なぜそれが想起されたかを、後から読み戻す口。

**この分類が守っているのは「中核は増やさない」という制約そのものである。**新しく何かを
足したくなったとき、それが記憶そのものを動かす操作なら中核には足せない。保守・是正・説明の
どれかに当たるなら、その層の性格に合っているかを問う——合わないなら、そもそも mnemora が
持つべき機能かどうかを疑う。

一点、判断が必要になったのが「どの記憶を実際に使ったか」というフィードバックをどう受けるかである。**これは新しい動詞を作らず `observe()` で受ける**（`observe(ctx, { kind: 'memory_usage', recallId, usedMemoryIds })`）。理由は三つ。「起きたことを記録する」入口をひとつに保てること、冪等キーの扱いが一箇所で済むこと、そして動詞を増やさないという要求を満たせることである。

代案として「`recall()` の戻り値にメソッドを生やす」「6つ目の動詞 `reinforce()` を作る」も検討したが、**戻り値にメソッドを生やすとシリアライズできず、HTTP 越しに使えなくなる**（将来 HTTP server / SDK を持つ構成で破綻する）ため却下した。この判断の詳細は ADR に残す。

API の詳細な型・スコアリング・説明可能性の設計は `docs/architecture.md` と `docs/recall.md` に譲る。

## やらないこと

mnemora が明示的にスコープ外とするもの。

- 独自 LLM / Embedding モデルの学習、そのための GPU 基盤
- LangGraph のようなエージェントフレームワークの代替
- 汎用の Workflow Engine
- AGI のシミュレーション、脳の忠実な再現
- 複雑な感情シミュレーション
- 3D Avatar、Voice Interface
- **テナント・ユーザーの台帳や認証の管理**

最後の項目は mnemora 側の判断として加えたものである。`tenantId` は呼び出し側が渡す不透明な文字列として扱い、mnemora はその正当性を検証しない。誰が誰であるかを管理する仕事（認証・アカウント管理）は上位のアプリケーションの責務であり、mnemora が持つと責任の境界が曖昧になる。

## 用語整理

| 用語 | 意味 |
|---|---|
| **Observation** | 外から入ってきた出来事の生の記録。不変。解釈しない。 |
| **Memory** | Observation から抽出された、再利用可能な単位の記憶。 |
| **Digest** | Memory の要旨1行。必須（NOT NULL）。目次に載るのはこれ。 |
| **Recall** | 問いに対して Memory を取り出す一回の操作。識別子を持ち、記録される。 |
| **Provenance** | その Memory がどこから来たか。判別可能ユニオンで表す。 |
| **Strength / Decay** | 記憶の強さと、時間による減衰。 |
| **Reinforcement** | 実際に使われたことによる強化。検索に出ただけでは強化しない。 |
| **Consolidation** | 複数の Memory を統合してより上位の Memory を作ること。 |
| **Reflection** | 入力が無い状態で、既存の Memory から新しい Memory を作ること。 |
| **Tenant** | **隔離境界。安全性の単位。** 跨いだら事故になる。 |
| **Subject** | テナント内の**分割。整理の単位。** 跨いでも事故ではない。 |
| **Embedding Space** | (モデル, 次元) の組。mnemora は次元を固定せず、「空間」を単位にする。 |

### Tenant と Subject を混同しない

この二つはよく似た概念に見えるが、意味が異なる。**Tenant は隔離境界であり、Subject は整理の単位である。**

例として Discord Bot を考える。ひとつの Bot がいくつものサーバー（Discord のギルド）に導入されるとき、**「Bot の導入先ギルド」が Tenant** になる。あるギルドの記憶が別のギルドに漏れることは、設計上あってはならない事故である。一方、**「そのギルド内の各ユーザー」は Subject** になる。同じギルド内でユーザー A の記憶とユーザー B の記憶が混ざることは望ましくないが、これは整理の失敗であって、Tenant を跨ぐ事故とは性質が違う。

`tenantId` は全テーブルで NOT NULL とし、すべての一意制約・索引の先頭に置く。`subjectId` はテナント内の分割軸のひとつにすぎない。この非対称性——**Tenant を跨ぐことは事故だが、Subject を跨ぐことは事故ではない**——を、用語としても実装としても曖昧にしない。詳細は `docs/architecture.md` の multi-tenant の節に譲る。

## 名前について

**名前は `mnemora`（scoped では `@mnemora/*`）に確定した。** 2026-09-05、オーナーの判断による。
暫定ではない。

- **npm の org `@mnemora` はオーナーが作成し、使用できることを確認した。** この確認をしたのは
  オーナーであり、**この文書の書き手ではない**——本書は npm の状態を自分では確かめていない。
- **unscoped の `mnemora` については何も調べていない。**

決定の記録（採らなかった案とその理由を含む）は
[ADR 0014](./decisions/0014-package-name-mnemora.md) にある。

### 経緯（改名前。当時の名前は `mnemo`）

**以下は改名前に書かれた当時の記述であり、当時の調査・当時の推奨をそのまま残してある。**
ここに出てくる `mnemo` は**当時の名前**、または**他人の npm パッケージの名前**であって、
現在のこのプロジェクトの名前ではない。

パッケージ名は `mnemo`（scoped では `@mnemo/*`）を予定している。確認できた事実と、まだ確認できていないことを分けて書く。

- **unscoped の `mnemo` は npm に既に存在する。** 2014年公開、`dist-tags.latest = 0.0.4`、Rufus::Mnemo という別ツールの JS 移植で、最終更新は 2022-06。4年以上更新が無い、別ジャンルの小さなパッケージである。
- **`@mnemo/core` は 404（未公開）を確認した。** ただし **npm の org `mnemo` が確保できるかどうかは確かめられていない。** org のページは未ログインだと 403 を返すため、取得可否を判定できなかった。

この状況で、**名前 `mnemo`（scoped `@mnemo/*`）を維持する**という判断をしている。理由は次の三つである。

1. scope 付きの `@mnemo/*` であれば、unscoped の `mnemo` との衝突は実務上問題にならない。
2. 既存の `mnemo` は更新の止まった別ジャンルの小パッケージであり、検索上の混同リスクは低いと見ている。
3. 名前の変更は後からでもできるが、設計そのものの議論を止める理由にはならない。

一方で、**npm org `mnemo` が実際には取得できなかった場合にどうするかは、この文書の判断だけでは決め切れない。** オーナーが決めるべき点として `docs/roadmap.md` の「設計上まだ判断が必要な点」に残す。代案の候補は次の通り。

| 候補 | 理由 |
|---|---|
| `@mneme/*`（推奨） | ギリシャ神話の記憶の女神。意味が近い。`mneme`（unscoped）自体は npm に存在するが、scope は別なので衝突しない。 |
| `@anamnesis/*` | 「想起」そのものを指す語で意味は強いが、読みにくく打ちにくい。 |
| `@recall-os/*` | 機能語なので衝突しにくいが、名前としては凡庸。 |

**この文書としての推しは `@mnemo/*` の維持である。** ただし最終判断はオーナーに委ねる。

**この当時の推奨は覆った。** 2026-09-05、オーナーの判断により名前は `mnemora`
（`@mnemora/*`）に変更され、`@mnemo/*` の維持も上表の3候補も採られなかった
（[ADR 0014](./decisions/0014-package-name-mnemora.md)）。
