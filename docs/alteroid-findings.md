# alteroid 調査の記録 — 確かめたこと / 確かめられなかったこと

この設計の材料として、**alteroid**（https://github.com/takecchi/alteroid）の運用知見が
6項目（A〜F）添えられていた。**現物を読んで、それが本当かを確かめた。**その記録である。

**この文書を残す理由**: 設計の各所（`recall.md` の目次帯、`memory-model.md` の矛盾の扱い、
`decisions/0001` の ORM、`decisions/0008` の不在の分類）が alteroid を根拠として引いている。
**根拠を辿れない主張を置かない**——これはこのプロジェクト自身の原則
（[vision.md](./vision.md) の「文脈を剥がして提示しない」）を、設計文書そのものに適用したものである。

**読んだ範囲**: `AGENTS.md`（`CLAUDE.md` はその symlink）、`docs/`、`packages/core`、
`packages/storage-pg`、`apps/daemon`、`apps/cli`。
**読んでいない範囲**: `packages/api-client`、`apps/web`、`packages/storage-fs` の実装本体、
`docs/` 各文書の本文（目次のみ確認した部分がある）。

## A. 目次の不変条件 — 確認できた

**確認できたこと**
- 区分 `premise | fact` は実在する（`packages/core/src/schema.ts` の union）。
  **ただし DB の列ではない。**Markdown の frontmatter を毎回パースして導出している。
- 全文帯と目次帯への排他的な振り分けは実在する
  （`packages/core/src/memory.ts` の `renderMemoryDocuments` / `buildMemoryDocumentSections`）。
  **分岐が2値しかなく、第三の状態を作れない**形でコードが担保している。慣習ではない。
- **安全弁**: frontmatter が無い・壊れている・未知の値は、**すべて `premise`（全文・厚い側）に倒れる。**

**限定（重要）**
1. **不変条件が厳密に成立するのは、セッション構築時の1回（システムプロンプト全体）についてだけ。**
   セッション途中の差分通知（「変わった文書だけ」を渡す経路）では成立しない。
   **これはコードの doc コメント自身が明記している穴である。**
2. **alteroid には埋め込み（ベクトル検索）が存在しない。**
   ⟹ 「埋め込みを安全に外せるようにする」という教訓は、alteroid では
   **「埋め込みが最初から無い」状態の記述**であって、
   **「埋め込みを持つ系に目次を足した」経験ではない。**
3. **目次のエントリ数に上限（300件）がある。規模で壊れる経路がコード上に既に見えている。**
4. 要旨は **LLM 生成ではない**。書き手が frontmatter に手で書いた `description` を200文字で切るだけ。
   無ければ「（要旨なし）」という固定文言（先頭N文字のフォールバックすら無い）。

**mnemora での扱い** → [recall.md](./recall.md) の目次帯 / 被覆不変条件
- 定式（「目次は検索が外れたことを可視化する仕組み」）は採る。
- **保証の単位を最初に定義した**: 被覆不変条件は `recall()` 1回の返り値について成立する。
- **二階建てを三階建てにした**（1テナント100万件の digest はプロンプトに載らない）。
- **安全弁の思想は採る**: 分類に失敗したら薄い側でなく厚い側に倒す。
- **要旨は抽出時に生成し NOT NULL にする**（alteroid と違う。人手編集を前提にしないため）。

## B. 「無い」の種類を潰さない — 現物は違う

**確認できなかったこと**
- **alteroid には、スコア付き候補・閾値・LLM 選別を伴う検索が存在しない。**
  記憶へのアクセスは `memory_list`（一覧）と `memory_read`（slug 指定で開く）のみ。
- **埋め込み・ベクトル検索・rerank はリポジトリ全体で1件もヒットしない。**
- ⟹ 「候補には出たがスコアで落ちた」「候補に出たが LLM が使わなかった」に相当する処理は**そもそも無い。**
  この主張が前提とする RAG 的なパイプラインは alteroid には存在しない。

**確認できたこと（1箇所）**
- 日誌の部分一致検索（`ILIKE`）が0件を返したとき、
  **「探索対象に入っていない欄がある」ことまで自然文で応答に含めている。**
- これは「**検索して0件**」と「**そもそも検索していない**」の区別そのものであり、**原則の核は本物だった。**
- **違うのは、それが自然文1メッセージであって型ではないこと。**

**mnemora での扱い** → [recall.md](./recall.md) §4、[ADR 0008](./decisions/0008-absence-taxonomy.md)
- 原則は採る。**ただし「alteroid で実証済み」とは書かない。**
- mnemora がやるのは**それを型に持ち上げること**で、alteroid の延長ではなく新しくやること。

## C. 矛盾の扱い — 記録が見つからない

**渡された主張**: 訂正を文書の末尾に積んだところ、先に読まれるのは古い方だった（実害が出た）。
結論は「偽になった記述は、積むのではなくその場で置き換える」だった。

**確認できなかったこと**
- **この因果を記した記述は、コードにもドキュメントにも見つからなかった。**

**確認できたこと**
- **全文置換ツール（`memory_write`）と末尾追記ツール（`memory_append`）が両方存在する。**
  どちらを使うかは書き手に委ねられており、「積むのではなく置き換える」は強制されていない。
- frontmatter だけを直す差分パッチの口（`memory_frontmatter_set`）もあるが、これは別軸の機構。
- **supersede / 失効マーク / 版管理に相当する機構は無い。**
- 「保護状態」（human / clone-only / unknown）という機構は在るが、
  これは人間が書いた文書を自動処理が勝手に置換・削除しないための歯であって、訂正の衝突への対処ではない。

**この判定の読み方**
**クローン自身の経験を否定するものではない。**経験はリポジトリに残らない。
だが「alteroid で検証された結論」として設計の根拠に据えることはできなかった。

**mnemora での扱い** → [memory-model.md](./memory-model.md) の矛盾の節、[ADR 0006](./decisions/0006-memory-schema.md)
- 問題設定そのものは正しいと判断して解いた。
- **ただし診断を一段ずらした**: 実害の正体は「古い方が上だった」ことではなく
  **「古い方と新しい方が離れていた」**ことだと読んだ。⟹ **順序では解かない。**
  1. `status` 列で `superseded` を既定の recall から**外す**（下に出すのではなく出さない）
  2. 決められないときは `contested` に落とし、**対向をスコアに関係なく必ず同伴取得する**
  3. **隣接を不変条件にする**（対向を提示順で分離させない）

## D. 強化は「実際に使った」ものだけ — 未実装

**確認できなかったこと**
- **alteroid に reinforcement の実装は一切存在しない。**
  使用回数・最終使用時刻・スコア更新のいずれも無い。
  （`lastUsedAt` という列は在るが、これは認証トークンのもので記憶とは無関係。）
- **この設計原則を明文化した記述もドキュメント上に見つからなかった。**

**mnemora での扱い** → [memory-model.md](./memory-model.md) の強化の節
- 結論そのものは採る（検索に出ただけで強化すると、たまたま出続ける記憶が自己強化される）。
- **ただし「alteroid でも同じ結論に至っている」とは書かない。**
  これは運用で検証された結論ではなく、**設計上の判断である。**

## E. 焼かれる量を測って出す — 確認できた。そして最も重い発見がここにある

**確認できたこと**
- 計測は実在する。**単位は文字数（`String.length`）であって token ではない。**
- 書き込み系4ツールすべてが「前後の文字数」と「セッション構築時点からの増分（%）」を応答に連結する。
- 増分の基準値は**プロセス内のメモリ変数**で、システムプロンプト構築時に1回確定し、以後固定。
  ⟹ **1クローン = 1長寿命プロセスという前提に強く依存している。**
- 閾値付きの警告（+10%）も在るが、これは定期ジョブ側に付くもので、
  書き込みツールの応答に付くのは生の増分%文言のみ。**二つは別経路。**

**⚠ 最も重い発見**
- **alteroid のコード自身が「この機能が効くかは未検証」と書いている。**
- 実測で **37,515 → 51,751 文字（+38%）**まで増えたのを見ながら、
  **使う側は畳む行動を取らなかった**、という事例がコード内に記録されている。

**mnemora での扱い** → [recall.md](./recall.md) §6、[roadmap.md](./roadmap.md) の「計測と抑止を混同しない」
- **「測って見せれば行動が変わる」を検証済みの知見として輸入しない。**
- mnemora は計測（`usage`）を**提供する**が、**それが肥大を抑止するとは主張しない。**
- **抑止する力を持つのは計測ではなく、超えたら実際に落とす予算（`budget`）である。**
  ⟹ **計測と強制を分けて両方持つ。計測だけで済ませない。**
- **「セッション構築時点からの増分」は持たない。**基準値がプロセス内変数であることが示す通り、
  この機能は単一プロセス前提に依存している。mnemora は多テナント・マルチインスタンスであり、
  セッションという概念は呼び出し側にある。
- さらに: **mnemora はプロンプトを組み立てないので、「プロンプト全体の何割か」は原理的に測れない。**
  alteroid が割合を出せるのは、alteroid 自身がプロンプトを所有しているからである。

## F. 削除は追記専用の記録に必ず残す — 確認できた。担保の作り方まで良い

**確認できたこと**
- 追記専用ログの実体は PostgreSQL の `journal` テーブル。
- **`JournalStore` interface は `append` / `list` / `get` の3つしか持たず、
  update / delete に相当するメソッドが型として存在しない。**
- 記憶の削除経路は2つ（クローン向けツールと人間向け HTTP）に閉じており、
  **どちらも削除の直後に必ず日誌へ追記する。**CLI は独自実装を持たず HTTP 経路を叩くだけ。
- 記録項目は slug・原因（human / clone / distill）・削除直前のバイト数・要約。**本文は本当に残らない。**
- 「必ず」の強制度は**型レベル（update/delete が無い）と経路の集約の二重**で担保されている。

**確認できなかったこと**
- DB へ直接 `DELETE FROM journal` を打つ運用者に対する防御は、コードレビューの範囲外。
- `storage-fs` 側で同じ規律が守られているかは**読んでいない。**

**alteroid に無く mnemora に要るもの**
- **保持方針・ローテーション・上限が無い**（無期限に積む設計）。**multi-tenant では破綻する。**

**mnemora での扱い** → [memory-model.md](./memory-model.md) の監査ログの節、
[architecture.md](./architecture.md) §5.8
- **担保の作り方をそのまま採る**: `EventStore` interface に `update` / `delete` を持たせない。
  **型に無ければ、間違って消す経路がそもそも生えない。**
- **Phase 1 に入れる**（追加費用は1テーブルと1 INSERT。
  後から入れると「入れる前に消えたもの」が永久に見えない）。
- **保持方針を追加する**: テナント単位で設定可能にし、
  **期限切れの削除自体が `purged` イベントとして残る**（件数と期間のみ）。
  「消えたことが見える」を、ログの掃除に対しても保つ。

  > ⚠ 訂正注記（2026-09-29、[ADR 0375](./decisions/0375-purge-scope-widened.md) 作業中に気づいた）:
  > 上の「`purged` イベント」は取り違えである。期限切れの `memory_events` の削除自体が積むのは
  > `kind: 'purged'` ではなく **`kind: 'events_purged'`**（`memory_id` は必ず `NULL`。
  > `memories` を物理削除する `purge()` が積む `kind: 'purged'`（`memory_id` を持つ）とは別のイベント種）
  > ——[ADR 0115](./decisions/0115-event-retention-purge.md) と `docs/memory-model.md` §9 参照。
  > 本文はここでは書き換えず、注記だけを足す。

## 補足: alteroid から得られなかったもの

設計の判断材料として期待していたが、alteroid には無かったもの。

| 論点 | alteroid の状態 |
|---|---|
| **ベクトル検索 / pgvector** | **使っていない。**リポジトリ全体で1件もヒットしない |
| **multi-tenant** | **明示的な非ゴール。**持ち主は高々1人で、DB 制約で強制されている |
| **忘却 / 減衰 (decay)** | **実装なし** |
| **強化 (reinforcement)** | **実装なし** |
| **スコア付き検索** | **実装なし**（一覧と slug 指定の読み出しのみ） |
| **ORM** | Drizzle。ただし **pgvector を使っていないので「pgvector × ORM」の判断材料にはならない** |

**記憶の単位そのものも違う。**alteroid の Memory は slug で引く Markdown 文書であり、
mnemora の Memory は行単位のレコードである。粒度が違うため、
**強化・忘却・矛盾の扱いは、そもそも alteroid の設計をそのまま持ち込める形になっていない。**
