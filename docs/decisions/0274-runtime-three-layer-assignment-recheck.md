## 決定4. 「どちらの読みも成り立つ」2件 — 両方の読みと根拠

### `applyCorrection`

**読みA（是正・取り消しに当たる）**:
`applyCorrection` は「候補を選ぶ」ことは一切せず（doc コメント「⛔ この口も『相手を選ぶ』ことは
一切しない…`correctedId` は必ず呼び出し側が渡す」）、呼び出し側が既に決めた
`correctedId`/`correctingId`/`resolution` を、決められた手順で `markContested`/
`resolveContested` に書き込むだけである（ADR 0242 決定3、実装で確認済み——issue #605 自身も
この事実を「機械的な材料」として名指ししている）。**これは是正・取り消しの定義文「呼び出し側が
既に下した判断…を、決められた形で書き込む口。どちらが正しいかを mnemora 自身は判定しない」と
語のレベルで一致する。**⟹ この読みを採るなら、現在の3文書の「どの層にも置かれていない」という
扱いは**食い違い**であり、是正・取り消しへ動かすのが筋、ということになる。

**読みB（どの層にも自然には当てはまらない）**:
`applyCorrection` は是正・取り消し層のメンバー（`markContested`/`resolveContested`/
`restoreArchived`/`restoreSuperseded`/`purge`）のように**それ自身が単発の書き込みを行う**
のではなく、doc コメント自身が「発見（`findCorrectionCandidates`）と書き込み
（`markContested`/`resolveContested`）の**間**——『選択』の段」と位置づける**合成・調整
（orchestration）操作**である。`correctedId` が無ければ何も呼ばずに `awaiting_choice` を
返し、`resolution` が無ければ `markContested` までで止まる——**呼び出しごとに、実際に是正・
取り消し層のどのメンバーを何回呼ぶかが変わる**。是正・取り消し層の他の5メンバーは「1つの
判断を1つの書き込みに変換する」という一様な形をしているのに対し、`applyCorrection` は
「2つの既存の口（発見と書き込み）を状態機械でつなぐ層」であり、性質が1段階上にある。**⟹ この
読みを採るなら、既存の3層のどれにも自然には収まらず、3文書の現在の扱い（未配置）は正しい。**

**本 ADR はどちらか一方に決めない。**issue #605 自身が「`findCorrectionCandidates` と
`applyCorrection` を、どの層に置くか」をオーナー領分の1番目に明示しており（下の「引き受けた
負債」参照）、この判断はそこに属する。

### `findCorrectionCandidates`

**読みA（保守操作に当たる、という弱い読み）**:
保守操作の定義文は「『いつ動かすか』を呼び出し側が決める口。自動では走らない」であり、
`findCorrectionCandidates` の doc コメントにも「⚠ `tick()`/`observe()` からは一度も呼ばれない。
`markContested` と同じ立場——呼び出し側が明示的に呼んだときだけ動く」とある。**定義文の
「自動では走らない」だけを見れば字面は一致する。**

**読みB（どの層にも当てはまらない、という読み。本 ADR はこちらを有力と見る）**:
保守操作の実例4本（`tick`/`reembed`/`reextract`/`sweepArchive`）はいずれも「既存のパイプライン
処理（抽出・埋め込み・アーカイブ）を、呼び出し側の指示で再実行・進行させる」という共通の性質を
持つ。`findCorrectionCandidates` は**書き込みを一切しない**検索操作であり（doc コメント
「⛔ 書き込みを1件もしない」）、`recall()` を1回呼ぶだけの薄いラッパーに近い——パイプラインの
保守とは性質が異なる。**さらに重要な観察**: 「自動では走らない」という性質は、是正・取り消し
層の全メンバー（`markContested` 等も「呼び出し側が明示的に呼んだときだけ動く」と doc コメントに
明記）にも共通しており、**保守操作の定義文はこの1文だけでは保守操作と是正・取り消しを判別
できない**——実際の判別は、定義文に明示されていない暗黙の基準（パイプラインの再処理か、
既存メモリの状態についての判断の書き込みか）に依存している。⟹ **この曖昧さ自体が、ADR 0171
の定義文の精度についての発見であり、個々のメソッドの誤配置の話とは別に記録する価値がある。**

**判定はどちらの読みも成り立つとした**が、読みBのほうが実例との整合が強い、という所見を添える。
最終的な帰属先の決定はオーナー領分（下記）。

2. **⛔ 3層の判定を機械的な歯（テスト）に広げる案。** 却下——issue #605 が明示的に「引き受け

   照らしても、ADR 0171 は既に「採用」状態であり、かつ**追記すら本 ADR がやってよい範囲では
   ない**——「文書側を直すのか層の定義側を見直すのか」自体がオーナー領分（引き受けた負債1番）
   だからである。

## これが覆るとしたら何が起きたときか

- **オーナーが「引き受けた負債」の3点に回答したとき**——特に1番（`findCorrectionCandidates`/
  `applyCorrection` の帰属）に回答が出れば、決定4の「どちらの読みも成り立つ」は「一致」または
  「食い違いだった」のどちらかに確定し、本 ADR のその部分は古い記録として残るだけになる。
- **`Runtime` に18本目のメソッドが増えたとき**——本 ADR の決定1・決定3 の「17本」は
  `main = 722f45d` 時点の記録であり、以降の変化はこの ADR を検算し直す別の作業が要る
  （`AGENTS.md`「数を、道具と生成物に焼き込まない」により、本 ADR 自身は将来のツールに
  この数を埋め込んでいない——ADR は当時の記録なのでここに書くこと自体は許容される）。
- **保守操作と是正・取り消しの判別基準（決定4で指摘した「自動では走らない」の共通性）に
  ついて、ADR 0171 の定義文が改定されたとき**——本 ADR の該当所見はその時点で解消済みの
  指摘として残る。
