## 文脈

### 1. 北極星が矛盾について約束していること —— **全文はこれだけである**

**【実測】`grep -n "矛盾\|訂正\|間違い\|contested\|争" docs/north-star.md` は 2行しか返さない。**
要約せずに、その2行を逐語で引く。

**（1）「目指す姿」の項目5**（`docs/north-star.md:32`）:

> - **間違いを正すと、古いほうが先に出てこなくなる。**

**（2）「この問いが、実際に案を落とすことの確認」の表、問い5 の行**（`docs/north-star.md:112`）:

> | 5 | 「矛盾を recall のたびに LLM に判定させる」「目次帯を LLM に要約させる」 | **落とせた**（`status` 列と集約クエリで解ける） |

**⟹ 正典が矛盾について言っているのは、「外から見てこう現れる」が1つと、
「この形では解かない」が1つ、それだけである。**

🔴 **ここから3つのことが従う。読み違えやすいので分けて書く。**

1. **正典は「mnemora が矛盾を自動で検出する」とは書いていない。**項目5 の主語は
   「間違いを正す」側であり、それが mnemora なのか採用者なのかは文面から決まらない。
   ⛔ **だから「検出が無いのは正典違反である」とは、この2行からは言えない。**
2. **正典が落としたのは「recall のたびに LLM に判定させる」である。**
   ⛔ **「LLM に判定させる」一般ではない。**【現物】Issue #197 に付いた2件目のコメントが
   同じ区別を既に指摘している（逐語: 「**北極星が問い5を落とした案とは別物である点に注意
   ——落とされたのは『recall のたびに』であり、これはバッチで1回**」）。
   ⚠ **ただし、この区別に寄りかかる案は問い5 の本文
   （「列と索引で解けるものを、モデルに問わない」）を別途通す必要がある**——
   落とされた行の外に出ることと、問いを通ることは別である。
3. **括弧の中の「`status` 列と集約クエリで解ける」は、矛盾の*提示*について言っている。**
   `status IN ('active','contested')` のゲートと段3 の同伴取得のことであり、
   **「どの2件が矛盾しているかを `status` 列から導ける」とは言っていない。**
   検出の側は、正典のこの行では解かれていない。

**どちらになるかは、#197 でどの検出方式を選ぶかが決める。**⟹ **依存の向きは、

**【現物】Issue #208 本文、逐語:**

> 落とした問いは **問い3「この記憶が選ばれた理由を、後から説明できるか」**。⟹ **説明できない賢さは採らない。**

### 6. 🔴 これは3回目である —— **出荷される既定が、北極星と反対を向く**

⛔ **項目5 の「半分」を、個別の不足として片付けない。**同じ形が既に3回出ている。

| # | 何が | 機構は | 出荷される既定は | 結果 |
|---|---|---|---|---|
| 1 | **連想枠**（項目2「聞かれていないことを、自分から思い出す」） | 在る（`recall-runtime.ts` の段3.5） | **off**（`recall.ts` の `association?:` は optional で既定値の代入が無い） | **半分**（§7.4） |
| 2 | **矛盾の検出**（項目5「間違いを正すと、古いほうが先に出てこなくなる」） | **検出は無い**。書き込みの口だけ在る | 呼ばれない（`packages/` に呼び手0件） | **半分**（本 ADR §4） |
| 3 | **連想枠の `omitted`**（項目6「知らないことを、知らないと言える」） | — | — | 【受】**別の担い手が 2026-09-17 に見つけたと受け取った。⛔ この作業者は現物を確認していない** |

**⟹ 共通の形は「機構が無い」ではない。「機構は在るが、出荷される既定がそれを使わない」である。**

🔴 **そして、この形は #284 の規律では捕まらない。**#284 が問うのは「**それを書くコードが1行でも在るか**」であり、
**在れば通る。**⟹ `examples/chat` に1本在れば、#284 の字義では「在る」になる。
⛔ **だが `examples/chat` は `"private": true` で出荷されない**（`package.json:4`、`PUBLISH_TARGETS` 6件に不在）
⟹ **利用者には1バイトも届かない。**

**⟹ #284 は「機構が空振りしていないか」を測る歯であって、「利用者に届いているか」を測る歯ではない。**
§7.2 が要求しているのは後者である（逐語「目指す姿が*外から見て*満たされる」）。
**この2つを同じ歯で測ろうとしたことが、3回とも同じ形の誤判定を生んでいる。**

⚠ **本 ADR はこの癖を直さない。**名指しするだけである——直すなら
**「`packages/` の外に唯一の呼び手が在る」を機械的に検出する歯**が要り、
それは矛盾の設計とは別の主張である。⛔ **混ぜない。**

## 決定

### 決定1: 検出を「誰が矛盾だと決めるか」×「誰が相手を探すか」の2軸で分ける

**⛔ 「自動検出を入れるか / 入れないか」の1軸で考えない。**その形にすると、
ADR 0134 が既に落とした案（案A）を再提出するか、今日のまま何もしないかの2択になる。
**現物を読むと、独立した2つの仕事が1つに潰れている。**

| | **相手を探すのは採用側** | **相手を探すのは mnemora** |
|---|---|---|
| **矛盾だと決めるのは採用側** | **(A) 今日の姿。**採用側が2件の `MemoryId` を知っている前提で `markContested` を呼ぶ | **(C) 訂正の口。**採用側が「これは訂正である」とだけ言い、相手は mnemora が自分の recall で探す |
| **矛盾だと決めるのは mnemora** | （意味を成さない） | **(B) 主張キー。**抽出時に「何についての主張か」を構造として持たせ、同じ鍵の衝突を列と索引で見つける／**(E) LLM に矛盾判定そのものを問う** |

**⟹ (A) と (B) の間は空白ではない。(C) が在る。**
Issue #197 が挙げた3択（抽出時 / 背景処理 / 明示的操作）は**置き場所**の軸であり、
**責務の軸ではなかった**——(C) はその3択のどこにも現れない。

### 決定2: 候補の評価 —— **(C) を第1弾、(B) を第2弾、(D)(E) は落とす**

| 案 | 中身 | 費用 | 北極星 | 判定 |
|---|---|---|---|---|
| **(A) 現状維持** | 何も足さない | 0 | 問い1◯ 問い2◯ 問い3◯ 問い4◯ 問い5◯ | ⛔ **落とす。**どの問いにも触れないが、**項目5 が「半分」のまま固定される。**#197 は永久に閉じない |
| **(C) 訂正の口** | `Runtime` に「この発話は訂正である」を受ける口を足す。相手は既存の recall で探し、見つけた相手と `markContested` する。**LLM を1回も呼ばない** | 🟡 中。core に口1本 + 相手探しの配線。**抽出プロンプトを変えないのでカセットの録り直しが要らない**（後述の費用の節） | 問い1△（同伴で増えるが、解決で恒久的に減る）問い2◯（呼ばなければ今日と同じ）問い3◯（相手を選んだスコアを `explain` に出せる）問い4◯（`provenance` を触らない）問い5◯ | ⭕ **採る（第1弾）** |
| **(B) 主張キー** | 抽出の構造化出力に「何についての主張か」の鍵を足し、同じ鍵・同じ `subjectId` で値が違う `active` 同士を**列と索引で**見つける | 🔴 大。**抽出プロンプトの変更 ⟹ カセット全滅**（後述）＋ 多対多 ⟹ **#207 が前提になる** | 問い1△ 問い2◯ 問い3◯（「同じ鍵・重なる有効期間・違う内容」は1行で説明できる）問い4🔴（鍵は LLM が作る＝推論。**混ぜない設計が要る**）問い5◯（**判定は列と索引。LLM には「何の話か」しか訊かない**） | ⭕ **採る（第2弾。ただし前提2つ）** |
| **(D) 埋め込み類似度 + 閾値** | 「同じ `subjectId` かつタグ重複かつ類似度が閾値超え」で矛盾を推測 | 小 | 問い3🔴 **落ちる** | ⛔ **落とす。**ADR 0134 案A(b) が既に落としている。**「0.87 > 0.85 だから矛盾」は数であって理由ではない**——Issue #208 が reranking に掛けたのと同じ条件で落ちる。**「類似しているが違う」と「矛盾している」を混同する** |
| **(E) LLM に矛盾判定を問う** | 抽出時または背景処理で、既存の記憶を添えて「どれと矛盾するか」を LLM に訊く | 大（プロンプトに既存記憶を積む） | 問い1🔴（毎回積む量が増える）問い5🔴（**(B) で列と索引に解ける以上、モデルに問う理由が無い**） | ⛔ **落とす。**ただし (B) の鍵が実用にならなかったときの退路として記録する |

**🔴 (B) と (E) の差が、この ADR のいちばん細い線である。**どちらも LLM を呼ぶ。違うのは**何を訊くか**である。

- **(E) は「この2件は矛盾するか」を訊く**——判定そのものをモデルへ出す。
  ⟹ 判定の理由はモデルの中にしか無い ⟹ 問い3 に答えられない。
- **(B) は「この記憶は何についての主張か」を訊く**——**抽出が今日すでに訊いていること**の
  延長である。**判定は列の等値比較で行う。**⟹ 理由は「同じ鍵・重なる有効期間・違う内容」と
  1行で書ける ⟹ 問い3 を通る。
- **⟹ 問い5「列と索引で解けるものを、モデルに問わない」は、(B) を通して (E) を落とす。**

**【現物】(B) が実現可能である根拠**: 抽出は既に
`LLMProvider.completeStructured` で構造化出力を受け取っており、
`ExtractedMemoryCandidateSchema`（`packages/core/src/extraction.ts:18-34`）は
`content` / `digest` / `tags` / **`provenanceKind`** / `confidence` を持つ。
**`provenanceKind`（`'stated' | 'inferred'`）は既に「LLM 自身に構造を申告させている」先例である**
——鍵を1つ足すことは、新しい種類の要求ではない。

### 決定3: (B) は ADR 0134 が自分で書いた「覆る条件」の1つ目そのものである

**⛔ この ADR は ADR 0134 を覆していない。**ADR 0134「これが覆るとしたら」の1番、逐語【現物】:

> - **`Memory` 型に構造化された属性・値の表現（主語・述語・対象等）が入ったとき**——
>   「採らなかった案A」の前提（列と索引だけでは矛盾を一般的に判定できない）が変わる。
>   **自動検出（抽出時・背景処理）を LLM 無しで実装できる可能性が生まれる。**

⟹ **(B) は「ADR 0134 を覆す案」ではなく、「ADR 0134 が名指しした条件を、意図的に満たしに行く案」である。**
⛔ **だから (B) の第一の仕事は検出ではなく、鍵を持たせることである。**
**鍵を入れる PR と、検出する PR は分ける**（分割の節）。

⚠ **ただし ADR 0134 が想定した形とは1点ずれる。**0134 は「`Memory` 型に構造化された表現が
入ったとき」と書いており、**その鍵を誰が作るかは書いていない。**(B) では **LLM が作る。**
⟹ **鍵は「AI の推論」である。**これが決定4 の制約になる。

### 決定4: 🔴 (B) の鍵は「推論」として扱う。検出は `contested` までで止め、`superseded` へ進まない

北極星の問い4（逐語）:

> ### 4. AI の推論と、ユーザーが言った事実を、区別しているか。
> **混ぜた瞬間に、記憶は信用を失う。**

**(B) の鍵は LLM が付ける ⟹ 鍵は推論である ⟹ 鍵の一致から導いた「矛盾」も推論である。**
⛔ **推論を根拠に、ユーザーが言った事実を消してはならない。**

⟹ **検出が書けるのは `active → contested`（`docs/memory-model.md` §11 行6）までとする。**
`contested → superseded`（行7）へ進めるのは、**今日どおり `resolveContested` を明示的に
呼んだときだけ**である。

**⭕ これは正典と噛み合っている。**`memory-model.md` §5 機構2 は逐語
「**判定できないときは `contested` に落とす。**…両者を `superseded` にはしない」と書いている
——**自動検出はまさに「判定できない」側であり、`contested` が正しい行き先である。**
そして `contested` に落ちれば段3 が両方を隣接させて出す ⟹ **誤検出しても、
採用者と LLM の目の前に両方が並ぶ。黙って片方が消えることは無い。**

**⟹ 決定4 は、(B) の誤検出の被害を「余分に1件出る」に限定する。**
⛔ これが無ければ (B) は採れない。

### 決定5: 依存の向き —— **(C) は #207 を要らない。(B) は #207 を前提にする**

- **(C) は1回の訂正につき1つの相手しか作らない**⟹ `contested_with_id` の1対1に収まる
  ⟹ **#207 は要らない。**⟹ Issue #207 の「#197 が先」はそのまま成立する。
- **(B) は同じ鍵に3件以上が並びうる**（「好きな食べ物」が3回変われば3件）
  ⟹ **1対1では表せない**⟹ **#207 が (B) の実装の前提になる。**
  ⚠ **これは Issue #207 本文が書いている向き（#197 が先）と*部分的に*逆である。**
  ⛔ **矛盾ではない**——#207 が言っているのは「エッジを書く側が無いとグラフが空になる」であり、
  この ADR が言っているのは「(B) が書くエッジは1対1の列に入らない」である。
  **両方成り立つ。**⟹ 並びは **(C) → #207 → (B)** になる。

### 決定6: 🔴 `v1.0.0` を止めるか —— **止めない。ただし、数え方の訂正と採用者向けの明記を条件にする**

⛔ **判定の基準は `docs/roadmap.md` §7.10 と揃える**——
「§7.2 の定義どおりに v1.0 を切ることを妨げるか」で判定する。「あったほうがよい」では止めない。

**⭕ 止めない理由:**

1. **`v1.0.0` は既に §7.2 の定義を満たさないまま切ることが決まっている。**
   オーナーの決定（2026-09-16、逐語「**Aでお願いします。**」、§7.12）は
   **項目2 を「半分」のまま `v1.0.0` を出す**である。
   ⟹ **「7項目が全部揃うまで切らない」という門は、既に存在しない。**
   項目5 が半分であることは、**新しい種類の障害ではなく、同じ種類の2件目である。**
2. **物差しは緑である。**北極星の物差しは「使う側が、会話ログを全部プロンプトへ積むのを
   やめられたか」であり、⭐門（ADR 0133）は §7.10 の時点で退行ゼロ。
   **矛盾の検出が無いことは、積む量を1バイトも増やしていない。**
3. **今日壊れているものが無い。**検出が無いことで誤った答えが返るわけではない。
   返るのは「訂正しても古いほうが出続ける」という**不足**であって、**故障ではない。**
   （比較: Issue #347 は「期限切れの記憶が黙って返る」という**故障**だったので §7.10 は止めた。）
4. **実装の残量では詰まらない。**(C) だけでも1本の PR では終わらず、(B) は #207 を前提にする。
   ⟹ **`v1.0.0` の前に入れようとすると、急いで間違った形を入れることになる。**

**🔴 止めないための条件（これは満たさなければならない）:**

| 条件 | なぜ |
|---|---|
| **① `docs/roadmap.md` に「在る5 / 半分2」への訂正を書く**（§7.4 の表は書き換えず、新しい節として） | ⛔ **オーナーは「在る6 / 半分1」という数を前提に (A) を選んだ。**その数が違うなら、**オーナーは違う情報の上で決めたことになる。**⟹ 訂正を出すのは、決定を覆すためではなく、**決定の前提を直すため**である。**覆すかどうかはオーナーが決める** |
| **② 採用者向けの文書に「矛盾の検出は採用側の責務である」と明記する**（`README` / `docs/migration-v1.md` / `CHANGELOG`） | §7.12 が項目2 について「**採用者向けの文書が『連想枠は opt-in である』を正確に書いているかどうかが、この決定の後始末である**」と書いたのと、**同じ後始末である。**⛔ これを書かずに `v1.0.0` を切ると、**出荷物が支えていない約束（項目5）を、正典が謳ったまま出すことになる** |

**⛔ ①②が満たされないまま `v1.0.0` を切ることには、この ADR は反対する。**
理由は機能の不足ではなく、**「満たしていないことを書いたまま切る」という §7.12 が自分で立てた
規律（逐語「**基準はそのまま、届いていないことも書いたまま、切る**」）を、
項目5 についてだけ守らないことになるからである。**

⛔ **切る/切らないの決定そのものはオーナー専権である**（§7.8・ADR 0070）。
**この ADR は判定を書いただけで、何も切っていないし、版も上げていない。**

### 決定7: ⛔ 既定を on にするか off にするかは、この ADR では決めない。**そして、その衝突を解いてもいない**

**(C) も (B) も、この ADR では「既定 off の opt-in」として設計している**（決定2・採らなかった案2）。
⛔ **だがこれは「既定は off が正しい」と決めたのではない。**

**決めない理由**（オーナー判断、2026-09-17）:

> **検出本体が1行も無いのに既定を決めても、決めたことにならない。**

⟹ **既定の判断は、#372 が着地して初めて意味を持つ。**⛔ **それまで決めない。**

#### 🔴 だが、決めないことで消える問題ではない —— **衝突はここに在る**

| | |
|---|---|
| **北極星 問い2** | 「これを無効にしたとき、Memory Framework として成立するか」⟹ **既定 off が正しい側** |

⛔ **この ADR はこの衝突を解いていない。**
🔴 **解けたふりをしないために、ここに名前を付けて残す。**

⚠ **「opt-in なら問い7（どれだけ載せるかを使う側が決められる）で正当化できる」とは書かない。**

**⟹ 衝突を解くのは、次の3つのどれかである。どれもオーナーの判断である:**

1. **既定を on にする**（⟹ 破壊的変更の告知と ⭐門の基準値の更新が要る）
2. **項目5 の読みを「呼び手がオプトインしたとき」と確定する**（⟹ `docs/north-star.md` に触る＝オーナー専権）
3. **半分のまま出すと決める**（⟹ 項目2 で既に採られた道 (は)。§7.12）

⛔ **この ADR は、3つのどれも選んでいない。**

## 採らなかった案

### 案1: Issue #197 を「解決済み」として閉じる

ADR 0134 / 0150 で `markContested` / `resolveContested` が入り、

## 引き受けた負債

### 負債1: 🔴 (B) は、この器では費用を測れない —— **カセットの録り直しが要る可能性が高い**

**【現物】カセットの鍵の作り方**（`packages/testkit/src/__fixtures__/cassette.ts:77-83`）:

> **`schema` を鍵に含めない。**スキーマは「何を返してほしいか」であって「何を訊いたか」
> ではなく、鍵に混ぜるとスキーマの些細な変更で全記録が引けなくなる。

```js
export function llmCassetteKey(prompt: PromptSpec): string {
  const canonical = JSON.stringify({
    system: prompt.system ?? null,
    messages: prompt.messages.map((m) => ({ role: m.role, content: m.content })),
  });
  return sha256Hex(canonical);
}
```

⟹ **2つの場合に分かれる。この差は大きい。**

| (B) の入れ方 | カセットへの影響 | 費用 |
|---|---|---|
| **`ExtractedMemoryCandidateSchema` に optional な鍵を足すだけで、プロンプト本文を変えない** | **鍵は変わらない。**記録済みの応答には新しい欄が無いが、**optional なので zod を通る**⟹ 再生は今までどおり動く。**鍵は常に空** | ⭕ **録り直し不要。**ただし**鍵が1件も埋まらない**⟹ 検出も動かない |
| **プロンプト本文（`system` か `messages`）に「主張の鍵も返せ」を足す** | 🔴 **`llmCassetteKey` が全件変わる ⟹ `compare`（657回）・`retrieval`（74回）の記録が1件も引けず、`recorded` は「記録に無い入力」として例外を投げる** | 🔴 **`OPENAI_API_KEY` を持つ者による録り直しが要る。**⟹ **抽出結果が変わる ⟹ ⭐門（ADR 0133）の基準値が動く** |

**⟹ (B) を実際に効かせるには2段目が要り、それは⭐門の基準値の更新を伴う。**
⛔ **この ADR はその費用を測っていない**——この器に `OPENAI_API_KEY` が無いためである。
**⟹ 分割の節で、これを独立した issue にした。**「鍵を足す」より前に決着が要る。

⚠ **「⭐門は片側判定（増加のみ赤）だから大丈夫」とは言えない**——
抽出の出力が変われば `mnemoraShareOfNaiveChars` はどちらへも動きうる。
**【実測】ではない。動く向きを予測していない。**

### 負債2: (C) の「相手探し」は、正しい相手を選んだことを保証しない

(C) は recall で相手を探す ⟹ **間違った相手を `contested` にしうる。**

⟹ 採用者と下流の LLM の目の前に両方が並ぶ。**黙って片方が消えることは無い。**

### 負債3: 段3 の歯には、既知の弱点が1件開いたままである

【現物】Issue #293（OPEN）が「段3 の歯に『壊れても緑のままの assert』が2つ」あることを

## 北極星の問いに当てた結果

**上ほど強い。衝突したら上を採る**（`docs/north-star.md:55`）。

### 問1: 毎回渡す量を減らす方向に働くか。増やすなら、その分だけ想起が良くなると言えるか

**🔴 検出**（`active → contested`）**は増やす。**`contested` は段3 で対向を必ず連れてくる
（`recall-runtime.ts:908-950`）⟹ スコアだけなら選ばれない1件が強制的に足される。

**⭕ 解決**（`contested → superseded`）**は恒久的に減らす。**`superseded` は段1 の SQL の
`status IN ('active','contested')` ゲートから外れ、候補にすら上がらない
（【実測】`recall-runtime.ts:563` ANN ／ `:630` 語彙 ／ `:1123` 連想枠。⚠ **`docs/roadmap.md` §7.4 が挙げる `:474`/`:550`/`:1057` は既にずれている**——`grep` で取り直した）。

⟹ **検出単体では増える。検出と解決が対で回って初めて減る。**
⛔ **これは ADR 0134 が問1 に出した答えと同じ形であり、この ADR で変わっていない。**
**増える分の正当化**: 争われている事実を単独の顔で出すより、対向を隣接させるほうが、
下流の LLM が古い事実を信じる事故を減らす（`memory-model.md` §5 機構3）。

⚠ **「どれだけ減るか」は測っていない。**⭐門の12行に矛盾は1件も含まれていない
（`correction-scenario.ts:21-24` が `compare` から完全に隔離されている）
⟹ **今日の器では、この削減を測る場所が無い。**

### 問2: これを無効にしたとき、Memory Framework として成立するか

**⭕ 成立する。**(C) も (B) も **opt-in として設計する**（採らなかった案2）。
呼ばなければ・鍵が無ければ、**今日と全く同じ挙動が続く。**
`tick()` / `observe()` から自動で駆動しない。

🔴 **ただし、その代償が項目5 の「半分」である**（採らなかった案2 の ⚠）。
**問2 と §7.2 は、ここで正面から当たる。**
⛔ **この ADR はその衝突を解かない**——**解けるのはオーナーだけである**（既定を変えるか、
項目5 の読みを確定するか）。§7.4 が項目2 で通ったのと同じ分岐である。
🔴 **衝突そのものには決定7 で名前を付けた。**「決めない」と「解けた」を混ぜないためである。

### 問3: この記憶が選ばれた理由を、後から説明できるか

**⭕ 説明できる。これが (D) と (E) を落とす基準そのものである。**

| 案 | 「なぜ矛盾と判定したか」の説明 | 判定 |
|---|---|---|
| (C) | 「採用側が訂正だと宣言し、その発話に対する recall の1位がこれだった」+ そのスコアの内訳 | ⭕ |
| (B) | 「同じ `subjectId`・同じ主張キー・有効期間が重なる・内容が違う」 | ⭕ |
| (D) | 「コサイン類似度が閾値を超えた」 | 🔴 **数であって理由ではない** |
| (E) | （モデルの中） | 🔴 |

さらに、どの案でも `memory_events` に `kind:'updated', meta.reason:'contested'` が積まれ
（`memory-model.md` §11 行6、ADR 0134 決定6）、recall 側は
`retrievedVia:'mandatory_companion'` / `companionOf` で辿れる。
**⟹ 検出の根拠は `meta.note` に構造として載せること**（決定の一部として分割の節に入れた）。

### 問4: AI の推論と、ユーザーが言った事実を、区別しているか

**🔴 ここが (B) のいちばん危ない場所であり、決定4 がそのために在る。**

(B) の主張キーは **LLM が作る ⟹ 推論である。**
⟹ **推論から導いた「矛盾」で、ユーザーが言った事実（`provenanceKind: 'stated'`）を
`superseded` にしてはならない。**
⟹ **決定4: 検出は `contested` までで止める。**`superseded` へ進めるのは明示的な
`resolveContested` だけ。

⚠ **(C) は問4 に触れない**——採用側が「訂正である」と言った時点で、それは
**ユーザーの行為**であって推論ではない。`markContested` は `provenance.kind` を
一切参照・変更しない（ADR 0134 問4）。

### 問5: これは、LLM を呼ばずに済ませられないか

| 案 | LLM を呼ぶか | 判定 |
|---|---|---|
| (C) | **呼ばない。**相手探しは既存の recall（ANN + スコア） | ⭕ |
| (B) | **検出は呼ばない**（列の等値比較）。**鍵の生成は、抽出が今日すでに行っている LLM 呼び出しの中で済む**⟹ **呼び出し回数は増えない** | ⭕ |
| (E) | 呼ぶ。しかも既存記憶をプロンプトへ積む | 🔴 **(B) で解ける以上、落ちる** |

🔴 **(B) について正直に書く。**問い5 の文面は「**列と索引で解けるものを、モデルに問わない**」である。
(B) がモデルに問うのは「**この記憶は何についての主張か**」であり、**これは列と索引では解けない**
——【現物】`packages/core/src/memory.ts:74-180` の `Memory` 型に、
主語・述語・対象に当たる構造化フィールドは**存在しない**（`content` / `digest` / `tags` /
`subjectId` / `provenance` / 時刻の各列のみ）。ADR 0134 案A が同じ確認をしている。
⟹ **「解けないものを問うている」ので、問い5 は通る。**
⛔ **通らないのは (E) のほう**——(E) が問うのは「矛盾するか」であり、
**鍵さえ在れば列の等値比較で解ける。**

## これが覆るとしたら

1. **主張キーが LLM から安定して返らないと分かったとき**——(B) が丸ごと落ち、
   残るのは (C) と、退路としての (E) だけになる。**確かめていないこと1番が、この ADR の急所である。**
2. **カセットの録り直しが現実的でないと分かったとき**（費用・鍵の出どころ・⭐門の基準値）
   ——(B) の第2段以降が止まり、分割の 5〜6 が入らなくなる。負債1。
3. **オーナーが項目5 の既定を「on」と決めたとき**——採らなかった案2 と問2 の答えが変わる。

   ——文脈の節4 の数え直しが覆り、決定6 の条件① が要らなくなる。

   短くなり、(B) を先に始められる。
