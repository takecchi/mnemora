# ADR 0291: 主測定の被覆の地図（第2弾）— 北極星から見た被覆表と、次に作る領域として「訂正候補探索」を選ぶ

- **状態**: 提案 (2026-09)
- **日付**: 2026-09-24

**⚠ 各主張の出所を分ける**（[ADR 0135](./0135-numeral-token-discriminator-probe-domain-design.md) の体裁を踏む）。

- **【現物】** — この repo のコード・文書を、この ADR の担当者が自分で読んで確かめた。
- **【実測】** — この ADR の担当者が、この手元の器に対して実際に走らせた。
- **【受】** — マネージャーからの指示・報告として受け取り、自分では再導出していない。

⛔ **この ADR は設計のみであり、実装は含まない。**理由と残件は §7「引き受けた負債・残件」。

## 0. 依頼の要旨と、この ADR が答える範囲

マネージャーから、Issue #109（「実 embedding での継続計測のゴールデンセットが数十件に
届いていない」「採用を検討する側から『精度が上がる』と言える根拠が見えない」）の
**第2弾**として、次を依頼された【受】:

> [ADR 0135](./0135-numeral-token-discriminator-probe-domain-design.md)（第1弾）は
> 「単独トークンの数詞・記号インデックス」という1領域だけを設計した。今回は、
> `docs/north-star.md` から見て主測定が覆うべき領域を列挙し、被覆の地図を作る。
> 未被覆のうち次に作る領域を1つ選び、ADR 0135 と同じ6点の枠で設計する。
> 実装は含めない。

**この ADR がやること**:

1. 北極星（`docs/north-star.md`）から見て、主測定（`examples/chat/src/*-probe-set.ts` と
   その arm、CI で継続計測されるベンチ全体の家系）が覆うべき領域を列挙し、
   既存の被覆状態を表にする（§1・§2）。
2. 未被覆から1領域を選び、理由を書く（§3）。
3. 選んだ領域について、ADR 0135 と同じ6点（領域／fact・query・distractor の選び方／
   distractor の弁別軸／lexicalControl 相当の対照群／件数の出し方／margin の分布で
   読む評価）を決める（§4・§5）。
4. 採らなかった案（機械的な水増し・`probe-set.ts` の編集）を、却下した出所とともに書く（§6）。
5. 実装を含まないことと、次段で何をするかを明記する（§7）。

**この ADR がやらないこと**: 実装（新しいコード・CI ジョブ・基準値ファイル）は一切含まない。
実 API（OpenAI 等）は一度も叩いていない。測定は行わず、既存の ADR・コードの現物確認だけで
設計を組んだ（理由は §9「確かめていないこと」）。

## 3. 未被覆の中から、次に作る領域を選ぶ — **訂正候補探索**

**選んだのは「§2 の (b)」——訂正候補探索の精度を、CI で継続計測できる形に育てること
（今回の設計対象は、その前段としての fact/query/distractor 拡張）。**

### 3.1 なぜ「未被覆」の中でもこれか

他の未被覆領域（説明可能性・absence taxonomy・語彙チャンネル・関係の反転・否定・実 API
経由・本番規模）と比べて、この領域だけが次の3条件をすべて満たす:

1. **すでに実装と ADR がある。** `findCorrectionCandidates`（ADR 0232、状態=採用）が本番
   コードに存在し、`correction-candidates` サブコマンドも動く。設計対象は「ゼロから作る」
   ではなく「拡張し、CI に載せる」で済む。
2. **ADR 0232 自身が「残債」として名指ししている。** 同 ADR「引き受けた負債」節3番
   （逐語）:

   > `correction-candidates` サブコマンドは手で走らせるものであり、CI ジョブを足していない。
   > Issue #217 が「probe を作ったが CI に配線しなかった」形で残債になった前例がある。
   > **同じ形の残債である。**

   これは Issue #109 全体が指摘している問題（「仕組みは在るのに外から見つけられない」）と
   **同一の形**である。2026-09-11 のコメント【現物、Issue #109】が既に一度この形を
   踏んでいる（identifier probe が CI 配線されるまで見つからなかった）。
3. **すでに実害の実測値が在る。** ADR 0232 の測定【現物・受】:

   | 量 | 値 |
   |---|---|
   | B群（⛔ 訂正してはいけない8件）の**深い誤爆率** | **6 / 8 ＝ 75.0%** |
   | B群の**棄権率** | **0 / 8 ＝ 0.0%**（1件も止まらない） |
   | A/B の score 分布 | **重なっている**（閾値でA/Bを分離できない） |

   **この数字は今日 `main` に存在する。**しかし継続計測が無いため、次の変更でこの数字が
   さらに悪化しても、良くなっても、**誰にも気づかれない**——まさに Issue #109 の主題
   「良くなる/悪くなるを外から確認できない」がそのまま当たる。

### 3.2 北極星への当て方

- **目指す姿5**（間違いを正すと、古いほうが先に出てこなくなる）に直接対応する。
  他の未被覆候補（説明可能性・absence taxonomy）よりも、**目指す姿の項目に1対1で
  対応する**という点で選びやすい。
- **迷ったときの問い4**（AI の推論と、ユーザーが言った事実を、区別しているか）に
  最も鋭く当たる。B群（否定・曖昧・別人・別期間）は、まさに「ユーザーが実際に言った
  こと」と「AI が推論で結びつけたこと」を混同しないかを問う設計であり
  （`docs/autonomy.md` §2.2 決定1 が同じ4分類を明示的に要求している）、
  **問い4が実際にこの領域を落とせる**（深い誤爆が起きている＝いま落ちている）。
- **「採用を検討する側」にとって重い理由**: 想起の失敗（見つからない）は「不便」だが、
  **誤った訂正候補を機械的に採用すれば「まだ真である事実が、間違って古い扱いになる」**
  ——これは目指す姿1（次の日も覚えている）を能動的に裏切る失敗であり、Issue #109 の
  報告者が最初に書いた「精度が上がると言える根拠が見えない」という懸念のうち、
  **最も静かに、最も気づかれにくい形**で製品への信頼を損なう。ADR 0232 決定文自身が
  「候補を返すだけであり、採用側が機械的に1位を採れば危険はそのまま再現する」と
  明記しており、**mnemora を使う側の実装判断に、誤った前提を与えかねない**。

### 3.3 選ばなかった他の未被覆領域について

- **説明可能性・absence taxonomy**: fact/query/distractor 形式（hit@k/MRR/margin）に
  そもそも馴染むかどうかが未検討。この ADR の枠を無理に当てはめると、
  「測れる形に測定対象を歪める」リスクがある。**別の測定様式を検討する仕事が先に要る**
  ——このADRの範囲外として §7 に残す。
- **語彙チャンネル**: ADR 0108/0148 により on/off が選択可能になっているが、
  「新しい probe 集合を作る」話ではなく「既存集合を語彙チャンネル有効で走らせる」話
  であり、この ADR が扱う「fact/query/distractor の新規選定」という枠に馴染まない。
- **関係の反転・否定**: **ADR 0135 §7 がすでに検討し、範囲外にした**（矛盾検出領域
  ——[ADR 0134](./0134-mark-contested-explicit-operation.md)——と構造的に衝突しやすい
  ことを試作で確認済み）。同じ壁に再度当たるだけなので選ばない。
- **実 API 経由・本番規模**: どちらも「新しい fact/query/distractor の設計」ではなく
  「既存集合を別の条件で再実行する」話であり、この ADR の枠外。かつ実 API 経由は
  カセットの録り直し（課金）を伴う——[ADR 0276](./0276-retrieval-quality-shadow-verdict-stage1.md)
  「検討して採らなかった案」の案1が同じ理由で退けている。

## 4. 決めたこと

1. **`correction-case-set.eval.ts`（ADR 0232）を拡張する。新しい probe 集合ファイルは
   作らない**——ADR 0135 が新集合を作った判断（既存集合と目的が異なるため混ぜない）とは
   逆に、こちらは**同じ arm・同じ測定様式（A群/B群、hit@k・MRR・誤爆率・棄権率）に
   セルを追加する拡張**である。理由は §5.0。
2. **弁別軸に「短い索引の型」を1軸追加する**——ASCII 識別子・日本語固有名詞・
   数詞インデックス（ADR 0094/ADR 0135 がすでに一般的な想起で脆いと実測した3型）を、
   訂正候補探索という**別の機構**（同じ `recall()` のランキングだが、目的は
   「話題の関連性」ではなく「同一 entity の識別」）でも測る。
3. **A群は「索引型 × 2インスタンス」、B群は「索引型 × `docs/autonomy.md` §2.2 決定1 の
   4分類 × 2インスタンス」の行列で件数を導出する。件数を先に決めない**（§5.4）。
4. **correction（訂正の発話）は既存15件と同じ様式（旧値を明示して名指しする）を保つ**
   ——「明示度」を新しい軸にしない理由は §5.2。
5. **lexicalControl 相当の対照群は置かない**——ADR 0094/0135 と同じ理由（§5.3）。
6. **`CorrectionHitOutcome`/`CorrectionAbstainOutcome` に margin 相当の値を足す設計にする**
   ——ADR 0135 §5.5 が識別子集合に足した設計を、この arm にも適用する（§5.5）。
7. **⛔ 門にしない**——既存の全集合と同じ理由（標本が少なく閾値は偽陽性を出す。
   ADR 0232 決定文自身が「n=8 では偽陽性率に上限を置けない」と明記）。
8. **この ADR は実装しない**——理由は §7。

## 5. 各項の設計と理由

### 5.0 なぜ「新集合」ではなく「既存集合の拡張」か（ADR 0135 §6 との対比）

ADR 0135 は「既存 `identifier-probe-set.ts`/`japanese-name-probe-set.ts` に項目を追加する
だけで済ませる」を**却下**している（目的が違う集合を混ぜるとADR 0094 §3の問題を再発する
ため）。**この ADR は逆の判断をする**——理由は、混ぜようとしている対象の性質が違うからである:

- ADR 0135 が混ぜるのを避けたのは、**「領域(識別子/固有名詞)を広く浅く覆う」という
  既存集合の目的**と、**「文字種×共有前置長を系統的に動かす」という新集合の目的**が
  **別物**だったからである。
- この ADR で足すのは、**同じ `correction-case-set.eval.ts`・同じ目的（訂正候補探索の
  精度と安全性を測る）の中で、これまで手書きで選んでいた discriminator の種類
  （色・時刻・価格・地名等の「ふつうの値」）に、もう一種類
  （短い索引）を体系的に足すこと**である。**目的は変わらない**——ADR 0232 の
  A群/B群・hit@k/誤爆率/棄権率という測定様式はそのまま使う。

### 5.1 「短い索引の型」× 既存の A/B 群構造の行列

| 軸 | 値 | 根拠 |
|---|---|---|
| 索引の型 | ASCII 識別子 / 日本語固有名詞 / 数詞インデックス | ADR 0094（ASCII・日本語）と ADR 0135（数詞）が、この3型を「一般的な想起でも脆い」と実測または実装済みで確立している |
| A/B 群 | A（訂正すべき相手が実在）/ B（訂正してはいけない） | ADR 0232・`docs/autonomy.md` §2.2 決定1 がすでに置いている構造。変えない |
| B群のみ: kind | negation / vague / other_person / other_period | `docs/autonomy.md` §2.2 決定1 が明示的に要求する4分類。既存8件と同じ分類をそのまま使う |

⚠ **数詞インデックスのセルは、ADR 0135 の `numeral-token-probe-set.ts`（未実装）の語彙を
借りることを想定している。**この ADR の時点ではまだそのファイルが存在しないため、
**このセルの実装は ADR 0135 の実装が先に着地することに実質的に依存する**
（§7 で明記する順序の問題）。

### 5.2 fact/gold/distractor/correction の選定規則 — 明示的な訂正表現は変えない

既存15件の `correction` フィールドはすべて「訂正します。〜ではなく〜です。」のように
**旧値を明示して名指しする**様式である。**この ADR は、この様式を新しいセルにも
そのまま適用する**——「訂正表現を明示的/非明示的で軸にする」という案は採らない。

**理由**: `docs/autonomy.md` §2.2 決定1 の逐語「訂正では明示的な訂正だけでなく、否定・
曖昧な発言・別人や別期間の事実を誤って失効させないケースも扱う」は、
**「明示的訂正」と「否定・曖昧・別人・別期間」を対比する形で書かれている**——
これはすでに A群（明示的）/ B群（otherwise）の構造そのものであり、**A群の内部に
さらに「明示度」の軸を作ることを要求していない。**要求されていない軸を増やすと、
セル数が不必要に膨らむ（§5.4 で導出する数を、さらに掛け算で増やすことになる）。

gold/distractor/protected fact の書き方は、**それぞれの索引型の先例をそのまま踏襲する**:

- ASCII識別子: `identifier-probe-set.ts` と同じ「同じ書式・違う識別子」
  （例: `PROJ-1234` に対する `PROJ-5678`）。
- 日本語固有名詞: `japanese-name-probe-set.ts` と同じ「同じ書式・違う対象」
  （例: `藤井健太` に対する `藤井大輝`、`開発一課` に対する `開発二課`）。
- 数詞インデックス: ADR 0135 §5.1 の行列（文字種×共有前置長）が定める語彙の作り方
  （共有前置＋末尾の短い索引だけが違う）。

### 5.3 lexicalControl 相当の対照群は置かない

ADR 0094 §5.3・ADR 0135 §5.3 と同じ理由をそのまま継承する。**訂正の発話は、対象の
索引そのものを含む**（「その文字列を含む発話が、正しい相手を指せるか」を測るのが
この領域の狙いであるため）。既存の A群15件・B群8件（一般値のセル）が、そのまま
「短い索引ではない場合」の対照として機能する——**新設ではなく、現状維持のまま
対照群の役割を引き継ぐ**（ADR 0135 の numeral-token 領域が `probe-set.ts` の7件を
対照として引いたのと同じ形）。

### 5.4 件数は行列から導く

**A群の新セル**: 索引型3 × 最小2インスタンス = **6件（新規）**。既存15件はそのまま
「一般値」のセルとして残す（触らない）。

**B群の新セル**: 索引型3 × kind4 × 最小2インスタンス = **24件（新規）**。
既存8件（kind4 × 一般値2インスタンス）はそのまま残す。

**⟹ 追加は A群6件・B群24件の計30件。既存23件（+開発用5件）と合わせて、eval 側の
母数は 23 → 53 になる。**

⚠ **最小2インスタンスの根拠は ADR 0135 §5.4 と同じ**——ADR 0135 の担当者自身が
「n=1 で誤った規則性を結論しかけた」ことを実測で踏んでいる（同 ADR §3.3）。**この
ADR はその実測を自分で再現していない**が、同じ規律を予防的に適用する（§9で
「確かめていない」と明記する）。

⚠ **B群のほうが大きくなるのは、危険の非対称性を反映した結果である**——ADR 0232の
測定が示した実害（深い誤爆75%）は B群側で起きている。**件数を先に決めてから行列を
埋めたのではなく、行列（索引型×kind）を先に決めた結果、B群のほうが大きくなった**
——「数を大きく見せたい」という作為ではないことを、この順序で示す。

⚠ **これは ADR 0135 の18件よりかなり大きい。**実装時にコスト（`local` embedding は
鍵不要・無料だが、ケースを書く手間と CI 実行時間は増える）が問題になったら、
**セルあたりのインスタンス数を1に減らす**判断はありうる——ただしその場合、
n=1 の危険（ADR 0135 §3.3）を引き受けることになる、とここに明記しておく
（実装時の判断として残す。§7）。

### 5.5 margin(intrusion margin) を一級の値にする

**現状の欠落**【現物】: `CorrectionHitOutcome` は `goldScore`（gold の `ScoreBreakdown.total`）
を持つが、gold と distractor の差（margin）は計算されていない。`CorrectionAbstainOutcome`
は1位のスコアを持つが、「1位のスコアが、保護すべき事実のスコアをどれだけ上回ったか」
（intrusion margin）も同様に無い。

**決めたこと（設計。実装は§7で残件にする）**:

```
// A群（CorrectionHitOutcome に足す）
margin: number | null;  // goldScore − distractorScore
                         // どちらかが取れなければ null

// B群（CorrectionAbstainOutcome に足す）
intrusionMargin: number | null;
  // 深い誤爆のとき: topScore − protectedFactScore（正なら誤爆が「強く」1位に来ている）
  // 誤爆していない/棄権のとき: null
```

**⚠ 二値（hit@1・誤爆の深/浅）と併記する。置き換えない**——ADR 0135 §5.5 と同じ理由
（二値は「候補に入ったか」という別の情報を持つ）。

**この設計は `correction-candidate-arm.ts` に新しいフィールドを足すことを意味するが、
既存の A群15件・B群8件の出力形式にも影響する共有変更である**——実装 PR では、
既存ケースの report が壊れないことを変異試験で示すこと（ADR 0135 §8-2 と同じ規律）。

## 6. 検討して採らなかった案

- ⛔ **既存 probe（`probe-set.ts` を含む主測定7件、または識別子・日本語固有名詞の
  既存件数）を機械的に水増しする。** 却下。**出所は3つ**:
  1. [ADR 0092](./0092-lexical-or-coverage.md) の「差の出る probe を足せばよい、では
     閉じない。probe 集合そのものが、このベンチに何を測れるかを決めている」
     （Issue #109 コメント 2026-09-10T13:47:58Z に逐語引用）。
  2. **2026-09-15T07:30:18Z の Issue #109 コメント**（ADR 0135 の着地報告）の
     逐語「⛔ 機械的な水増しは踏まない——ADR 0092 の警告と、12→30に増やしても
     天井が動かなかった実績（PR #191 → ADR 0110）に従った」。
  3. **識別子 probe を12→30に増やした実績（PR #191）自体が、天井を動かさなかった**
     ことが、Issue #109 の2026-09-14T21:05:02Z コメントで確認されている
     （「識別子 probe を 12 → 30 件へ増やしたとき、母数は『数十件』へ届いたが
     天井は動かず、その後 `org-b` の1件を切り分けるのに ADR 0110 まで要した。
     水増しは同じ失敗を繰り返す」）。
  ⟹ **この ADR も同じ規律に従う**——新セルは、既に脆いと分かっている軸
  （索引型）を独立変数として動かす**系統的な拡張**であり、母数を大きく見せるための
  水増しではない（§5.4 の「先に行列を決め、後から件数が付いてきた」順序が、
  この区別の実質的な担保である）。
- ⛔ **`probe-set.ts`（主測定7件）を編集する。** 却下。理由は ADR 0058 §1.4 の
  統制条件（時間項を定数に保つ）を外すことになるため。**⚠ さらに
  [ADR 0227](./0227-fixed-retrieval-probe-gold-presence-gate.md) の「決定」節2番が、
  「1件も足さない・変えない」扱いを敷いている**（Issue #649 の追記により、
  ADR 0058 §1.4 自体は「凍結」を直接は言っておらず、この扱いは ADR 0135 の
  マネージャー指示記録と ADR 0227 決定2 が敷いたものだと訂正されている——
  ⟹ **この ADR も同じ出所を引き、`probe-set.ts` には1文字も触れない**）。
- ⛔ **正面から新しい probe 集合ファイルを作る（ADR 0135 と同じ形）。** 検討したが
  採らない。理由は §5.0——混ぜようとしている対象が「同じ arm・同じ目的の拡張」で
  あり、ADR 0135 が新集合を作った動機（目的の違う集合を混ぜない）がここには
  当てはまらない。
- ⛔ **説明可能性・absence taxonomy を次の領域として選ぶ。** 検討したが、
  fact/query/distractor 形式に馴染むかが未検討のため見送った（§3.3）。
- ⛔ **関係の反転・否定を次の領域として選ぶ。** ADR 0135 §7 がすでに検討し、
  矛盾検出領域との構造的な衝突を理由に却下している。同じ壁を再検証する
  価値は低いと判断し、選ばない（§3.3）。

## 8. これが覆るとしたら

- **ADR 0232 の実害の数値（深い誤爆75%・棄権率0%）が、実装後の測定で大きく
  変わったとき。**この ADR が §3 で選んだ理由（実害が既に実測されている）の
  前提が変わるため、次に選ぶべき領域の優先順位も見直しになる。
- **数詞インデックスの3型（ASCII/日本語/数詞）を訂正候補探索でも測った結果、
  一般的な想起（識別子・日本語名 probe）で見られた脆さが再現しなかったとき。**
  §5.1 の「同じ `recall()` の機構だから同じ脆さが起きうる」という仮説が誤りだった
  ことになり、このセルの優先度を下げる材料になる。
- **説明可能性・absence taxonomy を fact/query/distractor 形式で測る設計が、
  別の担当者によって先に示されたとき。**§3.3 で「馴染むか未検討」として見送った
  判断が覆り、次の弾の選び直しが要る。

## 9. 確かめたこと / 確かめていないこと

**確かめた【現物】**

- §1 の8集合すべての件数・discriminator・CI 配線状況を、コードとワークフロー
  ファイルを読んで数え直した。
- `correction-candidate-arm.ts` の `CorrectionHitOutcome`/`CorrectionAbstainOutcome` に
  margin 相当の値が無いことを、型定義とレポート生成コードを読んで確認した。
- `probe-set.ts` には1バイトも触れていない（この PR は ADR ファイル1つの追加のみ）。

  同 ADR 本文から引用した。**この ADR の担当者自身は測り直していない**（下記）。

**確かめていないこと**

- **ADR 0232 の測定を自分で再現していない。**「深い誤爆75%」等の数字は
  ADR 0232 本文からの引用であり【受に近いが、実際には同一 repo の採用済み ADR
  本文からの引用】、この ADR の作業ではローカル環境で走らせ直していない。
- **§5.4 で「最小2インスタンス」を根拠づけている ADR 0135 の n=1 落とし穴を、
  この訂正候補探索の文脈で自分では再現していない。**ADR 0135 は一般的な想起の
  文脈（`probe-set.ts` 系）で実測したものであり、訂正候補探索という別の機構
  （`findCorrectionCandidates`）でも同じ危険（n=1 で誤った規則性を結論する）が
  起きるかは、**類推でしかなく、実測していない。**
- **数詞インデックスのセルが、実際に ASCII・日本語と同じように脆いかは全く
  測っていない。**§8「これが覆るとしたら」に書いたとおり、これは仮説である。
- **本番（Postgres + pgvector / HNSW）での実測**——この ADR は設計のみであり、
  対象コードも実装していないため、そもそも実測する対象が無い。
- **実装した場合の6つの門・変異試験**——この PR は設計のみであり、新規コードを
  含まないため該当しない（§7 が実装の残件を明記する）。
- **§2 の被覆表そのものの網羅性**——`examples/chat/src/` にある8個の集合と
  `docs/north-star.md` の7項目を突き合わせたが、**この突き合わせ自体に見落としが
  無いかは、別の担当者による独立した読み直しをしていない。**
