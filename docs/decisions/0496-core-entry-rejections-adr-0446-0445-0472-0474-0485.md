# ADR 0496: 型の外の入力を、新しく例外で断る5つの口 — `findCorrectionCandidates`・`resolveContested(Group)`・`tick`・`decayFloorOffset`/`floorAt`・`attributes` の `__proto__`（ADR 0446・0445・0472・0474・0485・0490 が「オーナーの領分」に残したもの）

- **状態**: 採用 (2026-10)
- **日付**: 2026-10-02

クローン miku の決定。担い手が書いた。オーナーではない（[ADR 0220](./0220-issue-comment-author-does-not-distinguish-owner-from-agent.md)）。オーナーが v1.X.0 で破壊的変更を許したので、「型の外の入力を新しく例外で断る」直しはクローンが決めてよくなった。各 ADR が「前例の無い新しい断り」「オーナーの領分」として材料に残した5件を直した。公開 API（export）は足していない（`pnpm api:check` は変わらない）。

出所の区別: 【現物】は読んだコード・文書、【実測】は手元で走らせた結果、【判断】は担い手の判定、【未確認】は確かめていないこと。

- **文脈**: 5件はどれも「型の外の値（JavaScript・`as`・外部の JSON）を渡すと、断られずに別の結果になる」口である。どれも、型どおりに呼ぶ限り何も変わらない。

## 着手前に現物を読んで、記述と違ったところ

1. **ADR 0485 決定2の「文字列でない要素は触らない（`[null]` は今までどおり通る）」**【現物】は、今回の決定で**変わる**（文字列でない要素は `TypeError`）。ADR 0485 の本文は書き換えていない（この ADR が追記の代わり）。`correction-candidates-exclude-edges.test.ts` に `[null]` を通す歯は無かった【現物】。
2. **ADR 0445 BK-2 の記述は現物と合っていた**【実測】（Postgres は SQLSTATE `22007` の `Error`、testkit の fixture は名前の無い `Error`、`tick(ctx)` は素の `TypeError`）。ただし `TickOptions.leaseMs` の TSDoc は「**0 以下も受け付ける（検査しない）**」と、0 以下の `leaseMs` の振る舞い（claim した行がその時点でリース切れになる）を**今の振る舞いとして**書いている【現物】。依頼の「有限の正数でない」はこれと食い違う（決定3）。
3. **ADR 0472 材料1の「キーの文字種から `__proto__` を外す」では直らない**【実測】。zod 4 の record は、`__proto__` を**キーの検査より前に**読み飛ばす（`Reflect.ownKeys` の走査で `if (key === "__proto__") continue`）。キー側の `.regex`・`.refine` には `__proto__` が届かない。キー側の `.refine` を足して試し、`JSON.parse('{"__proto__":"x"}')` が通ることを実測した（決定5）。
4. **`floorAt` の入力は、テスト・fixture が壊れた値を渡している**【現物】。`buildNewMemoryFixture`（testkit）は `strength` に `NaN`・`Infinity` を渡す値域の歯（`memory-store-conformance.ts`）の中でも `floorAt` を先に呼ぶ。`halfLifeHours: 0` の「壊れた」記憶は `recall-pipeline.test.ts`・`fake-store-postgres-parity.test.ts` が作る（決定4）。

## 決めたこと

1. **`findCorrectionCandidates`**（ADR 0485・ADR 0490 穴3）: 入口で、`recall()` を呼ぶ前に次を `TypeError` で断る。`input.text` が文字列でない（`undefined`・欄なし・数・`null`・配列）。`input.excludeMemoryIds` が `undefined` でないのに配列でない（裸の文字列・`null`・`Set`・数・object）、または文字列でない要素を含む。省略（`undefined`）は今までどおり。空文字の `text` は今までどおり `recall()` の検証が断る。**裸の文字列を配列に包んで通す案は採らない**（下）。ADR 0490 が書き換えた `outcome` の TSDoc（`text` が `undefined` なら `no_candidates`）を、断る振る舞いに戻した。
2. **`resolveContested`（2者版）・`resolveContestedGroup`・`applyCorrection`（`resolution` を渡したとき）**（ADR 0446）: `resolution.kind` が `"supersede"`・`"both_active"` のどちらでもなければ、**書き込みより前に** `RangeError`（`Runtime.resolveContested: resolution.kind must be "supersede" or "both_active"`。群版は `resolveContestedGroup`）。既存の `winnerId` 不一致の `RangeError` と同じ位置・同じ作法。2者版と `applyCorrection` は、共有の `resolveWinnerSideId` の先頭で断る（`applyCorrection` は `markContested` の前にこれを呼ぶので、`contested` の印も event も残らない）。
3. **`tick`**（ADR 0445 BK-2）: 入口で、`claimBatch` の前に、`opts` が object でない（`null` を含む）と `TypeError`（`Runtime.tick: opts must be an object`）、`opts.leaseMs` が**有限の数でない**（省略・`undefined`・文字列・`null`・`NaN`・`±Infinity`）と `RangeError`（`Runtime.tick: opts.leaseMs must be a finite number`）。**0 以下の有限の数は断らない**【判断】: TSDoc が今の振る舞いとして明記しており（事実2）、「正の数に絞る」は、重複 claim を許す使い方（`leaseMs: 0`）を新しく断る、一段大きい変更になる。依頼は「有限の正数でない」だったが、**正に絞るかは直し方が1つに決まらない**ので、今回は絞らず、選択肢を材料に書いた。`TickOptions.leaseMs`・`Runtime.tick` の TSDoc の「今の振る舞い」の追記を書き換えた。
4. **`decayFloorOffset`（と、これを通る壁時計・活動時計の `floorAt`）**（ADR 0474 材料3）: `threshold` が有限かつ 0 超でない、`strength`・`halfLife` が有限かつ **0 以上**でない、のどれかなら `RangeError`。検査は `strength <= threshold` の早期 return の前（どの経路でも断る）。**0 は断らない**【判断】: `halfLifeHours: 0` の「壊れた」記憶を作る既存のテスト・fixture が `floorAt` を通る（事実4）。`halfLife: 0` の戻り値は `0`（有限）で、壊れた値（`NaN`・負）にならない。`(0, ∞)`（ADR 0125）まで締めるかは決めない（材料）。`strength` の上限（`MAX_STRENGTH`）も検査しない。testkit の `buildNewMemoryFixture` は、`decayFloorAt` を上書きで渡したときは `floorAt` を呼ばない形にした（値域の歯が `strength` に `NaN` を渡しても、fixture の中で落ちない。結果は同じ）。
5. **`attributes` の `__proto__`**（ADR 0472 材料1）: `Runtime.observe` と `runRecall` が、zod の `parse` の**前**に、`attributes` が自前の `__proto__` を持てば `ZodError`（`invalid_key`・`origin: "record"`・path `attributes.__proto__`。ほかのキーの検査エラーと同じ形）で断る（内部ファイル `attributes-guard.ts`。export しない）。`constructor`・`prototype`・`toString` などは落ちない（実測）ので断らない。`AttributesSchema` を直接 `parse` する呼び出しは変わらない（`__proto__` を落として通す）——schema の中では断れないため（事実3）。

## 採らなかった案

1. **裸の文字列の `excludeMemoryIds` を `[文字列]` に包んで通す**。採らない【判断】。呼び出し側の取り違え（配列のつもりで文字列を渡した）を黙って直すと、同じ口に「配列か文字列」の2つの形が残る。型は配列だけ（`readonly MemoryId[]`）。断れば、呼び出し側は1行で直せる。
2. **`excludeMemoryIds: null` を「除外なし」として通す**。採らない【判断】。型にない値は同じ扱い（断る）にした。以前は `?? []` で通っていたので、これも破壊的である（CHANGELOG に書いた）。
3. **`leaseMs` を「有限の正数」に絞る**。決定3のとおり採らない（材料）。
4. **`decayFloorOffset` の `strength`・`halfLife` を `(0, ∞)` に絞る**。決定4のとおり採らない（材料）。
5. **zod の record の `_zod.parse` を包んで、schema の中で `__proto__` を断る**【実測】。`ZodRecord<ZodString, ZodString>` の型も `AttributesSchema` の形も変えずに断れるので、いったん入れた。直接 `parse` した最初の1回は断ったが、**最初の成功した `parse` のあとは断らなくなった**——zod 4 のメモ化（`memoizer.js`）が、再帰しないと分かった schema の `parse` を、包む前の関数へ戻す（`inst._zod.parse = base`）ため、包みが消える。zod の内部に依存し、版を上げると壊れうるので、採らなかった。
6. **`AttributesSchema` を `z.preprocess`/`pipe` に変えて schema の中で断る**。採らない。公開の型が `z.ZodRecord<z.ZodString, z.ZodString>` から変わり、`pnpm api:check`（公開 API の面）が変わる。
7. **キーの `.regex` の文字種から `__proto__` を外す・キーに `.refine` を足す**。採らない（実測: zod が `__proto__` をキーの検査の前に読み飛ばすので、効かない。事実3）。

## 引き受けた負債（材料）

| # | 負債 | 覆る条件 |
|---|---|---|
| 1 | `tick` の `leaseMs` は、0 以下・巨大な有限の値（例 `1e20`。store が落ちる）を断らない | オーナーが「正の数に絞る」と決めたとき。0 以下を使う呼び出し（重複 claim を許す）が無いことの確認が要る |
| 2 | `decayFloorOffset` は `strength`・`halfLife` の 0 を断らない（`halfLife: 0` の「壊れた」記憶を作る fixture が通る） | その fixture を直し、`(0, ∞)` に絞ると決めたとき |
| 3 | `AttributesSchema` を直接 `parse` する呼び出しは、`__proto__` を黙って落とす（`Runtime` の入口でだけ断つ）。ほかの経路（`Memory.attributes` を直接 store へ書く）は検査しない | schema の型を変えてよい（`pipe` にする）と決まったとき、または zod が record の `__proto__` をキー検査に回すようになったとき |
| 4 | `excludeMemoryIds` の `null` は以前通ったが、今は断る | `null` を「除外なし」として通すと決めたとき（決定は1行） |
| 5 | `tick` の `opts.kinds`・`limit`・`claimedBy` など、`leaseMs` 以外の欄の型の外の値は、今までどおり検査しない | 同じ作法で足すと決めたとき |
| 6 | ADR 0485 決定2（文字列でない要素は通る）の記述は、この ADR で覆った。本文は書き換えていない | — |

## これが覆るとしたら何が起きたときか

オーナーが「型の外の入力を、これらの口で断らない」「`leaseMs` は 0 以下も断る」など、線を引き直したとき。`null` を通す（負債4）・`leaseMs` を正に絞る（負債1）は、それぞれ1行の変更である。

- 【実測】歯 5 ファイル（`packages/core/src/__tests__/` の `correction-candidates-input-rejections`・`resolve-contested-unknown-kind`・`tick-lease-ms-validation`・`decay-input-rejections`・`attributes-proto-key`、計108件）: 実装を戻した状態で86件が赤・22件が緑（緑は陽性対照）、直して108件が緑。`runtime-entry-exception-kinds.postgres.test.ts`（実 Postgres。以前の版を新しい実装に当てると、`tick` の3件が赤）は、新しい版で19件が緑。
