# ADR 0267: 出す版の節を要求する publish の門を撤回する —— 🔴 **門は正しく鳴っていた。外すのはオーナーの判断であって、門の欠陥ではない**

- **状態**: 採用 (2026-09-23)
- **日付**: 2026-09-23

---

## 🔴 先に、誤読を1つ潰す

⛔ **「門が壊れていたので外す」ではない。偽である。**
⛔ **「門が `v1.0.0` を止めているので外す」でもない。これも、この ADR を書いた時点では偽である。**

**【実測 2026-09-23】** `CHANGELOG.md` の `## [1.0.0]` の節は
[PR #602](https://github.com/takecchi/mnemora/pull/602) で released の形へ起こされ、
`main` に入っている。⟹ **この時点で門を実走させると通る。**
**つまり、この撤回が行われる瞬間において、門は何も止めていない。**

⭐ **外す理由は1つだけである —— オーナーがそう判断したからである。**
⟹ **その判断を、この ADR は「技術的な欠陥の修正」に化粧しない。**

---

## 文脈 —— [ADR 0252](./0252-release-changelog-section-is-a-publish-gate.md) が入れたもの

ADR 0252 は、`npm publish` の前に **「出す版の節が `origin/main` の `CHANGELOG.md` に在るか」**
を確かめ、無ければ落とす門を `.github/workflows/publish.yml` に入れた。

**その門が防いでいたのは、3回続けて実際に起きた事故である:**

| 版 | 起きたこと |
|---|---|
| `v0.3.0` / `v0.4.0` / `v0.5.0` | **3回とも「Release は出たのに `CHANGELOG.md` に節が無い」**。節は publish の後から書かれた |

⚠ **[ADR 0251](./0251-release-follow-up-notice-not-a-gate.md) の非ブロッキング通知は、
この3回とも動いていた。**🔴 **落ちたのは検出ではなく、検出を受けて計上する側である**
——**3回とも読まれなかった。**⟹ ADR 0252 はそれを理由に「門にする」側へ倒した。

さらに ADR 0252 は 2026-09-21 の追記で、**`v1.0.0` ちょうどのときだけ開く穴**を塞いでいる
——未リリース節の名前が `## [1.0.0]` であるため、
**述語が「`## [X.Y.Z]` が在るか」だけだと、未リリース節のまま出しても通った。**
⟹ **見出しが `- YYYY-MM-DD` で終わることまで**を要求する肯定形の述語へ変えた。

## 🔴 測ったこと —— この門は真陽性で鳴った

⭐ **ADR 0252 の逆測定**（同 ADR 本文）: **真陽性 4/4・偽陽性 0/4。**
`v0.2.0`〜`v0.5.0` のいずれも、節が `main` に入る前に publish されていた
——**門が在れば4回とも止め、4回とも正しかった。**

⭐ **そして 2026-09-22、5回目が実際に起きた。**
`v1.0.0` の tag に対する publish run
（[35722327950](https://github.com/takecchi/mnemora/actions/runs/35722327950)）で、
門は `CHANGELOG.md` が `## [1.0.0] - 未リリース` のままであることを見つけて止めた。
**出力の逐語:**

> 🔴 `## [1.0.0]` の見出しは在るが、**出した版の節の形をしていない**（… の 42 行目: `## [1.0.0] - 未リリース`）。
> ⟹ **その節を「出した版の節」へ起こしてから出すこと**——見出しを `## [1.0.0] - YYYY-MM-DD` にする。

🔴 **これは偽陽性ではない。**未リリース節のまま tag が切られていた、という**実際の状態**を
名指ししている。⟹ **前日に塞いだばかりの穴を、翌日に踏んだ。門はその1回目の実戦で仕事をした。**

⟹ ⛔ **[ADR 0254](./0254-no-gate-without-a-false-positive-ceiling.md)
（偽陽性率に上限を置けない検査は門にしない）は、この撤回の根拠にならない。**
0254 が扱うのは偽陽性であり、ここで観測されたのは偽陽性ではない。
**⟹ この ADR は 0254 を援用しない。**

## ⟹ 外すことで、何が戻るのか

🔴 **`v0.3.0` / `v0.4.0` / `v0.5.0` で3回続けて起きた
「Release は出たのに `CHANGELOG.md` に節が無い」が、再び起こりうる状態に戻る。**

⛔ **これを「起こりにくくなった」と書かないこと。**
**起こりにくくする変更は、この PR には1つも入っていない。**
入っているのは、**止めていたものを外す**ことだけである。

## 決めたこと

### 決定1. 🔴 門を撤回する —— **理由はオーナーの明示の判断である**

**オーナーの逐語（2026-09-22、会話で直接。担い手が書き起こした）:**

> **今の状況だといつまでたってもpublishしてv1.0.0をリリース出来ないのでこちらのPRを通してくださいお願いします。**

⟹ **これが、この ADR の唯一の根拠である。**
⛔ **技術的な論拠で補強しないこと。**補強できるものが無いのは、上の「測ったこと」のとおりである。
⭐ **オーナーの判断はオーナーの専権であり、担い手が覆すものではない**
（`docs/autonomy.md` §3）。**担い手の仕事は、判断の中身ではなく、
判断が何を引き受けたかを正確に残すことである。**

⚠ **担い手はこの判断の前に、別案（`CHANGELOG.md` の節を起こし、失敗した publish run を
再実行する。ADR 0252 が記録している回復手順そのもの）を
[PR #601 のコメント](https://github.com/takecchi/mnemora/pull/601#issuecomment-5781710080)
として提示している。**⟹ **オーナーはそれを読んだうえで、この PR を通すことを選んだ。**
⛔ **同じ提案をやり直さないこと。**

### 決定2. 実体を消す —— **「配線を外すだけ」にしない**

`.github/workflows/publish.yml` から段を消すだけだと、
**門の道具が repo に残り、1行の復活で戻せる状態になる。**
⟹ **判定の本体と、それを呼ぶ CLI を消す:**

| 消すもの | 何だったか |
|---|---|
| `scripts/check-release-changelog-section-gate.mjs` | 門の CLI（`publish.yml` から呼ばれていた唯一の入口） |
| `scripts/release-changelog-gate-lib.mjs` の `decideReleaseChangelogGate` / `parsePrereleaseFlag` | 門の判定そのもの |

### 決定3. ⛔ `isReleasedHeading` は道連れにしない

**`scripts/release-changelog-gate-lib.mjs` の `isReleasedHeading` は残す。**
これを使っているのは `scripts/__tests__/changelog-released-heading-format.test.mjs` であり、
その歯が測っているのは **`CHANGELOG.md` の見出しの形そのもの**——
🔴 **とくに「未リリース節を *起こす* のではなく *足して* しまい、同じ版の見出しが2本になる」
事故の検出**である。
⟹ **これは publish を止める話とは独立に効く。**⛔ **門を外したついでに落とさない。**

⚠ **ファイル名の `gate` は残る**（改名しない）。理由は下の「引き受けた負債」。

### 決定4. ⭐ 配線の歯は**消さずに反転**させる

`scripts/__tests__/publish-yml-changelog-gate-wiring.test.mjs` は、
**「門が配線されていること」から「門が配線されていないこと」へ向きを変える。**

🔴 **なぜ消さないか**: **撤回は決定であって事故ではないからである。**
⟹ **門の配線が黙って復活したら、それは この ADR を読まずに戻したということである。**
そのときに赤くなる場所が要る。
⛔ **`publish.yml` は required の check を持たない**（`release` の引き金でしか走らない）
⟹ **歯を消すと、復活は誰にも気づかれないまま次のリリースまで残る。**

⚠ **これは「門を二度と入れるな」という意味ではない。**入れ直す判断が出たなら、
**この歯をもう一度反転させること**（＋ ADR を積むこと）が、その判断の記録になる。

### 決定5. 🔴 代わりに置くものは **ADR 0251 の非門の通知だけ** である —— ⛔ **それは弱い**

**【実測 2026-09-23、現物で確認】**
`.github/workflows/release-followup-notice.yml` は**残る**。
`release` の引き金で走り、`scripts/check-release-changelog-section.mjs` を呼び、
**終了コードは常に 0** である（ADR 0251 の核心）。

⟹ ⭐ **「代わりに置いたもの」として書けるのは、これ1つだけである。**

🔴 **そして、これが弱いことは実測済みである。**
**ADR 0252 が門を入れた理由そのものが「この通知は3回とも動いていたが、3回とも読まれなかった」
だった。**⟹ **撤回後に残るのは、その、読まれなかった通知である。**

⛔ **「通知が在るから大丈夫」と書かないこと。**
⛔ **通知を門へ格上げして埋め合わせないこと**——それは ADR 0251 が明示的に却下した案であり、
やるなら別の ADR が要る（歯がそれを縛っている）。

### 決定6. ADR 0252 の本文は1バイトも書き換えない —— 撤回は追記で積む

`docs/decisions/README.md` の規律のとおり、**採用済み ADR の本文は書き換えない。**
⟹ ADR 0252 には**撤回された旨の追記**だけを足し、決定の中身はこの ADR が持つ。

## 検討して採らなかった案

### 案A. `CHANGELOG.md` の節を起こし、失敗した publish run を再実行する（門は残す）

**ADR 0252 が記録している回復手順そのものであり、技術的にはこれで `v1.0.0` は出る。**
⛔ **採らなかったのは、オーナーがこの PR を通すことを選んだからである**（決定1）。
⚠ **【実測】節を起こす側は既に済んでいる**（PR #602）。
⟹ **この案は、いまも実行可能な状態のまま残っている。**

### 案B. 門を残したまま `v1.0.0` だけ除外する

⛔ **ADR 0252 決定5 が「除外を3つ目にしないこと」と書いている。**
そして**版番号での除外は、門が主張していることを版ごとに空洞化する**
——次に同じことが起きたとき、また1つ足す圧力が掛かる。

### 案C. 歯ごと消す（配線の歯を削除する）

⛔ **採らなかった理由は決定4 のとおり**——復活が誰にも見えなくなる。

### 案D. 門を「警告」へ落とす（exit 0 にして出力だけ残す）

**一見すると穏当だが、それは ADR 0251 の通知と同じものを2つ持つことである。**
⟹ **読まれなかったものを、もう1つ増やすだけである。**
⛔ **`release-followup-notice.yml` が既にその役をしている**（決定5）。

## 引き受けた負債

1. 🔴 **「Release は出たのに `CHANGELOG.md` に節が無い」が、機械では止まらなくなる。**
   **3回起きた事故であり、防いでいたものが外れる。**⟹ **次に起きたときの検出は
   `release-followup-notice.yml` の通知だけであり、それは読まれなかった実績を持つ。**
2. ⚠ **`scripts/release-changelog-gate-lib.mjs` の名前と中身がずれる。**
   中身は `isReleasedHeading` だけになるのに、名前は `gate` を名乗り続ける。
   ⛔ **改名しなかったのは、ADR 0252 の本文がこのパスを名指ししており、
   本文を書き換えられないからである**——改名すると、0252 の記録が存在しないパスを指す。
   ⟹ **ファイルの docstring に、ずれの理由を書いた。**
3. ⚠ **`docs/release-v1.md` §0.10 は「人が読む手順」としてのみ残る。**
   同節が持っていた「ここを通さないと `npm publish` が止まる」という**裏づけが消える。**
   ⟹ **手順に従わなくても、機械は何も言わない。**
4. ⚠ **この ADR は「門を戻すべきか」を決めていない。**決めたのは「いま外す」ことだけである。

## これが覆るとしたら

- 🔴 **撤回後の最初のリリースで、また「節が無いまま出た」が起きたとき。**
  ⟹ **そのときは、この ADR が引き受けた負債1がそのまま現実化した、と読むこと。**
  ⛔ **「通知を読み落とした個人の問題」に還元しないこと**——ADR 0252 が既に3回それを見ている。
- **`release-followup-notice.yml` の通知が、実際に読まれて計上される仕組みが別に入ったとき。**
  ⟹ そのときは門が無くても同じ結果になりうる。**いまは、その仕組みは無い。**
- **オーナーの判断が変わったとき。**⭐ **この ADR の根拠はオーナーの判断1つなので、
  それが変われば、この ADR はそのまま覆る。**

## 確かめたこと

- **【実測 2026-09-23】`CHANGELOG.md` の `## [1.0.0]` は released の形（`- 2026-09-23`）で
  `main` に入っている**（PR #602）。⟹ **撤回の時点で、門は何も止めていない。**
- **【実測 2026-09-23】`.github/workflows/release-followup-notice.yml` は現物に存在し、
  `release` の引き金で `scripts/check-release-changelog-section.mjs` を呼ぶ**
  （終了コードは常に 0）。⟹ 決定5 の「残るもの」を現物で確かめた。
- **【実測 2026-09-22】publish run
  [35722327950](https://github.com/takecchi/mnemora/actions/runs/35722327950) の生ログで、
  門が `## [1.0.0] - 未リリース` を名指しして止めていること。**
- **【実測 2026-09-23】`scripts/check-release-changelog-section-gate.mjs` を参照していたのは
  `publish.yml`・配線の歯・ADR 0252・自分自身の4箇所だけであること**（`grep`）。
  ⚠ **これは `grep` が当たった範囲の結果であり、網羅の証明ではない**（`AGENTS.md`）。

## 確かめていないこと

  過去3回起きたという事実が在るだけで、**頻度の見積もりは持っていない。**
- ⛔ **`release-followup-notice.yml` の通知が「今後は読まれるか」は測れない。**
  ⟹ **読まれなかった実績（3回）だけが在る。**
- ⛔ **この撤回が `v1.0.0` のリリースを実際に通すかは、この ADR の時点では確かめていない。**
  ⚠ **そもそも門は既に通る状態だったので、この撤回が `v1.0.0` の可否を動かしたとは言えない。**
