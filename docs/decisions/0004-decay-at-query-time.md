- **文脈**:
  pgvector の HNSW/IVFFlat 索引は `ORDER BY embedding <=> $1 LIMIT k` という形——`ORDER BY` が
  距離演算子の結果そのもので、昇順である場合——にしか効かない（確認済み）。忘却（時間経過による
  記憶の減衰）をスコアに反映させたい場合、素朴には `ORDER BY similarity * decay(...) DESC` のように
  書きたくなるが、**この瞬間に式化されて索引が死ぬ。**
  一方で、大量データに対する cron の全件 `UPDATE`（減衰値を定期的に書き戻す方式）は運用上禁止されている
  （multi-tenant で件数が増えるほどこの種のバッチは破綻し、テナントごとの負荷偏りも制御できない）。
  「索引を殺さずに減衰を反映する」という要求と「全件更新をしない」という要求を同時に満たす必要がある。

- **検討した選択肢**:
  - **cron による全件 `UPDATE`**: 減衰後のスコアや状態を定期バッチで書き戻す案。実装は単純だが、
    テナント数・Memory 数が増えるほどバッチの実行時間が伸び、実行中のテーブル全体を触るため
    運用上の制約に反する。却下。
  - **段階的 materialize（hot/warm/cold のような階層に定期的に振り分ける）**: 一定期間ごとに記憶を
    温度帯に振り分け、帯ごとに異なる検索経路を使う案。**この方式の実務での採用度を示す一次情報は
    見つからなかった。**cron による全件更新に近い問題（振り分けバッチ自体が全件走査になりうる）を
    抱えており、かつ実装の複雑さに見合う裏付けが得られなかったため却下。
  - **ベクトル DB 側でのスコア融合機能に丸投げする**: 一部のベクトル DB 製品はメタデータとベクトル
    距離を組み合わせたスコアリングを提供するが、mnemora は pgvector を前提とした Postgres 単一実装を
    リファレンスにしており（`0002-embedding-space-tables.md`）、特定ベクトル DB の機能に決定を
    依存させると `VectorStore` interface の抽象が漏れる。却下。
  - **「閾値を割る時刻」を書き込み時に一度だけ計算して保存する**: 採用（下記）。

- **決定**:
  **「減衰した値」そのものは保存しない。代わりに「この記憶が閾値を下回る時刻」`decay_floor_at` を
  Memory の列として持つ。**

  - 減衰は純関数 `decay(now, lastReinforcedAt, strength, halfLife)` で計算する。この関数の結果は
    **どこにも永続化しない。**
  - `decay_floor_at` は書き込み時（作成時・強化時）に一度だけ計算して列に持つ。時間の経過だけでは
    値は変化しない（単調）。**値が変わるのは強化（reinforcement）が起きたときだけ**——つまり
    イベント駆動の更新であり、cron の全件更新が不要になる。
  - 検索は二段構成にする。
    - **段1（索引が効く）**: `WHERE tenant_id = $1 AND status = 'active' AND decay_floor_at > now()`
      に加えて `ORDER BY embedding <=> $q LIMIT k'`（`k'` = 要求件数 `k` × over-fetch 係数）。
      フィルタはすべて等値または単調な範囲比較にとどめ、索引で表現できる形を守る。
    - **段2（索引が要らない）**: 段1で取れた `k'` 件だけに対して、減衰・タグ一致・鮮度・強度を
      掛け合わせて再スコアし、`k` 件に絞る。計算量は `O(k')` であり、テーブル全体には触れない。
  - アーカイブ（実際に検索対象から落とす操作）は低頻度の掃引でよいが、これも `decay_floor_at` の
    範囲走査であり、全件走査ではない。

- **理由**:
  1. pgvector の索引は式化された `ORDER BY` では効かないという技術的制約が、二段構成そのものを
     必須にする。これは設計上の迂回策ではなく、pgvector を使う以上避けられない要件である。
  2. `decay_floor_at` を単調な値として持つことで、フィルタ段（段1）を索引が効く形（等値・範囲比較）
     に保ったまま、忘却の効果（閾値を割った記憶を検索対象から外す）を反映できる。
  3. イベント駆動の更新（強化が起きたときだけ再計算）にすることで、cron の全件更新という禁じ手を
     使わずに済む。

- **⚠ 二つの別問題を混同しないこと**:
  pgvector 0.8.0 で導入された **iterative index scan**（`hnsw.iterative_scan = strict_order | relaxed_order`、
  確認済み）は、**フィルタ問題**（`WHERE` で絞り込みが強いときに ANN の候補が想定件数に届きにくい問題）
  への対処であり、`hnsw.ef_search` と組み合わせて使う。これは段1に効く。
  一方、**スコア問題**（減衰・タグ・鮮度を掛け合わせて並べ替えたい問題）は iterative scan では
  解決しない。**iterative scan はスコア問題の解決策ではない。**スコア問題を解くのは over-fetch と
  段2の再スコアであり、この二つは別の問題であり対処も別である。本 ADR ではこの区別を維持する。

  もう一点、**partial index は離散値・低カーディナリティのフィルタに公式に推奨されている**手法であり、
  `decay_floor_at > now()` のような連続値には向かない。「直近30日」のように離散化したバケットになら
  partial index を使えるが、`decay_floor_at` そのものに対しては使わない。この違いを取り違えない。

- **結果（この決定が招くもの）**:
  良い面: 索引を保ったまま忘却を検索に反映できる。cron の全件更新が不要になり、multi-tenant で
  データ量が増えても更新コストが増殖しない。忘却の計算自体は状態を持たない純関数のままテスト可能。

  引き受ける負債:
  - **over-fetch は近似である。**段1で `k'` 件に絞り込む際、「段1では順位が低かったが段2の再スコアなら
    上位に入っていたはずの記憶」を取りこぼす可能性がある。これは構造的な限界であり、隠さずに
    recall の結果に出す（`omitted: { kind: 'ann_truncated', countKind: 'unknown' }`。
    `docs/decisions/0008-absence-taxonomy.md` 参照）。
  - **half-life をテナント単位で後から変更すると、そのテナントの全 Memory の `decay_floor_at` を
    再計算する必要が生じる**——これは避けたかった「全件更新」そのものに逆戻りするリスクである。
    対処: **half-life は Memory 単位の列として持ち、テナント設定はその既定値としてのみ使う。**
    テナント設定を変えても既存 Memory の half-life は自動では変わらない。テナント全体を新しい
    half-life に揃えたい場合は、それ自体を明示的な（かつ低頻度の）移行操作として扱い、全件更新の
    禁止原則の例外ではなく、意図的な一括操作として運用する。

- **これが覆るとしたら**:
  - pgvector が将来、式化された `ORDER BY`（`similarity * decay` のような形）でも索引を使えるように
    なったら、二段構成の必要性自体が薄れる。その場合でも over-fetch を伴わない厳密な再スコアが
    可能になるという利点があるため、移行を検討する価値はある。
  - over-fetch の取りこぼしが実運用で無視できない頻度・重要度で発生すると分かったら、over-fetch
    係数の見直し、あるいは段階的 materialize のような別方式の再検討が必要になる（その際は却下した
    案の実務採用度を改めて調査すること）。

- **確かめていないこと**:
  - pgvector 0.8 系の iterative index scan を実際のフィルタ組み合わせ（tenant_id + status +
    decay_floor_at の複合条件）でどの程度の `ef_search` 値が必要になるかは、Phase 1 の実装・負荷試験を
    通さないと分からない。本 ADR は挙動の理解までを確認済みとし、具体的なチューニング値は未検証としている。
  - over-fetch 係数の適切な初期値（k' = k × 何倍か）は決めていない。実測に基づいて Phase 1 実装時に
    決定する。
