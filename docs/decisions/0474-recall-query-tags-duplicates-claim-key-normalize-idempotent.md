# ADR 0474: 穴探し45巡目 — `RecallQuery.tags` の重複の数え方を文書と歯に書く・`normalizeClaimKeyPart` のべき等が破れる入力を記録して直さない

- **状態**: 採用 (2026-10)
- **日付**: 2026-10-01

クローン miku の委譲先（担い手。マネージャー mgr-0d3098f9 の指示による）が書いた。直す線（約束に実装を戻す・落ちる入力を減らす・前例のある同種の穴は直す。新しく断る入力・既定値や公開の型の変更・順位が変わる直しは材料に回す）は依頼主が決めた。オーナーの判断ではない（[ADR 0220](./0220-issue-comment-author-does-not-distinguish-owner-from-agent.md)）。
出所の区別: 【現物】は読んだコード・文書、【実測】は手元で走らせた結果、【判断】は担い手の判定、【未確認】は確かめていないこと。

- **文脈**: 45巡目は、今日の ADR 0441〜0472 が見ていない面を選ぶところから始めた。選んだのは、(A) recall の段2の数値の端として、`RecallQuery.tags` の重複が `tagMatch` の加点に与える影響、(D) 公開ヘルパーのうち歯の薄いもの（`scripts/__snapshots__/public-api/core.d.ts` の公開関数を、`packages/*/src/__tests__` に名前が出るファイルの数で洗った）の入力の端。

## 面A: `RecallQuery.tags` の重複

- **今の振る舞い**【現物・実測】: `computeTagMatch`（`packages/core/src/strategies/scoring.ts`）は `queryTags.filter((tag) => tagSet.has(tag)).length` で数える。`tagSet` は記憶側の `tags` から作るので、記憶側の重複は1回、**クエリ側の重複は重複のまま**数える。`RecallQuerySchema.tags` は `z.array(z.string())` で、件数・重複・長さの制約が無い。

  | 記憶の `tags` | クエリの `tags` | `tagMatch`（実測） |
  |---|---|---|
  | `["a"]` | `["a"]` | 1.1 |
  | `["a"]` | `["a","a","a"]` | **1.3** |
  | `["a","b"]` | `["a","b","a"]` | 1.3 |
  | `["a","a"]` | `["a"]` | 1.1 |
  | `["a"]` | `["a","A"]` | 1.1（`A` は別の語） |
  | `[""]` | `[""]` | 1.1（空文字も語として一致する） |
  | `["a"]` | `[""]`／`[]` | 1 |
  | 上界 `nonSimilarityUpperBound({ queryTags: ["a","a","a"] })` | | 1.3（重複も数えた要素数。`tagMatch` を下回らない） |

- **約束を当てた結果**【現物】: 重複を数えるとも数えないとも、はっきりとは書いていない。
  - `docs/memory-model.md:927`「クエリタグとの一致数に応じて `ScoreBreakdown.tagMatch` を押し上げる」。
  - `docs/memory-model.md:969`「`tags` の生の一致数による加点、`recall.md` §7」。
  - `docs/recall.md` §7 の `tagMatch` の欄は型の記述だけで、定義は無い。
  - [ADR 0069](./0069-ann-truncated-says-nothing-about-loss.md) の表（225・324 行）は「`tagMatch` の上界 = `1 + 0.1 × クエリタグ数`」「`computeTagMatch` の形そのもの。クエリ側だけで決まる」。**クエリタグの個数で上界を決めている**ので、重複を数える今の実装と整合する（種類数に改めるなら上界も揃える必要があった）。
  - `RecallQuery.tags` の TSDoc（`packages/core/src/recall.ts`）は「スコアの `tagMatch` にだけ効く」だけ。
  - 「一致数」は、クエリの要素ごとの一致にも、種類ごとの一致にも読める。【判断】**種類数とはっきり読める約束は無い**。
- **決定**（線の内側＝文書と歯だけ。実装は変えない）:
  1. `RecallQuery.tags` の TSDoc と `docs/recall.md` §7（7.1 の前）に、今の数え方を書いた（クエリ側の重複は重複のまま数える・記憶側の重複は1回・完全一致・上界との関係）。**「約束」ではなく今の振る舞いの記録**であることを明記した。
  2. 歯 `packages/core/src/__tests__/tag-match-query-duplicates.test.ts` で、上の表を縛った。上界が `tagMatch` を下回らないこと（ANN の打ち切りの健全性）も、重複の入る入力の組で縛った。
- **直さなかった理由（材料）**: クエリ側を `Set` にしてから数えると、**重複したクエリタグを渡している呼び出し側の順位が変わる**。約束が「種類数」と読めない以上、約束に実装を戻す直しではなく、挙動を変える直しになる（依頼主の線の外側）。重複を渡すのは通常は呼び出し側の組み立てのミスだが、意図して「重みづけ」に使っている利用者がいないとは言えない【未確認】。
- **`labels` の重複**（従）: `labels` は OR の集合絞り込みで、重複は結果を変えない（`tags && ARRAY[...]` と `labels.includes`）。無害。

## 面D: 歯の薄い公開ヘルパーの入力の端

### 見つけた穴: `normalizeClaimKeyPart` は、「大文字 + 結合文字」の一部の入力でべき等でない

- **約束**【現物】: TSDoc（`claim-key.ts`）は「べき等（2回適用しても結果が変わらない）——`normalizeClaimKeyPart(normalizeClaimKeyPart(x)) === normalizeClaimKeyPart(x)` が**常に**成り立つ」と書いていた。理由は「正規化済みの既知 predicate 一覧（`knownPredicates`）をそのまま再度この関数に通しても壊れない」こと。
- **実装**【現物】: `NFKC → trim → toLowerCase → 空白を _`。小文字化が NFKC のあとに走る。
- **破れ方**【実測】: 大文字 + 結合文字は、小文字化で「結合文字が付いたままの分解形」になり、2回目の NFKC が合成形に替える。例: `Α` + U+0342 は、1回目が `α` + U+0342、2回目が `ᾶ`。
- **総当たりの結果**【実測。この ADR の初稿は「9組」と書いたが、文脈を絞った総当たりの数え落としだった。下が訂正後の数】:

  | 総当たり | 結果 |
  |---|---|
  | `\p{Lu}`・`\p{Lt}` の全コードポイント × U+0300〜U+036F の結合文字 1 つ（214,704 組） | べき等が破れたのは **253 組**（ギリシャ文字 55・それ以外 198）。結合文字を伴わない大文字では 0 |
  | ギリシャ文字の大文字 + 結合文字 1 つ（U+0370〜03FF・U+1F00〜1FFF の基底 × 全結合文字） | 54 組（`Α`/`Η`/`Ι`/`Υ`/`Ω` + U+0342、`Υ` + U+0313/0343/0344、`Ϊ`・`Ϋ` + U+0300/0301/0340/0341/0342、`Ά`/`Ή`/`Ώ` + U+0345、`ᾼ`/`ῌ`/`ῼ` + U+0300 台ほか） |
  | ラテン文字の例 | `H` + U+0331、`J` + U+030C、`T` + U+0308、`W`・`Y` + U+030A、`İ`（U+0130）+ 多数の結合文字（U+0316〜U+0359 のうち約 40）、全角・数学用英数字の同じ形 |
  | 結合文字 2 つが続くギリシャ文字 | 1,000 組を超える（例 `Α` + U+0300 + U+0345） |

  **「ポリトニックのギリシャ語だけ」ではない。**ただし入力は「大文字の基底文字 + 分解形の結合文字」の形に限られ、合成済みの文字（`Ά` の合成形、`Ḥ` など）・小文字・結合文字の無い入力では破れない。
- **直し案の確認**【実測】: 小文字化のあとにもう一度 NFKC（`NFKC → trim → toLowerCase → NFKC → 空白を _`）にすると、上のどの総当たりでも破れは 0 になった。出力が直す前と変わるのは、破れる入力（上の表の組を含む入力）だけ。ほかの入力の出力は 1 バイトも変わらない。
- **決定**（**直さない。材料止まり**）:
  1. **実装は変えない。**
  2. TSDoc の「常に成り立つ」を「ほとんどの入力で成り立つ」に改め、例外（上の表の形・数・理由・ADR 0474）を書いた。
  3. 歯 `packages/core/src/__tests__/claim-key-normalize-idempotent-exceptions.test.ts`: 破れる入力 15 組（ギリシャ 9・ラテン 6）を名指しした表を **`it.fails`**（今は破れていることを記録する）で縛り、1回目の出力が NFKC の不動点でないこと・2回目が合成形になることを普通の `it` で縛った。陽性対照として、結合文字を伴わない・合成済み・小文字の入力ではべき等が成り立つこと、既存の規則（全角・空白・`İ`・`ǅ`・`Σ`）の出力が変わらないことを縛った。**実装が直ってこの歯が赤になったら、この ADR と保存済みの鍵の扱いを読み直させる**のが役目である。
- **直さなかった理由**: 鍵は保存され、突き合わせに使われる【現物】。`deriveClaimKeys`（`claim-key.ts:270` 付近）が LLM の出力を `normalizeClaimKey` に通し、その結果が `claim_key` として保存され、`findContestedByClaimKey` が同じ導出の結果で引く。今の実装は、該当する入力で**毎回同じ分解形**を作るので、保存済みの鍵と新しい観測の鍵は一致し、contested の検出は効いている。直すと、該当する入力の新しい鍵は合成形になり、**直す前に保存された分解形の鍵と一致しなくなる**。既存の行と新しい観測が別の主張と見なされ、contested の検出を新しく逃す（遡った書き換えはしない線）。
- **選択肢**（依頼主がオーナーへのまとめ問いに回す）:

  | 案 | 内容 | 線 |
  |---|---|---|
  | 案1（採用） | 直さない。TSDoc を実装に合わせ、歯で破れを記録する | 内側（文書の直し） |
  | 案2 | 食い違いを承知で直す（小文字化のあとにもう一度 NFKC）。該当する入力を含む既存の行は、新しい観測と同じ主張として見つからなくなる。`reextract` で鍵が揃う | 外側（contested の検出を新しく逃す形。保存済みの値の扱いが変わる） |
  | 案3 | 保存済みの鍵を揃える手段（`reextract` での再導出を勧める文書、または鍵の再計算の口）を入れてから直す | 外側（新しい口か運用の約束を足す） |

- **既存の保存値**: 触らない。

## 検討した代替案

1. **面A: クエリ側の重複を 1 つに数える。** 採らなかった。約束が無く、順位が変わる。ADR 0069 の上界は個数で書かれているため、上界も一緒に揃える必要が出る。
2. **面A: 重複したクエリタグを断る。** 採らなかった。新しく断る入力を増やす。
3. **面D: 小文字化のあとにもう一度 NFKC をかけて直す。** 上の案2・案3。依頼主が材料にした。
4. **面D: 小文字化を先にして NFKC を最後に 1 回だけかける。** 採らなかった。NFKC が先に走ることで、全角の大文字などが先に半角になってから小文字化される現在の順序（出力）を変えうる。

## これが覆るとしたら

重複したクエリタグを「重みづけ」として意図して使う利用者が現れたとき（面Aの文書は今の振る舞いを固定する方向に働く）。オーナーが案2か案3を選んだとき（`claim-key-normalize-idempotent-exceptions.test.ts` の `it.fails` を普通の `it` に替える）。

## 測っていないこと

実 Postgres（どちらも純関数）。fake の Runtime で、重複したクエリタグが実際の順位を入れ替える様子の走行。結合文字の列が 3 つ以上続く入力、`\p{Lu}`・`\p{Lt}` 以外の基底文字（`\p{Lo}` など）でのべき等の破れ。保存済みの鍵に、上の形の入力から作られたものがどれだけあるか（実データは見ていない）。
