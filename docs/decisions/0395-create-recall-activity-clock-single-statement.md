# ADR 0395: `createRecall` の活動時計の加算を、`recalls` の INSERT と1つの SQL 文にする（ADR 0165 負債1 への案1）

- **状態**: 採用 (2026-09)

- **文脈**:

  [ADR 0165](./0165-decay-activity-clock.md) 引き受けた負債1 は、`decay_clock != 'wall'` のテナントでは
  `tenant_activity` の1行が recall ごとのホット行になる、と書いて**測っていない**と残した
  （[ADR 0353](./0353-activity-counting-per-call.md) の `tenant_subject_activity` も同じ形）。
  前段の調査が、同じテナントへの同時 `createRecall` はこの行で直列になることを測った
  （並列度16・32 で、`activityCounting` を使わない対照の約1/10 のスループット。待ちは
  `Lock/transactionid`・`Lock/tuple`・`LWLock/LockManager`、待っている文は
  `INSERT INTO tenant_activity ... ON CONFLICT`）。

  `createRecall` は `db.transaction` の中で ①`recalls` の INSERT ②カウンタの UPSERT を撃ち、
  COMMIT する。カウンタの行ロックは②で取られ、COMMIT まで持たれる。

  オーナー代理は、**案1（1文にまとめる）だけ**を入れ、案2（カウンタを16行に分ける）は採らないと決めた。
  **入れる理由は「意味を変えず、クライアントとの往復が1回減り、害が無い」ことであり、「速くなった」ではない。**
  下の実測は、器のノイズ（±20〜30%）に埋もれて、効果を示せていない。案2 を採らない理由と、
  判断に使った分析を下に置く。

- **決めたこと**:

  1. **`advanceActivityClock` ありの2分岐（tenant 単位・subject 単位）を、`WITH r AS (INSERT INTO recalls ...
     RETURNING id), u AS (INSERT INTO <カウンタ表> ... ON CONFLICT ... DO UPDATE SET activity_seq =
     <カウンタ表>.activity_seq + 1) SELECT id FROM r` の1文にする。** `db.transaction` は使わない
     （1文は1トランザクションで走る。`requeueEmbedJobs` と同じ形）。
  2. **意味は変えない。** 1 recall = 1 単位、`recalls` の行とカウンタは同じ原子性で書かれる
     （どちらが失敗しても両方戻る）、返り値は `recalls.id`。`advanceActivityClock` が `false`/未指定の分岐は
     1バイトも変えていない（カウンタ表に触れない）。公開 API・スキーマ・マイグレーションは変えていない。
  3. **1文にできなかった部分は無い。** `createRecall` が書くのは `recalls` とカウンタだけで、`recall_usages` は
     `recordUsageAndReinforce`（別の口）が書く。`u` は外側の SELECT から参照されないが、
     data-modifying CTE は参照の有無によらず最後まで実行される（PostgreSQL の仕様）。

- **検討した代替案**:

  - **案2: カウンタを16行に分ける（採らない）。** 書き込みは `(tenant_id, shard)`
    のうち乱数で選んだ1行に +1、読みは `SUM(activity_seq)`。ホット行の競合は原理的に約1/16 になる。
    **採らない理由は2つ**: (1) **案1 の効果すら、この器ではまだ示せていない**——ホット行の直列化が
    実際にどこまで効いているかを、ノイズの外で測れていない段階で、分割の効果を前提にできない。
    (2) **読みの費用と実装の複雑さが増える**——段1の相関サブクエリが行ごとに16行の `SUM` になり、
    シャード数のスキーマ・掃除も要る（下の分析）。
    **「いま」のずれと、それが何に効くかの分析を下の節に置く。**
  - **`synchronous_commit` を変える（採らない）。** ロックの保持時間は主に COMMIT の WAL 同期で決まるが
    （下の実測で `IO/WalSync` が見える）、耐久性を落とす設定を1つの経路のために動かさない。
  - **プロセス内での集約（採らない）。** 複数プロセス・再起動をまたぐと数え漏れ／二重計上の境界が増え、
    「recalls 行とカウンタが同じ原子性」が崩れる。
  - **起点を2列に分ける（採らない）。** 読み側全部（段1・掃引・作成/強化）とスキーマに触れ、本 PR の範囲を超える。

- **引き受けた負債**:

  1. **ホット行は残る。** 1文にしても、同じ行を更新する2つのトランザクションは COMMIT まで直列である。
     縮んだのはロック保持のうちクライアントとの往復1回分だけで、WAL 同期は残る。
     **下の実測では、この器の並列度16・32 に、ノイズの外の差は示せなかった。** ホット行の解消は案2 の領分だが、採らない。

- **これが覆るとしたら**:

  1. **専用の器（他の負荷が無いもの）で測り直し、並列度16以上で同じテナント（subject）への createRecall の
     直列化が実際に効くと示せたら、案2（カウンタの分割）を見直す。** そのときも、読みの費用の増加を
     併せて測ること。本 ADR の1文は `shard` を足した形でそのまま使える。
  2. 専用の器で測っても案1 に差が出ないと分かれば、CTE の形に固執する理由は無い。`db.transaction` の形へ
     戻してよい（意味は同じなので戻すのは安全）。

- **実測**【2026-09-30、PostgreSQL 17、`initdb` で立てた自分専用のインスタンス（既定設定に
  `max_connections=200`・`pg_stat_statements` の preload だけ足した）、共有器（48 コア）】

- **案2（カウンタを16行に分ける）の判断材料——「いま」のずれ**

  以下は**コードを読んだ上での分析であり、測定ではない**。

  **前提: 現行（1行カウンタ）でも、読みと書きは別トランザクションで、同時実行中の読みは既にずれる。**
  `recall()` は、段0の前に T を1回読み（`recall-runtime.ts` の `readActivitySeq`）、パイプラインの最後
  （段6）で `createRecall` が +1 する。その間に他の `recall()` が COMMIT した分だけ、この呼び出しの
  「いま」は古い。

  | 読み取り経路 | 現行の「ずれ」 | 案2（`SUM` を**1文**で読む）で増える分 |
  |---|---|---|
  | 段1（ANN）の T | 呼び出し冒頭で1回読んだ値をパラメータで渡す。**ずれ = 冒頭から段1の実行までに COMMIT された他 recall の数** | 0（読みは今と同じ1回の読み。1文の中の `SUM` は文のスナップショットで、他 recall の +1 は1行ぶんが全部見えるか全部見えないか） |
  | 段1 SQL の S_x（相関サブクエリ） | **文の実行時に読む**（T より新しい） | 0。ただし行ごとの相関サブクエリが 16 行の `SUM` になり、**読みの費用は増える** |
  | 後置フィルタ・段2 の S_x（`ensureSubjectSeqs`） | 段1とは**別の時刻**に読むキャッシュ。段1 SQL とずれうる（**現行の既存の不整合**） | 0 |
  | 掃引（`sweepArchive`） | 呼び出し冒頭で T を読み、S_x は SQL 内 | 0 |
  | 作成・強化時の起点（`resolveActivityClockInputs`／`resolveReinforceNowSeq`） | T と S_x を別の読み取り（`Promise.all`）で読む | 0（各読みが `SUM` の1文なら） |

  - **最大**: 現行のずれは、**そのパイプラインの所要時間 D のあいだに COMMIT された他 recall の数**である。
    並列度 M の定常状態で、他の M−1 個のワーカーが D のあいだに約1回ずつ完了するので
    **典型的には約 M−1**（測定の N=32 なら約31）。**厳密な上限は M ではない**（速いワーカーは、遅い1件の
    D のあいだに何回も完了できる）——上限は「D × 全体のスループット」である。
  - **案2 が増やす分**: `SUM` が**1つの文**なら 0 単位。増えるのは、実装が読みを**複数の文に割る**
    （例: シャードごとに読む）場合に限り、その文の実行時間のあいだに COMMIT された分
    （測定のスループット約 1,000〜1,400 ops/s で、5 ms なら数件）である。
    **1シャードだけ読んで16倍する概算読み**は、ずれが確率的になり上限を置けない——**採らないこと**を
    案2 の条件にすべきである。
  - **確かめていないこと**: 上の「約 M−1」は、D が一定で、全ワーカーが同じ速さという仮定の見積りであり、
    実測していない。`SUM` の1文が READ COMMITTED でスナップショット一貫であることは PostgreSQL の
    仕様に基づく主張で、案2 は実装していないので**試していない**。

  **そのずれが何に効くか**（`strength × 0.5^((nowSeq − baseSeq) / halfLifeRecalls)`、`halfLifeRecalls` 既定 720、
  忘却ゲートは `decay_floor_seq > nowSeq`）:

  | ずれ Δ（単位） | 強さ | 1000件・強さ 0.5・閾値 0.05 の記憶で、境界を越える件数（一様分布の仮定） |
  |---|---|---|
  | 1 | −0.096% | 約 0.4 件 |
  | 15 | −1.43% | 約 6 件 |
  | 31 | −2.94% | 約 13 件 |

  - 強さ 0.5 の記憶の床は `base + ceil(720 × log2(0.5/0.05)) = base + 2392`。床が 2392 単位に一様に
    散っていれば 1000 件で 1 単位あたり約 0.42 件なので、**Δ 単位のずれは約 0.42×Δ 件を、
    「早く沈んだ／まだ沈んでいない」の判定でずらす**（Δ が正なら遅い＝生き残る側。向きは
    「いま」が古い側にずれるので、沈むのが遅れる）。**一様分布は仮定であり、実物の床の分布は測っていない。**
  - **結論**: 案2 が「いま」を増やすずれは（`SUM` 1文なら）0 で、現行の約 M−1 単位のずれ
    （並列度32で強さ約 −3%）に**上乗せされない**。効きは半減期 720 に対して小さい。
    案2 の実際の代償は、ずれではなく**読みの費用**（段1の相関サブクエリと `SUM`、行数が16倍）と
    実装の複雑さ（シャード数のスキーマ・掃除）である。

- **確かめていないこと**:

  - 上の測定は、共有器（load 30〜48）の1台での結果である。**別の器・専用の器での結果は測っていない。**
  - ロック保持のうち、COMMIT の WAL 同期の割合は測っていない（`IO/WalSync` のサンプルは見えているだけ）。
  - 実際の `recall()` は段1〜5（ANN・埋め込み）が同じ Postgres を使うので、`createRecall` 単体の
    スループットの差が、`recall()` 全体の差にどう写るかは測っていない。
