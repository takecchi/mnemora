## 決定

### 決定1: 正典値は ADR 0085 という同じ1ファイルの中に literal で持ち、決定7 の構造パースはしない

ADR 0085 決定7 の実測値を正規表現で構造的にパースする案も検討したが、**表現が
変わるたびに歯そのものが壊れる**(先例 [ADR 0199](./0199-identifier-probes-readme-freshness-tooth.md)
が「見出しと表の形」に依存した parser を負債として引き受けているのと同じ問題)。

代わりに、正典値(`42MB` / `36MB` / `4ファイル` / `37,142,404`)を歯の中に literal で
持ち、**その literal が ADR 0085 の本文に実在すること**を別の `it` で検査する形にした
(依頼元が明示的に許容した代替案)。決定7 が変わればこの `it` が赤くなり、
「直すべき場所」を名指しする。

**【現物】ここで1つ、想定と違う発見があった**: `42MB`・`4ファイル`・`37,142,404` は
ADR 0085 の決定7 に実在するが、**丸めた重みの値 `36MB` は決定7 ではなく決定1 の
比較表(モデル選定根拠)にしか出てこない。** 決定7 は「42MBを4ファイル」としか
書いておらず、そこから `36MB` を再導出することもできない——`model_quantized.onnx`
の厳密バイト値 `37,142,404` B は、1024² で割ると約35.42MB、10⁶ で割ると約37.14MB
になり、**どちらの単位換算でも機械的に「36」には丸まらない。** `36MB` は決定1で
独立に実測された値であり、決定7の厳密バイト値の丸めではない(ADR 0085 自身の中に
残る、約1MB相当の丸め方の不一致)。

⟹ **`36MB` と `42MB` は、ADR 0085 という同じ1ファイルの中の、別々の決定に住んでいる。**
「一次資料は単一である」という #455 の前提を保ちつつこれを検査するため、実在チェックの
スコープを「決定7 の見出しブロックだけ」ではなく **「ADR 0085 ファイル全体」** にした。

### 決定2: 「対応」は、正規表現マッチの前後にある名詞の**最近傍**で判定する

非ADRファイル全体から `36MB`/`42MB` の出現を拾い、各出現の前後50文字の窓の中で
「一式」系の名詞と「重み」系の名詞のどちらがより**近い**か(文字距離)を比べ、
近いほうをその数字の文脈と判定して期待値(一式=42・重み=36)と突き合わせる。

🔑 **なぜ「窓に含むか」ではなく「最近傍」か**: 実際の文の大半は
「4ファイル計42MB(うち重み36MB)」のように、**1つの文の中に両方の名詞が近接して
同居する。** 単純な「窓に含むかどうか」の判定では、42MBの窓にも36MBの窓にも両方の
名詞が入ってしまい、対応が判定できない。**最近傍**を使えば、「4ファイル計」が42MBに
直接隣接し、「重み」が36MBに直接隣接するという実際の語順を、機械的に正しく拾える。
【実測】この方式で、現物の28箇所すべてが正しく`total`/`weight`のどちらかに解決され、
`none`(判定不能)は0件だった(下記「測ったこと」)。

🔴 **【実測】この歯は、自分自身の docstring を誤検知した。** 最初の実装は
`git ls-files` の全件をスキャン対象にしており、この歯自身のファイル
(`scripts/__tests__/local-embedding-size-noun-correspondence.test.mjs`)も対象に
含んでいた。この docstring は「取り違えの実例」を説明するために36MB/42MBを並べて
言及しており(例:「重み(`model_quantized.onnx` 本体、36MB)」と「一式(4ファイル計、
42MB)」)、これは**事実の主張ではなく事例の解説**である。しかし最近傍判定にとっては
ただの文字列であり、直前に置いた `model_quantized.onnx`(重み側の名詞)よりも、
直後の例示で置いた「一式」のほうが文字距離で近かったため、**この歯自身が CI 上で
実際に自分の docstring を「一式文脈に36MBが付いている」と誤検知して赤くなった。**
⟹ **スキャン対象から自分自身のファイルパスを明示的に除外した**(`selfPath` で
`import.meta.url` から動的に算出。相対パスのハードコードではない)。この歯は
「他のファイルの記述」を検査するものであり、自分の解説文を検査対象にする必要は
無いと判断した。

【現物】実際に `AGENTS.md` の該当行を見ると、この一覧表の1セルで「実行時に何を
落とすか」を一目で示す設計になっており、リンクへの置き換えは可読性を落とす。採らない。

### 案2: 値を1箇所に持たせて生成する

🔴 **観測された壊れ方を防がない。**定数を2つ(重み用・一式用)用意しても、
Markdown へ手で書き写す人が**間違ったほうの定数を選べる**——#455 が記録した
「取り違えの方向が一定ではない」という壊れ方は、定数の個数を減らしても直接には
防げない。加えて、Markdown への生成機構という新規実装(生成元と手書き部分の境界設計)
が要り、[ADR 0199](./0199-identifier-probes-readme-freshness-tooth.md) 案C が
同種の理由で見送ったのと同じコスト構造になる。**検査だけを足す(生成はしない)**
という ADR 0199 の判断を踏襲し、この案は採らない。

### 案3: 何もしない

⛔ **2周目である。**1周目(#451/#452)で9ファイル・11箇所を直したにもかかわらず、
一次資料は今も1つに集約されておらず、次にモデルを差し替える判断が入れば同じ手作業
掃引が要る。歯自体のコストが小さい(既存の vitest に相乗り、CI ジョブ追加なし、
新しい情報源も作らない)ため、何もしない理由が無いと判断した。

### 案4: ADR も対象にする

⛔ **できない。**このリポジトリは ADR 本文を書き換えない規律であり、
ADR 0184・ADR 0107 は本文の誤りをファイル冒頭の訂正の追記で対応済みである。
決定3 の通り、ADR は対象外にした。

## 引き受けた負債

### 負債1: ADR 3箇所(0184に2箇所、0107に1箇所)は、この歯では守れない

決定3 の通り ADR は対象外である。ADR 本文に残った誤りは、既に各ファイル冒頭の
訂正の追記で対応済みであり、この PR ではそれ以上手を出さない。

### 負債2: 許す名詞の集合そのものが腐りうる

`TOTAL_NOUNS`/`WEIGHT_NOUNS` は、いまの `main` の実際の記述に当てて決めた固定リスト
である。次に誰かが両方のリストに無い言い回し(例: 新しい比喩・別の助数詞)で36MB/42MB
に言及すると、この歯は「未判定(none)」として赤くなる(誤検知ではなく、
「見直しが要る」という形の赤)——`describe` 内の最後の `it` がこれを拾う設計にした。

### 負債3: 文字列に対する検査であり、表現の揺れに弱い

`42 MB`(半角スペース入り)・`42.0MB`(小数)・全角数字のような、いまの `main` に
存在しない表記の揺れは検査対象にしていない。存在しない形が今後増えたとき、
この歯は「見えない」まま緑を返す(誤検知ではなく検出漏れ)。

### 負債4: 数えた数は境界次第である

【受】#455 は「12箇所(表は13行)」、母集合から数えると約35箇所、`__tests__` を
除いて数字のみだと「41行/14ファイル」と数えている。【実測】この歯自身が非ADR全体
から機械的に数えた結果は「28箇所・12ファイル(実体11ファイル、`CLAUDE.md` は
symlink)」だった——境界の取り方(単独の `36MB`/`42MB` のみを拾うか、`362MB` のような
無関係な数字を含む上位互換の正規表現を使うか、`__tests__` を含めるか等)によって
数字が変わる。**「いくつ」はこの歯の実装が選んだ境界の産物であり、絶対値ではない。**

### 負債5: `docs/release-v1.md` / `CHANGELOG.md` / `docs/release-notes-v1.0.0.md` を
スキャン対象から明示的には除外していない

現状これらのファイルに local-embedding のサイズ言及は無いため実害は無いが、
別の担い手がリリース窓で編集中であり、この歯が将来これらのファイルに対して
赤くなったとしても、本PRのスコープではこれらを書き換えない。

## これが覆るとしたら

**モデルが差し替わり、ADR 0085 決定7/決定1 の数値そのものが変わるとき。**
⭐ **そのとき、この歯はまず「正典値が ADR 0085 の本文に実在する」`it` で赤くなる**
——歯の中の `CANONICAL` リテラルを新しい値に直すよう促す。その後、`CANONICAL` を
更新すれば、**非ADRファイル側の古い数値がすべて「対応」の `it` で赤くなり、
直すべき場所を名指しする。** これが本 ADR の狙いである——「値が古くなった」ことを
歯自身に教える作業と、「写しを直す」作業を、この2段構成で分離した。

また、`36MB`/`42MB` 以外の表記(新しい丸め方、別の単位)が採用された場合は、
負債3・負債2の通り、この歯は追随できない——`SIZE_RE`/`TOTAL_NOUNS`/`WEIGHT_NOUNS`
を合わせて見直す必要がある。
