## 決定

### 1. ADR 0067 の決定 (B) の列挙のうち、「存在検査」を訂正する

**予行は「既に在るか」を読める。**⟹ ADR 0067 の
「サーバ側の権限・**存在**・検証の状態については、緑からも赤からも何も読み取れない」は、
**存在について言いすぎている。**

⛔ **崩れたのは列挙の1項目だけである。**次は崩れていない:

- **認証・認可（トークン / OIDC の信頼関係 / 権限）** — 予行は書き込みの `PUT` を投げないので、
  依然として見えない。**【現物】**ADR 0067 が記録した実測（予行は全ステップ success、
  同じ commit の `release` 契機は `403 OIDC permission denied` で failure）が**そのまま生きている。**
- **書き込みを伴うサーバ側の検証全般** — 同じ理由で見えない。

⚠ **機構は packument の `GET` による preflight だと思われるが、これは推測である。**
断定できるのは「予行の出力が存在状態と一致した」ことだけであり、
**`GET` を投げていることを直接観測したわけではない。**
（`PUT` を投げていないことは、測ったこと3 から確実である。）

⟹ ⭐ **一般化のほうを直す**: **予行に見えないのは「サーバ側の状態」全般ではなく、
「書き込みの要求を投げないと分からないこと」である。**読み取りだけで分かることは、
予行にも見える。

### 2. 予行の網羅性は、木の版と registry の状態の関係で「黙って」落ちる

**測ったこと2 の裏返しである。**予行が梱包するのは木の `version`（＝ `0.1.1`）であり、
**それが registry に既に在る本は、`publish.yml` の冪等の分岐へ短絡する。**
⟹ **今回、実際に publish の経路を通ったのは6本のうち2本だけである。**

**⚠ これは今回はじめて起きた。**2026-09-08 の予行2件（run `34248494960` / `34262743432`）では
**対象パッケージ全部が経路を通っていた。**根拠が2方向に在り、互いに一致する:

- **【現物】**ADR 0067 の「確かめたこと」が当時を記録している——
  `npm view @mnemora/{core,testkit,postgres,openai} versions` が **4つとも `["0.1.0"]` のみ**、
  `package.json` の `version` は **4つとも `0.1.1`**。⟹ `0.1.1` はどこにも上がっていなかった
  のだから、短絡する余地は無い。⚠ **この最後の一歩は、記録された実測からの推論である。**
- **【受】**作業者がその2件のログを直接引き、「既に在る（飛ばした）」が1件も出ていないことを
  確認した。**この ADR の書き手は、その2件のログを自分では引いていない。**

🔴 **⟹ 予行は、同じ引数・同じ緑のまま、確かめる範囲が狭くなっていく。**
**木の版が上がるまで、その4本は何度予行を回しても短絡し続ける。**
⛔ **run の `conclusion` にも、段の `success`/`skipped` にも、この劣化は現れない。**

⟹ ⭐ **決めること: 予行の結果を「何本について確かめたか」の証拠として使うなら、
段14 のログを `::group::` ごとに開き、「publish した」と「既に在る（飛ばした）」の
どちらが出ているかを1本ずつ読むこと。**「run が緑だった」では足りない。

**⚠ 当日（`v1.0.0`）に効く形**: `1.0.0` はどのパッケージにも無いので**6本とも短絡しない。**
⟹ **当日に警戒すべきものは、予行で通った2本ではなく、予行が飛ばした4本の側である。**

### 3. 版を決める経路は、予行では一度も走らない

**測ったこと4 から。**段8 が `release` 限定でスキップされる ⟹
`versionFromTag()` の semver 判定・先頭の `v` が必須であること・dist-tag の決定・
6つの `package.json` への書き込みは、**予行では一度も実行されない**（ADR 0070 の経路そのもの）。
⟹ **`v1.0.0` という tag 文字列が正しく `1.0.0` になることは、予行では確かめられていない。**

### 4. ADR 0067 の現物は書き換えない。訂正はこの ADR に置く

**形**: **ADR 0067 の主張・判断・実測の記述は1行も変えない。**訂正の中身はすべてこの ADR に置く。
0067 へ足すのは、**冒頭の1ブロック——「後にこの ADR が列挙のうち1項目を訂正した」ことを指す
前方参照だけ**である（⚠ 0067 を先に読んだ人が、訂正を知らずに引用してしまうのを防ぐため。
**0067 だけを読んで止まる経路が実在する**——`docs/release-v1.md` §2.2 がその列挙を逐語引用している）。

**理由**: ⭐ **この形は、すでに規約として明文化されている。**
**【現物】**[ADR 0064](./0064-exact-path-cost-vs-scale.md) の「採らなかった案」が逐語で:

> **ADR 0063 の本文を書き換えて「約2.5倍」を直す**: 却下。**ADR は上書きせず追記して積む**
> のがこのリポジトリの作法であり（ADR 0059 → 0063 で同じ形を採った）、
> **上書きすると「当時そう判断した」という記録そのものが消える。**
> ⟹ **1行のポインタだけを足し、訂正の中身は本 ADR に置く。**
> **加えて、自分が書いた ADR を自分で書き換えるのは、いちばん歯止めが効かない形である。**

⟹ **本 ADR はこの作法にそのまま従う。**
[`docs/decisions/README.md`](./README.md) も逐語で
**「決定そのものをやり直す場ではなく、決定を記録する場である」**と定めている。
⟹ **2026-09-08 にそう書いたこと自体が記録すべき事実であり、遡って消すと
「なぜ当時そう判断したか」が読めなくなる。**⭐ **そして 0067 の判断は当時の材料から見て正しい**
——当時の registry は4本とも `0.1.0` のみで、**短絡の実例が観測できる状態ではなかった。**

### 5. 併せて `docs/release-v1.md` §2.2 に追記する

**当日の手順書を読む人が、この ADR を読まなくても 1〜3 に届く必要がある。**
⟹ §2.2 に「予行を1回走らせて分かった、この節が書いていなかったこと3つ」として追記する
（**この ADR と同じ PR に入っている**）。

## 「予行が緑でも本番が落ちた」実例（参照のみ）

- **`v0.1.1`（run `34254090760`）** — 一覧では `success` だが**それは attempt 2** で、

  記述は `docs/release-v1.md` §2.2 と ADR 0067。
  ⚠ **【受】**この run が全 publish run のうち `run_attempt ≥ 2` の唯一の1件であることは、

  **形（ループが途中で止まる）は再発しうる**——そこも同節が書いている。

## 採らなかった案

- **ADR 0067 の本文を書き換えて「存在検査」を列挙から削る。**⛔ 採らない——
  **ADR 0064 の「採らなかった案」が、まさにこの案を却下する形で作法を明文化している**（決定4 に逐語）。
  **当時の判断の材料ごと消えてしまう。**
- **前方参照を `## 訂正の追記` という節見出しで足す**（[ADR 0038](./0038-vector-hit-distance-is-cosine.md) /
  [ADR 0026](./0026-ann-unreached-omission.md) がその形）。⛔ 採らない——
  **【現物】ADR 0067 は `#` の見出しを1行目にしか持たず、節はすべて `- **見出し語**:` の箇条書きである。**
  ⟹ **ラベルの文言は 0038 の「🔴 訂正の追記（日付、ADR 番号）」に揃えたが、
  構造は 0067 自身の箇条書きに合わせた。**⭐ **置く位置は冒頭である**
  ——0067 を先に読んだ人が (B) の列挙へ到達する**前**に訂正を見る必要があるため
  （ADR 0038 も冒頭側に置いている）。
- **ADR 0067 を「棄却」に落として全体を置き換える。**⛔ 採らない——**崩れたのは列挙の1項目
  だけ**であり、決定 (A)（fail-open の反転）と、決定 (B) の残り2項目は**いまも正しい。**
  全体を落とすと、いま現物のコードを支えている根拠が読めなくなる。
- **予行を「6本とも必ず publish 経路を通る」形に直す**（たとえば木の版を毎回上げる、
  使い捨てのパッケージ名へ publish する等）。⛔ **この ADR では採らない**——
  `docs/autonomy.md` §3 が「npm への publish・npm 側の設定」をオーナー専権としており、

  4番目が、同じ趣旨の残る負債として既に挙げている。⟹ **ここでは「緑の読み方」だけを決める。**
- **予行を回すのをやめる。**⛔ 採らない——短絡した4本についても、段1〜13
  （門・`pack:check`・梱包・版のずれ検査）は**6本とも通っている。**
  短絡が消すのは段14 の振る舞いだけである。

## 引き受けた負債

- **🔴 短絡した4本について、段14 の振る舞いは当日まで分からない。**この ADR はそれを
  **測れるようにしていない**——**読み違えないようにしただけである。**
- **⚠ 機構（`GET` preflight）を確かめていない。**⟹ **npm が preflight の有無を変えたら、
  決定1 の訂正そのものが揺れる。**下の「これが覆るとしたら」に置いた。
- **⚠ 「段14 のログを1本ずつ読む」を機械が強制していない。**人が読むことに依拠している。
  ⟹ 次に予行を回す担い手が、`conclusion` だけ見て「確かめた」と書く余地は残っている。
  ⭐ **機械化するなら、段14 のログから「publish した」の件数を数えて
  `PUBLISH_TARGETS` の本数と突き合わせる歯が置ける**——この ADR では置いていない。

## これが覆るとしたら

- **npm が `--dry-run` の preflight をやめたとき。**そのとき4本は短絡せず、
  予行は「まだ上がっていない」として6本とも通る。⟹ **決定1 の訂正が逆向きに覆り、
  ADR 0067 の元の列挙が正しくなる。**⚠ **そして決定2 の劣化は自然に消える**
  ——**消えたことも緑からは見えない。**
- **npm が `--dry-run` を認証まで問い合わせる形に拡張したとき。**ADR 0067 の
  「これが覆るとしたら」1番目と同じ条件である。そのときは「認証・認可」も予行に見えるようになり、
  決定1 が訂正する範囲が1項目から2項目へ広がる。
- **木の `version` が registry の最新を追い越したとき**（たとえば `v1.0.0` の後に
  `package.json` が `1.0.1` へ進んだとき）。⟹ **6本とも短絡しなくなり、決定2 の劣化が
  一時的に閉じる。**⛔ **だが原因は消えていない**——次に registry が追いつけば同じ形が戻る。
- **段14 の件数を突き合わせる歯が置かれたとき。**「引き受けた負債」の3番目が解消し、
  決定2 の「人が1本ずつ読む」は機械の仕事になる。
