# ADR 0050: 記録した実 API の応答を再生する provider を、物差しの経路にだけ入れる（二層にする）

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-07

**⚠ 各主張の出所を分ける。**「私が実行して確かめた」と「推測」を混ぜない。
本 ADR の数字は、断りの無い限り**すべて実行して取った**ものである。

---

## 問い

北極星の物差し——「使う側が、会話ログを全部プロンプトへ積むのをやめられたか」——を測る経路が、
**擬似 provider でしか走っていなかった。**[ADR 0019](./0019-real-openai-measurement-cost.md) §1 が
既に数えているとおり、`compare` も `retrieval` も、CI では実 API を一度も叩かない。

そのうえで、擬似物が何をしているかを現物で確かめた（**出所: 私が読んだ**）:

| 擬似物 | 実際にしていること |
|---|---|
| `DeterministicEmbeddingProvider` | 文字コードを次元数で剰余したバケットに足し込み、`% 997` して丸める（**既定8次元**） |
| `DeterministicLLMProvider` | 発話をそのまま `content` にし、40文字で切って `digest` にする（**抽出をしていない**） |

**どちらにも意味の情報が入っていない。**docstring は用途を正しく書いている——
「`observe → embed → embeddingStatus` 遷移の**配線**を検査するために十分な性質」。
つまりこれは配線検査用の stub であって、想起の質を測れる代物ではない。

**実測がそれを裏付けた**: `retrieval` の arm A（擬似LLM+擬似埋め込み）の MRR は **0.018**。
実質ランダムである。**⟹ 擬似物で測った ✅/❌ は、mnemora の性能について何も言っていない。**

## 決めたこと

**記録した実 API の応答を再生する provider を足す。ただし擬似物を置き換えるのではなく、
用途で二層に分ける。**

| 用途 | 使うもの |
|---|---|
| 配線・契約・適合テスト（現在669件の大半） | **従来どおりの stub**（`Deterministic*`）。速く、入力が自由 |
| 北極星の物差し（`examples/chat` の `retrieval`） | **記録した対応表**（`Recorded*`）。実キー無しで本物由来の数字が出る |

実装は3つに分かれる。

- `packages/testkit`: 再生する provider（`RecordedLLMProvider` / `RecordedEmbeddingProvider`）、
  録る側のデコレータ（`Recording*` / `CassetteRecorder`）、カセットの型と鍵（`cassette.ts`）
- `examples/chat/cassettes/retrieval.json`: 記録そのもの
- `examples/chat`: `record`（録る）/ `verify`（乖離を測る）サブコマンドと、
  `retrieval` の「キーがあれば実 API、無ければ再生」の分岐

**鍵は入力の SHA-256 とする。**埋め込みは入力テキスト、LLM は `PromptSpec` を正規化した JSON。
**`schema` は鍵に含めない**——スキーマは「何を訊いたか」ではないため、鍵に混ぜると些細な
スキーマ変更で全記録が引けなくなる。代わりに**再生時に呼び出し側の `schema` で検証し直す**ので、
記録とスキーマのずれは「順位が微妙に変わる」ではなく**例外**として現れる。

**記録に無い入力は例外にする。**黙って stub へ倒れない。これは
`DeterministicLLMProvider` が既に守っている原則（「知らない形に遭遇したら黙って何か返すことをしない」）の
適用である。一部が擬似物で埋まった出力は、**どの行が信用できるかを誰にも分からなくする。**

## 測った: 記録は再現するのか

**出所: 私が実行した。**カセットを録った後、DB を作り直し、`OPENAI_API_KEY` を外して再生した。

| arm | 実 API（2026-09-07） | カセット再生 | 一致したか |
|---|---|---|---|
| A: 擬似LLM+擬似埋め込み | 0.018 | 0.018 | ✅（API を叩かないので当然） |
| B: 擬似LLM+本物の埋め込み | **0.714** | **0.714** | ✅ **完全一致** |
| C: 本物LLM+本物の埋め込み | 0.714 | **0.738** | ❌ **ずれた** |

**arm B は完全に再現した。**probe 7件すべてで goldRank / hit@1 / hit@10 / distractorRank が一致。

**arm C はずれた。原因は LLM の非決定性であり、この仕組みの欠陥ではない。**
記録は `gpt-4o-mini` の**ある1回のサンプル**である。実 API 実行時と記録時で抽出結果が違った
（例: `travel` の gold digest が「来月京都へ出張する予定がある。」→「来月、京都へ出張する。」、
`diet` の goldRank が `(無し)` → `6`）。

**⟹ カセットが与えるのは「実 API との一致」ではなく「測定の再現性」である。**
再生は決定的で、DB を作り直しても arm C は 0.738 を寸分違わず再現した（**実行して確認**）。

### ⚠ 埋め込みも、ビット単位では再現しない（当初の想定が実測で否定された）

本 ADR を書き始めた時点では「埋め込みは決定的だから、差が出たらモデルが変わった証拠」と
考えており、`verify` の閾値をコサイン `1 - 1e-6` に置いていた。**これは誤りだった。**

**出所: 私が実行した。**同じ日・同じモデル（`text-embedding-3-small` / 256次元）に、
記録済みの152件を投げ直した結果:

| 測ったもの | 値 |
|---|---|
| 完全一致した件数 | **152件中 5件** |
| 最小コサイン類似度 | **0.998646713** |
| 最も離れた入力 | `"自転車のパンク修理が終わった"` |

**実 API 側に揺らぎがある。**方向はほぼ保たれる（最小でも 0.9986）が、値は一致しない。
そこで `verify` は「完全一致したか」と「乖離したか」を**別々に数える**形へ直した。
前者が欠けるのは普通のことであり、後者だけが記録し直す理由になる。

閾値は `DRIFT_COSINE_THRESHOLD = 0.99` に置いた。**根拠は上の実測（152件・1日・1回）である。**
**⚠ ただし「モデルが替わったときコサインがどこまで下がるか」は測っていない。**
0.99 は揺らぎの実測の下に引いた線であって、モデル交代を実際に検出できると確かめた値ではない。

## ⚠ 「黙って別のものへ倒れない」は、表示層まで及ばないと意味が無い（レビューで見つかった）

**provider の配線は正しかったが、それを人に見せる経路が嘘をついていた。**
`ProviderMode` に `"recorded"` を足したとき、`createProviders` は直したのに
`describeMode` と `formatNoApiCallsNotice` は「`openai` でなければ擬似 provider」のままだった。
その結果、記録を再生している run の画面はこうなっていた:

```
[provider] Embedding : @mnemora/testkit の決定的な擬似 provider   ← 嘘
provider: llm=recorded / embedding=recorded                      ← 正しい
擬似 provider（@mnemora/testkit）で走っているため、…              ← 嘘
```

**同じ report の中で、3行が互いに矛盾していた。**本 ADR の土台は「どちらで走ったかを隠さない」
ことなので、これは最も起こしてはならない壊れ方である。**しかも691テストが緑のまま通っていた**
——この層に歯が1本も無かったためである。

**⟹ 直したのは2つ。**(1) `describeMode` を3分岐の網羅的な `switch`（`never` で塞ぐ）にし、
`formatNoApiCallsNotice` は**モードを必須の引数で受け取る**形にして、呼び出し側に真実を
言わせるようにした。(2) `providers.test.ts` に `"recorded"` の配線と表示の歯を11本足した。

**教訓**: 「フォールバックしない」という規律は、**値を作る側だけでなく、値の出所を名乗る側にも
掛かる。**モードを増やす変更は、provider の構築だけでなく、それを人に見せる経路まで含めて検査する。

## 採らなかった案

- **擬似物を全部カセットに置き換える**: 却下。「記録に無い入力は例外」が669件のテスト全部に
  効いてしまい、テストを1本足すたびに実キーが必要になる。二層にした理由がこれである。
- **`compare` も同時にカセット化する**: 却下（**今回は**）。`compare` は実 API で657回の
  LLM 呼び出しを要する（ADR 0019 §3）。範囲を `retrieval` に絞って効果を先に確かめる。
  **ただし `compare` の ✅/❌ 表（322ターン以降が ❌）は依然として擬似埋め込みの産物であり、
  mnemora の限界を示すものとして読んではならない。**これは未解決のまま残る。
- **鍵に `schema` を含める**: 却下。スキーマの些細な変更で全記録が無効になる。
  再生時の再検証で代替した（上記）。
- **記録に無い入力を stub へフォールバックさせる**: 却下。出力の一部だけが意味を持たない値になり、
  どの行が信用できるか分からなくなる。**この仕組みで最も譲ってはいけない点である。**
- **probe set を読んで「必要そうな入力」を列挙して録る**: 却下。列挙が漏れると再生時に落ちる。
  **再生する当のもの（arm B・C）をそのまま走らせて録る**形にした。
- **LLM 応答も `verify` で照合する**: 却下。同じ入力でも応答が揺れるため、差が出ても
  「モデルが変わった」とは言えない。**照合できないものを照合したふりをしない。**

## 引き受けた負債

1. **モデル版の凍結。**カセットは 2026-09-07 時点の `gpt-4o-mini` / `text-embedding-3-small` の姿である。
   OpenAI 側が変わっても**記録は変わらず、テストは緑のまま**になる。
   → `verify` で検出できるようにしたが、**`verify` は手動であり、CI には載せていない**
   （実キーを要求するため）。乖離は「誰かが `verify` を叩いたとき」にしか見つからない。
2. **リポジトリに 1.2MB の生成データが乗る。**256次元 × 152件 + LLM 応答74件。
   probe set を広げれば比例して増える。
3. **arm C の数字は「ある1回のサンプル」である。**上記のとおり実 API 実行と 0.024 ずれた。
   **カセットの arm C を「本物の LLM の実力」と読んではならない。**
4. **`record` は毎回新しいテナントで走る必要がある。**`observe()` が `externalId` で
   重複排除するため、取り込み済みのテナントで走らせると抽出も埋め込みも呼ばれず、
   空のカセットができる（**実際にこれで一度落ちた**ので `Date.now()` を tenantId に混ぜてある）。
5. **probe が7件しかない。**カセット化しても probe set の小ささは変わらない。
   ここから出る MRR は、この7件についての値である。

## これが覆るとしたら

- **`verify` が閾値割れを報告したとき。**モデルが替わったか、記録が壊れたか。どちらでも記録し直す。
- **`verify` の閾値 0.99 が、実際のモデル交代を検出できないと分かったとき。**
  上記のとおり、この線はモデル交代で確かめていない。次にモデルが替わった機会に測り直すこと。
- **probe set を広げたとき。**記録に無い入力が増えるので録り直しが要る。
  **例外で落ちるので、黙って古い記録のまま走ることはない**（そこは設計で塞いである）。
- **`compare` もカセット化する判断をしたとき。**本 ADR の範囲を広げる形になる。
  そのときは 322ターン以降の ❌ が擬似埋め込みの産物だったのかを、まず確かめること。
