# ADR 0179: ADR の番号は「マージ直前」に確定させる — 採番を、衝突しようがないタイミングまで遅らせる（Issue #295）

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-17

**⚠ 各主張の出所を分ける**（ADR 0132 / 0137 の体裁を踏む）。

- **【現物】** — この repo のコード・文書を書き手が読んで確かめた。
- **【実測】** — この書き手が自分の手で `git`/`gh`/`vitest` 等を走らせて確かめた。
- **【受】** — 報告として受け取り、再導出していない（出所を明記する）。

## 問い

[Issue #295](https://github.com/takecchi/mnemora/issues/295)。[ADR 0137](./0137-adr-index-generated-from-source.md)
は「索引（`docs/decisions/README.md`）の _行位置_ の衝突」を消したが、
「_番号そのもの_ の払い出し」は各 PR の作成者が手で選ぶままだった。issue は
【実測】として、2026-09-16 に `0146` を4本の PR が同時に主張していた事例を
挙げている（`docs/263-adr-0022-premise-replaced` / `feat/200-unprompted-association` /
`feat/276-recall-footprint` / `feat/197-resolve-contested`）。解決も手作業で、
最後に push した側が空いている `0150` へ手で移し、ファイル名・見出し・
`docs/`・`packages/*/src` のコード内参照を含め14ファイルを書き換えたと記録されている。

issue は4案を並べ、どれを採るかを未決のまま残していた。本 ADR は、
マネージャーの設計指示（「番号を後から正規化する」— 採番をマージ直前に確定させる）
に沿って実装し、検討した他の3案を却下する。

## 前提を自分の手で確認した

### 【実測】「main へのマージは直列化されている」

この前提は ADR 0137「決定」2番が既に述べている（「並行する ADR PR が複数開いていても、
この手順は**マージする側が1本ずつ直列に**実行する」）が、**その記述自体は
「issue の割り振り元が『私が最後にマージする』と明言している運用」という
【受】に基づいており、0137 自身もそれを再検算してはいない。** 本 ADR では、
以下を自分の手で確認した:

```
git log origin/main --merges --oneline | wc -l
→ 0
```

**`origin/main` には merge commit が1本も無い。** 全てのコミットが
`<subject> (#<PR番号>)` という GitHub の squash merge が生成する形をしている
（`git log origin/main --oneline -20` で確認、例: `d2f5e40 ... (#359)`）。
これは「ある瞬間に2本の PR が同時に `main` へ着地する」という状態が
git の履歴モデル上そもそも存在しないことを裏付ける——squash merge は必ず
「直前の `main` の1コミットへ、1つの新しいコミットを積む」形であり、
2つの squash が同時に同じ親を指すことはできない（片方が先に着地すれば、
もう片方はその新しい `main` を取り込み直すまで push できない。GitHub 側で
branch protection の "must be up to date" が有効かは未確認——下記
「確かめていないこと」参照）。

**⚠ ただし、これは「履歴が直列に見える」ことの確認であって、「2人（2エージェント）が
同時に `adr-renumber.mjs` を走らせてマージ作業を進めることが構造的に防がれている」
ことの証明ではない。** 後者は依然として運用（「マネージャーが1本ずつ順にマージする」）
に依存する——**引き受けた負債**参照。

### 【実測】既存の重複検出の歯（`adr-duplicate-number.test.mjs`）の射程

`scripts/__tests__/adr-duplicate-number.test.mjs`（Issue #315）を読み、
`vitest.config.mts` で `include: ["scripts/**/*.test.mjs"]` に素直に拾われ、
`describe.skipIf` を持たないことを確認した——**PR ブランチでも `main` でも
無条件に走る。** ただし、この歯が検査するのは「`docs/decisions/*.md` の
**現在の**ファイル名一覧に重複が無いか」だけであり、**単一ブランチ内では
常に緑になる**（衝突相手の ADR はまだそのブランチに存在しないため）。

**⟹ この歯は「検出」であって「採番の確定」ではない。** 2本の PR がそれぞれ
`0174` を名乗った状態で、片方が先に `main` へ squash merge されると:

- 1本目の squash merge 直後の `main` — 歯は緑（`0174` は1本だけ）。
- 2本目の squash merge 直後の `main` — **歯は赤くなる**（`0174` が2本）。
  この赤は `main` への push で `ci.yml` が走った時点で初めて現れる
  （`on: push: branches: [main]`）。

**⟹ 検出は必要だが、「2本目が着地する前に止める」ことはできない。**
この lib（`generate-adr-index-lib.mjs` の `buildAdrEntries`）は
`docs/decisions/README.md` の生成そのものも同時に失敗させる（例外を投げる）
ので、2本目が着地した瞬間に索引生成・鮮度検査の両方が壊れる——**Issue #295
が問題にしている「後から気づいて片方を動かす」コストが、この歯だけでは
消えない。**

### 【実測】`docs/decisions/` の現状

`git ls-tree -r --name-only origin/main -- docs/decisions/` で数え、
`origin/main` に ADR は 173 本（`0001`〜`0173`、欠番なし）あることを確認した。
`git branch -r` / `gh pr list --state open` で当時 open だった3本の PR
（#308 / #314 / #320）を確認したが、いずれも `origin/main` に対して
新しく追加する ADR ファイルを持たない、または既に `main` に着地済みの
番号（`0157`/`0158`）しか名乗っていなかった（`git ls-tree` で各ブランチの
`docs/decisions/` を突き合わせて確認）——**この時点では ADR 番号の衝突は
起きていない。**

## 決定

### 1. 番号は2段階で扱う——「最初の1本（楽観的）」と「確定（マージ直前）」

- **`node scripts/adr-renumber.mjs --next`** は、新しく ADR を書き始める人が
  最初の番号を選ぶための**助け**である。`origin/main` に加えて、他のリモート
  ブランチ（`refs/remotes/origin/*`）と open な PR（`gh pr list` +
  `gh pr view --json files`）が主張している番号も見て、まだ誰も取っていない
  次の番号を返す。`gh` が使えない環境では、その旨を告げて `origin/main` だけで
  答える——静かに劣化させない。
- **これは衝突を防がない。** 2本の PR がほぼ同時に `--next` を叩けば、
  同じ番号を返しうる。**確定させるのは、次の一手である。**
- **`node scripts/adr-renumber.mjs`（引数無し）が採番を確定させる。**
  マージする側が、squash merge する**直前**に、PR ブランチ上で
  `git merge origin/main` した**直後**に実行する。このブランチが
  `origin/main` に対して新しく追加した `docs/decisions/*.md` のうち、
  番号が `origin/main` 側で既に使われているものだけを、空いている次の番号へ
  `git mv` し、参照を書き換える。**`main` へのマージが直列化されている
  （上記「前提を自分の手で確認した」）ため、この時点で他の ADR が同時に
  着地することは構造的に無い。**

この一手は、ADR 0137「決定」2番が既に持っている儀式（squash merge 直前に
PR ブランチ上で `generate-adr-index.mjs` を走らせる）に、**索引の再生成より
前**の一手として挿し込む。順序:

```
git fetch origin main && git merge origin/main
node scripts/adr-renumber.mjs
node scripts/generate-adr-index.mjs
git add -A && git commit -m "..."
git push
node scripts/ci-green-check.mjs --pr <N>
gh pr merge <N> --squash
```

（`docs/autonomy.md` §4 の該当行を、この順序に書き換えた。）

### 2. 付け替えるもの

`node scripts/adr-renumber.mjs` が衝突を検出したら、次を書き換える:

1. **ファイル名**（`git mv`）。
2. **ファイル1行目の見出し**（`# ADR NNNN: ...`）。
3. **このブランチが `origin/main` に対して実際に追加した行の中にある参照**——
   旧ファイル名の stem（`NNNN-slug`、拡張子抜き）を含む文字列と、
   `ADR ` に続く旧番号。**裸の4桁数字はどちらの形にもマッチしない限り
   一切変更しない。**

変更した箇所は全部標準出力に列挙する（`ファイル: 種別 ADR 旧番号 -> ADR 新番号（N箇所）`
の形。監査できるように、行ではなくファイル単位で列挙する）。

### 3. ⚠ 「参照の全置換」ではなく「このブランチが追加した行だけ」に絞った——自分で確かめた実例に基づく設計変更

マネージャーの指示は「リポジトリ内の全参照…追跡対象のテキストファイル全体を
走査すること」だったが、**実装の途中でこれをそのまま実装すると壊れる実例を
自分の手で見つけた**ため、対象を「このブランチが `origin/main` に対して
追加した行」だけに絞った。

**【実測】** 衝突する可能性のある番号（例: `0173`）は、定義上「`origin/main`
で既に使われている」番号である。そして `git grep -n "ADR 0173\b"` を
実際に打つと、`packages/core/src/recall-runtime.ts`・`packages/core/src/recall.ts`・
`docs/recall.md`・`docs/roadmap.md`・複数のテストファイルにまたがって、
**その既存の ADR 0173 を指す正当な言及が repo 全体に数十箇所ある**ことを
確認した（`adr-renumber-lib.mjs` の docstring に一次確認の記録がある）。

もし「衝突した番号への言及をリポジトリ全体で一括置換する」という素朴な実装
（最初に書いたもの）のまま進めていたら、**このブランチとは無関係な、
`origin/main` 側の正当な言及まで巻き込んで書き換えてしまう**——これは
実際に手を動かして初めて気づいた。修正前の実装で、実際に自分の書いた
`scripts/adr-renumber-lib.mjs`・`scripts/__tests__/adr-renumber-lib.test.mjs`
自身（衝突テスト用に別ブランチへ複製したもの）を対象に再現し、
`packages/core/src/recall-runtime.ts` のような**このブランチが一切触っていない
ファイル**は無傷のまま、**このブランチが新しく足した行だけ**が書き換わることを
確認した（下記「測ったこと」）。

**⟹ 決定: 書き換えの対象を「`git diff --unified=0 origin/main -- <file>` が
示す、追加された行番号」だけに絞る。** `origin/main` から継承した行（この
ブランチが触っていない行）は、たとえ同じファイル内に衝突した番号への
正当な言及が同居していても、一切変更しない。これは「リポジトリ全体の
ファイル種別を横断して見る」というマネージャーの意図（docs だけでなく
`packages/*/src` やスクリプトも見る）は満たしつつ、「継承した正当な参照を
巻き込む」という副作用を消す設計変更である。

## 検討して採らなかった案

- **案1（issue #295 案1・検出の歯を足すだけ）**: 既に
  `scripts/__tests__/adr-duplicate-number.test.mjs`（Issue #315）が在る。
  **却下（というより「既に在るが、これだけでは足りない」）**——上記
  「前提を自分の手で確認した」で示した通り、この歯は**単一ブランチ内では
  常に緑**であり、衝突は2本目が `main` へ着地した**後**に `main` を
  赤くする形でしか現れない。検出は必要（実際にこの ADR も歯を削除しない）
  だが、**採番の問題そのものは解けていない**——「2本目が着地する前に
  空いている番号へ動かす」という本 ADR の主題に、この案は答えない。
- **案2（issue #295 案2・ファイル名から番号を外す）**: 索引の生成時に採番する。
  **却下**——既存173本と、名前で参照している全箇所（コード内コメント含む
  数百箇所、上記 `git grep` の実測が一端を示す）が壊れる。破壊的で、
  得られる利益（採番の自動化）に対して割に合わない。ADR 0137 が既に
  「索引の生成」で同種の判断（front matter を増やさず既存ファイルへの
  変更をゼロにする）をしており、本 ADR も同じ判断を踏襲する。
- **案3（issue #295 案3・手順を文書に書くだけ）**: 「ADR を足すときは
  `git fetch origin && git branch -r` で他ブランチを見てから番号を選ぶ」と
  `docs/autonomy.md` に書く。**却下**——`AGENTS.md` が「規律ではなく
  注意力に依存しており、必ず失敗する」と明記している形そのものである。
  `--next` はこの手順を**機械化**したものとして残すが、それ単独では
  「最初の1本を選ぶ助け」でしかなく、確定の手段にはしない。
- **案4（issue #295 案4・番号の予約）**: issue かファイルで番号を先に取る。
  **却下**——予約先自体（issue・ファイル）が並行 PR から見て同じ衝突の
  形を持つ。「予約を取る」という行為そのものを直列化する仕組みが無ければ、
  予約の取り合いが起きる。
- **ADR 番号 = PR 番号にする**: 一意性は構造的に得られる。**却下**——
  【実測】この repo の PR は #359 まで進んでいる一方、ADR は 173 本目である
  （`git ls-tree -r --name-only origin/main -- docs/decisions/ | wc -l` で
  確認）。番号が飛び飛びになり、「0173 の次が 0174」という現在の読み方
  （`pickNextFreeNumber` が拠り所にしている「単調増加」の慣行そのもの）が
  壊れる。また、PR を作る前に ADR を書けなくなる——このリポジトリでは
  ADR を先に書いてから PR を出す運用が一般的である（`docs/decisions/` の
  多くが対応する Issue 番号を先に持つ）。

## 引き受けた負債

1. **番号がマージ直前に変わりうるため、PR 本文や issue コメントに書いた
   「ADR 0174」という言及が事後に陳腐化しうる。** repo の中（ファイル名・
   見出し・このブランチが足した行の参照）は `adr-renumber.mjs` が
   自動で書き換えるが、**GitHub 上の PR 本文・issue コメントに書いた
   文言は書き換わらない。** `--next` で楽観的な初手の精度を上げることで
   付け替えの発生自体を稀にし、緩和する——確定した番号と最初の番号が
   一致する限り、この負債は顕在化しない。
2. **「main へのマージは直列化されている」は、git の履歴が merge commit を
   持たないことから確認できるが、それを構造的に強制する仕組み
   （branch protection・merge queue 等）の有無は確認していない。**
   運用（1人のマネージャーが1本ずつマージする）に依存する部分が残る——
   もし将来複数の担い手が同時にマージ作業を行うようになれば、
   「`git merge origin/main` した直後から `gh pr merge` するまでの間」に
   別の squash merge が割り込む余地が生まれ、この ADR の前提が崩れる。
3. **書き換えの対象を「このブランチが追加した行」に絞ったことで、
   逆に見落としが起きる場合がある**——例えば、このブランチが
   *既存の main の行を編集した*場合（新規追加ではなく既存行の修正）、
   その編集後の行は「追加行」として拾われるので対象になるが、
   **このブランチが一切触れていない、しかし意味的にはこのブランチの
   新しい ADR を指しているべき行**（想定しにくいが、例えば別の担い手が
   同じ番号を見越して先に書いていた言及等）は拾えない。今回はこの
   ケースを実際には確認していない——**確かめていないこと**参照。
4. **`--next` の PR 検出は `gh pr view --json files` を PR ごとに個別に
   呼ぶ**ため、open な PR が多いと相応の回数 `gh` を呼ぶ。今回は
   数十本規模までしか想定していない——それ以上の規模でのレイテンシは
   測っていない。

## これが覆るとしたら

- `main` へのマージが直列でなくなった場合（複数の担い手が同時に
  マージ作業を行う運用に変わった場合、あるいは GitHub 側の merge queue が
  複数 PR を並行して処理するようになった場合）、「マージ直前に
  `origin/main` を取り込めば衝突しない」という前提が崩れる。その場合は
  `adr-renumber.mjs` の実行そのものを、実際に `gh pr merge` する
  直前の再確認（`ci-green-check.mjs` の直前に `git fetch origin main` して
  差分が無いことを確かめる、等）で挟み直す必要がある。
- ADR の総数が増え、`--next` が `gh pr list` を呼ぶコストが無視できなくなった
  場合、ページングや呼び出し回数の削減が要る。
- 「このブランチが追加した行だけを見る」という境界が、実際に見落としを
  起こした事例が観測された場合、対象範囲を広げる判断がありうる——
  ただしその場合も「継承した正当な参照を巻き込む」問題（本 ADR の
  「決定」3番）を再度解く必要がある。

## 測ったこと

- 【実測】`git log origin/main --merges --oneline | wc -l` → `0`
  （merge commit が無いことの確認、上記「前提を自分の手で確認した」）。
- 【実測】`git ls-tree -r --name-only origin/main -- docs/decisions/` で
  `origin/main` の ADR が173本（`0001`〜`0173`、欠番なし）であることを確認。
- 【実測】`git grep -n "ADR 0173\b"` で、既存 ADR 0173 への正当な言及が
  `packages/core/src/recall-runtime.ts`・`recall.ts`・`docs/recall.md`・
  `docs/roadmap.md`・複数のテストファイルにまたがって多数（数十箇所）
  存在することを確認した。
- 【実測】`scripts/__tests__/adr-renumber-lib.test.mjs`（25 tests）が全て緑。
  `planRenumbering`（衝突なし/衝突あり/複数衝突時の相互非重複/一部だけ衝突/
  形式不正での例外）、`rewriteReferencesInText`（正しい2形だけを拾う/
  裸の数字を巻き込まない/似た slug や長い数字列を誤って巻き込まない/
  `oldNumber===newNumber` では何もしない）、`addedLineNumbers`（新規ファイル/
  1行挿入/削除のみ/差分なし/複数ハンク/継承行を含めない）を検査する。
- 【実測】変異試験: `rewriteReferencesInText` の境界条件（stem の右側境界
  `(?![a-z0-9-])`、ADR 表記の右側境界 `(?!\d)`）を意図的に削除したところ、
  「似た別の slug を持つ同じ番号は誤って巻き込まない」「後ろにもっと長い
  数字が続く場合は ADR 表記として巻き込まない」の2 test が red になり
  （期待通りの誤検出）、退避コピーから復元して 25 test 全て green に
  戻ることを確認した（`git checkout` は使わず、`cp` で取った退避コピーから
  復元した——`docs/autonomy.md` §4「`git checkout <file>` で変異を戻す」の
  穴を踏まないため）。
- 【実測】`git worktree` を使った実地の smoke test（実際の repo 内容に対して
  実行し、テスト用の一時 worktree として破棄した）:
  - `origin/main` の既存 ADR 0173 と番号が衝突する偽の ADR を作り、
    `docs/roadmap.md`（`origin/main` に既に多数の「ADR 0173」言及を持つ
    ファイル）へこのブランチ自身の新しい言及を1行追加した状態で
    `node scripts/adr-renumber.mjs` を実行した。
  - 結果: 偽の ADR は `0173-fake-conflict-test.md` → `0174-fake-conflict-test.md`
