# ADR 0135: 主測定の被覆を広げる設計（第1弾）— 「単独トークンの数詞・記号インデックス」を弁別軸とする第4の probe 集合を置く。件数は行列から導き、margin の分布で読む

- **状態**: 提案 (2026-09)
- **日付**: 2026-09-15

**⚠ 各主張の出所を分ける**（[ADR 0094](./0094-identifier-probes-local-embedding.md) /
[ADR 0110](./0110-single-char-token-discriminator.md) の体裁を踏む）。

- **【実測】** — この ADR の担当者が、この手元の器（in-memory fake store +
  `@mnemora/local-embedding` + `DeterministicLLMProvider`）に対して実際に走らせた。
- **【現物】** — この repo のコード・文書を読んで確かめた。
- **【受】** — マネージャーからの指示・報告として受け取り、自分では再導出していない。

⛔ **この ADR は設計のみであり、実装は含まない。**理由と残件は §8「引き受けた負債・残件」。

## 0. 依頼の要旨と、この ADR が答える範囲

マネージャーから、Issue #109（「実 embedding での継続計測のゴールデンセットが数十件に
届いていない」）の**第1弾**として、次を依頼された【受】:

> 主測定（意味的関連性、`probe-set.ts` 7件）の被覆をどう広げるかの**設計**をし、ADR に落とす。
> 件数を先に決めず、(1) どの領域を測るか (2) fact/query/distractor の選定規則
> (3) distractor の弁別軸 (4) lexicalControl 相当の対照群を置くか (5) 件数の導出
> (6) margin の分布で読む評価設計、の6点を決めて理由を書く。実装をどこまで含めるかは
> 担当者が決めてよい。

**⛔ 制約として明示されたこと**（マネージャー指示、[ADR 0058](./0058-measure-the-time-term-in-a-separate-arm.md) §1.4
がすでに置いている規律の再確認）:

> `examples/chat/src/probe-set.ts` の既存7 probe（gold/distractor 14件）は**意図して
> 凍結されている**。時間項が定数であることは統制条件であり、そこへ手を入れるのは
> 計装ではなく統制を外すことである。⟹ 被覆を広げる仕事は、`probe-set.ts` を編集する
> 仕事ではなく、**第3の別集合を作る仕事**である。

**⟹ この ADR は、`probe-set.ts` に1文字も触れない**（§7 検討して採らなかった案、
§9 確かめたことで裏付ける）。

`PROBES`（`probe-set.ts`）は7件（color/pet/exercise/diet/family/language/travel）。

### 1.2 【現物・受】ADR 0110 が実測で確定した、まだ「系統立てて測られていない」事実

ADR 0110 §5 は、`japanese-name-probe-set.ts` の `org-b`（`開発一課`/`開発二課`）が
落ちる理由を切り分け、次を実測した（逐語の要点）:

> 区別が失われているのは、`tokenizer` が弁別部分を「**単独1文字のトークン1個**」に割り、
> かつ mean pooling がそれを**長い共有トークン列で薄めた**ときである。
> 軸1（表現の遠さ）: 漢数字1文字は算用数字・ラテン文字1文字の約1/2.2しかベクトルを
> 動かさない。軸2（希釈）: 共有前置を外すだけで符号が反転する。

**⟹ ADR 0110 はこの現象を1文の反実仮想（`一/二` → `1/2` → `A/B` → 前置除去）でしか
確かめていない。**しかも ADR 0110 自身が「案B（ベンチが自分の分解能を印字する）」
「案C（バッチ依存に名前を付ける）」を**採らなかった案として書き残し**、
「案A（読み方だけ直す。probe は増やさない）」を選んでいる。

**⟹ これは Issue #109 の主張とは別の、しかし密接に関連する未測定領域である**:
「単独トークンの数詞・記号インデックスが、共有前置の長さと文字種によって
どれだけ脆くなるか」は、**1つの偶然見つかった事例（`org-b`）でしか観測されておらず、
系統的な probe として存在しない。**

### 1.3 洗い出した「1件も測っていない」領域（3つ。うち1つをこの ADR の対象に選ぶ）

コードを読んで確認した、既存3集合のどれも1件も測っていない領域:

1. **⭐ 単独トークンの数詞・記号インデックスの脆さを、文字種×共有前置長で系統的に測ること。**
   `japanese-name-probe-set.ts` の `org-a`/`org-b`/`org-c` は結果として1文字違いだが、
   「文字種」「共有前置の長さ」を**独立変数として動かした**probe は0件（ADR 0110 は
   1文で6つの反実仮想を回しただけで、常設した probe にしていない）。
2. **関係の反転**（同一の2entity間で役割が入れ替わる: 「AがBに~」対「BがAに~」）。
   既存3集合はいずれも「どのentityか」を変える設計であり、「同じentity対の役割を
   入れ替える」形の distractor は0件。
3. **否定**（肯定/否定のみが差である）。既存3集合の distractor はいずれも
   「話題は合うが対象/値が違う」であり、「対象は同じで極性だけが違う」形は0件
   ——ただし後述(§7)のとおり、これは構造的に「同一 entity の矛盾する事実」
   （[ADR 0134](./0134-mark-contested-explicit-operation.md) の矛盾検出の領域）と
   衝突しやすく、**独立した弁別軸として切り出すのが難しい**（§7 で却下理由を書く）。

**⟹ この ADR は 1 を選ぶ。**理由は §2。2・3 は §10「残件」に明記して次へ渡す。

## 2. なぜ「単独トークンの数詞・記号インデックス」を選んだか

- **すでに実害が1件観測されている**（ADR 0110 の `org-b`）。「測っていない領域を
  当てずっぽうで選ぶ」のではなく、**この repo が偶然踏んだ穴を、意図して再現可能な
  形に格上げする**——docs/autonomy.md §1 の段4「測れていないものを測る」に正確に当たる。
- **製品価値に直結する**——日付・号店番号・版番号・部署番号のような「短い索引」を
  取り違えることは、記憶想起の信頼を損なう典型例である。
- **ADR 0110 自身が、この方向を明示的に示唆している**（§7 案B「ベンチが自分の
  分解能を印字する」・案C「バッチ依存に名前を付ける」）。**この ADR は、
  ADR 0110 が採らなかった道を、別の決定として拾う。**
- **margin 分布で読む設計（依頼の6番目）と相性が良い**——後述 §5 のとおり、
  この軸は「大半は通り、まれに壊れる」という**分布**を測ることそのものが目的であり、
  二値の hit@1 だけでは意味を失う対象である。

### 3.2 測ったこと(1): 文字種 × 共有前置長 の2軸で、`org-b` と同型の文を測った

**方法**: `org-b` と**同じ11文字の共有前置**（`北陵物産株式会社の開発`）を持つ文で、
弁別トークンの文字種だけを変えた（漢数字/算用数字/アルファベット）。加えて、
**共有前置をほぼ0文字にした**同型の文（`3号店`/`A店` 等）も測った。

| id                                             | 文字種         | 共有前置   | goldRank      | margin(similarity, gold−distractor) |
| ---------------------------------------------- | -------------- | ---------- | ------------- | ----------------------------------- |
| `long-kanji`（= ADR 0110 の `org-b` そのもの） | 漢数字         | 長い(11字) | **2**（負け） | **`-8.015200e-5`**                  |
| `long-arabic`                                  | 算用数字       | 長い(11字) | 1             | `+2.697353e-2`                      |
| `long-alpha`                                   | アルファベット | 長い(11字) | 1             | `+1.987733e-2`                      |
| `short-kanji`                                  | 漢数字         | 短い(0字)  | 1             | `+3.638654e-2`                      |
| `short-arabic`                                 | 算用数字       | 短い(0字)  | 1             | `+4.480890e-2`                      |
| `short-alpha`                                  | アルファベット | 短い(0字)  | 1             | `+3.366741e-2`                      |

**⟹ ADR 0110 §5.3 の反実仮想（`long-kanji`/`long-arabic`/`long-alpha` の3値）と
小数第6位まで一致した**——同じ現象を独立に再現できた（自分の実装のバグではないことの
確認でもある）。**そして新規に測った `short-*` は全件、健全な正のマージンだった。**

### 3.3 🔴 測ったこと(2): 「長い前置+漢数字」だけでは再現しない — n=1 の危険を自分で踏んだ

**⚠ ここが、この ADR にとって最も重要な実測である。**§3.2 だけを見ると
「長い共有前置+漢数字なら落ちる」と結論したくなる。**それを検証するため、
`org-b` とは別の語彙で、同じ構造（11文字共有前置+漢数字1文字+1文字助数詞）の文を
もう1件作って測った:**

| id             | 文                                                                                                   | goldRank      | margin                     |
| -------------- | ---------------------------------------------------------------------------------------------------- | ------------- | -------------------------- |
| `long-kanji-2` | 「彩雲物流株式会社の営業**一**部は法人向け商材を扱っています。」対「…営業**二**部は個人向け商材を…」 | **1**（勝ち） | **`+2.417745e-2`**（健全） |

**⟹ 「長い共有前置 + 漢数字」という2要因だけでは `org-b` の失敗を予測できない。**
`long-kanji-2` は `long-kanji` とほぼ同じ構造（前置11文字・弁別漢数字1文字・
末尾1文字の助数詞）でありながら、健全な正のマージンだった。

**🔑 これは ADR 0110 の一般則2（「二値ではなく margin の分布で読む」）を、
この ADR の担当者自身が実装前に踏んで検証したことを意味する**——
もし `long-kanji-2` を測らずに「2軸モデルが正しい」と決め打ちして probe を
設計していたら、**存在しない規則性を製品の設計根拠にするところだった。**
⟹ **この発見自体が、§5 の「margin 分布で読む」設計を実装前から必要とする根拠になる**
——**まれにしか起きない、まだ全容の分からない現象**を測るのに、
二値の hit@1 だけでは「12件中11件は勝ち」で片付き、`org-b` のような
ほぼ同点のニアミスを埋もれさせる。

**⚠ この ADR は「なぜ `long-kanji` だけ落ちるのか」の完全な機序を特定していない。**
ADR 0110 が特定した2軸（文字種・希釈）は**必要条件ではあるが十分条件ではない**
——第3の要因（語彙・字面・トークン境界の細部）が残っている。**この先を追うのは
この ADR の範囲外である**（ADR 0110 §6 も「他の tokenizer では境界が別の場所に来る」
と、機序の完全特定を範囲外に置いている)。

## 4. 決めたこと

1. **第4の probe 集合を新設する**（仮称 `numeral-token-probe-set.ts`。
   `examples/chat/src/`。既存3集合には1文字も触れない）。
2. **弁別軸は「単独トークンの数詞・記号インデックス」**——gold/distractor は
   共有する語幹（店舗名・部署名・版番号の接頭辞等）を持ち、末尾の**短い索引
   （数詞または英字1〜2文字）だけ**が異なる。
3. **文字種（漢数字/算用数字/アルファベット）× 共有前置長（長い/中間/短い）の
   行列で、意図して系統的に振る**（§5.1）。**値を見てから調整しない**
   ——ADR 0094 §6 の規律（「値を見る前に1度だけ固定する」）をそのまま適用する。
4. **query は discriminator（索引そのもの）を含める**——識別子集合・日本語固有名詞
   集合と同じ立場（§5.2 で理由を書く）。
5. **lexicalControl 相当の対照群は置かない**——識別子集合・日本語固有名詞集合と
   同じ理由（§5.3）。
6. **件数は行列から導く。件数を先に決めない**（§5.4）。
7. **arm の報告に `margin`（gold と distractor の `similarity` の差）を
   一級の値として持たせ、hit@1 の二値ではなく分布（平均・標準偏差・最小値）で
   要約する**（§5.5）。**ADR 0110 §7 案B が「本当はこうあるべき」として書き残し、
   採らなかった道を、この新集合に限って先に実装する設計にする。**
8. **⛔ 門にしない**（既存2集合・ADR 0088/0094 と同じ理由。標本が少なく閾値は
   偽陽性を出す）。
9. **sparse/dense の2 haystack 条件を、最初から両方持つ**——ADR 0094 §6 が
   「疎条件だけでは #106 を代表していなかった」と学んだ教訓を、**後から追加する
   のではなく最初から適用する。**

## 5. 各項の設計と理由

### 5.1 文字種 × 共有前置長の行列（§3 の実測に基づく）

| 軸         | 値                                                         | 根拠                                                                                                                                                                                                           |
| ---------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 文字種     | 漢数字 / 算用数字 / アルファベット                         | ADR 0110 §5.3 が実測した軸1（表現の遠さ）をそのまま流用。3値とも実務のインデックス表記として自然（「第一営業部」「開発1課」「Aプラン」）                                                                       |
| 共有前置長 | 長い(目安10文字以上) / 中間(目安4〜6文字) / 短い(0〜1文字) | ADR 0110 §5.4 が実測した軸2（希釈）を2値（長い/除去）から3値へ拡張。**中間**を新設するのは、§3 では長い/短いの2点しか測っておらず、**margin がどう連続的に変化するかを見るため**（分布として読む設計との整合） |

⚠ **§3.3 の実測により、この2軸だけでは「いつ壊れるか」を予測できないことは
分かっている。**⟹ **この行列は「壊れる条件を狙い撃つ」ためではなく、
「この2軸を独立変数として動かしたとき、margin がどう分布するかを観測する」
ための実験計画である。**壊れる/壊れないの結果は、行列を組んだ後に**測って初めて
分かる**——これは意図した設計であり（ADR 0094 §6 と同じ規律）、
「狙って `org-b` 相当をもう1件作る」ことは目的にしていない。

### 5.2 fact/query/distractor の選定規則 — 「discriminator を query に含める」を継承する

`probe-set.ts`（凍結・内容語を共有しない）と `identifier-probe-set.ts`/
`japanese-name-probe-set.ts`（逆・discriminator を含める）という、依頼で示された
2つの立場のうち、**この新集合は後者を継承する**。

**理由**: この軸が測りたいのは「**短い索引そのものを、embedding がどれだけ精密に
区別できるか**」であり、「文の意味を丸ごと言い換えても引けるか」（`probe-set.ts` が
測る対象）ではない。もし query から discriminator を落とすと、gold/distractor を
分ける手がかりが embedding 全体の意味的な近さだけになり、**この ADR が測りたい
「単独トークンの精密さ」という論点が測れなくなる**——それは
`probe-set.ts` が既にやっていることの再演になる。

⚠ **第三の立場（discriminator を含まないが、内容語も完全には避けない）は検討した
が採らなかった**——§7 で理由を書く（「同一entityの数量差」という構造に落ちて
矛盾検出の領域と衝突することを、実際に試作して確認した)。

### 5.3 lexicalControl 相当の対照群は置かない

ADR 0094 が識別子集合について書いた理由をそのまま継承する(逐語):

> ここでは MRR(全体)しか持たない…**全件が「識別子を含む問い」**であり、対照群を
> 分ける設計にしていない(この母数で対照群まで割ると1群あたりの件数がさらに
> 小さくなり、何も主張できなくなるため)。

**この新集合も同じ構造**(query が discriminator を含む)であり、同じ理由がそのまま
当たる。**⚠ 追加の理由**: そもそも `lexicalControl` は「擬似 embedding でも
引けるはずの対照」として `probe-set.ts` に置かれたものであり(内容語を共有しない
設計との対比が前提)、**discriminator を含める設計では対照の意味が変わってしまう**
——query が discriminator を含む時点で、擬似 embedding(文字コード由来)でも
部分一致しうるため、「対照」として機能する保証がない。

### 5.4 件数は行列から導く

**行列**: 文字種3 × 共有前置長3 = **9セル**。

**セルあたりの最小標本数**: §3.3 で自分自身が「n=1 で誤った規則性を結論しかけた」
ことを実測した。**⟹ 1セルにつき最低2つの独立した語彙インスタンスを置く**
(同じ構造・違う単語で、`long-kanji`/`long-kanji-2` の対と同じ検証をセル内でも
できるようにする)。

**⟹ 最小件数 = 9セル × 2インスタンス = 18件。**

これは「数十件」という Issue #109 の目安には届かないが、**依頼の明示的な制約
(「件数を先に決めない。1〜4から導く」)に従った結果である。**⚠ 実装時にセルごとの
インスタンスを3つに増やせば27件になる——**その判断は実装時に行う(残件)。**
いずれにせよ、**根拠は「行列のセル数 × n=1 の危険を避けるための最小反復数」であり、
狙った丸い数字ではない。**

**haystack**: sparse(既存 `buildHaystackUtterance` を再利用、`probe-set.ts` は
1文字も変えない)/dense(同じ索引ファミリーの near-miss を敷き詰める)の両方を
最初から持つ。dense の件数比は既存2集合の先例(5:1)に倣う——
`18件 × 5 = 90`(実装時のセル数次第で変動)。

### 5.5 margin を一級の値にする

**現状の欠落**(§1.2・ADR 0110): `IdentifierProbeOutcome`/`ProbeOutcome` は
`scoreDetails`(gold/distractor/1位の `ScoreBreakdown`)を**すでに記録している**
(`collectScoreDetails`、`retrieval-quality.ts`)。しかし **margin(gold と
distractor の差)を計算して残す場所が無い**——ADR 0110 の margin 表はすべて
この ADR の担当者(および ADR 0110 の担当者)が**手作業で `scoreDetails` から
引き算した値**であり、arm の出力にもベースラインファイルにも存在しない。

**決めたこと(設計。実装は§8で残件にする)**:

```
margin: number | null;  // similarity(gold) − similarity(distractor)
                         // どちらかが scoreDetails に無ければ null
                         // (「差が0だった」と「測れなかった」を同じ顔にしない。
                         //  ADR 0033 の「無いには種類がある」をこの値に適用する)
```

を probe ごとの outcome に足し、arm 全体では**平均・標準偏差・最小値**
(ADR 0110 §3 の Welch t 検定の表と同じ形の集約)を report に持たせる。

**⚠ 二値(hit@1)と併記する。置き換えない。**理由: hit@1 は「limit の窓に
入ったか」という別の情報(§6 相当)を持っており、margin だけでは
`omitted`(閾値落ち・窓落ち)を区別できない(ADR 0033 の absence taxonomy)。

**この設計は、識別子集合・日本語固有名詞集合が使う共通の arm
(`identifier-arm.ts` の `runIdentifierProbeArm`/`ArmProbeSetSpec`)に
`margin` フィールドを足すことを意味する。**これは**この ADR の決定に必須の
変更**(margin を分布で読むという依頼の6番目に直接応える)であり、
「ついでに直す」ではない——ただし、既存2集合の report・summary script・
baseline JSON の schema にも影響するため、**実装は別途行う**(§8)。

## 6. 検討して採らなかった案

- ⛔ **`probe-set.ts` に discriminator を書き込む/時刻同様に手を入れる。**
  §0 の制約どおり却下。ADR 0058 §1.4 の統制条件を外すことになる。
- ⛔ **既存 `identifier-probe-set.ts`/`japanese-name-probe-set.ts` に項目を
  追加するだけで済ませる(新集合を作らない)。** 却下。この ADR が測りたいのは
  「文字種×共有前置長を独立変数として動かした系統的観測」であり、
  既存2集合は「領域(識別子/固有名詞)を広く浅く覆う」という別の目的で設計されている
  ——目的の異なる観測を1つのファイルに混ぜると、ADR 0094 §3 が既に警告した
  「母数の違う数字を同じ表に同居させる」問題を再発する。
- ⛔ **query から discriminator を落とし、代わりに「同一entityの数量差」
  (例: 同じチームの人数違い)にする。** 試作して測定した(§3 とは別に、
  この ADR の下書き段階で実際に12件のコードを書いて local embedding で
  走らせた)。**結果、entity名の違い(第三/第四等)と数値の違いが交絡し、
  「数値そのものの弁別力」を独立に測れないことが分かった**(entity名を
  完全に同一にすると、それは2つの矛盾する事実になり、
  [ADR 0134](./0134-mark-contested-explicit-operation.md) の矛盾検出の
  領域と衝突する)。⟹ 採らない。**この試作コードはコミットしていない**
  (使い捨てスクリプトとして走らせ、削除した)。
- ⛔ **件数を「数十件」に合わせて先に決め、行列を後から埋める。**
  依頼の明示的な禁止(§0)に反する。
- ⛔ **「関係の反転」「否定」もこの ADR で一緒に設計する。**
  1つの probe 集合は1つの弁別軸、という既存3集合の先例(識別子=ASCIIコード、
  固有名詞=日本語名、時間項=freshness/decay)を踏まえ、混ぜない。§10 に残す。
- ⛔ **この ADR で実装まで完了させる。** 下記§8で理由を書く。

## 7. 「否定」「関係の反転」を選ばなかった理由(§1.3 の残り2領域)

- **否定**: 「肯定/極性だけが違う」形にすると、**同一entityの矛盾する事実**
  (ADR 0134 の対象領域)に構造的に近づく。異なる2つのentityに分けて極性だけを
  変えると、実際にはentity名の違いが discriminator になり、
  「否定を弁別軸にする」という当初の狙いが測れなくなる
  (§6 で数量について試作して確認したのと同型の問題)。**独立した設計課題として
  扱う価値はあるが、この ADR の範囲では解けない**——次に着手する人への
  引き継ぎとして§10に残す。
- **関係の反転**: 同一の2entity間で主語/目的語を入れ替える設計は、
  [ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md) §2.2 が
  実測した「gold の主語がゼロ代名詞で落ちる」問題(抽出スキーマに主語の構造化欄が
  無い)と地続きであり、**抽出側の欠陥(該当 ADR が「この ADR では直さない」と
  明示的に保留した領域)を先に踏むことになる。**この ADR の範囲外とする。

## 9. これが覆るとしたら

- **§3.3 の「第3の要因」が特定されたとき。**この ADR の行列(文字種×共有前置長)は
  必要条件のみを捉えており、特定できれば行列にもう1軸足す設計に直す必要がある。
- **本番(pgvector/HNSW)での実測が、in-memory の結果と食い違ったとき。**
  §5.1 の行列設計はそのまま有効だが、§3 で示した具体的な margin の値は
  作り直しになる。
- **既存2集合(識別子・日本語固有名詞)の report に `margin` を足す実装で、
  既存の歯や基準値ファイルに想定外の影響が出たとき。**§5.5 の「共有 arm に
  足す」という設計判断自体を見直す(専用の別 arm に分ける代替案に戻る)。
- **この新集合に閾値の門を検討する提案が出たとき。**そのとき初めて
  ADR 0133 と同じ「そもそも値が揺れるか」の実測が必要になる(§8-6)。
