# ADR 0110: `org-b` が落ちる理由を切り分けた — 「日本語の1文字違い」ではない。弁別が**単独1文字のトークン1個**に載ったときだけ差が消える

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-14

**⚠ 各主張の出所を分ける**（[ADR 0094](./0094-identifier-probes-local-embedding.md) /
[ADR 0103](./0103-negative-tooth-declares-its-precondition.md) の体裁を踏む）。

- **【実測】** — この ADR の作業でこの手元の器に対して走らせた。
- **【現物】** — この repo のコード・文書を読んで確かめた。
- **【受】** — 報告として受け取り、再導出していない。
  ⚠ **委譲文で渡された数字は、書き手にとってはすべて【受】である。**

## 問い

[ADR 0094](./0094-identifier-probes-local-embedding.md) が「確かめていないこと」に、
自分でこう書いていた。逐語:【現物】

> - **`org-b` が落ちる理由を切り分けていない。**「一/二 を弁別できない」と読めるが、
>   **その1件からそう読んだだけで、漢数字を振った対照実験はしていない。**

**⟹ この ADR は、その1行だけを塞ぐ。**⛔ **何も直さない。**

そして ADR 0094 は、同じ節でこうも書いていた。逐語:【現物】

> 🔑 **対照が効いている。**ASCII 側の**1文字違い**（`TICKET-48213` 対 `TICKET-48214` …）は
> **30件すべて hit@1** である。
> **⟹ 「1文字違いが弁別できない」のではない。「*日本語の*1文字違い（一/二）が弁別できない」である。**

**⟹ 問いは2つある。**

1. **どこで区別が失われているのか。**
2. 🔴 **上の「⟹」は、測定として成立しているのか。**
   ——「ASCII が 30/30 通った」は、本当に「ASCII なら頑健である」を意味しているのか。

---

## 結論（先に）

**両方とも、測定としては成立していなかった。**

1. 🔴 **「日本語の1文字違いが苦手」は誤りである。**
   日本語 probe 12件のうち**5件が文字列としては1文字違い**であり、
   そのうち1件（`org-c`、`東日本`/`西日本`）は**12件中で最大の margin** を持つ。【実測】
2. 🔴 **「ASCII 30/30 が対照として効いている」も誤りである。**
   ASCII 30件の margin 平均は日本語群より**小さい**。2群の margin 分布は区別が付かない。【実測】
3. ⭐ **効いているのは文字数でも文字種でもなく、`tokenizer` が弁別部分を
   「単独1文字のトークン1個」に割ったかどうかである。**
   **repo の中に、既に完璧な対照対が在った**——`org-a` と `org-b` は
   **同カテゴリ・同じ1文字違い（一/二）・同じ11文字の共有前置**でありながら、
   margin が **約400倍**違う。違いは `第一` が1トークンに融合するか、`一` が単独で立つか、だけである。【実測】

### 1.3 ⭐ これは「負け」ではなく「ほぼ同点」である

`org-b` のスコア内訳【実測】:

```
#1 [distractor] total=0.950150 = similarity 0.950151 × decay 1.000000 × ...
#2 [gold]       total=0.950070 = similarity 0.950071 × decay 1.000000 × ...
```

順位を決めたのは `similarity` ただ1項である（[ADR 0109](./0109-which-score-terms-actually-rank.md)

⚠ **印字は信用しない。**`formatScoreValue`（`retrieval-quality.ts:537`）は
`|value| < 1e-4` のとき `toExponential(3)`、それ以外は **`toFixed(6)`＝小数第6位で丸める**【現物】。
⟹ 以下はすべて `toExponential(17)` の生値である。

**`margin = cos(query, gold) − cos(query, distractor)`（本番と同じ1件バッチ）**:

| | 値 |
|---|---|
| `cos(query, gold)` | `9.50070562746479497e-1` |
| `cos(query, distractor)` | `9.50150714746254232e-1` |
| **margin** | **`−8.01519997747357493e-5`** |

`+3.43866899655542665e-2` であり、**`org-b` はその約 430 分の1** である。

⟹ 🔑 **これは「順位付けの問題」ではない。**reranking も閾値も融合重みも、
**存在しない差を復元することはできない。**

## 2. 🔴 【実測】「日本語の1文字違いが苦手」は成立しない

`JAPANESE_NAME_TOPIC_KEYWORDS` の gold/distractor 対を文字レベルで数えた
（Levenshtein 距離と、差異が始まるまでの共有前置の文字数）:

| probe | lev | 共有前置(文字) | **margin** |
|---|---|---|---|
| **org-b** | **1** | **11** | **`−8.015200e-5`** |
| **person-c** | **1** | 2 | `+7.949071e-3` |
| person-d | 2 | 2 | `+1.413945e-2` |
| person-a | 2 | 2 | `+2.843333e-2` |
| **org-a** | **1** | **11** | `+3.172468e-2` |
| **product-a** | **1** | 4 | `+3.364908e-2` |
| place-b | 2 | 0 | `+3.737143e-2` |
| place-a | 2 | 0 | `+3.977217e-2` |
| person-b | 3 | 2 | `+3.978045e-2` |
| product-c | 2 | 3 | `+4.732659e-2` |
| **org-c** | **1** | 9 | **`+4.854132e-2`** |
| product-b | 2 | 4 | `+4.956601e-2` |

**12件のうち5件（`org-a` / `org-b` / `org-c` / `person-c` / `product-a`）が1文字違いである。**
その5件の margin は `−8.0e-5` から `+4.85e-2` まで、**12件の全域に散らばっている**——
**最悪も1文字違いだが、最良（`org-c`）も1文字違いである。**

⟹ 🔴 **「日本語の1文字違いが引けない」は、この12件のデータに支持されない。**
ADR 0094 の「*日本語の*1文字違い（一/二）が弁別できない」という読みは、
**落ちた1件だけを見て文字数を数えた結果であり、通った4件の1文字違いを見ていなかった。**

## 3. 🔴 【実測】「ASCII 30/30 が対照として効いている」も成立しない

ASCII 識別子 probe 30件についても、同じ器で同じ3類似度を測った。

| 群 | n | margin 平均 | sd | 最小 |
|---|---|---|---|---|
| 日本語（全12件） | 12 | `3.15144531351101778e-2` | `1.62540865036896118e-2` | `−8.0e-5` |
| 日本語（`org-b` 除く） | 11 | `3.43866899655542665e-2` | — | `+7.95e-3` |
| **ASCII** | **30** | **`2.79867084823506064e-2`** | `1.43280737765301095e-2` | `+2.44e-3` |

⭐ **ASCII 群の margin 平均は、日本語群より小さい。**
Welch t = 0.657 / df = 18.2 / **p ≈ 0.52** ——**2群の margin 分布は区別が付かない。**

⚠ **これは「差が無いことの証明」ではない**（n=12 / n=30、[ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md) §3）。
言えるのは「**この標本から『ASCII のほうが頑健である』とは言えない**」までである。
**それで十分である**——ADR 0094 が主張したのは、まさにその「ASCII のほうが頑健である」だったからである。

さらに、ASCII 群の最小 `system-d`（`SYS-LG21`/`SYS-LG22`）の margin は **`+2.44e-3`** であり、
§4 の「モデル自身の振れ幅」より小さい。⟹ **その符号が正であることに意味があるとは言えない。**

⟹ 🔑 **ASCII 群が0件負けたのは、群としての優位ではない。
`一`/`二` ほど退化した弁別対を1件も含んでいなかっただけである。**
**陰性対照としては、「何を見ていないか」——すなわち「弁別が単独1文字トークンに載る条件」——を
ASCII 群は1件も踏んでいなかった。**

## 4. 【実測】比較の物差し — モデル自身が、契約上許された範囲でどれだけ動くか

⚠ **これは器（provider の呼び方）の性質であって、想起の質ではない。**

`EmbeddingProvider.embed(ctx, texts)` に**同じ文字列**を渡しても、
**バッチの長さ構成だけでベクトルが動く**（`q8` 量子化カーネルが tensor の shape に依存する）。
`org-b` の3文で測った【実測】:

| batch 条件 | cos(q,gold) | cos(q,distr) | margin |
|---|---|---|---|
| **b=1 ずつ（本番条件）** | `9.50070562746479497e-1` | `9.50150714746254232e-1` | **`−8.01519997747357493e-5`** |
| b=3 | `9.52583498913561977e-1` | `9.42424423992605398e-1` | `+1.01590749209565789e-2` |
| b=3（順序入替） | `9.52583498913561977e-1` | `9.42424423992605398e-1` | `+1.01590749209565789e-2` |
| b=4（短い pad 追加） | `9.52006694720574309e-1` | `9.41047916153589070e-1` | `+1.09587785669852389e-2` |
| b=4（長い pad 追加） | `9.52938534756780586e-1` | `9.41591423916653070e-1` | `+1.13471108401275167e-2` |
| b=9 | `9.54527231851244218e-1` | `9.45250307748592977e-1` | `+9.27692410265124057e-3` |

**margin の振れ幅 `1.14272628399022524e-2`。順序では動かず、長さ構成でだけ動く。**
⟹ **バッチを1つ組み替えるだけで `org-b` の符号は反転する。**

### ⚠ これを「ノイズ」と呼んではいけない

**b=1 は決定的である**——プロセスをまたいでビット一致する【実測】。
⟹ **走行ごとに揺れる誤差ではない。**動くのは「**呼び方を変えたとき**」だけである。

**では何の物差しなのか。**[ADR 0095](./0095-embedding-provider-conformance.md) の**決定5**は、
**バッチ不変性を意図して契約から外している**。逐語:【現物】

> `embed([a,b])` が `embed([a])` と `embed([b])` の連結に一致するか——**測らない。**
> **理由**: 本物の埋め込みモデルは**バッチを padding して処理する。**

⟹ 🔑 **つまり上の 1e-2 は、「この repo が provider に許すと明文で決めた表現の任意性」である。**
**`org-b` の弁別信号 `8e-5` は、その任意性の 1/100 以下である。**
**⟹ `開発一課` と `開発二課` の区別は、このモデル・この量子化では
「弱く符号化されている」のではなく、`EmbeddingProvider` の契約が意味を保証していない
桁の中に沈んでいる。**

⭐ **ADR 0095 §6 は、この事態を自分で予告していた。**逐語:【現物】

> - **バッチ不変性を実測したとき。**成立するなら歯を1本足せる。
>   成立しないなら、**それは `packages/local-embedding` の側に名前を付けるべき事実**になる。

**⟹ 実測した。成立しない。**§7 の選択肢 C がその「名前を付ける」案である。

## 5. ⭐ 【実測】切り分け — 区別が失われている場所

### 5.1 repo の中に、既に対照対が在った（`org-a` 対 `org-b`）

|  | `org-a` | `org-b` |
|---|---|---|
| category | org | org |
| 文字列の差 | **1文字**（`第一`→`第二`） | **1文字**（`一`→`二`） |
| 共有前置 | **11文字** | **11文字** |
| 弁別する漢字 | **漢数字 一/二** | **漢数字 一/二** |
| **tokenizer の割り方** | `の`\|**`第一`**\|`営業部` | `の開発`\|**`一`**\|`課` |
| **弁別トークンが担う文字数** | **2** | **1** |
| **margin** | **`+3.172468e-2`** | **`−8.015200e-5`** |

**文字レベルの条件が完全に一致していて、`tokenizer` の割り方だけが違う。margin は約400倍違う。**

トークン列は自分の手で確認した【実測】:

```
org-a gold: [<s>][蒼][天][ロジ][ス][ティクス][の][第一][営業部][は][関東][エリア][を担当][しています][。][</s>]
org-b gold: [<s>][北][陵][物産][株式会社][の開発][一][課][は][モバイルアプリ][を担当][しています][。][</s>]
org-c gold: [<s>][桜][庭][商事][株式会社][の][東日本][支社][は][法人向け][営業][を担当][しています][。][</s>]
```

**`org-c` の `東日本` も1トークン（3文字）である**——だから1文字違いなのに margin が最大になる。

### 5.2 落とした候補（数字で落とす）

| 候補 | 判定 | 落とした数字 |
|---|---|---|
| 「日本語だから」 | **✕** | 日本語11件（`org-b` 除く）の margin 平均 `3.44e-2` > ASCII 30件 `2.80e-2` |
| 「1文字違いだから」 | **✕** | 1文字違い5件の margin は `−8.0e-5` 〜 `+4.85e-2`。最良も1文字違い |
| 「漢数字（一/二）だから」 | **✕** | `一`→`七` で `−5.88e-3`、`一`→`十` で `−7.96e-3`。**離しても符号は負のまま、むしろ悪化** |
| 「字形・語彙が近すぎるから」 | **✕** | 同上。近い `二` より遠い `七`/`十` のほうが悪い |
| 「数詞だから」 | **✕** | `本`/`副`（数詞でない漢字1文字）も `−6.36e-3` |
| 「トークナイズの粒度（数字が独立トークンになるか）」 | **✕** | 日本語側も `一`(id 791)/`二`(id 1463) は独立トークン。ASCII の `3`/`4` も独立トークン。**両群とも「約7トークン中1トークンだけ違う」で同型** |
| 「共有接頭辞の比率」 | **✕（単独では）** | fact/distractor の共有トークン比の中央値は JP ≈ 0.73 / ASCII ≈ 0.77 と**ほぼ同じ**。`org-b`(0.769) と `ticket-a`(0.750) はほぼ同値なのに margin は `−8.0e-5` 対 `+1.57e-2` |

⚠ **委譲で渡された候補（埋め込みの性質／トークナイズの粒度／共有接頭辞の比率／数字が別トークンか）は、
4つとも数字で落ちた。正解は列挙の外に在った。**

### 5.4 🔑 切り分けの結論

> **区別が失われているのは、`tokenizer` が弁別部分を「単独1文字のトークン1個」に割り、
> かつ mean pooling がそれを長い共有トークン列で薄めたときである。**
>
> - **軸1（表現の遠さ）**: 単独トークンとしての漢字1文字は、算用数字・ラテン文字1文字の
>   **約 1/2.2 しかベクトルを動かさない。**⟹ 文字種が効く。**文字数ではない。**
> - **軸2（希釈）**: mean pooling は、その1トークンぶんの差を残りの共有トークンで割る。
>   共有前置を外すだけで符号が反転する（`−8.0e-5` → `+2.01e-2`）。
> - **2つは独立に効き、どちらか一方を外せば反転する。**
>   `org-b` は日本語12件・ASCII 30件の**計42件で、両方の底を同時に踏む唯一の probe** である。

**ASCII 側の最小 `system-d`（`SYS-LG21`/`SYS-LG22`、5トークン中4共有・弁別は1桁）も同じ形である。
ASCII の1桁は漢字1文字の 2.2 倍動くため、床をかろうじて超えて残った。**

⟹ ⭐ **`org-b` は「日本語の失敗」ではない。「単独1文字トークン × 長い共有前置」の失敗であり、
ASCII でも同じ条件を作れば起きる**（`system-d` がその縁に居る）。

### 5.5 【実測】この結論から、既に測ってあった数字の読み方が変わる

**42件のうち3件は、結果が §4 の任意性の内側に居る**——
`org-b`（`−8.0e-5`）・`person-c`（`+7.95e-3`）・`system-d`（`+2.44e-3`）。
⟹ ⛔ **この3件については、hit@1 の ✅/❌ を「引けた/引けなかった」と読んではいけない。**
残る39件の ✅ は床の外に在る。

## 6. ⚠ 測っていないこと（名指しで）

1. **`recorded`（OpenAI `text-embedding-3-small` / 256次元）では1件も測っていない。**
   カセットに probe のテキストが1件も入っていないため、代理でも測れなかった——
   カセット内の日本語対は「大きく違う内容語」か「です・ます↔常体の活用差（意味は同じ）」の二択で、
   **`org-b` が居る中間領域（短い差分で指す対象が変わる）の標本が0件である。**【実測】
   ⟹ **「OpenAI なら一課/二課を分離できる」とも「できない」とも言えない。**
2. **`q8` 以外の dtype で測っていない。**fp32 なら §4 の任意性が下がり、
   `org-b` の符号が変わる可能性があるが、**測っていない。**
3. **本番（postgres + pgvector / HNSW）で測っていない**（この容器に PostgreSQL が無い）。
   float4 化だけなら反転しないことは確認した（`8.029e-5`、同符号・同桁）【実測】が、
   **HNSW の近似が `8e-5` 差の2件を同じ順で返すかは一切測っていない**——
   `ef_search` 次第で「順が入れ替わる」「片方しか拾われない」のどちらにも倒れうる大きさである。
   ⟹ ⛔ **§1.2 の順位が本番でも同じになるとは言えない。**
4. **`recall()` の全経路で測っていない。**§2〜§5 の margin は生の cos であり、
   融合・`scoring.ts`・ANN 経路を通していない（`org-b` は cos の時点で負けが確定しているが、
   「ベンチの失敗がこれだけで説明し尽くせる」とは測っていない）。
5. **語彙チャンネルを通していない**（ADR 0108 の状態のまま。[Issue #179](https://github.com/takecchi/mnemora/issues/179) は製品の判断待ちであり触っていない）。
6. **標本は12件と30件である。**ADR 0033 §3 により、ここから成功率も失敗率も統計的に主張しない。
   §3 の Welch 検定も「差が**在る**とは言えない」までであり、「差が無い」の証明ではない。
7. **他の日本語 tokenizer で測っていない。**§5 の結論は
   `sirasagi62/ruri-v3-30m-ONNX` の語彙（`第一` は融合するが `開発一` は融合しない）に依存しており、
   **別の tokenizer では境界が別の場所に来る。**

### 【現物】副産物: `ci.yml` のコメントが古い

`.github/workflows/ci.yml:576` は「この bench の probe は12件(識別子)・7件(日本語)」と書いているが、
実際は識別子 **30件**（PR #191）で、**PR #192 が足した日本語固有名詞12件×2群がコメントに無い。**
**閾値の門にしない根拠として母数を挙げている箇所であり、その母数がずれている。**
⛔ **この ADR では直していない**（報告のみ）。

## 7. 選択肢（⛔ どれもこの ADR では実装していない）

### ⭐ 案 A（推奨・**いま在るもので済む**）: 何も直さず、**読み方だけを直す**

**やること**: この ADR を根拠に、ADR 0094 の「*日本語の*1文字違いが弁別できない」という読みを
**上書きする**（§2 / §3）。probe set も scoring も provider も1バイトも変えない。
`identifier-probes` は今までどおり値を残すだけ。

- **買えるもの**: **いま一番高いものが買える**——「日本語が弱い」という**誤った方向へ設計が動くのを止める。**
  §5 の結論が正しければ、日本語向けの正規化も分かち書きも `org-b` を救わない
  （`一`/`七` が `一`/`二` より悪いことがそれを示している）。
- **代償1**: **`org-b` は落ちたままである。**hit@1 は 11/12 のまま。
- **代償2**: **`recorded`（OpenAI）で確かめていない**（§6-1）。
  この読み替えが `local` 固有かどうかは分からないままになる。
- **代償3**: 42件中3件が §4 の任意性の内側に居るという事実（§5.5）が、
  ADR の本文にしか無く、**ベンチの出力には現れない。**

### 案 B（**本当はこうあるべき**）: ベンチが**自分の分解能を印字する**

**やること**: `identifier-arm` が probe ごとに margin を出し、
**§4 の任意性（この provider では 1e-2 オーダー）と並べて印字する。**
margin がその内側に居る probe には「**この ✅/❌ は分解能の内側である**」と明示する。

- **買えるもの**: ⭐ **「引けた」と「たまたま符号が正だった」を、読む側が区別できるようになる。**
  ADR 0068「**ベンチは自分が何を測ったかについて嘘をついてはならない**」の直系である。
  §5.5 の読み替えが、ADR の本文ではなく**出力に載る。**
- **代償1**: **分解能の値を、provider ごとに測って持たねばならない。**
  `local` は測った（1.14e-2）が、`openai` は測っていない。⟹ **測っていない provider の欄が空く。**
- **代償2**: ⚠ **この量は「器の性質」であって、想起の質ではない。**
  出力に並べると、**読む側がそれを品質指標だと取り違えうる。**表示の文言に費用が要る。
- **代償3**: `retrieval-json.ts` / baseline JSON の schema が増える（下位互換の作業）。

### 案 C（**ADR 0095 §6 が自分で予告していた道**）: バッチ依存に**名前を付ける**

**やること**: `@mnemora/local-embedding` の README／doc comment に
「**このモデルの出力はバッチの長さ構成に 1e-2 オーダー依存する**」と明記し、
`packages/testkit` の適合テストには**足さない**（ADR 0095 決定5 を維持したまま、
`local-embedding` 側の**既知の性質**として書く）。

- **買えるもの**: **利用者が「バッチで速くしよう」としたとき、静かに測定値が変わることを事前に知れる。**
  §4 は**そこそこ大きい**（弁別信号の100倍）。
- **代償1**: **文書だけでは腐る。**⟹ この ADR は代わりに**歯を1本置いた**（§8）。
- **代償2**: **fp32 でも同じかを測っていない**（§6-2）。
  「q8 だから」なのか「このモデルだから」なのかを書き分けられない。

### 案 D（却下）: `org-b` を「引ける」ようにする

probe を易しくする（`開発一課`→`開発1課`）／閾値や融合重みを触る／
`LexicalStore` を配線する。

- 🔴 **却下する。**probe を易しくするのは**測れるようになったものを捨てる**ことである
  （ADR 0094 が意図して置いた「引けないもの」が消える）。
  重みを触るのは §1.3 の通り**存在しない差を復元しようとする**ことである。
  `LexicalStore` の配線は**製品の判断**であり [Issue #179](https://github.com/takecchi/mnemora/issues/179) が住所を持っている。

**⟹ 推奨は A。**B は「本当はこうあるべき」だが**分解能を provider ごとに測る作業が先**であり、
この ADR はその測定を `local` について1つ持っているだけである。C は A と同時に採れる。

## 8. 置いた歯（⛔ `org-b` の失敗を固定していない）

**⛔ 「`org-b` が落ちる」を assert する歯は1本も置いていない**——ADR 0094 §「🔴 失敗している1件を、
赤い歯にしていない」の判断をそのまま引き継ぐ。**置いたのは向きが逆の歯である。**

### 歯1: `packages/core/src/__tests__/embed-batch-size.test.ts`（**いま緑**）

**core が `EmbeddingProvider.embed()` を1件ずつ呼ぶ**ことを機械的に固定する
（`dependency-boundary.test.ts` と同じ源走査の形）。呼び出しは2箇所だけである【現物】:
`runtime.ts:1322` と `recall-runtime.ts:316`。

🔴 **この赤が意味すること**: 壊れたのは core ではなく、**すでに測ってある埋め込みの数字のほうである。**
バッチ化した瞬間、§4 の通り全ベクトルが 1e-2 オーダー動き、
**それより2桁小さい margin で決まっている順位は意味を失う。**
⟹ **バッチ化するなら、この ADR の測定と `identifier-probe-baseline.json` を同じ変更の中で引き直すこと。**

⚠ **この歯はバッチ不変性を主張していない**（ADR 0095 決定5 は有効なままである）。
主張しているのは「**core の本番経路がバッチを組んでいない**」という、この repo が自分で守れる事実だけである。
**変異（`embed(ctx, [c, c])`）を入れて赤くなることを確認した**【実測】。

### 歯2: `examples/chat/src/__tests__/japanese-name-probe-set.test.ts` に1本追加（**いま緑**）

**2つを固定する。**

1. **gold/distractor が文字列として1文字違いなのは
   `org-a` / `org-b` / `org-c` / `person-c` / `product-a` の5件である**（§2 の標本の形）。
2. 🔑 **その5件が弁別している1文字は、いずれも ASCII ではない。**

⚠ **1 だけでは足りなかった**——`org-b` を `開発1課`/`開発2課` に書き換える変異を入れても、
それは**依然として1文字違い**なので 1 は緑のままだった【実測】。
**2 がその変異を捕まえる。**§5.3 の通り、同じ位置の漢字1文字を算用数字へ替えるだけで
margin は `−8.0e-5` → `+2.70e-2` と**符号が反転する**——
⟹ **probe は通るようになるが、それは想起が良くなったのではなく問いが易しくなっただけである。**
**変異を入れて 2 が赤くなることを確認した**【実測】。

🔴 **この赤が意味すること**: **この ADR が測った標本の構成が変わった**ということである
（案 D を黙って踏めない）。
⚠ **この歯は文字数を数えているが、「文字数が原因だ」とは主張していない。**
効いているのは弁別トークンが担う文字数である（§5.4）——
**その区別は失敗メッセージ自身に書いてある。**

⛔ **既存の歯7本と `japanese-name-probe-set.ts` 本体は1バイトも変えていない。**
