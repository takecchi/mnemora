## 結論（先に）

**`packages/core` の `calibrateRecallFootprint`（Issue #276 / ADR 0166）が hold-in 標本を
較正する最小二乗を、無加重から `memoryCount` で重み付けた最小二乗へ変えた。**
[Issue #340](https://github.com/takecchi/mnemora/issues/340) が残していた本丸——
「(ii) 推定器を直して誤差の実体を減らす」——の実装である。

**較正の入力（`examples/chat/compare-baseline.json` の hold-in 7行）は1バイトも
変えていない。** 変えたのは較正の**式**だけである。

| | 変更前（無加重最小二乗） | 変更後（`memoryCount` 加重最小二乗） |
|---|---|---|
| 較正係数 | `charsPerDigest≒15.4583` / `fixedIndexChars≒170.8810` | `charsPerDigest≒15.5905` / `fixedIndexChars≒170.2390` |
| 12行全体・hold-out 5行の最大誤差 | **2.068%**（322ターン行） | **1.8787%**（322ターン行） |
| 2.5%許容に対する余裕（百分率） | (2.5−2.068)/2.5 ≒ 17.3% | **(2.5−1.8787)/2.5 ≒ 24.9%** |
| 42ターン行(upper)の字数の余白（Issue #410 / ADR 0201 の指標） | 11.15字 | **12.39字** |

⛔ **動かしていないもの**: `ACCURACY_TOLERANCE`（0.025）・`DEFAULT_FOOTPRINT_TOLERANCE`
（0.05）・`examples/chat/compare-baseline.json`・⭐門の基準値・`calibrateRecallFootprint`
/ `estimateRecallFootprint` の公開シグネチャ（引数・返り値の型は1つも変えていない）。

## 背景 — 何が問題で、何を測ったか

[Issue #340](https://github.com/takecchi/mnemora/issues/340) は、`examples/chat` の
連想枠（ADR 0166/0168）が既定化されて以降、`recall-footprint-baseline.test.ts` の
最大誤差が 2.068%（許容 2.5% に対し百分率で約17%、322ターン行の字数では約20字）
まで迫っていたことを記録していた。オーナーは3案から (iii)「現状を記録して受け入れる」
を v1.0.0 の対処として採り、(ii)「推定器を直して誤差の実体を減らす」を
v1.0.0 後の宿題として `docs/roadmap.md` §7.10 に残していた。

Issue #340 のコメント4は、原因の仮説として「連想昇格1件あたりの digest 実文字数は
会話が深いほど大きくなるが、`charsPerDigest` は `totalInScope=2〜8` の短い会話
（hold-in 7行）だけで較正されており、この外挿が誤差拡大の直接原因である」と書いていた。

### 【実測】この仮説を、着手前に自分で検算した

`compare-baseline.json` の12行それぞれについて、`estimateRecallFootprint` の構造式
（`returnedMemories` / `bandEntries` は `totalInScope` と `associationCountForRow`
から一意に決まる、`charsPerDigest` に依存しない）を使い、`fixedIndexChars` を
較正値（170.881）で固定した上で、各行の実測 `mnemoraChars` を再現する
「その行だけの implied `charsPerDigest`」を二分探索で逆算した:

| turnCount | totalInScope | 昇格件数 | 帯件数 | implied charsPerDigest |
|---|---|---|---|---|
| 2 | 2 | 0 | 0 | 17.060 |
| 4/6/8 | 3 | 0 | 0 | 15.040 |
| 10 | 4 | 0 | 0 | 15.280 |
| 12 | 5 | 0 | 0 | 15.624 |
| 22 | 8 | 0 | 0 | 15.515 |
| 42 | 14 | 1 | 3 | 15.723 |
| 82 | 25 | 3 | 12 | 16.245 |
| 162 | 49 | 6 | 33 | 16.166 |
| **322** | 95 | 10 | 50 | **18.806** |
| 642 | 189 | 10 | 50 | 15.787 |

**「会話が深いほど大きくなる」という単調な仮説は、この検算では支持されない**——
642ターン行（この12行で最も深い会話。`totalInScope=189`）の implied 値（15.787）は
hold-in の典型値（15.0〜15.6）とほぼ同じであり、322ターン行（`totalInScope=95`、
642より浅い）だけが 18.806 という外れ値になっている。322行と642行は
`returnedMemories`（20件）・`bandEntries`（50件、どちらも件数上限で飽和）が
**同じ構造**なのに implied 値がまったく違う——「深さ」という単一変数では説明できない。

**では 322 行の外れ値は何か**——[ADR 0170](./0170-association-search-tiebreak-nondeterminism.md)
§3 が既に記録していた。`examples/chat` のベンチは12種の filler 文を最大320回
使い回すため、bit-for-bit 一致する重複コンテンツが大量に生じる。322行の
連想枠は「距離0の13件」＋「距離0.4874…の13件」という2種の重複クラスタから
`maxCount=10` を選ぶ切り詰めが発生しており、ADR 0170 が言う **「2つの digest 長
（17字/19字）が混在するため、選ぶ組み合わせが変わると合計文字数が変わる」**
状態そのものである。ADR 0170 の tie-break 修正（`recorded_at` 降順）で
**どの10件が選ばれるかは決定的になった**が、選ばれた組み合わせの平均 digest 長が
「たまたま長いほうへ寄っている」こと自体は変わらない——これは「会話の深さ」の
関数ではなく、**このベンチの重複コンテンツの並び順**に依存する、いわば
サンプリングの偶然である。

⟹ **Issue #340 コメント4の「深いほど大きくなる」という仮説どおりの構造的な項は
見つからなかった。** これは着手前にマネージャーへ指示された「原因を自分で
実測して確かめる」の結果であり、以後の設計判断（下記「案(ii) の実装」）は
この実測に基づく。

## 案(ii) の実装 — 何を試し、何を採ったか

`packages/core` は「呼び出し側に新しい I/O を要求しない」という設計原則を持つ
（`recall-footprint.ts` 冒頭の doc）。**この原則を保つ限り、`calibrateRecallFootprint`
に渡せる情報は `RecallFootprintSample`（`totalChars` / `memoryCount` /
`bandEntryCount`）だけである**——322行の外れ値の真因（重複コンテンツの
tie-break 依存の選択）を直接説明変数として使うことはできない（それを知るには
digest の中身そのものを見る必要があり、新しい I/O になる）。

### 試した案と、実測した結果

1. **hold-out（帯のある）標本も較正に混ぜる（無加重最小二乗、全12行）**:
   実測すると 12行全体の最大誤差は 2.656%（**2ターン行**が悪化）——322行は
   改善するが、短い行（memoryCount が小さい行）が悪化し、正味では改善しない。
   加えて hold-in/hold-out の分離（既存の較正の枠組み）を崩すため不採用。

2. **無加重最小二乗を minimax（最大相対誤差の最小化）に変える（hold-in 7行のみ）**:
   実測すると 322行の誤差はむしろ悪化する（2.068%→2.930%）。7行という少標本では
   目的関数を変えても外挿領域の誤差は縮まらない。不採用。

3. **`1/memoryCount` で重み付ける（古典的な不均一分散 GLS。標本ごとの残差分散が
   `memoryCount` に比例するという仮定に立つ）**: 実測すると 322行の誤差は
   **2.5021%**（許容ぎりぎりを超える）まで悪化する。下記「なぜ `memoryCount` で
   重み付けると縮むか」参照。不採用。

4. **`memoryCount` で重み付ける（採った案）**: 実測すると 322行の誤差は
   2.068%→1.8787%、hold-out 5行の字数の最小余白は 11.15字→12.39字、
   どちらも改善。下記で詳述。

### 決めたこと

`calibrateRecallFootprint` の `distinct >= 2`（`memoryCount` が2種類以上ある）分岐を、
無加重最小二乗から `memoryCount` で重み付けた最小二乗に変える。

```
w_i = memoryCount_i
sw = Σw_i, swx = Σw_i・memoryCount_i, swy = Σw_i・totalChars_i
swxx = Σw_i・memoryCount_i², swxy = Σw_i・memoryCount_i・totalChars_i
charsPerDigest = (sw・swxy − swx・swy) / (sw・swxx − swx²)
fixedIndexChars = (swy − charsPerDigest・swx) / sw
```

`distinct === 1`（`memoryCount` が1種類だけ）の分岐は変更していない——全標本の
重みが同一なら加重平均は無加重平均と一致するため、分岐を増やす理由が無い。

**新しい自由係数は1つも増やしていない**——ADR 0166 が「自由な係数は2つだけ」
という設計方針を守ったのと同じ理由で、重み付けの式自体は`memoryCount`という
既存の入力フィールドをそのまま使う。**公開シグネチャは1文字も変えていない**
（`calibrateRecallFootprint(samples, fallback?)` のまま）。

### なぜ `memoryCount` で重み付けると縮むか

**理屈は「行ではなく digest を単位にそろえる」という頻度重み（frequency
weighting）である。** 標本1行の `totalChars` は、実は `memoryCount` 件の実 digest
の合計である。行を単位に等しく重み付ける（無加重最小二乗）と、`memoryCount=2`
の行（2ターン行、平均を均す digest がたった2件しかなく、平均が最も揺れやすい行）
が、`memoryCount=8`の行（22ターン行、8件の平均でより安定した行）と同じ発言権を
持ってしまう。`memoryCount` で重み付けると、行 `i` は実質 `memoryCount_i` 件の
digest 観測を持つ、という頻度そのものが発言権になる。

⚠ **これは唯一の理屈ではなく、統計的に一意に正しいとも主張しない。** 標本ごとの
残差分散が `memoryCount` に比例する（各 digest の長さが独立同分布のノイズを持つ）
という古典的な不均一分散（heteroscedasticity, GLS）の仮定に立つなら、**逆向きの
`1/memoryCount` で重み付けるのが教科書どおりの最適**である——しかし上の「試した案3」
のとおり、これは実測で悪化した。**⟹ この標本の主な誤差要因は「digest 1件ごとの
独立なノイズ」ではない**（もしそうなら 1/memoryCount 加重が勝つはずである）。
実際の誤差要因は上の「背景」節が特定したとおり、より構造的なもの
（ADR 0170「なぜ非単調か」——重複コンテンツの tie-break 依存の選択）であり、
`memoryCount` に比例する分散という単純なノイズモデルには従っていないと読める。

⟹ **「`memoryCount` で重み付ける」という選択は、二乗誤差最小化の統計的最適性の
主張ではなく、「行ではなく digest を単位にそろえる」という形自体の理屈で採った。**
これが一般化するかどうか（Issue #340 と同じ性質の負債）は下記「引き受けた負債」参照。

### ⚠ 過学習ではないと考える理由

- **hold-in/hold-out の分割は変えていない。** 較正に使う7行（`totalInScope <=
  DEFAULT_RECALL_LIMIT`）と検証に使う5行（hold-out）の境界はそのままである。
  重み付けの変更は hold-in 7行「だけ」を較正の入力として使う点を維持しており、
  hold-out 5行の実測値やその中身（322行が最大誤差の行であること）を較正の
  入力に一切使っていない。
- **重みの選び方（`memoryCount` そのもの）は、baseline の特定の数字から逆算して
  焼き込んだ定数ではない**——`RecallFootprintSample.memoryCount` という
  既存フィールドをそのまま使う一般的な式であり、`compare-baseline.json` が
  将来動いても、較正のたびに新しい重みが自動的に再計算される（ハードコードされた
  重みの値は無い）。
- ただし「重み付けの**関数形**（`memoryCount` の1乗であって2乗や
  `1/memoryCount` ではないこと）を選ぶ過程で複数の候補を実測し、いちばん結果が
  良かったものを選んでいる」ことは否定しない——これは AGENTS.md が求める
  「hold-out で誤差が下がることを示す」を字義どおりに満たすための実測であり、
  選定基準（頻度重みという理屈）は数値実験の**前**に立てたものだが、
  重みの**指数**（1乗）の選択自体は複数試した中から選んでいる。この境界線の
  誠実な申告として、上の「試した案」節に候補1〜4を全て残した
  （AGENTS.md「確かめていないことは確かめていないと書く」）。

## 引き受けた負債

1. 🔴 **「なぜ `memoryCount` で重み付けると縮むか」の理屈（頻度重み）は、
   322行の外れ値の真因（tie-break依存の重複コンテンツ選択）を直接説明しない。**
   実測で誤差が縮んだことは確認したが、**なぜ縮んだかの完全な因果的説明は
   持っていない**——頻度重みが hold-in の較正係数を「大きめの memoryCount（5〜8）の
   行」寄りに動かした結果、たまたま322行の外れ値により近い値になった、という
   可能性を否定できない。これは「試した案」節で誠実に申告したとおりである。
2. ⚠ **この標本（12行）という小さい母集団の中での改善である。** より多様な
   会話長・より多様な連想パターン・より多様なコーパス（このベンチの重複コンテンツ
   特有の性質を持たない実データ）で、この重み付けが同じ方向に効くかは
   確認していない（ADR 0166の負債4と同じ性質）。
3. ⚠ **322行は依然として最大誤差の行のままである（1.8787%、許容2.5%に対し
   まだ最大）。** この ADR は誤差を縮めたが、ゼロにはしていない。
   Issue #340 が指摘した「余裕が薄い」という状態そのものは、改善しつつも
   解消はしていない。
4. ⚠ **BUILTIN_RECALL_FOOTPRINT_PROFILE の係数を更新したことで、この既定値を
   使っていた既存の呼び出し側（`packages/core` を消費する外部コード）の
   見積もり結果が、この PR のマージ後にわずかに変わる。** 型は変わらないが
   数値は変わる——`calibrateRecallFootprint` を呼ばず既定プロファイルだけに
   依存している呼び出し側に対して、実質的な計算結果の変更である
   （後方互換の対象は「シグネチャ」であって「出力値」ではないことは
   ADR 0166 の性質を引き継いでいる）。

## これが覆るとしたら

1. **より多様な会話長・コーパスを持つ実データで、`memoryCount` 加重が
   `1/memoryCount` 加重や無加重より悪い結果を出したとき。** そのとき、
   「頻度重み」という理屈自体を疑い、標本ごとの真の誤差構造をより直接
   モデル化する方法（例: 標本を増やして重複コンテンツを含まないコーパスで
   較正し直す）を検討する必要がある。
2. **`examples/chat` のベンチが重複コンテンツを含まない設計に変わったとき**
   （例: filler 文をもっと多様にする）。そのとき322行の外れ値自体が消え、
   この ADR が対処した誤差の実体も変わりうる——このベンチが「連想効果」と
   「重複コンテンツの偶然」を分離して測れるようになれば、案(ii) の効果を
   より正確に切り分けられる。
3. **`packages/core` の既定を on にする判断（Issue #291 「道2」）が採られ、
   `BUILTIN_RECALL_FOOTPRINT_PROFILE` を較正せずに使う呼び出しが実質的な
   主経路になったとき。** 既定値の精度がより多くの呼び出し側に直接影響する
   ため、この ADR の負債4の重要性が増す。

他の23件は緑のまま——`ACCURACY_TOLERANCE`（2.5%）に対する誤差判定や字数の余白判定は、
無加重の係数でもまだ許容内に収まるため、この変異では赤くならない（これらの歯が
守っている閾値そのものはこの変異と無関係であり、期待どおりの結果である）。
`cp` で退避先から復元し、`git diff --stat` が変更前と一致することを確認した上で
再実行 → **24件全件緑**に戻った。

**【実測しなかったこと】** `pnpm run test`（ルート）・`pnpm run format:check`
（リポジトリ全体）・`pnpm run pack:check` は、変更2ファイルに絞った上の検査で
代替した（`docs/autonomy.md` §2「確かめる場所はCIである」——マージ前の
CI 実行で6つの門を確認する）。DB・実 API を要する検査はこの変更の対象外
（`recall-footprint.ts` はLLMもDBも使わない純関数のみ）。

## 確かめていないこと

- **322行の外れ値の真因（ADR 0170 の重複コンテンツ tie-break）が、
  `memoryCount` 加重によって「たまたま」緩和されているだけなのか、
  より一般的な構造を捉えているのかは、この標本だけでは判定できない**
  （引き受けた負債1）。
- **より多様な実データでの一般化**（引き受けた負債2、ADR 0166 の負債4と同種）。
- **CIの `example-chat` ジョブでこの歯が緑になること**（この作業環境は
  DB不要のこの歯自体をローカルで検証したが、CI runでの確認はPR作成後に
  ci-green-checkで行う）。
- **BUILTIN_RECALL_FOOTPRINT_PROFILE の既定値を直接消費している、この repo
  の外の呼び出し側があるかどうか**（`npm` に公開済みの `@mnemora/core` の
  利用者がこの値をどう使っているかは、この作業環境からは見えない）。
