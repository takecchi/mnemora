# ADR 0661: #1741（ADR 0655）の Redis の歯に変異を当て、すり抜けた2つを塞ぐ歯を足す（Issue #1758）

- **状態**: 採用 (2026-10)
- **日付**: 2026-10-06

**これはクローン（miku）の判断で、オーナーの判断ではない**（[ADR 0220](./0220-issue-comment-author-does-not-distinguish-owner-from-agent.md)）。出所は Issue [#1758](https://github.com/takecchi/mnemora/issues/1758)（[ADR 0658](./0658-merged-1005-1006-recheck-teeth.md) の「確かめていないこと」の1つ目）。
出所の区別: 【現物】は読んだコード、【実測】は手元で走らせた結果、【受】は自分で測らずに受け取ったもの、【判断】は担い手の判定。
これは試験だけの変更で、実装・TSDoc・CHANGELOG は触らない（ADR 0658 などの試験だけの PR と同じ）。

**測定条件**: main `8f43f588`、redis-server 7.4.7（conda-forge の `redis-server-7.4.7-h35e630c_0` のバイナリ、自分専用ポート、永続化なし）、Postgres 17 + pgvector（AGENTS.md の手順、自分専用ポート）、bullmq 6.3.8。

## 経緯

ADR 0658 の器には Redis が無く、`tick-driver.stop-last-worker.redis.test.ts` と `tick-driver.shared-scheduler.redis.test.ts`（`test:redis`）には変異を当てていなかった。
docker・コンパイラ・Python の無い器でも、conda-forge の `.conda`（zip の中の tar.zst）を node の `zlib.zstdDecompressSync` で展開すれば、redis-server 7.4.7 が動いた【実測】。PyPI の `redis-server` の wheel は 6.0.9 止まりで、7.x ではない【現物】。

`tick-driver.ts` を `cp` で退避し、変異を当て、2本の Redis の歯（10件）と単体の歯 `tick-driver.stop-last-worker.test.ts`（8件）を走らせ、`cp` で戻して `cmp` で一致を確かめた【実測】。
変異の前後とも、Redis の歯 10/10・単体の歯 8/8 が緑だった。

あわせて、本物の Redis で `getWorkers()` を読んだ【実測】。

- `rawname` は `bull:<base64(queue)>:w:mnemora-tick-<uuid>`、`name` は queue 名に書き換わる。ADR 0655 の【現物】の記述どおり。
- 名前なしの Worker の `rawname` は `bull:<base64(queue)>` で、単体の歯のモックの形と一致する。
- 一度も `start()` していない driver の Worker も、接続名付きで一覧に出る（`autorun: false` でも blocking 接続は構築時に繋がる）。

## 決定【判断】

1. **実装は変えない。**
2. 次の歯を足す。

| 穴                                                                                                                                           | 足した歯                                                                                                                                                                                                          | 変異での赤   |
| -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| M05: 「他が居る」を行の数で読む。M05 が正しい実装とずれるのは、一覧に自分の行が無く、他が1行だけのときに限る。今の歯はどれもこの形を作らない | `tick-driver.stop-last-worker.test.ts`（単体）に「一覧に自分が出ていなくても、他の Worker が1件居れば消さない」                                                                                                   | 下の「実測」 |
| M13: 名前なしの Worker（ADR 0655 より前の版の driver）を「他」と数えない。単体の歯は殺していたが、それはモックの接続名の形を前提にしていた   | `tick-driver.stop-last-worker.redis.test.ts` に「名前なしの Worker が同じ queue に居れば、`stop()` は scheduler を消さない」。本物の CLIENT LIST に `bull:<base64(queue)>` の行が出ることも、健全性として確かめる | 下の「実測」 |

## 実測

足した歯は main `de41711c` の木で緑だった（Redis の歯 11/11、単体の歯 9/9）。同じ13個の変異を当て直した【実測】。

- M05: 足した単体の歯が赤（単体 8/9）。Redis の歯は 11/11 で緑のまま（上の「生き残ったが、塞がないもの」）。
- M13: 足した Redis の歯が赤（Redis 10/11）。
- 足した歯は、M01・M04・M10・M11 でも赤になった。残りの変異の結果は、足す前と同じだった。
- 戻して `cmp` で一致させたあと、Redis の歯 11/11・単体の歯 9/9 が緑に戻った。

## 生き残ったが、塞がないもの

- **M06（B6: 閉じてから読む）と M09（B5: `includes`）は、Redis の歯では緑のまま。** 単体の歯が赤にする（ADR 0658）。本物の Redis では、自分の Worker を閉じると自分の行は一覧から消えるので、閉じてから読んでも、自分を除いてから読んでも、残る行は同じになる。uuid を含む名前どうしでは、`includes` と末尾一致の差も出ない【判断】。Redis の歯で区別できる形が無いので、塞がない。
- M05 を Redis の歯で殺すには、`stop()` の時点で自分の blocking 接続だけを切る必要がある。再現を保証できないので、単体の歯で縛る【判断】。

## 採らなかった案

- **M05 を Redis の歯で縛る（`CLIENT KILL` で自分の blocking 接続を切ってから `stop()`）。** ioredis が再接続するので、切れている間に `stop()` が `getWorkers()` を読むことを保証できない。
- **M06 を Redis の歯で縛る。** 上のとおり、本物の Redis では観測できる違いが無い。単体の歯が呼び出しの順で縛っている。

## 引き受けた負債

- M05 で「自分の行が無い」形が実際に起きるのは、`stop()` の時点で自分の blocking 接続が切れているときだと読んでいる。本物の Redis では再現していない【判断】。
- 足した Redis の歯は、名前なしの Worker を bullmq の `Worker` で直接作っている。前の版の driver そのもの（npm の `v1.1.0` など）を入れて測ってはいない。

## これが覆るとしたら

- bullmq を上げて、名前なしの Worker の接続名や、`getWorkers()` が名前なしの接続を拾う規則が変わったとき（足した Redis の歯の健全性の行が落ちる）。
- 自分の行が一覧に無い状況で「消す」側に倒すべきだ、と判断が変わったとき（足した単体の歯を外す）。

## 確かめていないこと

- ADR 0655 の残り（別プロセスでの再測定、同時 `stop()` の残骸、`CLIENT LIST` を実際に ACL で禁じた Redis）。この PR では測っていない。
- Redis Cluster・Sentinel。
