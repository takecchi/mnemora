## 2. 決定 — `docs/architecture.md` §5 は「写した側」である

**理由は、ADR 0269 決定3 自身が測った非対称にある。**

- **文書に無いのに実装されている（drift）: 4件**（`MemoryStore` 10口・`VectorStore` 1口・
  `TenantSettingsStore` 7口・`ScoringStrategy` 型名1件）。
- **文書にあるのに実装が無い: 0件。** 実装の無い3件（`RelationStore`/`Sensor`/`SpeechPolicy`）は
  **文書自身が「Phase 2」「仮置きに過ぎない」と明記しており**、ADR 0269 決定3もこれを
  drift ではなく「⚪ 比較不能」と分類している。

**【推論】もし §5 が「定める側」（契約を先に書き、実装がそれに追随する側）であったなら**、
この非対称は逆になるはずである——**文書が実装より先に進み、実装がまだ追いついていない
箇所（文書にあって実装が無い）が、少なくとも時々は現れるはずである。** ところが実際に
見つかったのは一方向だけであり、しかも「文書が実装より先に進んでいる」ように見える
唯一の3箇所（`RelationStore`/`Sensor`/`SpeechPolicy`）は、**文書自身がそのことを
「まだ実装しない」「仮置きに過ぎない」「設計が済んでいることを意味しない」と明示的に
断っている。** 定める側の文書が、自分の定めた契約について「これは仮置きであり、
まだ設計が済んでいない」と自ら断る必要は無い——**定めるならそう書けばよいだけである。**
この自己申告的な留保こそが、§5 が「実装に先んじて契約を宣言する権威を持たない」ことの
現れであり、**§5 が実装の後追いでしか物を言っていない**——つまり写した側である、という
読みを支持する。

**⟹ 本 ADR は、ADR 0269 決定2 の保留に対し「§5 は写しである。実体（`packages/core/src/`）が
正本であり、drift が見つかったら文書を直す」と答える。**

### 3つに割る（⛔ 2択にしない）

ADR 0269 決定3 の17項目は、次の3種類に分かれる。**種類を混同しないこと。**

1. **写し（実体が在る14個: ⭕一致10 + 🔴drift4）** ⟹ **実体が正本。drift が見つかったら
   文書を直す。⛔ 実装側を疑わない**——「文書にあって実装が無い」形の drift が0件である以上、
   実装が契約に違反しているという読みは成立しない。
2. **予告（実体が無いと文書自身が明記している3個: `RelationStore`/`Sensor`/`SpeechPolicy`）**
   ⟹ **drift ではない。**文書がこの3件について「まだ実装しない」と自ら宣言している以上、
   実体との不一致を修理対象として扱わないこと。⛔ 歯（テスト）の対象にしない。
3. **⚠ `ScoringStrategy`（型名ずれ）** ⟹ **歯の形が他の drift と違う。**`MemoryStore` 等は
   「メソッドの集合」の欠落だが、`ScoringStrategy` は関数型（`(input) => ScoreBreakdown`）
   であり、メソッド件数という概念そのものが無い。**将来もし歯を作る PR が出るなら、
   `MemoryStore` 型の「メソッド集合の一致」と `ScoringStrategy` 型の「型名の一致」は
   別の検査ロジックが要る。**（本 ADR はこの歯そのものを作らない。次にこれをやる人への
   申し送りである。）

## 3. `ScoringStrategy` の型名ずれは「改名」だったか — 【実測】、ただし依頼の仮説とは違う形だった

**依頼された仮説**: 「実装側がかつて `Score` で、後に `ScoreBreakdown` へ改名されたのなら、
それは読みA（文書は写しで、改名に追随し損ねた）の直接証拠になる」というものだった。

**【実測】この仮説はそのままの形では成立しない。** 次の3点を確認した:

1. `git log --oneline --all -p -S"ScoreBreakdown" -- packages/core/src/strategies/scoring.ts`
   を実行すると、`ScoreBreakdown` は**最初の実装コミット（`1eee055`、PR #2
   「Phase1 段階1: monorepo の骨格 / core interfaces / testkit 適合テストの雛形」）から
   既に存在する。**
2. `git show 1eee055 -- packages/core/src/recall.ts` を読むと、同じ最初のコミットで
   `export interface ScoreBreakdown { ... }` が定義されている。
3. `git log --oneline --all -p -S"interface Score {"` / `-S"type Score ="` を
   `packages/core/src` 全体に対して打つと、**該当コミットは1件も無い**——
   **コード側に `Score` という名前の型が存在した痕跡は、この repo の全履歴を通じて無い。**

**⟹ 実装側で `Score` → `ScoreBreakdown` への改名は起きていない。`ScoreBreakdown` は
実装の最初の瞬間から今日までその名前のままである。**

**では `docs/architecture.md` の `Score` はどこから来たか。** 【実測】
`git log --oneline --all -S"type ScoringStrategy = (candidate: ScoringInput) => Score;"
-- docs/architecture.md` を実行すると、該当するのは**設計フェーズの成果物コミット
`1cf6a60`（PR #1「設計フェーズの成果物: 北極星 / アーキテクチャ / 記憶モデル / recall /
ADR 9本」）**であり、これは実装コミット `1eee055`（PR #2）**より前**である
（`git log --oneline --all --reverse | head -5` で全履歴中の最初の5コミットの順序を確認
——`1cf6a60` が4番目、`1eee055` が5番目）。

**【推論】これが意味すること**: `docs/architecture.md` の `Score` は、**実装がまだ
存在しない設計フェーズで書かれたコードスケッチの中の、簡略化された（あるいは
確定前の仮の）型名だった。** その直後の実装フェーズ（PR #2）で、実装者は `ScoreBreakdown`
という別の名前を選んだ。**その時点で文書側の `Score` は現物と食い違ったが、以後一度も
揃え直されていない**——**「後から改名されて追随し損ねた」のではなく、「設計時の仮の名前が、
実装が確定した後も一度も現物と照合されなかった」という形である。**

**⚠ これは依頼の仮説（後からの改名）を裏付けない。だが、読みA（§5 は写しであり、
現物に追随できていない）そのものへの支持は失っていない**——むしろ**より直接的な形**
（文書の記述が、実装が確定した後の現実と一度も同期されていない）に置き換わっている。
**⛔ ただし本 ADR は「改名があった」とは書かない**——確認できたのはこの経緯だけであり、
依頼が示唆した「改名」という語をそのまま使うと事実と異なる。

## 4. 読みB を退ける — ADR 0269 決定2 の3つの根拠を、1つずつ検討する

ADR 0269 決定2「読みBを支持する手がかり」は3点あった。**逐語を引き、1つずつなぜそれが
読みB を支えないかを書く。**

### 根拠1: `RelationStore` に実体が無い（「存在しないものは写せない」）

**ADR 0269 の逐語**（決定2・読みB 1点目）:

> §5.3 `RelationStore`【現物・逐語、`docs/architecture.md:607`】は「Phase 2」と明記され、
> `packages/core/src/` のどこにも実体が無い（決定3で確認）。⟹ 存在しないものは「写せない」
> ——この節は実装から写したのではなく、将来の契約を*先に*書いている。

**【推論】なぜこれが読みBを支えないか**: 「存在しないものは写せない」は真だが、そこから
「だから §5 は契約を定めている」を導くには、もう一段の前提が要る——**「§5 が将来の契約を
先に書いた以上、実装はいずれそれに従う義務を負う」という前提である。** だが決定3の表を見ると、
**この義務が働いた形跡は無い。** `RelationStore` は Phase 2 のまま何年も実装されておらず
（§2 の非対称の議論と同じ）、それを「契約違反」として扱っている記述はどこにも無い。
**むしろ、§2 で述べた非対称（文書にあって実装が無い＝0件、実装が10口以上先に進んでいる
箇所が複数）が示すのは逆である**——**この文書が実装を先導した実績は無く、実装のほうが
常に先を行き、文書だけが取り残されている。** 「存在しないものを書く」という行為それ自体は
定める側にも写す側にも起こりうる（写す側でも「予告として書いておく」ことは矛盾しない）
——この根拠だけからは、実は決着が付かない。**そして決定的なのは、次の根拠2の逐語である。**

### 根拠2: `Sensor`/`SpeechPolicy` の「仮置きに過ぎない」（逐語）

**ADR 0269 の逐語**（決定2・読みB 2点目）:

> §5.13 `Sensor`/`SpeechPolicy`【現物・逐語、`docs/architecture.md:858-861`】:
> > 正直に書く: この2つは Phase 1〜2 の設計検討の対象外であり、**現時点では interface の
> > 形すら仮置きに過ぎない。**（中略）**ここでの掲載はオーナー要求の11項目網羅のためであり、
> > 設計が済んでいることを意味しない。**
> ⟹ 文書自身が「これは写しではなく仮置きの宣言である」と述べている。実装が無いものを
> 「オーナー要求への網羅」のために書いているのだから、これは定義行為そのものである。

**【推論】なぜこれが読みBを支えないか**: ⭐ **この逐語は、読みAの根拠として読み直せる。**
**定める側の文書は、自分が定めた契約について「仮置きに過ぎない」「設計が済んでいることを
意味しない」と自ら断る必要が無い。** 定めるなら、そう書けばよいだけである——
「`Sensor` はこの2メソッドを持つ」と言い切ればそれで契約は成立する。**ところがこの文書は
真逆のことをしている**——**わざわざ「これは仮の記述であり、権威を持たない」と自己申告して
いる。** これは「定める」ではなく「まだ定まっていないことを、正直に、権威を持たない形で
書き残している」という行為であり、**むしろ「この文書は自分自身に契約を定める権威が無いことを
自覚している」ことの証拠になる。** ⟹ **依頼が指摘した通り、この根拠は実は読みBを支持して
いない。**

### 根拠3: §5 冒頭の「契約」という語

**ADR 0269 の逐語**（決定2・読みB 3点目）:

> §5 冒頭【現物・逐語、`docs/architecture.md:357-361`】:
> > 各 interface は「型シグネチャ」と「契約（振る舞いの約束）」の両方で構成される。
> > **型だけでなく振る舞いが契約である**——（中略）adapter は型を満たすだけでなく、
> > testkit のスイートを通ることで初めて「準拠」とみなす。
> ⟹ 「契約」という語を使っており、adapter 実装者に向けて「満たすべきもの」を述べる体裁を
> 取っている。これは記述（写し）よりも規範（定める）に近い語り口である。

**【実測】この逐語を `docs/architecture.md:357-361` で現物確認した**（本 ADR §0 の作業3）。
一字一句 ADR 0269 の引用と一致する。

**【推論】なぜこれが読みBを支えないか**: この段落が「契約」という語で指しているものを
最後まで読むと、**契約の実体は §5 の文面そのものではなく、`packages/testkit` の
適合テストスイートに置かれている**——「adapter は**型を満たすだけでなく**、testkit の
スイートを**通ることで初めて**『準拠』とみなす」とある。⟹ **この段落が主張しているのは
「§5 の文章を守れ」ではなく「§5 の文章だけでは足りず、実行可能な検査（testkit）を通れ」
である。** これは「文書の記述こそが権威である」という主張とは逆で、**「本当の契約は
別の場所（実行可能なコード）にあり、この文書はそれを説明しているだけだ」という宣言に近い。**
さらに、`docs/architecture.md` §3.2（`Runtime` の節、ADR 0244 が直した箇所）には
「何が在るかの正本は `packages/core/src/runtime.ts` の `export interface Runtime` であり、
ここに個数を写さない」という、まさに同じ構図の明言が既に付いている（ADR 0269 決定2 が
自ら引用）。**§5 冒頭の「契約」という語も、この §3.2 と同じ構図——正本はコード・テストキット側にあり、
文書はそれを記述している——の中で使われていると読むほうが、文書全体の一貫性に合う。**

### 🔴 3つとも読みBを支えない、という結論

**根拠1は前提が成立せず決着しない。根拠2・3は、詳しく読むとむしろ読みAを支持する。**
**⟹ 読みBを積極的に支持する一次資料の手がかりは、検討の結果、実質的に残らなかった。**

## 5. なぜこれはオーナー領分ではないか

**ADR 0269 決定2 は「これはオーナー領分の論点である」として保留した。本 ADR はそれを
覆し、「オーナー領分ではない」と判断する。理由は次の通りである。**

`docs/roadmap.md` §5 冒頭【現物・逐語、`docs/roadmap.md:220`】は、オーナー判断を要する
ものの範囲をこう定義している:

> ここに集めるのは「妥当なデフォルトを技術側だけで決め切れない」もの——**製品の性格・
> データの安全性・事業の前提**に関わる判断であり、オーナーの判断を必要とする。
> それ以外は足さない。

`docs/autonomy.md` §3.1【現物・逐語】も同じ線を引く:

> 見分け方: 「どちらを選んでも技術的には成立するが、選び方が製品の性格を決める」なら
> §5 行きである。

**§5 が写しか定めかという問いは、この線に当たらない。** どちらの答えを採っても——
「§5 は写しであり実体を直す」でも「§5 は契約でありいずれ実装を疑う」でも——
**mnemora が使う側に対して何を提供するか（製品の性格）は1ミリも変わらない。**
変わるのは「**この文書をどう保守するか**」という、純粋に文書運用上の役割分担だけである。
これは `docs/decisions/README.md`【現物・逐語、ADR 0269 決定2 が既に引用済み】が
ADR と生きた文書の役割を「決定を記録する場」と「決定を記述する場」に分けているのと
同じ層の話であり、**製品の方向・公開 API の破壊的変更・正典の数え方（north-star の
物差し）・取り返しのつかない行為（npm publish・バージョン上げ・north-star の書き換え等、
`docs/autonomy.md` §3 の ⛔ 表に残る5行）のどれにも当たらない。**

**この判断の後ろ盾は [ADR 0156](./0156-delegate-5-grade-judgment-and-breaking-changes.md)
である。**同 ADR は `docs/autonomy.md` §3 の ⛔ 表から「§5 級の判断を自分で決めること」を
外し、その決定が現在 `docs/autonomy.md` §3 に次の形で残っている【現物・逐語】:

> **§5 級の判断は、クローンが北極星（`docs/north-star.md`）に照らして自分で決めてよい。**
> 迷ったら §3.1 のとおり `docs/roadmap.md` §5 へ足して止まる、という既定は残る
> ——変わるのは「自分で決めてよい」という許可が足されたことであり、§3.1 の手順そのものは
> 消えない。

**⟹ 「§5 は写しか定めか」は、`docs/roadmap.md` §5 の基準（製品の性格・データ安全性・
事業の前提）に当たらない以上、そもそも §5 行きの論点ではなく、通常の技術的判断の側にある。**
ADR 0269 が「オーナー領分」として保留したのは、**この線引きを一段深く検討する前の、
より慎重な判断だったと読める**——本 ADR は ADR 0156 の委譲済みの権限に照らして、
その保留を1段先へ進める。

**🔴 だが決めないことにも費用がある。** drift 4件の修理は、決定2が保留されている限り
「実装を疑うべきか文書を疑うべきか」が定まらず止まったままである。**この保留自体が、
Issue #604 が引き受けた「掃引して棚卸しするところまで」を超えて、次の一手（修理）を
無期限に凍結させている。**本 ADR がその保留を解くのは、この費用が実在するからである。

## 6. 確かめていないこと（🔴 どちらも本 ADR の結論を覆しうる）

- 🔴 **ADR 0269 が引く ADR 0100 / 0114 / 0134 / 0165 の原典を、本 ADR の書き手は
  読んでいない。** ADR 0269 決定2 はこれらの ADR を「`archiveDecayed`/`purgeMemory`/
  `markContestedPair` 等」「`getDecayClock` 等4メソッド」を先に決めた根拠として名指しして

  §5 の扱いについて何を書いているか（例えば「§5 も同時に更新すること」という指示が
  実は在ったが実行されなかった、等）は確認していない。** もしそれらの原典が「§5 は
  この決定と同時に更新される契約文書である」という運用を明記していたなら、

- 🔴 **17個の掃引は `packages/core/src/` 以外を掃いていない**——これは ADR 0269 決定1・

**⟹ 上のどちらの調査も、この ADR の書き手（クローン・担い手）自身がまだ行っていない。
どちらも、本 ADR の結論を覆す方向に転びうる。**

## 採らなかった案

### 1. ADR 0269 を直接書き換えて決定2 を確定させる

⛔ **依頼の指示により禁止**——ADR は書き換えず、新しい ADR で追記して積む
（`docs/decisions/README.md`「決定そのものをやり直す場ではなく、決定を記録する場」の
運用と同じ理由。ADR 0269 は「その時点で下した保留判断の記録」として履歴に残し、
新しい判断は新しい ADR に書く）。

### 2. 決定2 に決着を付けず、drift の修理を「読みAでもBでも成立する形」で進める

⛔ 検討したが**採らなかった**。ADR 0269 決定3 が既に書いている通り、読みAとBでは
「疑う対象」が逆になる（読みA: 文書を直す／読みB: 実装・adapter を疑う）。**決着を
付けないまま修理 PR を出すと、その PR 自身が暗黙に読みAを前提にしてしまい、
決定2 の保留を実質的に上書きすることになる。**それなら、明示的に ADR として決着を
付けて次の作業者に渡すほうが、正典（ADR 群）と実際の運用の乖離を残さない。

### 3. `ScoringStrategy` の型名ずれについて、依頼の「改名」という語をそのまま使う

⛔ **採らなかった**——§3 の【実測】が示す通り、実装側の改名は起きていない。
事実と異なる語をそのまま使うと、後から読む人が「改名 PR を探しても見つからない」という
形で混乱する。**代わりに、実際に確認できた経緯（設計フェーズの仮スケッチが、確定した
実装名と一度も同期されなかった）をそのまま書いた。**

## 引き受けた負債

- **本 ADR は §2〜§4 の論証だけで「写し」と判断しており、ADR 0269 決定2 が「決定的な
  一次資料の記述は見つからなかった」と書いた状況そのものを覆す新しい一次資料
  （例えば「§5 は写しである」と明言する別の ADR・コミットメッセージ）を新たに発見した
  わけではない。** 本 ADR がしたのは、**既存の3つの手がかりの読み直しと、非対称という
  構造的論拠の追加**であり、確実な決め手ではなく推論の積み重ねである。オーナー本人が
  読んで「その推論は違う」と判断すれば、本 ADR はその場で覆る。
- **§6 の2点（ADR 0100/0114/0134/0165 原典未読、他パッケージ未掃引）は、本 ADR の結論を
  覆しうる形のまま残る。** どちらも埋めていない。
- **drift 4件の修理・歯の追加は、本 ADR が決定を出した後もなお着手されていない。**
  本 ADR は「疑う対象は実装ではなく文書」という向きだけを確定させ、実際の修理は
  別 PR に委ねる。**その別 PR が出るまで、drift はそのまま残り続ける。**
- **`ScoringStrategy` の型名ずれに対する歯の設計（§2「3つに割る」3番）は、方針
  （メソッド集合の一致検査とは別ロジックが要る）だけを申し送り、設計自体はしていない。**

## これが覆るとしたら何が起きたときか

- **オーナー本人が「§5 は写しではなく契約である」と明言したとき。** その場合、本 ADR は
  無効になり、drift 4件は「文書の記述に実装を合わせる」または「文書と実装の乖離を
  容認しない代わりに実装側を見直す」という逆方向の対応が必要になる。
- **§6 で確かめていない2点のどちらかが、逆方向の証拠を持って埋まったとき**——
  ADR 0100/0114/0134/0165 の原典が「§5 も同時に更新する契約だった」と明記していた
  場合、または他パッケージの掃引で「文書が実装より先に進んでいる」実例が見つかった場合。
- **`docs/architecture.md` §5 自体に、§3.2 と同じ形の明示的な「写し」宣言
  （「正本は `packages/core/src/interfaces/*.ts` であり、ここに個数を写さない」等）が
  後から追加されたとき**——そのときは本 ADR の推論部分は不要になり、文書自身の宣言が
  一次資料として決定的な証拠になる。
- **本 ADR の判断（§5 級の判断としてクローンが決めてよい）自体に、オーナーが
  「この種の判断は§5 級ではなくロードマップ §5 行きだった」と後から言ったとき**——
  そのときは ADR 0156 の適用範囲の見直しが必要になり、本 ADR も手続き上、
  再度オーナー判断待ちへ差し戻される。
