# ADR 0636: テナントが食い違った参照の既存行は、検出だけする関数 `findCrossTenantReferences` で見つける（何も書き換えない・複合外部キーは足さない）

- **状態**: 採用 (2026-10)
- **日付**: 2026-10-06

> **⚠ この判断の出所は、オーナー回答 374f6f88 の問27（全部推奨）である。**
> オーナーが決めたのは「推奨の採否」だけで、推奨の中身（検出の口の形・種類・サンプルの上限・読み取り専用）は
> 担い手（マネージャーの指示による）が作った。**中身をオーナーが1行ずつ決めたと読まないこと。**
> 実装と歯は担い手が書いた。決めた主体の区別は ADR 0220。

- **【現物】** — 読んだコード・文書。**【実測】** — 手元（PostgreSQL 17 + pgvector、`initdb` で立てた自分専用のインスタンス）で走らせた結果。

## 文脈

- 【現物】[ADR 0439](./0439-memory-store-reference-writes-check-target-belongs-to-ctx-tenant.md) は、
  `recall_usages`・`memories.source_observation_id`・`memories.contested_with_id`・`memories.superseded_by_id` の
  書き込み口に入口検査を入れた。外部キーが `(id)` だけでテナントを含まないので、入口検査の無かった時代の書き込みは、
  別のテナントの行を指す行を残しえた。ADR 0439 は「複合外部キーの migration は入れない」と決め、既存行を調べる
  SELECT を4本、本文に書いた。
- 【現物】既存行が0件であることを確かめてから複合外部キーを足す、という道筋では、「確かめる」手段が手で流す SQL
  だけだった。
- 【現物】`memory_events`・`memory_embeddings_<space>`（ADR 0436）・`memory_relations`（ADR 0398）は、
  それぞれの ADR が自分の検査 SQL を持つ。

## 決定

1. **`@mnemora/postgres` に `findCrossTenantReferences(pool, { schema?, sampleLimit? })` を足す。**
   上の4種について、参照先のテナントが行のテナントと違う行を数え（`count`）、先頭の `sampleLimit` 件（既定 20、0 以上
   1000 以下の整数。0 なら件数だけ）を返す。検出の条件は ADR 0439 の4本の SELECT と同じで、`JOIN` なので参照が
   NULL の行は対象外。`recall_usages` は recall 側か memory 側のどちらかが食い違えば1行である（両方でも1行）。
2. **何も書かない。**消す・付け替える・NULL にするのは利用者のデータの書き換えで、オーナーの判断である。
   `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY` の中で読み、`ROLLBACK` で閉じる。書こうとしてもサーバー側で
   拒まれる。REPEATABLE READ なので、種類ごとの count とサンプルは同じスナップショットを見る。
3. **複合外部キーは足さない。**この関数は、0行を確かめてから足す、の「確かめる」手段である。足すかどうかは、
   実データでこの関数を流した結果を見て、オーナーが決める。
4. **食い違いが見つかっても投げない。**どうするかは呼び出し側の判断である。
5. **対象は4種に限る。**`memory_events`・`memory_embeddings_<space>`・`memory_relations` は、それぞれの ADR の SQL を
   手で流す（関数の doc に書いた）。
6. **新しい公開 API を足すだけで、既存の振る舞いは変えない。**CHANGELOG の `### Added` に載せ、
   `docs/migration-v1.md` には項目を足さない（同文書は既存の振る舞いが変わるものを載せる）。

## 採らなかった案

- **検出と同時に直す（食い違い行を NULL にする・消す）。**利用者のデータの書き換えで、オーナーの判断である。
- **複合外部キーを同じ PR で足す。**既存行に食い違いがあれば migration が失敗する。確かめる手段を先に出す。
- **食い違いがあれば例外にする。**0件でない結果は、異常ではなく調査の材料である。

## 引き受けた負債

- 0件は「食い違いが無い」の証明ではなく、「この4種について、この呼び出しの時点のスナップショットに無かった」である。
  呼び出しの後に書かれた行は見ない。
- **大きな表での所要時間は測っていない。**`memories` を全行、参照が NULL でない行について引く `JOIN` で、
  `statement_timeout` はこの関数では設定しない。
- 4種以外の参照（上の決定5）は、この関数の外にある。

## これが覆るとしたら

- 実データで流したら食い違いが見つからず、複合外部キーをそのまま足せるなら、関数は役目を終える（消すかは別の判断）。
- 4種以外にも同じ検出が要るなら、`CROSS_TENANT_REFERENCE_KINDS` に足す形で広げる。

## 測ったこと / 確かめていないこと

- 【実測】歯は `packages/postgres/src/__tests__/cross-tenant-reference-detection.postgres.test.ts`。
  生 SQL で仕込んだ食い違い行を4種とも捕まえること（陽性対照）、正しい行・別テナントの正しい行・NULL の参照を
  数えないこと（陰性対照）、`sampleLimit` が count に影響しないこと、読み取り専用であること、`schema` を渡すと
  専用スキーマの側を見ることを縛る。実装を1つずつ壊す変異試験を行い、通り抜けた変異（`recall_usages` の片側だけの
  食い違い・専用スキーマでの `recall_usages`/`observations`/`recalls`・サンプルの並び・トランザクションの隔離レベルと
  ROLLBACK）には歯を足した。表は PR #1743 の本文。
- 確かめていない: 大きな表での所要時間。並行する書き込みがあるときの挙動（REPEATABLE READ のスナップショットの
  範囲で一貫することは見たが、競合する書き込みを走らせた試験は無い）。
