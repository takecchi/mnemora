## 決定

### 決定1: 「中核の5動詞 + 3つの層」という構造にする

**中核の5動詞**（`observe` / `recall` / `reflect` / `consolidate` / `forget`）は
**記憶そのものを動かす操作**であり、**ここは増やさない**——元の一文「6つ目は作らない」が
守ろうとしていたものを、そのまま引き継ぐ。

残り9個は「6つ目の動詞」ではなく、中核を狭く保つために別の層へ出した口として、3層に分ける。
**分類は doc コメントを全14個読んで検算し、現物と合わせた**（下の「分類の検算」参照）。

- **保守操作**（`tick` / `reembed` / `reextract` / `sweepArchive`）——
  「いつ動かすか」を呼び出し側が決める口。自動では走らない。
- **是正・取り消し**（`markContested` / `resolveContested` / `restoreArchived` / `purge`）——
  呼び出し側が既に下した判断（矛盾の指摘・決着・復帰・完全削除）を、決められた形で
  書き込む口。どちらが正しいかを mnemora 自身は判定しない。
- **説明**（`getRecall`）——なぜそれが想起されたかを、後から読み戻す口
  （`docs/north-star.md`「目指す姿」項目3）。

### 決定2: この構造の要点は「歯止めが何に効くか」を明示すること

**分類表で終わらせない。**「新しく何かを足したくなったとき、それが記憶そのものを動かす
操作（中核5動詞と同じ性質）なら、足せない。保守・是正・説明のどれかに当たるなら、
その層の性格に合っているかを問う」という、後から使える判定の形にする。

⚠ **この判定は「3層のどれかに当てはまれば足してよい」ではない。**3層は既存の9個を
説明する後付けの整理であり、新しい口を作る免罪符にはしない（下の「引き受けた負債」1番）。

### 分類の検算【現物】

マネージャーが doc コメントから立てた分類を、`runtime.ts` の該当 doc コメント全文を読んで
検算した。

| メソッド | doc コメントの根拠 | 分類は合うか |
|---|---|---|
| `tick` | 「`InlineScheduler`（キュー無し）構成では、これを誰かが明示的に呼ばない限り抽出・埋め込みは永久に走らない」（1150-1153行） | 合う。保守操作 |
| `reembed` | 「呼んだだけでは索引は埋まらない」「同じ形の型を2つ置くと片方だけ直したときに黙ってずれる」（1229-1237行） | 合う。保守操作 |
| `reextract` | 「失敗した抽出をやり直す」（1206-1207行） | 合う。保守操作 |
| `sweepArchive` | **「呼び出し側が明示的にこれを呼んだときだけ走る保守操作である（`reembed` と同じ立場）」**（1260-1262行、**この repo 自身が「保守操作」という言葉を使っている**） | 合う。保守操作 |
| `markContested` | 「呼び出し側（人・上位のアプリケーション層・将来の自動検出）が既に『この2件は対向する』と決めていることを前提に…機械的に書き込むだけ」（1455-1458行） | 合う。ただし「人が誤りを正す」だけではない——**将来の自動検出も呼び手になりうる**と doc 自身が書いている。⟹ 層の説明を「人が」ではなく「呼び出し側が下した判断を」に修正した |
| `resolveContested` | 「どちらが正しいかを判定しない」「呼び出し側が既に下した決定…を機械的に書き込むだけ」（1514-1519行） | 合う |
| `restoreArchived` | 「`archived` な Memory を、呼び出し側が明示的に取り戻す」（1266-1267行） | 合う |
| `purge` | 「`forgotten` からのみ遷移できる」「不可逆操作に対する最小の安全弁」（1391-1393行） | 合う |
| `getRecall` | 「`recall()` が返した `RecallId` から…後から読み戻す」「北極星の目指す姿の『後から』を…採用側にも届かせるための口」（1176-1186行） | 合う。単独の層でよい——他のどのメソッドも「後から説明する」ことを主目的にしていない |

**合わなかったのは1点**: マネージャー案の是正・取り消し層の説明「人が誤りを正す・取り消す・
消す操作」は、`markContested` の doc が「将来の自動検出」も呼び手として想定している点と
厳密には合わない。**⟹ 層の説明文を「呼び出し側（人・上位アプリケーション・将来の自動検出）が
既に下した判断を書き込む・取り消す・消す操作」に直した**（上の README.md / vision.md の
編集に反映）。

## ADR 0147 の判断は揺らがない

**ADR 0147 決定5**（`compareWithFullLog` を `Runtime` のメソッドにせず純関数にする）は、
「6つ目の動詞を作らない」という規約を引きつつ、**逐語でこう続けている**
（`docs/decisions/0147-recall-footprint-estimator.md:118-121`、【現物】確認済み）:

> **理由は規約の遵守だけではない**——`Runtime` のメソッドにすると **`Runtime` を組み立てられる
> 環境（＝ DB も provider も配線済みの環境）でしか呼べなくなる。** この関数に問いたいのは
> 「mnemora を入れるべきか」であり、**それを判断したい時点では、まだ何も配線していないのが
> 普通である。**

**⟹ この2つ目の理由は、「5つの動詞」という規約の文面が変わっても単独で成立する。**
`compareWithFullLog` が `ctx` を取らない純関数である理由は「Runtime の口を1個も使わずに
呼べる必要がある」ことそのものであり、これは中核5動詞の数え方（5個か、5+3層か）とは
独立した主張である。**⟹ 一文を書き換えても ADR 0147 の結論は変わらない。**

**ADR 0147 自体は書き換えていない**（当時の判断の記録であり、AGENTS.md の指示通り）。
本 ADR はそれを参照するだけである。

`README.md:240` の「これは『6つ目の動詞』ではない」という主張も同じ理由で引き続き成り立つ
——`compareWithFullLog` は中核5動詞にも、保守・是正・説明のどの層にも属さない。属する
必要が無い（`Runtime` のメソッドではないため、そもそも動詞の数え方の対象外である）。

   `recall()` が積む量にも `compare` の数値にも触れない。
2. **これを無効にしたとき、Memory Framework として成立するか。** ⟹ **落ちる案なし。**

3. **この記憶が選ばれた理由を、後から説明できるか。** ⟹ **この問いにこそ関わる。**

4. **AI の推論と、ユーザーが言った事実を区別しているか。** ⟹ **落ちる案なし。**

**⟹ 5問中、実際に判断を導いたのは問い3だけである。**残り4問は「飾りで当てはめない」

## 検討して採らなかった案

1. **⛔ 実装を記述に合わせる（`Runtime` を5メソッドに削る）。** 却下——上の「文脈」節の
   通り、`getRecall`/`markContested`/`resolveContested` は v1.0 の残り2項目
   （北極星「目指す姿」項目3・5）の本番経路そのものであり、削ると v1.0 が定義上到達
   不能になる。オーナーの逐語「1でお願いします」もこの案を明示的に外している。
2. **⛔ 「14個あります」と実態を並べるだけで終わる。** 却下——マネージャーの指示通り、
   これでは元の一文「6つ目は作らない」が守ろうとしていたもの（**中核を絞るという歯止め**）
   が失われる。単なる実態の追認は、次に誰かが15個目を足したくなったときに、何を根拠に
   問い直せばよいかを与えない。
3. **⛔ 9個をまとめて「補助動詞」のような1層にする。** 却下——`sweepArchive`/`reembed`
   （保守）と `purge`/`markContested`（是正・取り消し）は「いつ動かすか」を委ねる操作と
   「呼び出し側の判断を書き込む」操作という性質が異なり、1層にまとめると
   `docs/vision.md`「文脈を剥がして提示しない」原則が繰り返し戒めている「性質の違うものを
   同じ顔で出す」形になる。`getRecall` を保守・是正のどちらかに混ぜることも同じ理由で
   避けた——これは「説明」であって「操作」ですらない。
4. **⛔ 5層以上に細分化する（例: `markContested` と `resolveContested` を別層にする）。**
   却下——両者は対称な対（ADR 0150 が「解決側であり、`markContested` の形を手本に対称に
   書いてある」と明記）であり、分ける実益が無い。層を増やすほど「新しく足すときにどの層か
   迷う」コストが上がる（引き受けた負債1番と同じ緊張）。

## 引き受けた負債

1. **⚠ 層に分けたことで、「どの層にも当てはまらないから足せない」という歯止めが弱くなる。**
   分類は増やす理由にも使える——新しい口を作りたくなったとき、「これは保守操作だから」
   「これは是正操作だから」と理由付けして3層のどれかへ滑り込ませることが、素の「6つ目は
   作らない」1文よりも容易になる。**この ADR はこの危険を消していない。**歯止めとして
   機能させるには、新しいメソッドを提案する側が「なぜこれが記憶そのものを動かす中核操作
   *ではない*のか」を毎回説明する義務を負う、という運用でしか埋められない——**この運用は
   本 ADR の文書変更だけでは強制できず、レビューの規律に依存する。**
2. **9メソッドの3分類は、この ADR の書き手が doc コメントを読んで立てたものであり、
   オーナー自身が確認した分類ではない。**マネージャーの原案を検算して1点修正したが
   （`markContested` の「人が」を「呼び出し側が」に直した）、将来 doc コメントが変われば
   分類がずれる可能性がある——分類を機械的に固定する歯（型やテスト）は無く、文書として
   置いてあるだけである。
3. **「いつからこの乖離が在ったか」の年表は、各メソッドが最初に増えた commit だけを
   `git log -S` で引いたものであり、シグネチャ変更や一度削除されて後で戻った経緯までは
   遡っていない。**調べ切れていない範囲として残る。

## これが覆るとしたら何が起きたときか

- **オーナーが「実装を5メソッドに削る」方針へ転換したとき。**その場合は
  `getRecall`/`markContested`/`resolveContested` の本番配線（v1.0 の残り2項目）を
  先に別の形で満たす必要があり、この ADR の決定1・決定2 は丸ごと覆る。
- **`Runtime` に15個目のメソッドを足す提案が出たとき。**決定2 の判定
  （「記憶そのものを動かす操作なら中核には足せない。3層のどれかに当たるなら層の性格に
  合っているかを問う」）を実際にその提案へ当ててみて、**もし3層のどれにも自然に
  当てはまらない**なら、4層目を作るか、そもそも mnemora が持つべき機能かを疑う判断が
  要る——これは引き受けた負債1番が名指しした緊張が実際に発火する場面である。
- **`markContested`/`resolveContested` の「将来の自動検出」（doc コメントが想定している
  呼び手）が実装されたとき。**その時点で「是正・取り消し」層の説明（「呼び出し側が
  既に下した判断を書き込む」）が「人 or 上位アプリ」だけでなく「mnemora 自身の検出器」も
  含む形になり、層の名前・説明を再検討する必要が出る可能性がある。

## 確かめていないこと

2. **定義の核**——「どちらが正しいかを mnemora 自身は判定しない」——**は今も真である。**

   正しいかには一切触れない（[ADR 0324](./0324-claim-key-contested-detection.md) 決定1・
   文脈節）。

⟹ **記録として残すのはこの読みである**: `markContested`/`resolveContested` の呼び出し元は

将来の自動検出）が既に下した判断を…書き込む口」）が予め用意していた `将来の自動検出`
