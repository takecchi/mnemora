# ADR 0637: 出荷済み migration の checksum を CI で固定する。`0027` の deadlock は、新しい番号の migration では直せないので、文書のままにする

- **状態**: 採用 (2026-10)
- **日付**: 2026-10-06

> **⚠ 出所**: オーナー回答 374f6f88 の問29（全部推奨）による。**オーナーが決めたのは推奨の採否だけ**であり、
> 下の「決めたこと」の設計（名簿の形・正規化・どこで走らせるか）と、「`0027` を新しい migration では直せない」という分析は、

> 問29の本文そのものは、この担い手には渡っておらず、呼び手の要約（下の3点）を受け取っただけで、原文は確かめていない。

> 受け取った推奨の要約: (a) `0027` を流している最中に observe が走ると deadlock する（5回中4回）ことを文書に書く。
> (b) 直すなら**新しい番号の migration** で直す。既存の migration は編集しない。(c) migration の台帳の checksum を CI で固定する。

- **【現物】** — 読んだコード・文書。**【実測】** — 手元で走らせた結果。**【受】** — 報告として受け取り、再導出していない。

## 文脈

1. 【現物】`runMigrations`（`packages/postgres/src/migrate.ts`）は、`_mnemora_migrations` 台帳の**ファイル名だけ**で適用済みを判定する。
   台帳に checksum の列は無い。同ファイルの `stripCreateExtensionStatements` の doc が、適用済みの編集は
   「既適用の DB では再実行されず、実行済み内容と正本がずれるだけになる」と書いている（ADR 0057・ADR 0001）。
2. 【現物】`scripts/`・`.github/workflows/ci.yml`・`docs/decisions/` を `checksum` で `grep` した範囲では、migration の内容を固定する検査は無かった
   （当たったのは ADR 0143・0448・0461 の、別の話題での言及だけ）。「在るのに見つけられなかった」可能性は、`grep` の範囲の外では否定していない。
3. 【現物】`0027` の deadlock は、[ADR 0442](./0442-migrate-deadlock-subject-injection-ddl-lock-wait-docs.md) が**既に文書に書いている**
   （`docs/migration-v1.md` の `0027` の項目、`packages/postgres/README.md` の節、[ADR 0383](./0383-erase-tenant.md) の追記）。
   「5回のうち4回」の出所は、この ADR 0442 の【実測】（2026-10-01、PostgreSQL 17・ローカル、memories 10万件・recalls 3万件、
   observe・recall・tick の4本のループを回しながら `0025`・`0027`〜`0032` を当てた。migrate が犠牲になったのが2回、アプリが犠牲になったのが計4件）である。
   **この PR の担い手は、これを再測定していない。**`#1733`・`#1734`・`#1724` などの確かめ直しの Issue に当たる経路は、この担い手には無かった
   （`gh` で Issue 本文を読む手順を踏んでいない）。ADR 0442 以外に「5回中4回」の根拠は見つけていない。
4. 【現物】ADR 0442「検討した代替案」1は、`0027` を分割するか先頭で `LOCK TABLE` する案を「適用済みを編集しても、既に当てた DB には効かない。
   編集するか次の番号で足すかはオーナーへ回した」として採らなかった。問29の推奨(b)は、その「次の番号で足す」側である。

## 決めたこと

1. **checksum の固定を入れた（推奨(c)）。**
   - 名簿: `packages/postgres/migration-checksums.json`（ファイル名 → sha256）。publish 対象（`files` は `dist` と `migrations`）の外に置いた。
   - 判定: `scripts/migration-checksums-lib.mjs`（純関数）。入口は `scripts/check-migration-checksums.mjs`（`pnpm run check:migration-checksums`）。
   - 走る場所: ルートの `pnpm run test`（`scripts/__tests__/check-migration-checksums.test.mjs` が本物の `migrations/` を名簿に当てる）と、
     `ci.yml` の既存の `build` ジョブの1段（ジョブ名を変えない。required status check の文脈名のため）。
   - **赤にするもの**: 名簿に載っているファイルの**書き換え**・**削除**、名簿が無い・壊れている（exit 2。空として通さない）。
   - **赤にしないもの**: **新しい migration の追加**（新しい番号で直すのが正道なので、追加を拒む門は直し方と矛盾する）。
     改行（CRLF/CR）と先頭の BOM の違いだけ（正規化してから hash する。エディタや `core.autocrlf` で赤にならない）。
     空白・コメントの変更は**赤にする**（正規化は改行と BOM だけ）。
   - 名簿へ足すのは `--write`。**既存の行は書き換えない**（書き換えられたファイルがあれば、`--write` 自身が exit 1 で止まり、名簿を追従させない）。
2. **`0027` は編集していない。他の既存の migration も1本も触っていない**（名簿の作成時点の現物が名簿の値である）。
3. **`0027` の deadlock を、新しい番号の migration で直すことは、できないと判断し、直していない。**理由は次の構造による（推奨(b)の前提が成り立たない）。
   - 【現物】deadlock が起きるのは、**`0027` 自身が適用される瞬間**である（1トランザクションの中で複数の表に `CREATE INDEX` を撃ち、`ShareLock` を
     コミットまで持つ。ADR 0442）。
   - **`0027` がまだ当たっていない DB**: `0027` は番号順で `0033` 以降より**前**に走る。後ろの migration は、`0027` が走る瞬間に何もできない。
     `0027` の本文を変えない限り、`0027` の中の `CREATE INDEX` の順序・ロックは変わらない。
   - **既に `0027` を当てた DB**: すでに適用が終わっており、この deadlock は二度と起きない。後から足す migration が直すものが無い。
   - ⟹ 新しい番号の migration が効く DB は、**どちらの状態にも無い**。（論理の帰結であり、実 Postgres での再現・解消の測定はしていない。）
4. **だから、直し方は文書のまま止める。**ADR 0442 が書いた「アプリの書き込みを止めてから当てる」が、現時点で言える唯一の手当てである。
   この PR は、その文書の中身を書き換えていない。

## 検討した代替案

1. **`0027` を編集して、決まった順に `LOCK TABLE` する／分割する。**採らなかった。**既存の migration は編集しない**（推奨(b)・この PR の条件）。
   また、既に当てた DB には届かない（ADR 0442 代替案1）。⟹ この名簿の固定は、この編集を機械的に赤にする。
2. **`runMigrations`（runner）で、各ファイルの本文を流す前に、固定の順で関係する表を `LOCK TABLE` する。**
   既存の migration を編集せずに、未適用の DB の `0027` の deadlock を減らせる**可能性**がある。**この PR では実装も測定もしていない**:
   runner の動作が全 migration に対して変わり（ロックを取る表の選び方、`lock_timeout` との関係、`schema` オプションとの関係）、
   公開の挙動（利用者の稼働中のアプリを止める時間）に触れるので、推奨(b)（新しい migration で直す）の範囲を超える。
   オーナーの判断に回す（下の「残ること」）。
3. **アプリ側で `40P01` を受けて再試行する。**ADR 0442 が採らなかったまま。この PR でも触れていない。
4. **名簿に載っていない新しいファイルを、赤にする。**採らなかった。新しい migration を足す PR が、同時に名簿を更新することを強いる（追加を拒む門に近づく）。
   代わりに、名簿に無いファイルは「赤にはしないが知らせる」にした（下の「引き受けた負債」）。
5. **台帳 `_mnemora_migrations` に checksum の列を足し、`runMigrations` が実行時に突き合わせる。**採らなかった。
   スキーマと runner の変更になり、既に当てた DB の台帳の遡及（列を埋める元の値が DB に無い）が要る。この PR の範囲（CI の固定）を超える。

## 引き受けた負債

- **名簿に載せ忘れた新しいファイルは、固定されない。**`--write` で足すまでの間、そのファイルの編集は見えない。
  足すのは新しい migration を出す人の手順であり、機械は強制しない（`AGENTS.md`「機械には検出まで」と同じ線）。
- **正規化は改行と BOM だけである。**SQL として意味の無い変更（コメント・末尾の空白）も赤になる。偽陽性ではなく、**意図どおりの厳しさ**である
  （出荷済みのファイルを1文字も変えないのが規則）。ただし、末尾の空白を自動で直すエディタ設定は、赤にする。
- **`0027` の deadlock は、文書を読まずに稼働中のアプリへ当てた利用者には、今までどおり起こりうる**（ADR 0442 の負債のまま）。
- **名簿の値は、作成時点の `main` の現物から計算した。**その時点で既に書き換えられていた migration があっても、名簿はそれを正として固定する。
  出荷済みの内容との突き合わせ（`v1.2.0` などの tag の木との比較）は、この PR でしていない。

## これが覆るとしたら

- オーナーが、runner での固定順の `LOCK TABLE`（代替案2）、または `0027` の編集（出荷済みの扱いの方針変更）を決めたら、
  「直せない」の判断は、その決定に合わせて書き直すことになる。その場合、名簿の `0027` の行を更新する手順（名簿は人が意図して書き換える）も要る。
- `0027` 以外の migration（`0020`・`0032` など）が同じ形で deadlock すると測れたら、この ADR の文書の範囲は広げることになる（未測定のまま）。
