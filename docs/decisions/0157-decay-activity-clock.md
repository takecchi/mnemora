# ADR 0157: 減衰の時計を2本にする — 壁時計（`decay_floor_at`）に加えて活動時計（`decay_floor_seq`）を持ち、テナントが選ぶ

- **状態**: 採用 (2026-09)

- **文脈**:
  [Issue #305](https://github.com/takecchi/mnemora/issues/305) は、オーナー（takecchi）の
  次の指摘から立った（逐語）:

  > **日付をベースに減衰させてしまうと、記憶の使用頻度が低い(例えば1日1回しか記憶の出し入れが
  > ないような)場合にも一律で減衰してしまうのかなと心配してました。**

  そして issue が (a) 既定値の指針 / (b) 相対的な尺度の導入 / (c) 何もしない、の3案を並べたのに対し、
  オーナーは**設計の見直しそのものを指示した**（逐語）:

  > 「絶対時間のままだと、低頻度の採用者で一律に沈む」のは問題なので**場合によっては
  > 設計の見直しもお願いします。早速修正改修に取り掛かってください**

  > **どっちもあっていいと思います。時間減衰とそうじゃないもの**

  ⟹ **「どちらか一方を選ぶ」はオーナーの回答と食い違う。2本を共存させることが前提である。**

  ### 現状の時計は、すでに「純粋な時間減衰」ではない

  **この ADR に入る前に、いま在るものを正確に見ておく。**
  `docs/memory-model.md` §3 は逐語でこう書いている（`docs/memory-model.md:90`）:

  > **鮮度スコアは `occurred_at ?? recorded_at` を使う。減衰は `last_reinforced_at` を使う。**

  ⟹ 現行の減衰は「**起点は使用イベント**（最後に強化された時刻）、**進み方は壁時計の秒**」
  というハイブリッドである。**だから「時間減衰 vs そうじゃないもの」を「起点が時刻か否か」と
  読むと、差分がどこにあるのか見えなくなる。** 本 ADR が変えるのは**起点ではなく、進み方の単位**
  である——起点は両方の時計で同じく「最後の書き込み（作成・強化）」に置く。

  | | 起点（base） | 進み方（1単位） | 保存する床 |
  |---|---|---|---|
  | 壁時計（既存） | `last_reinforced_at ?? recorded_at` | 1時間 | `decay_floor_at timestamptz` |
  | 活動時計（本 ADR） | 同じ書き込み時点の `activity_seq` | そのテナントで `recall()` が1回起きること | `decay_floor_seq bigint` |

  ### 単調性は「数えること」では壊れない（Issue #305 が名指しした懸念の反証）

  Issue #305 は「⚠ (b) を採るなら、先に確かめること」として、**回数ベースにすると
  `decay_floor_at` の単調性（`docs/memory-model.md:318`「この値は時間の経過そのものでは
  変化しない——**単調**である」）が崩れる可能性がある**と書いた。マネージャー側も
  「他の記憶の書き込みが自分の減衰を進めるので、全行の再計算が要る」と予想していた。

  **現物を読むと、この懸念は成り立たない。** 段1のゲートの実体は
  `packages/postgres/src/vector-store.ts:72-73` で、

  ```ts
  if (opts.filter.decayFloorAtAfter !== undefined) {
    conditions.push(sql`m.decay_floor_at > ${opts.filter.decayFloorAtAfter}`);
  }
  ```

  ——**`now()` ですらなく、呼び出し側が渡すパラメータ**である。この形には性質が2つ
  **別々に**働いている:

  - **(P1) 保存側（`stored_column`）は、その行に何も起きていないのに書き換わってはならない。**
    これが `docs/memory-model.md:318` が「単調」と呼んでいるものであり、cron による全件
    `UPDATE` を不要にしている前提そのものである。
  - **(P2) 動く側（比較の右辺）は、行を走査せずに取れるスカラでなければならない。**
    `now()` はこれを満たす。

  「他の記憶の書き込みが自分の減衰を進める」は**(P2) 側の性質**であって、「時間が経てば
  全員の減衰が進む」と**まったく同じ構造**である——**どちらも保存列には触れない。**
  §7 が段1に課している条件も逐語で「**等値または単調な範囲比較で表現できるフィルタ**」
  （`docs/memory-model.md:333`）であり、**右辺が `now()` であることは条件に入っていない。**

  ⟹ **壊れるのは「数えること」ではなく、「カウンタを行ごとに持つこと」**である
  （`memories.times_passed_over` のような列を recall のたびに全該当行で increment する形）。
  **カウンタを「テナントごとに1行」にすれば (P1) は保たれる。** 本 ADR はその形を採る。

  ### なぜ「別の列」なのか — `decay_floor_at` を可変速の時刻にしない

  「活動量に応じて速さの変わる時刻」を `decay_floor_at`（`timestamptz`）1本で表す案は
  検討して落とした（下記「検討した代替案」3）。**書き込み時に閉じた形で未来の *時刻* を
  出すには、将来の活動量を予言しなければならない。** 予言できない以上、その案は
  §7 の「書き込み時に一度だけ計算する」を満たせない。**単位の違う床を、単位の違う列に
  持てばよい**——`bigint` の通し番号なら、書き込み時に閉じた形で出せる。

- **北極星の5つの問いに実際に当てた結果**（`docs/north-star.md`「迷ったときの問い」。
  各問いが実際に何を落としたかを記録する——問いは書いた時点では飾りと区別が付かない、
  という同文書の戒めに従う）:

  | 問い | この判断にどう当たったか | 落ちた案 |
  |---|---|---|
  | **1**（毎回渡す量を減らす方向に働くか） | **この機能の存在理由がここにある。** 低頻度のテナントでは、壁時計の床が全記憶を段1から落としきる時点が来る。そのとき `recall()` は空を返し、**呼び出し側は「会話ログを全部積む」へ戻る**——物差し（`north-star.md:45`）が逆行する。活動時計は「そのテナントで実際に何回素通りされたか」で床を決めるので、活動が無いテナントでは床が進まない。 | **既定を `'either'` / `'activity'` に変える案。** この問いは「増やすなら、その分だけ想起が良くなると言えるか」と聞いている。**言えるだけの数字を1つも持っていない**（実運用で何日で沈むかを測っていない）。⟹ 既定は `'wall'` 据え置き。<br>**`'either'` を全テナントに固定で適用する案**も同じ理由で落ちる——OR は寿命を延ばす方向にしか効かず、「念のため古いものも残す」そのものである。 |
  | **2**（これを無効にしたとき、Memory Framework として成立するか） | **既定が `'wall'` なので、この機能は最初から「無効」の状態で出荷される。** `decay_clock` を一度も設定しないテナントの挙動は、本 ADR の前後でビット単位で同じである（活動カウンタの `UPDATE` も走らない。下記「決めたこと」5）。 | **活動カウンタを常時進める案**——既定のテナントにまで recall ごとの `UPDATE` を負わせる。「これが無いと動かない」を増やさないという問いに、正面から反する。 |
  | **3**（選ばれた理由を、後から説明できるか） | どちらの時計でゲートが効いたかを `explain.stages` の `detail.decayGate` に出す（ADR 0153 が既に `decayGate` を出しており、そこに `clock` を足す）。**「沈まなかった理由」が2本になった以上、どちらで生き残ったのかを言えなければ説明可能性が落ちる。** | **列だけ足して `explain` に出さない案。** ADR 0153 が「黙って減らす案」を落としたのと同じ形で落とす。 |
  | **4**（AI の推論と、ユーザーが言った事実を区別しているか） | 活動時計は `provenance.kind` に触れない。無関係。 | 落ちる案なし——この問いはこの判断を規定しない。 |
  | **5**（LLM を呼ばずに済ませられないか） | **済む。** 床は `base_seq + half_life_recalls * log2(strength / threshold)` という、壁時計と**まったく同じ式**の別単位での実例である（`packages/core/src/strategies/decay.ts:53-55`）。段1の述語は `decay_floor_seq > $n` という、列と索引だけの範囲比較。 | **「会話の活性度」「話題の盛り上がり」のような量を LLM やヒューリスティックで判定する案。** この問いで即座に落ちる。⟹ **活動 = 「そのテナントで `recall()` が起きた回数」という、数えられるものだけに絞った。** |

- **決めたこと**:

  1. **`tenant_settings.decay_clock` を足す。値は `'wall'` / `'activity'` / `'either'` の3つ。
     既定は `'wall'`（＝本 ADR の前と同じ挙動）。**
     - `'wall'`: 段1のゲートは `decay_floor_at > now()` のみ（現行）。
     - `'activity'`: 段1のゲートは `decay_floor_seq > <そのテナントの activity_seq>` のみ。
     - `'either'`: どちらかが生きていれば通す（OR）。**最も緩い。**
     - `tenant_settings` に行が無いテナントは `'wall'` として動く（`DEFAULT_HALF_LIFE_HOURS` と
       同じ扱い。`docs/memory-model.md:556-561` が定める「行が無いテナントはコード中の定数で動く」）。

  2. **活動カウンタは「テナントごとに1行」の専用テーブル `tenant_activity` に置く。**

     ```sql
     CREATE TABLE tenant_activity (
       tenant_id    text   PRIMARY KEY,
       activity_seq bigint NOT NULL DEFAULT 0,
       updated_at   timestamptz NOT NULL DEFAULT now()
     );
     ```

     **`tenant_settings` の行に相乗りさせない。** `tenant_settings` は読み出しの多い設定行
     であり、そこを recall ごとに `UPDATE` する行にすると、**設定の読み出しまでカウンタの
     行ロックで待たされる。** 分けるのは正しさのためではなく、混ぜたときに払う待ちを
     避けるためである。

  3. **`memories` に3列を足す。壁時計の3つ組と1対1に対応させる。**

     ```sql
     ALTER TABLE memories ADD COLUMN decay_base_seq    bigint NULL;  -- 起点（書き込み時の activity_seq）
     ALTER TABLE memories ADD COLUMN decay_floor_seq   bigint NULL;  -- 床（書き込み時に一度だけ計算）
     ALTER TABLE memories ADD COLUMN half_life_recalls real   NULL;  -- Memory 単位の半減期（単位: recall 回数）
     ```

     **`half_life_recalls` を Memory 単位の列にするのは、`half_life_hours` がそうである
     のと同じ理由である**（`docs/memory-model.md:377-383`）——テナント設定を後から変えたときに
     既存行の床を全件再計算しなくて済むようにするため。**`tenant_settings.default_half_life_recalls`
     は新規作成時の初期値としてのみ使う。**

     **`decay_base_seq` も保存する。** 段2の再スコア（`strategies/scoring.ts:182`）が
     `strengthAt` を呼ぶのに起点が要るからである。床から逆算することも代数的には可能だが
     （`strength = threshold * 2^((floor - seq)/halfLife)`）、`strength <= threshold` の
     分岐で成り立たなくなる。**壁時計が起点を別に持っている（`last_reinforced_at`）のと
     同じ形に揃えるほうが、分岐を1つ減らせる。**

  4. **`NULL` は「この軸には床が無い＝活動時計では沈まない」を意味する。**
     段1の述語は `'activity'` のとき `(m.decay_floor_seq IS NULL OR m.decay_floor_seq > $n)` と書く。
     - **`NOT NULL` + マイグレーション時の全件 `UPDATE` は採らない。** 既存テーブルへの
       一括更新は、まさに §7 が避けようとしている形である。
     - **緩い側（沈まない）へ倒すのは意図的である。** ADR 0153 が「黙って減らさない」を
       選んだのと同じ向き——**列を足しただけで、今日返っていたものが明日返らなくなることが
       あってはならない。**

  5. **`activity_seq` を進めるのは、`decay_clock != 'wall'` のテナントに限る。**
     `createRecall`（`packages/postgres/src/memory-store.ts` の recall 記録）と同一トランザクション
     で `+1` する。**既定（`'wall'`）のテナントでは `UPDATE` が1本も増えない。**
     - ⟹ `'wall'` のテナントの `activity_seq` は 0 のまま。そのテナントで作られた Memory の
       `decay_base_seq` も 0 になる。**後から `'activity'` へ切り替えると、切り替え時点から
       減衰が始まる**——これは望ましい挙動であり、欠陥ではない。
     - **「活動時計は、テナントがそれを使うと決めるまで動かない」**——これが本 ADR の
       意味論である。

  6. **「1単位」は `recall()` 1回とする。`observe()` は数えない。**
     活動時計が測っているのは「**この記憶が、想起される機会を何回見送られたか**」である。
     recall は機会であり、observe は機会ではない。
     - ⟹ **一度も recall しないテナントでは、活動時計は1つも進まない。** 書き込みだけ
       しているテナントで記憶が際限なく生き残ることになるが、**そのテナントはそもそも
       何も想起していないので、「使われない記憶が遠ざかる」（`north-star.md:31`）の
       「使われない」という語が測る対象が存在しない。**
     - ⚠ **ここは製品の性格を決める判断であり、オーナーが逐語で指定した範囲の外にある。**
       オーナーの「時間減衰とそうじゃないもの」は2本の共存を承認したものであって、
       「そうじゃないもの」の中身までは指定していない。**覆るとしたら、ここが最初である**
       （下記「これが覆るとしたら」1）。

  7. **純関数は1つのまま。単位を引数にした2つの実例にする。**
     `defaultDecayStrategy.floorAt` の実体（`packages/core/src/strategies/decay.ts:53-55`）は

     ```
     floor = base + halfLife * log2(strength / threshold)
     ```

     であり、`base`・`halfLife` の**単位**が「時刻・時間」か「通し番号・回数」かが違うだけで
     **式はまったく同じ**である。⟹ 単位を持たない数値核（`decayOffset` / `decayFactor`）を
     切り出し、`floorAt`（Date を返す）と `floorSeqAt`（bigint を返す）はその薄い包みにする。
     **ADR 0010 が固定した式そのものは動かさない。** 動かすのは「その式を何の単位で
     読むか」だけである。

  8. **索引は壁時計と同じ形（partial 述語は離散値、連続値は末尾の列）で2本目を足す。**

     ```sql
     CREATE INDEX idx_memories_recall_gate_seq
       ON memories (tenant_id, status, decay_floor_seq)
       WHERE status IN ('active', 'contested');
     ```

     `docs/memory-model.md:358-370` が定める形をそのまま踏襲する。

  9. **索引の歯は「プランナが選んだか」ではなく「性質」を assert する。**
     `packages/postgres/src/__tests__/recall-gate-index.test.ts` が Issue #150 で
     書き直した3本の歯（**形** / **適用可能性** / **同値**）と同じ形を、2本目の索引にも置く。
     - ⚠ **`'either'`（OR）については、「1本の btree で範囲スキャンできる」とは主張しない。**
       そこで assert するのは**同値**（自然な計画・索引を強制した計画・全走査を強制した計画が
       同じ行を返すこと）だけである。**プランナが何を選ぶかは、他にどんな索引が在るかに
       依存する**——同ファイルが 2026-09-10 の CI 失敗から学んだ教訓そのものである。

  10. **既定を `'wall'` から動かす条件を、測る *前* に、ここに固定する。**
      **⛔ 出た数字に合わせてこの基準を書き換えないこと。** 書き換えるなら、
      「書き換えた」と本 ADR の改訂として明記すること。**後から決めた基準は、基準ではない。**

      次の3つが**同時に**満たされたときに限り、既定の変更を（オーナーへの提起として）持ち出す:

      1. **`reinforce` を呼ぶ本番経路が入っている**（Issue #204 系）。
         「使われれば時計が戻る」が動いていない状態では、**どちらの時計でも一律に沈む**
         ——既定を動かしても何も救わない。
      2. **1日あたりの `recall()` が10回未満のテナントを模した実測で、`'wall'` の既定
         （`half_life_hours = 720`）だと、想起できるべき記憶が段1のゲートで
         **90日以内に**落ちることが示されている。**
         （`720時間 = 30日` の半減期・閾値 `0.05` なので、強化が一度も起きなければ
         床は `30日 × log2(1/0.05) ≈ 129.7日` で来る。**⟹ 90日という線は
         「床が来るより前に、実用上の取りこぼしが観測できるか」を聞いている。**）
      3. **段1の EXPLAIN が、2列目を足した後も `'wall'` のときと同じプラン族を選ぶことが
         CI で確認されている。** これは ADR 0153 が自分で「未実測」と書いた点
         （`0153:296-301`）であり、**2列目を足すなら、ここは塞いでから既定を動かす。**

  11. **`examples/chat` が実際に `decay_clock` を設定して使う。**
      **設定項目を足して終わりにしない。** 北極星は「外から見てどう現れるか」で書かれており
      （`north-star.md:20`）、**誰も設定しない設定は「在る」と数えられない。**
      `examples/chat` に `--decay-clock` を通し、`compare` / `archive-sweep` の経路で
      実際にテナント設定へ書く。

  12. **時計は段1のゲートだけでなく、「減衰が読まれる場所」すべてに掛かる。**
      現物には減衰の読み出し点が**3つ**ある。**1つだけ直すと、掃引とゲートは活動量で
      判定するのに順位付けは壁時計のまま、という一貫性の無い実装になる。**

      | 場所 | 何をしているか | 活動時計での姿 |
      |---|---|---|
      | `packages/postgres/src/vector-store.ts:72-73` | 段1の SQL ゲート（ANN チャンネル） | `decay_floor_seq > $n` を足す |
      | `packages/core/src/recall-runtime.ts`（全チャンネル共通の後置フィルタ） | **語彙チャンネルには SQL ゲートが無いため**、core 側で `memory.decayFloorAt > now` を掛け直している | 同じ場所で `decayFloorSeq > nowSeq` も掛ける |
      | `packages/core/src/strategies/scoring.ts:182,191` | 段2の再スコア係数 `decay`（`strengthAt`） | `decay_base_seq` と `activity_seq` から同じ式で出す |

      ⟹ **`decay_base_seq` を保存する理由がここにある**（「決めたこと」3）。段2は床ではなく
      **いまの強度**を要求するので、起点が要る。

  13. **`TenantSettingsStore`（`@mnemora/core`）に、読み書きの口を明示的に足す。**
      この repo には前例が2つあり、**自動的には決まらない**:
      - `taxonomy_mode`: 列は在るが interface に出していない（オーナーが「必須」と決めたのは
        保持期間だけだから）
      - `event_retention_days`: 専用メソッド `getEventRetention`/`setEventRetention` を足した（ADR 0050）

      **後者を採る。** 理由は「決めたこと」11——**`examples/chat` が実際に設定できなければ、
      この機能は「在る」と数えられない。** 書き込みの口が無いまま列だけ足すと、
      `examples/chat/src/archive-sweep-cost.ts:80-113` が `default_half_life_hours` に対して
      既にやっている「**公開 interface を迂回して生 SQL で UPSERT する**」を、もう1つ
      増やすことになる。⟹ 足すのは `getDecayClock` / `setDecayClock` /
      `getDefaultHalfLifeRecalls` / `getActivitySeq`（**読むだけ**）。

      ⚠ **カウンタを進める口（`bumpActivitySeq`）は、ここに置けない。**
      本 ADR の初版はここに置くと書いていたが、それは「決めたこと」5（`activity_seq` の前進は
      `createRecall` と**同一トランザクション**）と矛盾する——**`MemoryStore` と
      `TenantSettingsStore` は別 adapter であり、トランザクションを跨げない。**
      ⟹ **5 のほうが正しい。** 前進は `MemoryStore.createRecall` の入力
      （`NewRecallRecord.advanceActivityClock?: boolean`）として渡し、adapter が
      `recalls` への INSERT と同じトランザクションで両方を書く。
      **（2026-09-16、実装中に発見して訂正した。）**

      なお `createRecall` の戻り値を `{ recallId, activitySeq }` へ広げる案は採らない
      ——`@mnemora/core` は npm 公開済みであり、破壊的変更になる。

  14. **境界の非対称を、1バイトも変えずに踏襲する。**
      現物はゲートが**狭義**（`decay_floor_at > $n`、境界は落ちる）、掃引が**境界を含む**
      （`decay_floor_at <= opts.now`）——**これは意図的な非対称だと doc に明記されている。**
      ⟹ `decay_floor_seq` 側も `> $n` と `<= $n` をそのまま写す。**片方だけ `>=` にする
      ミスは、境界1件のズレとして歯に出ないまま紛れ込む。**適合テストの境界の歯を
      seq 側にも同じ形で置く。

  15. **`archiveDecayed` は「いまの `activity_seq`」を呼び出し側から受け取る。**
      `ArchiveDecayedOptions.now: Date` が呼び出し側から渡される規律（ADR 0037「時刻は
      呼び出し側が渡す」）と同じ形で `nowSeq` を受け取る。**store が自分で
      `tenant_activity` を読みに行かない。**

- **検討した代替案（落とした案）**:

  1. **`'either'` を全テナントに固定で適用する（設定項目を作らない）。**
     ⛔ **落とした。** OR は「どちらかが生きていれば通す」なので、**寿命を延ばす方向にしか
     効かない。** 多忙なテナントで1万回素通りされた記憶を沈めることができず、
     `north-star.md:31`「使われない記憶が、静かに遠ざかる」を正面から弱める。
     **一方向にしか効かない忘却は、忘却ではない。**

  2. **既定を `'either'` にする。**
     ⛔ **落とした。** 「実運用で何日で沈むか」の数字を1つも持っていないのに既定を動かす
     ことになる。北極星の問い1（増やすなら、その分だけ想起が良くなると言えるか）に
     答えられない。⟹ 上記「決めたこと」10 の条件が揃うまで据え置く。

  3. **`decay_floor_at`（`timestamptz`）1本のまま、「活動量に応じて速さの変わる時刻」にする。**
     ⛔ **落とした。** 書き込み時に閉じた形で未来の *時刻* を出すには、**将来の活動量を
     予言する**必要がある。予言できない以上、`docs/memory-model.md:317-318` の
     「書き込み時（作成時・強化時）に一度だけ計算して列に持つ」を満たせず、
     全件再計算か定期走査に落ちる。**§7 のアーキテクチャそのものと衝突する。**

  4. **`memories` に `times_passed_over` のようなカウンタ列を持ち、recall のたびに
     候補行を increment する。**
     ⛔ **落とした。** これは (P1) を破る——**その行に何も起きていないのに保存列が
     書き換わる。** Issue #305 が心配した「単調性が崩れる」は、まさにこの形でだけ起きる。
     **カウンタをテナントごとに1行にすれば避けられる**（「決めたこと」2）。

  5. **`observe()` も活動として数える。**
     ⛔ **落とした（ただし覆りうる。「これが覆るとしたら」1）。** 活動時計が測るのは
     「想起される機会を見送られた回数」であり、書き込みは機会ではない。混ぜると、
     大量取り込みをしただけで既存の記憶が沈むことになる——それは「使われない」ではなく
     「新しいものが来た」を測っている。

  6. **`memories` にも `decay_clock` 列を持たせ、Memory 単位で時計を選べるようにする。**
     ⛔ **落とした。** `half_life_hours` が Memory 単位なのは**後から変えると全件再計算に
     なるから**であって（`docs/memory-model.md:377`）、`decay_clock` にその問題は無い
     ——**両方の床を常に保存しているので、時計の選択は読み取り時の方針にすぎず、
     切り替えても再計算が1行も発生しない。** 再計算の危険が無いものに Memory 単位の列を
     足すのは、理由の無い列である。

  7. **`LexicalStore` 側にも活動ゲートを足す。**
     ⛔ **落とした（範囲外）。** `LexicalFilter` は `decayFloorAtAfter` を**そもそも持って
     いない**（`packages/postgres/src/lexical-store.ts:29`、ADR 0153 が既に引き受けた非対称）。
     **本 ADR はこの非対称を広げも狭めもしない。** 壁時計で解いていない非対称を、
     活動時計のついでに解こうとすると、2つの判断が1つの PR で混ざる。

- **引き受けた負債**:

  1. **`decay_clock != 'wall'` のテナントでは、`tenant_activity` の1行が
     recall ごとのホット行になる。** 同一テナントの recall がその行で直列化する。
     **正しさの問題ではなく、処理量の問題である。**⟹ 測れる。既定のテナントには
     掛からない（「決めたこと」5）が、**opt-in したテナントがどこまで捌けるかは測っていない。**
  2. **段1のゲートが列2本になった。** `'either'` の OR は1本の btree では範囲スキャン
     できない。プランナは BitmapOr を選ぶかもしれないし、片方の索引 + フィルタを選ぶかも
     しれない。**どちらでも行の集合は同じである**（「決めたこと」9 の歯3が固定する）が、
     **`'either'` の段1が `'wall'` と同じ速さで済むとは主張しない。**
  3. **`archiveDecayed` の掃引が2軸になった**（ADR 0114）。`'activity'` / `'either'` の
     テナントでは、時刻の範囲走査だけでは沈んだ記憶を拾いきれない。
  4. **`memories` に列が3本増えた。** うち `decay_base_seq` は段2でしか読まれない。
  5. **`'wall'` のまま運用してきたテナントが `'activity'` へ切り替えると、既存の記憶の
     `decay_base_seq` は 0 であり、`decay_floor_seq` は `half_life_recalls` に応じた
     小さな値になる。**⟹ 切り替え直後に、その値を超えるだけの recall が起きた時点で
     まとめて沈みうる。**この段差を滑らかにする移行（切り替え時に `decay_base_seq` を
     現在の `activity_seq` へ寄せる）は、本 ADR では実装しない。**

  6. **既存の索引テスト2本（`recall-gate-index.test.ts` / `archive-decayed-index.test.ts`）は、
     強制プラン下の EXPLAIN 出力に `idx_memories_recall_gate` という**文字列が現れること**を
     assert している箇所を持つ。** 索引が1本増えると、プランナは実装が正しいまま別の索引を
     選びうる——**まさに `recall-gate-index.test.ts` が 2026-09-10 の CI 失敗から学んだ形
     （`idx_memories_lexical` が足された8時間後に赤くなった）である。** 本 ADR の実装で
     これらが赤くなったら、**赤くなったのは実装ではなく歯のほうだと疑う**こと。

- **これが覆るとしたら**:

  1. **「1単位 = recall 1回」が実運用に合わないと分かったとき**（「決めたこと」6）。
     ⟹ `observe()` を数える、`subject` 単位で数える、といった変種へ動く。
     **これはオーナーの判断を要する種類の分岐である**（`docs/autonomy.md` §3.1 の
     「どちらを選んでも技術的には成立するが、選び方が製品の性格を決める」に当たる）。
  2. **`'either'` を使うテナントが現れず、3値が2値でよかったと分かったとき。**
     ⟹ `'either'` を落とす（値を減らすのは破壊的変更なので、ADR と提起が要る）。
  3. **ホット行（負債1）が実測で問題になったとき。** ⟹ カウンタを「概算でよい」ものに
     緩める（例: `n` 回に1回だけ進める）か、`recalls` テーブルから導出する形へ動く。
  4. **「決めたこと」10 の3条件が揃ったとき。** ⟹ 既定の変更をオーナーへ提起する。
     **こちらで既定を動かさない。**

- **確かめていないこと**:

  - **実運用の数字は無い。** 「1日1回の採用側で実際に何日で沈むか」は測っていない。
    Issue #305 が最初にそう書いており、本 ADR でもそれは変わっていない。
    ⟹ **だから既定を動かしていない。**
  - **この ADR を書いた器には Postgres が無い。** 段1の EXPLAIN・索引の適用可能性・
    ホット行の待ち時間は、**すべて CI の実測に委ねている。** ADR 0153 と同じ制約である。
  - **`reinforce` を呼ぶ本番経路がまだ無い**（Issue #305 が `#284` の実測から引いた事実）。
    ⟹ **どちらの時計でも「使われれば戻る」は現時点で動いていない。** 本 ADR は
    その穴を塞がない——塞ぐのは Issue #204 系である。
  - **`compare-baseline.json`（ADR 0133 の門）が動かないことは、既定が `'wall'` で
    あることから予想はできるが、実測は CI に委ねている。**

- **出所について**:

  - **3値にすること・既定を `'wall'` に据え置くこと・活動の1単位を `recall` 1回にすること・
