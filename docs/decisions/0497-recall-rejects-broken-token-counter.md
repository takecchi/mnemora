# ADR 0497: 差し替えた `TokenCounter` が有限で 0 以上でない `tokens` を返したら、`recall()` は `RangeError` で断る（ADR 0483 の材料を直す）

- **状態**: 採用 (2026-10)
- **日付**: 2026-10-02

クローン miku の決定。担い手が書いた。オーナーではない（ADR 0220）。ADR 0483 が「材料（直していない）」に回した「壊れた値を返す counter で `recall()` を例外にする直し」を直す。

出所の区別: 【現物】は読んだコード・文書、【実測】は手元で走らせた結果、【判断】は担い手とクローンの判定、【未確認】は確かめていないこと。

- **なぜクローンが決めてよいか**【判断】: オーナーが v1.X.0 で破壊的変更を許した。ADR 0483 がこの直しを「材料」に回したのは、新しく断る入力を増やす（= 当時は破壊的変更で、ADR 0098 の既定を投げにしない決定と食い違うように見えた）ためだった。その前提が変わったので、クローンが決める。

- **文脈**【現物】: 利用者が `RuntimeDeps.tokenCounter` に渡す `TokenCounter`（既定は `heuristicTokenCounter`）は、段4の予算（`findBudgetCut`、`recall-budget-cut.ts`）、予算で落としたときの連結の測り直し（`recall-runtime.ts` 2468 行付近、Issue #829）、`usage` の計測（同 3281 行付近）の3か所から呼ばれる。ADR 0483 の実測のとおり、`tokens` が `NaN`・負の数だと予算が黙って外れて全件が返り（`budget_dropped` も出ない）、`Infinity` だと全件が落ち、`outputValidation: "off"` では何も知らされない。ADR 0483 の記述は現物と一致していた（食い違いは無かった）。

- **決めたこと**【判断】:
  1. `recall()` は、`deps.tokenCounter` を1回の呼び出しの頭で `checkedTokenCounter`（`recall-budget-cut.ts`、`index.ts` からは出さない内部の関数）で包み、`count()` の戻りごとに `tokens` が **有限で 0 以上の number** かを確かめる。違えば `RangeError`。対象は `NaN`・負の数・`Infinity`・`-Infinity`・number でない値（文字列・`null`）・`tokens` の欄が無い戻り値・戻り値そのものが `undefined`/`null`。
  2. message は `recall: tokenCounter.count() must return { tokens } as a finite number >= 0, got <種類>` で、種類は `NaN`・`Infinity`・`-Infinity`・`a negative number`・`a non-number (typeof)` のどれか。**入力テキストは入れない**。負の数の値そのものも入れない（種類だけ）。
  3. **検査の位置**: 3か所の呼び出しを個別に直さず、`count()` の戻りを包む1か所に置く。壊れた値は包みの中で投げられるので、`findBudgetCut`・測り直し・`usage` の計測は壊れた値を一度も見ない。**最初の壊れた値で止まる**（歯が呼び出し回数で縛る）。検査は `typeof` と数値比較だけで、文字列を走査・割り当てしない。
  4. **`count()` が投げた例外は、包まずそのまま素通し**。【現物】この repo の provider の例外の作法は、`tick()` の embed ジョブが embedding provider の例外を `describeFailure` で記録しつつ **元の例外をそのまま投げ直す**（`runtime.ts` 5975 行付近。`cause` に包むのは「失敗の記録の書き込みも失敗した」という別の例外を足すときだけ）形で、counter の例外はこれまでも素通しで、ADR 0483 の表もそうだった。素通しなら、呼び出し側が自分の例外の型で捕まえられ、挙動も変わらない（この直しが新しく断るのは壊れた**値**だけで、例外の扱いは変えない）。
  5. **小数（`0.5`）は通す**。`TokenCounter` の doc は「整数」と書くが、有限で 0 以上なら足し算も予算の比較も成り立つ。整数まで要求すると、実測トークナイザの割り算の結果などを返している利用者を、害がないのに断ることになる。小数が `usage.estimatedTokens` の `int()` を破ることは `outputValidation` が従来どおり知らせる（ADR 0483 のまま）。`0` も通す（空文字の既定の答え）。
  6. **`counter` の欄（`"heuristic" | "exact"`）は検査しない**。欠落・範囲外は従来どおり `usage.counter` に素通しして `outputValidation` が知らせる。ADR 0487 の「名乗りの規則をどう守らせるか」の材料と同じ問いであり、`counter` の誤りは予算の判定を外さないので、この直しの範囲に入れない。
  7. **既定の挙動は変えない**。`heuristicTokenCounter` は常に有限な 0 以上の整数を返す（ADR 0483 の実測。空文字 0・孤立サロゲート・結合文字・100万文字）。歯が、空・CJK・絵文字・孤立サロゲート・結合文字・長い digest を含む記憶で、既定の counter が予算ありの recall を通ることを確かめる。

- **ADR 0098 との関係**【判断】: ADR 0098 が決めたのは、`recall()` の**出力**の検査（`RecallResultSchema`）の既定を `"report"`（投げない）にすることである。理由は「既定を投げにすると、いままで動いていた呼び出しが例外になる」ことと、`docs/autonomy.md` が破壊的変更をオーナーの領分としていたこと。この ADR が断るのは、**利用者が渡した構成値（counter）が約束を破っていること**であり、別の軸である。(a) 出力の検査は、mnemora 自身が作った結果が約束を破ったことを呼び手に知らせる仕組みで、「壊れた出力でも受け取って自分で判断する」選択肢が意味を持つ。構成値の誤りは、呼び手が直せる原因（自分の counter）が `recall()` の前にあり、**壊れた構成値で動き続けても、返る結果そのもの（全件・0件）が黙って別物になる**（北極星・原則の姿3「黙って落とさない」）。(b) 既定を `"report"` にした理由だった「いままで動いていたものが例外になる」は、オーナーが v1.X.0 で破壊的変更を許したことで、この種の直し（壊れた構成値を新しく断る）については使えなくなった。(c) だから `outputValidation` の既定（`"report"`）は変えず、`"off"` でも断る。**これが覆る条件**: オーナーが「構成値の検査も `outputValidation` の三値（off/report/throw）で呼び手に選ばせる」と決めたとき、または、壊れた counter を返す実装が実際の利用者に広く在り、断ることで report で受け取りたい人まで巻き込むと分かったとき（その場合は、断る代わりに `RecallResult` に構成値の問題の欄を足す案——公開の型の変更でオーナーの領分——に切り替える）。

- **採らなかった案**:
  - **`outputValidation` のモードに従う（`"report"` では `outputValidation.issues` に載せ、`"throw"` で断る）**: 壊れた値のまま `usage` と予算の判定が走ってしまい、予算が外れた結果が返る。結果が別物になることを、受け取る側の選択にしてしまう。また `"off"` では無音のままで、この ADR が直したい形がそのまま残る。
  - **壊れた値を既定の `heuristicTokenCounter` の値に落とす（フォールバック）**: 黙って別の値で数える。`counter: "exact"` の名乗りと実際の数え方が食い違い、ADR 0487 の「推定を実測の顔で返さない」に反する。
  - **壊れた値を 0 や上限へ丸める**: 予算を黙って外す・全件を落とすのと同じ種類の、別の無音である。
  - **3か所の呼び出しの手前それぞれで検査する**: 検査の漏れが出やすい（3つ目の呼び出しだけ忘れる）。包みなら、新しい呼び出し元が増えても同じ検査を通る。
  - **整数でなければ断る**: 小数を返す利用者を、害のないまま断る（決めたこと5）。
  - **新しい例外クラスを作る**: 公開 API の追加で、オーナーの領分。素の `RangeError` を使った（入力値は入れない）。
  - **`findBudgetCut` の「負・NaN のときは線形に探す」分岐を消す**: `recall()` からは届かなくなったが、`findBudgetCut` を直接呼ぶ歯（ADR 0431 の旧実装との一致）がまだ縛っている。消すのは別の掃除。

- **引き受けた負債**:
  - `recall()` 1回ごとに包み（オブジェクト1つ・クロージャ1つ）と、`count()` 1回ごとに戻りの検査が増える。【実測】下の「測ったこと」。
  - 壊れた counter は、`recall()` が最初に `count()` を呼ぶ地点（段4、または `usage` の計測）まで断られない。**検索（段1〜3）の store・embedding の呼び出しは、断る前に行われる**。入口で `count("")` を試して先に断る案は、利用者の counter を余分に1回呼ぶことになる（副作用・コスト）ので採らなかった。
  - `counter` の欄・ADR 0487 の名乗りの食い違い・`heuristicTokenCounter` の CJK 範囲（ADR 0483 の材料2・3）は、直していない。
  - `findBudgetCut` の線形探索の分岐は、`recall()` からは死んだコードになった（上）。

- **これが覆るとしたら**: 上の ADR 0098 との関係の節の条件。加えて、`count()` が一時的に壊れた値を返すことがある実測トークナイザ（外部サービスの一時的な失敗など）を、**投げずに NaN で返す**作法の利用者が多いと分かったとき。その場合は、断る前に counter を1回だけ再試行する、または利用者が壊れた値の扱いを選べる設定（公開 API の追加）を、オーナーに提起する。

- **測ったこと**【実測】:
  - **歯**（`recall-pipeline.test.ts`「TokenCounter が約束を破る値を返したとき（ADR 0497）」）: 直す前は赤、直した後は緑。直す前の赤は 14 本（`NaN`・負の数・`-Infinity`・`Infinity` の4本、壊れた戻り値5本、message、最初で止まる、2件目以降、`usage` だけが壊れる、測り直し）。陽性対照・例外の素通し・0 と大きな有限値・小数 0.5・既定の counter・`counter` の欄は直す前から緑（直す前の振る舞いのままでよいもの。小数 0.5 は最初の実測で赤だったが、それは `setup-recall-output-contract.ts` の一覧に載せ忘れていた別の理由で、一覧に足して直した）。
  - **変異**: (a) `NaN` を見逃す実装は5本が赤、`Infinity` を見逃す実装は1本、負の数を見逃す実装は3本、最初の1回だけ検査する実装は3本、壊れた値を遅れて投げる実装は14本が赤。(b) 整数でなければ断る実装は小数の1本、0 を断る実装は 0 と既定の counter の2本、例外を包む実装は例外の素通しの1本、message に入力テキストを入れる実装は message の1本が赤。戻して緑。
  - **性能**: `findBudgetCut` を 4000 単位（各 約100文字、日本語・英語混在）・既定の counter で20回回した中央値（31回）の、包みなし／包みありの比。包みなし 約116〜119 ms、包みあり 約123〜135 ms（交互に5組。約 +5〜10%）。`count()` 1回あたり約0.1 µs の増え（80000回の呼び出しで約 6〜8 ms）。**counter の呼び出しだけを測った下限に近い比較であり、recall 全体（store・embedding の往復）の中では無視できる**が、全体の recall では測っていない。
  - 関連の既存の歯（`recall-budget-cut.test.ts`・`heuristic-token-counter.test.ts`・`recall-channels`・`recall-decay-gate`・`standalone-functions-omit-params`）が緑。
