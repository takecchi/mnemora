# ADR 0019: 本物の OpenAI で北極星の物差しを測る — 費用・実測値・分かったこと

- 状態: 採用
- 日付: 2026-09-06

**⚠ この文書は作業中に随時追記している。**節ごとに「実測」か「見積もり」かを明示する。
**確かめていないことは「確かめていない」と書く。**

---

## 文脈

`examples/chat` は [docs/north-star.md](../north-star.md) の物差し——

> 使う側が、会話ログを全部プロンプトへ積むのをやめられたか。

——を実測するために在る。しかし Phase 1 までの実測は**すべて `@mnemora/testkit` の
決定的な擬似 provider**で取られており、`examples/chat/README.md` 自身が
「擬似 embedding は意味的な類似度を表現しない」「一般に意味的な関連度で正しく順位付け
できるかは確認していない」と限界を明記していた。

**本 ADR は、その空白を実 API キーで埋めた記録である。**

| 操作 | LLM 呼び出し | 埋め込み呼び出し |

## 3. 1回あたりの実費（実測。2026-09-06）

**`gpt-4o-mini` の抽出呼び出し 1回**（実 API で3件測った）:

| 発話 | input tokens | output tokens | レイテンシ |
|---|---|---|---|
| 「私の好きな色は青です。誕生日は4月3日です。」 | 209 | 67（記憶2件） | 1880 ms |
| 「今日はいい天気ですね。」 | 196 | 5（記憶0件） | 672 ms |
| 「ところで、わたしの好きな色を覚えていますか?」 | 206 | 5（記憶0件） | 805 ms |

input が発話の長さにほぼ依らず 200 前後なのは、**固定費（system プロンプト
約120字 ＋ structured output の JSON schema 569字）が支配的**だから。

**`text-embedding-3-small`（dimensions=256）1件**: 22 tokens / 約 1.8 秒（初回）。

### 価格（コードに書いた定数。2026-09 時点の公開価格であり、API から取得したものではない）

- `gpt-4o-mini`: input **$0.15 / 1M tokens**、output **$0.60 / 1M tokens**
- `text-embedding-3-small`: **$0.02 / 1M tokens**

### `compare` を本物で1回走らせる費用（**見積もり**。実測は §7 に追記する）

`fillerPairsSequence = [0,1,2,3,4,5,10,20,40,80,160,320]`（`cli.ts` の既定）。
会話長ごとに独立のテナントで会話全体を `observe()` するので、
LLM 呼び出し回数 = Σ(fillerPairs+1) = **657回**。

| 項目 | 数 | トークン | USD |
|---|---|---|---|
| LLM input | 657回 | 約 134,000 | $0.020 |
| LLM output | 657回 | 約 4,000 | $0.002 |
| 埋め込み | 数十回（§4 の理由で少ない） | 約 800 | $0.00002 |
| **合計** | | | **約 $0.023（約2.3セント）** |

**所要時間の見積もり: 657回を逐次に叩いて約8〜15分**（1回 0.7〜1.9 秒の実測から）。
**⟹ オーナーの見積もり「1セント未満」より 2〜3倍高い。** 差の理由は、
オーナーの見積もりが埋め込み（`text-embedding-3-small`）だけを見ていたのに対し、
**実費の 99% 以上は LLM 抽出側**だからである。埋め込みだけなら確かに1セント未満である。

## 4. ⚠ 本物の LLM に替えると、既存ベンチの前提が1つ崩れる（実測）

**本物の `gpt-4o-mini` は、既存シナリオの filler を記憶として抽出しない。**
「今日はいい天気ですね。」に対して `{"memories":[]}` を返す（実 API で確認）。
これは抽出プロンプトの指示（「何も記憶に値しない場合は空配列を返してください」）通りの
正しい挙動である。

一方 `DeterministicLLMProvider` は**発話ごとに機械的に記憶を作る**。

**⟹ README の「642ターン ＝ スコープ内 321件」という干し草の山は、擬似 LLM の産物である。**
本物の LLM では、同じ会話のスコープ内 Memory は**数件**にしかならない。

これは mnemora にとって**悪い知らせではない**（積む量はさらに減る）。
**しかし「321件の中から目的の1件を引き当てた」という難しさは、本物では成立していない。**
⟹ 想起の質を測るには、**本物の LLM が実際に記憶として抽出する干し草**を積んだ
別のシナリオが要る。それが本作業で足した `retrieval-quality` である（§6）。

## 5. ⚠ もう1つ、既存ベンチが測れていなかったこと（実測。擬似 provider でも成り立つ）

`tick()` の既定 `limit` は **50**（`packages/core/src/runtime.ts` の `DEFAULT_TICK_LIMIT`）。
`examples/chat/src/mnemora-path.ts` の `ingestConversation` は **`tick()` を1回しか呼ばない**。
`PostgresOutboxStore.claimBatch` は `ORDER BY available_at ASC` なので**先着50件**を取る。

**⟹ 記憶が50件を超える会話長では、51件目以降は埋め込まれないまま残る**
（`embeddingStatus` が `pending` のまま ＝ ANN の候補になれない）。

**⟹ README の「スコープ内 321件のうち10件だけを返す」という表現は、
「321件と競って勝った」という意味には読めない。**実際に ANN の候補になれたのは
最大50件である。冒頭の事実は turn-0 ＝ 最初のジョブなので、必ずこの50件に入る。

**実際に確かめた**（擬似 provider・642ターン・既存の `ingestConversation` をそのまま呼ぶ）:

```
user発話 = 321
totalInScope = 321
omitted = [["ann_truncated"],["over_limit",30],["not_indexed","pending",271]]
returned = 10
```

**⟹ 321件のうち 271件は `not_indexed:pending` ——埋め込まれておらず、ANN の候補ですらない。**
**実際に競ったのは 50件である。** `recall()` はこれを `omitted` に正直に出しており、
**隠していたのは mnemora ではなく、`omitted` を読まずに表を書いた側である。**

**これは README の主張を否定するものではない**——README が主張しているのは
「量を1桁削っても目的の記憶が落ちなかった」であり、それは事実である。
**しかし「難しさ」を過大に読める書き方になっている。**

**追記（2026-09-06、[ADR 0021](./0021-drain-embed-ticks-in-ingest.md)）**:
この節が記録した欠陥は、後日 ADR 0021 で直した（`ingestConversation` が
`tick()` を干上がるまで回すようになった）。この節自体の記述は当時の記録
のため書き換えていない。

## 5c. ⚠ `OPENAI_API_KEY` を持つ環境で `pnpm run test` を走らせると、黙って課金される

`packages/openai/src/__tests__/live.openai.test.ts` は `it.skipIf(!apiKey)` なので、
**環境にキーが在れば、ルートの `pnpm run test` の一部として本物の API を叩く**
（埋め込み1回 + `completeStructured` 1回）。1回あたりの額は極めて小さいが、
**「テストを走らせた」だけで課金が発生することは、実行前に画面から読み取れない。**

本作業中に実際にこれを踏んだ（門を繰り返し走らせる過程で、意図せず本物の API を
複数回叩いた）。**この設計自体を変える判断はしていない**——`describe.skip` ではなく
`it.skipIf` を使うのは「skip されたことがレポートに必ず出る」ためであり、
その理由には価値がある。**ここでは事実として記録するにとどめる。**

## 6. 何を足したか — `retrieval-quality` ベンチ

**測り方はこちらで決めた。**狙いは1つ——**「意味的に関連する記憶が正しく上位に来るか」を、
擬似 provider では通らない形で問うこと。**

### 6.1 probe set の作り（`examples/chat/src/probe-set.ts`）

- **gold の質問は、gold の事実と内容語を共有しない。**
  例: gold「私は猫を2匹飼っています。」に対する質問は
  「うちのペットについて何か知っていますか?」——「猫」も「飼」も出さない。
  **擬似 embedding が持つのは文字コードに由来する重なりだけなので、
  内容語を共有しない質問は、意味を持つ埋め込みでしか引けない。**
- **1件だけ対照群を置く。** 既存ベンチと同じ「私の好きな色は青です」／
  「わたしの好きな色を覚えていますか?」——**語彙が重なる問い**である。
  擬似物でも通るはずのものを1つ混ぜておかないと、
  「擬似物が失敗した」のか「問いが難しすぎた」のかが区別できない。
- **distractor を置く。** 同じ話題・違う主語や値
  （gold「弟は札幌に住んでいます。」に対して「姉は福岡で働いています。」）。
  **これが gold より上に来たら、Recall@10 が緑でも中身は外れている。**
- **haystack（干し草）は、本物の LLM が実際に記憶として抽出する事実にした。**
  §4 の通り、既存 `scenario.ts` の filler（世間話）は本物の LLM では記憶にならず、
  干し草の山そのものが消えてしまう。乱数を使わず、1件ずつ内容の違う
  「事務手続き・家電の修理・買い物」等の事実を 60件生成する
  （probe の話題語と重ならないことを機械的に検査している）。

### 6.2 3つの arm に分けた理由

本物に替えて順位が変わったとき、**埋め込みのせいか抽出のせいかを切り分けないと、
どちらが効いたか言えない。**そこで LLM と埋め込みを別々に選べるようにし、3通り走らせた。

| arm | LLM | 埋め込み | 意味 |
|---|---|---|---|
| A | 擬似 | 擬似 | **いまのベンチと同じ配置** |
| B | 擬似 | 本物 | 埋め込みだけを入れ替えた効果 |
| C | 本物 | 本物 | 実運用の配置 |

### 6.3 守った規律

- **閾値・件数・over-fetch などのパラメータは既定のまま。一切いじっていない。**
- **gold は文字列一致では探していない。**本物の LLM は発話を書き換えて記憶を作るので、
  `memoryId` → `Memory.sourceObservationId` → `Observation.externalId` と辿って同定する。
- **outbox は `processed === 0` になるまで排出する**（§5 の 50件の頭打ちを踏まないため）。
  同時に「既定の `tick()` 1回なら何件で止まっていたか」も出力に残している。

## 7. 実測結果（2026-09-06。本物の `gpt-4o-mini` / `text-embedding-3-small`(256次元)）

観測 74件（gold 7 + distractor 7 + haystack 60）、スコープ内 Memory 74〜76件、
`recall()` は既定（`limit`=10）。

### 7.1 arm ごとのまとめ

| arm | LLM | 埋め込み | MRR（全体） | MRR（対照群・語彙が重なる） | MRR（語彙が重ならない6件） |
|---|---|---|---|---|---|
| **A（いまのベンチと同じ配置）** | 擬似 | 擬似 | **0.018** | **0.000** | 0.021 |
| **B** | 擬似 | 本物 | **0.714** | 1.000 | 0.667 |
| **C（実運用の配置）** | 本物 | 本物 | **0.743** | 1.000 | 0.700 |

### 7.2 probe ごとの順位（gold が `recall().memories` の何位に居たか）

| probe | 語彙が重なるか | A | B | C | distractor が gold より上（C） |
|---|---|---|---|---|---|
| color（好きな色） | **重なる（対照群）** | **(無し)** | 1 | 1 | いいえ |
| pet（ペット） | 重ならない | (無し) | 1 | 1 | いいえ |
| exercise（運動の習慣） | 重ならない | (無し) | 2 | 2 | **はい** |
| diet（避けるべき食べ物） | 重ならない | (無し) | **(無し)** | 5 | **はい** |
| family（家族の居住地） | 重ならない | (無し) | 1 | 1 | いいえ |
| language（好きな言語） | 重ならない | 8 | 1 | 1 | いいえ |
| travel（次の行き先） | 重ならない | (無し) | 2 | 2 | **はい** |

### 7.3 ⚠ 分かったこと1: 擬似 provider は、この物差しに対して**目が見えていない**

**arm A は7件中6件で gold を返せなかった。**残る1件（language）も8位である。
**語彙が重なる対照群（color）ですら落ちた。**

**⟹ `examples/chat/README.md` の「冒頭の事実が残るか ✅」は、
「意味的に関連する記憶が正しく上位に来た」ことを示していない。**
あの表の干し草は**12種類の filler の使い回し**であり、
**別々の内容が 60件並ぶとこの通り崩れる。**

**⚠ ただし、これは README の表を再実行して否定したものではない。**
測ったのは**新しい probe シナリオでの arm A** であり、
「同じ会話・多様な干し草」で旧シナリオを回し直したわけではない。
言えるのは「擬似 embedding は、多様な干し草の中から意味で引くことができない」までである。

### 7.4 ⚠ 分かったこと2: 本物に替えると引ける。効いているのは**埋め込みのほう**

**arm A → arm B で MRR が 0.018 → 0.714 に上がる。**この間で変えたのは**埋め込みだけ**である
（LLM は擬似のまま）。**⟹ この物差しを動かしていたのは埋め込みであり、抽出ではない。**

arm B → arm C（LLM も本物に）での上積みは 0.714 → 0.743 と小さい。
本物の LLM は発話を整理して記憶にする分わずかに効くが、**主役ではない。**

**⟹ 北極星の物差しに対して:「削っても目的の記憶が落ちない」は、
本物の埋め込みでは 7/7 の probe で hit@10 が真になり、成立している。**
`limit`=10 は 74〜76件の 13% であり、**87% を削っても目的の記憶は残った。**

### 7.5 ⚠ 分かったこと3: 悪い結果もそのまま出す——**「話題は合うが、答えが違う」**

**本物の埋め込みでも、7件中3件で distractor が gold より上に来た。**

| probe | 質問 | 1位に来たもの（distractor） | gold |
|---|---|---|---|
| exercise | 「私の運動の習慣はどんなものでしたか?」 | **「父は毎晩ウォーキングをしています。」** | 「毎朝5時に起きてジョギングをしています。」 |
| diet | 「私が避けたほうがいい食べ物はありますか?」 | **「妻は卵アレルギーがあります。」** | 「牛乳を飲むとお腹を壊します。」（**5位**） |
| travel | 「次の遠出の行き先はどこでしたか?」 | **「先月は大阪へ出張しました。」** | 「来月、京都へ出張します。」 |

**共通する形が2つある:**

1. **主語を見ていない。** 「私の」と聞いているのに「父は」「妻は」が先に来る。
   埋め込みの類似度は話題の近さを測っており、**誰の話かを区別しない。**
   `Ctx.subjectId`（スコープの次元として既に在る）はこのベンチでは使っていない——
   **主語を分ける仕掛けは在るが、埋め込みだけでは主語は分かれない**ということである。
2. **時制を見ていない。** 「次の」と聞いているのに「先月は」が先に来る。
   `occurredAt`（`freshness` の時計）は在るが、**質問側の時間の向きは
   スコアに入っていない**（`docs/recall.md` §7 のスコアは
   `similarity × decay × tagMatch × freshness × strength` であり、
   質問が未来を指しているか過去を指しているかを見る項が無い）。

**⟹ Recall@10 が 7/7 で緑でも、hit@1 は 4/7 である。**
「載せる量を削っても答えが残る」は言えるが、
**「一番上に正しいものが来る」はまだ言えない。**この2つを混同しないこと。

**⚠ 標本は probe 7件である。**この3件の失敗から一般的な失敗率は主張できない。
**言えるのは「この失敗の形が実在する」ということまでである。**

**🔴 追記（2026-09-06、[ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md)）**:
**上の「共通する形が2つある」は、返り値から測ったものではなく、順位の表を人が読んで立てた解釈だった。**
後日スコア内訳を実際に記録して測ったところ、**成立しなかった**——

- **5項のうち4項（`tagMatch` / `strength` / `decay` / `freshness`）は、この測定では
  候補間で差が付いていない。**順位は `similarity` だけで決まっていた。
  **⟹ 「スコアが主語と時制を見ていない」のではなく、スコアに見る場所が無い。**
- **失敗3件の原因は3件とも違う。**travel は時制（ただし埋め込みは時制を見ており、
  質問「どこ**でしたか**」の表層が過去形であることが効いている）、exercise は
  gold の主語がゼロ代名詞で落ちていること（埋め込みは主語の一致を見ている）、
  diet はどちらでもなく「記憶は症状、質問は帰結」という推論の飛躍である。
- **`occurredAt` はこの設計では原理的に常に `null` になる**（抽出スキーマに時刻の欄が無く、
  `observe()` に渡している箇所がリポジトリ内に0件）。

**この節自体の記述は当時の記録のため書き換えていない。**訂正の内容は ADR 0033 にある。

### 7.9 ついでに見つけたこと: `PostgresMemoryStore.get` は不正な id で例外を投げる

系譜追跡の負の検査（存在しない `memoryId` では `null` を返す）を書いたところ、
UUID の形をしていない文字列を渡すと `invalid input syntax for type uuid` で例外になった。
同じ `packages/postgres` の `PostgresOutboxStore.complete` は `isUuidLike` で
明示的に守っている（「べき等な終端更新という契約のため」とコメントに書いてある）ので、
**守り方が store ごとに揃っていない。**

**この非対称を直す変更はしていない**（本作業の範囲外であり、
`packages/postgres` は別の作業が走っている）。検査のほうを
「UUID として妥当だが存在しない id」に直した。**`resolveExternalId` 側で例外を握り潰す案は
採らなかった**——DB の異常を「辿れなかった」に読み替えると、系譜が壊れていることを見逃す。
**辿れない（`null`）と、壊れている（例外）は別物である。**

---

## 8. これが覆るとしたら

- **モデルを替えたとき。**本 ADR の数字はすべて `gpt-4o-mini` と
  `text-embedding-3-small`（256次元）に固有である。
- **抽出プロンプトを変えたとき。**input の 200 tokens はほぼ全部が固定費なので、
  プロンプトと schema を変えれば費用がそのまま動く。
- **`observe()` の抽出を非同期（`deferred`）に倒したとき**、あるいは
  **埋め込みをバッチ化したとき**（§2 の通り、いまは1件ずつ叩いている。
  まとめれば呼び出し回数は減るが、トークン数は減らないので費用はほぼ変わらない——
  **効くのは時間のほうである**）。

## 9. 採らなかった案

- **CI で毎回 API を叩く。** 採らない。**私が起こす回数・CI が走る回数に比例して実費が増える。**
  手で走らせて数字をこの ADR に残せば足りる（オーナーの明示的な線でもある）。
  したがって `.github/**` は本作業で一切変更していない。
