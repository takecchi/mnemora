## 文脈

[Issue #142](https://github.com/takecchi/mnemora/issues/142) は2件の欠落を名指しした。
そのうち②が本 ADR の対象である【現物・逐語】:

> 適合テストは「実際にどのモデルを読み込んでいるか」を見ていない

[ADR 0247](./0247-local-embedding-repo-model-id-declaration-guard.md)（PR #550）が埋めたのは
**宣言どうしの食い違いを宣言の時点で落とす**ところまでで、同 ADR 自身が「⛔ この guard が
塞いでいないもの」節で逐語こう書いている【現物】——「実際に読み込まれた重みが `modelId` の
名乗りと合っているかは、依然として誰も見ていない」。

**この穴は、`repo` を差し替えなくても踏める。**【実測】HF API
（`curl 'https://huggingface.co/api/models/sirasagi62/ruri-v3-30m-ONNX/tree/main?recursive=1&expand=1'`）
が返す tree に、次の3本が並んでいる:

| path | size | oid |
|---|---|---|
| `onnx/model_quantized.onnx`（**既定。`DEFAULT_LOCAL_EMBEDDING_DTYPE = "q8"`**） | 37,142,404 | `3d374a62…b33120d` |
| `onnx/model_int8.onnx` | 37,142,404 | `3d374a62…b33120d`（**バイト同一**） |
| `onnx/model_uint8.onnx` | **37,142,404** | `9ba6a410…f11ae2ab`（**別物**） |

🔴 **`model_uint8.onnx` は既定の重みと1バイトも違わないサイズで、中身は別物である。**
⟹ [ADR 0212](./0212-local-embedding-size-noun-correspondence-tooth.md) が縛っている
**サイズの対応（一式42MB / 重み36MB）は、この取り違えを原理的に検出できない。**
⟹ **「穴が在りうる」ではない。既存の歯をすり抜ける具体物が、現に repo に並んでいる。**
**踏むのに `repo` の差し替えは要らない——`dtype` を1つ間違えるだけでよい。**

### Issue #142 が自分に課していた縛りと、その射程

#142 本文は逐語でこう書いている【現物】——「⛔ どれを採るかは、まず『この穴が実際に
踏まれうるか』を測ってから決めるべきである。⛔ 測る前に歯を足さないこと。」

**この縛りは①（宣言どうし）には当たらず、②には当たる、と判断した。**
①「既定外の `repo` を `modelId` 無しで渡す宣言」は**それ自体が矛盾**であって、外部の
挙動に依存しない。②は**外部（HF）の挙動に依存する**——踏まれうるかが分からないと
偽陽性率が見積もれない。⟹ **②については、先に測った**（下記「測ったこと」）。

## 🔴 決め手になった発見 — **期待値を持たなければ、腐る対象が存在しない**

当初の検討では (a)「ファイル hash」の最大の弱点は**期待値の置き場**だった。
repo に焼き込めば [`AGENTS.md`「⚠ 数を、道具と生成物に焼き込まない」](../../AGENTS.md)
に触れ、HF の `main` は mutable ref なので同じ論理モデルの再変換でも赤くなりうる
——**偽陽性率に上限を置けない検査を門にするな**（[ADR 0088](./0088-retrieval-quality-with-recorded-embeddings.md) /
[ADR 0094](./0094-identifier-probe-gate-conditions.md) /
[ADR 0223](./0223-cross-cutting-disciplines-extracted-from-the-adr-corpus.md) 決定3）に抵触する。

**【実測】HF は各ファイルの hash を API で直接出している。ダウンロードは要らない。**
⟹ ⭐ **期待値を repo に持つ必要が無い。**

⟹ **両側をその場で取って突き合わせる形にできる**:

| | 何を取るか |
|---|---|
| 期待値 | **宣言された `repo`** が、**いま** HF 上で持っているファイルの hash |
| 実物 | **いま**手元のキャッシュに実在するファイルの hash |

⟹ 🔴 **腐る期待値が存在しない。** そして**赤くなるのは「HF が持っているものと、手元に在る
ものが違う」ときだけ**である——それは本当にずれている（キャッシュが古い・別物が落ちた・
ミラーが汚れた）。**「同じ論理モデルの再変換」という偽陽性の唯一の源も、期待値を
持たないので効かない。**

⟹ **偽陽性率に上限が置ける。⟹ 門にしてよい。**

## 決定

### 決定1. 照合は「宣言された repo が*いま*持つ hash」と「手元に*いま*在るファイルの hash」の突き合わせにする

⛔ **期待値をリポジトリにも道具にも焼き込まない。** repo 名すら書かない——
`packages/local-embedding/src/local-embedding-provider.ts` の `DEFAULT_LOCAL_EMBEDDING_REPO`
を唯一の出所として読む。

### 決定2. ハッシュは2種類を使い分ける。⭐ **どちらを使うかは HF の応答が決める**

【実測】HF API の tree エントリは2種類に分かれ、**ファイルごとに別のハッシュになる**:

| エントリ | HF が返す値 | 手元で計算するもの |
|---|---|---|
| **LFS のもの**（`lfs` を持つ） | `lfs.oid` | **ファイル内容の sha256** |
| **非 LFS のもの** | `oid` | **git の blob hash**（`sha1("blob " + 長さ + "\0" + 中身)`） |

**⚠ これはこちらの都合ではない。**HF が**ファイルによって違う種類の値を返す**からである。

🔴 **だから、どちらを使うかを*こちらが*決めてはならない。**
⛔ **ファイル名・拡張子・サイズで分岐しないこと**——それは**焼き込んだ期待値と同じで腐る**
（今日 `.onnx` だけが LFS でも、明日 `tokenizer.json` が LFS になれば外れる）。
⭐ **分岐の根拠は「その応答に `lfs` が在るか」ただ1つにする**——**応答そのものが教えてくれる。**
⟹ 決定1（期待値を焼き込まない）の**同じ原理を、ハッシュの選び方にも当てている。**

⚠ **片方しか計算できないときは緑にしない**（HF 側に `lfs.oid` も `oid` も無い、
手元のファイルが読めない等）——**照合が成立していない。**判定表は決定3 に在る。

⚠ **これは実装前に想定していなかった。**当初は「全部 sha256 で照合できる」と読んでいた
——【実測】で外れた（非 LFS の3ファイルは sha256 では一致しない。下記「測ったこと」2）。
⟹ **推定が半分だけ当たっていた**という形であり、落として測らなければ気づけなかった。

### 決定3. ⭐ 保留に倒してよいのは **HF API への到達失敗ただ1つ**である。それ以外は赤

「判定できなかったから緑」は採らない（`AGENTS.md`「⚠ 機械には『検出』まで」の逐語
「**機械が判定できなかったときは、従来どおりに倒さず赤／保留で止める**」）。
⭐ **だが「赤」と「保留」のどちらに倒すかは、事象ごとに分かれる。**

| 事象 | 判定 | なぜ |
|---|---|---|
| 全ファイル一致 | 緑 | — |
| ハッシュが食い違う | 🔴 **赤** | 門の本題 |
| 手元に在るのに HF の tree に無いファイルが在る | 🔴 **赤** | 素性の分からないものが混ざっている |
| `cacheDir` が引けない | 🔴 **赤** | **CI では置き場所が決まっているはず**＝設定の壊れ |
| 宣言された repo を読み取れない | 🔴 **赤** | 唯一の出所が壊れている |
| 片方のハッシュしか計算できない | 🔴 **赤** | **照合が成立していない**（決定2） |
| `cacheDir` は引けたがファイルが1本も無い | 🔴 **赤** | 測るべき実物が無い |
| **HF API に届かない**（再試行を尽くしても） | ⚠ **保留** | **こちらの管理外の事象で、偽陽性率に上限が置けない** ⟹ ADR 0223 決定3 に照らして門にできない |

🔴 **なぜ全部を赤にしないのか。** 逆に、**なぜ `cacheDir` を保留にしないのか。**

- `cacheDir` が引けないのは**この repo の設定の問題**であり、**こちらで直せる。**
  保留に倒すと「壊れているのに黄色で流れる」状態が常態化する
  ——[ADR 0251](./0251-release-follow-up-notice-not-a-gate.md) の非ブロッキング通知が
  **3回出力されて3回とも読まれなかった**【受: 依頼者の報告】のと同じ末路をたどる。
- HF API への到達失敗は**こちらの管理外**である。これを赤にすると、**HF の可用性が
  そのまま偽陽性率になり、上限が置けない。**⟹ 門にしてはならない側である。

⟹ ⭐ **線は「こちらで直せるか」である。** 直せるものは赤、直せないものは保留。

終了コードは `scripts/ci-green-check.mjs` の規約に揃える:
`0`=一致 / `1`=赤 / `2`=保留 / `3`=実行時エラー。

⚠ **この結果、純関数の側（`compareFingerprints`）に「保留」は現れない**——
保留は「HF に届かなかった」という I/O の事象であり、照合そのものの結果ではないからである。

### 決定4. 手元に在るファイルを起点に照合する。⛔ HF に在って手元に無いものは不一致にしない

transformers.js は**必要なものだけ落とす**【実測: 16エントリ在る repo から4ファイルだけが落ちた】。
⟹ 「HF の tree に在るが手元に無い」を不一致にすると、**構造的に必ず赤くなる。**

一方、**手元に在るのに HF の tree に無いファイルは不一致とする**——素性の分からないものが
キャッシュに混ざっている状態であり、まさに見たい事象だからである。

### 決定5. 門は `example-chat` ジョブ（必須 context）に1本だけ置く

【実測】必須 context 6件のうち2件が**既に本物の重みを落としている**
（`gh api repos/takecchi/mnemora/branches/main/protection` と `ci.yml` の突き合わせ）。
⟹ **追加のネットワーク費用がほぼ無い位置がすでに在る。**

⛔ **2つのジョブ両方には置かない。** 見たいのは「CI が使っている重みの素性」であって、
1回見れば足りる。⛔ `continue-on-error` を付けない——**門である。**

### 決定6. ⭐ この門は「キャッシュが古い」経路も同時に捕まえる

【実測】CI のモデルキャッシュ鍵は **`local-embedding-ruri-v3-30m-q8-v1`** という
**手で版を振った固定文字列**で、`ci.yml` の6箇所すべてが同一である。
**revision も hash も入っていない。**

⟹ 🔴 **HF の `main` が動いても、CI は誰かが `-v1` を手で上げるまで古い重みを配り続ける。**
⟹ ⭐ **これは「宣言と実物のずれ」の第3の経路である**——#142 も ADR 0247 も名指ししていない。
「**CI が測っている重み ↔ 利用者が新規に落とす重み**」のずれであり、
**CI が緑でも新規利用者は別のモデルを引いている、という形が構造的に可能である。**

**決定1 の形は、この経路も鳴らす**——手元（キャッシュ）の実物を HF の**現値**と
突き合わせるため、キャッシュが古ければそこで差が出る。

⛔ **キャッシュ鍵そのものの修正は、この PR では行わない。**[Issue #564](https://github.com/takecchi/mnemora/issues/564) へ切り出した。
**理由**: 決定1 は「**ずれていることに気づける**」ようにする変更で、鍵の修正は
「**ずれないようにする**」変更である。⟹ **前者が先。**気づけないまま「ずれない仕組み」だけ
入れると、**それが壊れたときに誰も分からない。**

### 決定7. 「保留」は CI でジョブを落とさない。⭐ ただし黙らせない

決定3 が「HF API に届かないときは保留」と決めたが、**exit 2 でステップを失敗させると
ジョブが赤になり、結局 PR が止まる**——⟹ **赤と区別が付かず、決定3 が空文になる。**

⟹ **CI 側の配線をこう分ける**:

| 終了コード | ジョブ | 出力 |
|---|---|---|
| `0`（一致） | 緑 | Job Summary に一致した旨を出す |
| `1`（赤） | **落とす** | 食い違った path と期待・実物の hex を出す |
| `2`（保留） | **落とさない** | ⭐ `::warning::` 注釈（PR の Checks に出る）＋ Job Summary に「**判定していない**」と明示 |
| `3`（実行時エラー） | **落とす** | — |

⚠ **これは [ADR 0251](./0251-release-follow-up-notice-not-a-gate.md) が踏んだ穴
（非ブロッキングの通知が3回とも読まれなかった）と同じ族である。**⟹ **同じ轍を踏む余地を
引き受けたうえで、次の2点で少しだけ弱めている**:

1. **`::warning::` 注釈は PR の Checks 画面に出る**——ログの中に埋もれない。
2. **Job Summary には、保留のときも一致のときも必ず1行出す**
   ⟹ 「何も出ていない」＝「ステップが走らなかった」であり、**沈黙と保留が区別できる。**

🔴 **それでも「保留が続いていることに誰も気づかない」経路は残る。**
⛔ **これを塞いだとは書かない。**塞ぐなら「保留が N 回続いたら赤」のような別の仕掛けが要り、
**その N を決めるだけの実測を持っていない。**

## 採らなかった案

### (a′) `.onnx` ヘッダの ONNX metadata（`producer_name` / `graph_name` / `opset`）を見る

**魅力**: バイト列ではなくモデルの素性を見るので、**再シリアライズには鳴らない**——
(a) の偽陽性の弱点を原理的に消す。

**却下の理由**: 【実測】`producerName` / `opsetImport` を型定義に持つのは
`onnxruntime-web` の **protobuf スキーマ**（`lib/onnxjs/ort-schema/protobuf/onnx.d.ts`）だけで、
**これは内部実装のパスであって公開 API ではない。**⟹ `docs/architecture.md` §3.8
（「core・呼び出し側に OpenAI/Anthropic SDK の型を漏らしてはならない」と同じ理由で、
provider 実装の内部型に依存しない）に触れうる。**別の ONNX パーサを足す必要が
あるかどうかは確かめていない。**

⟹ **決定1 が「期待値を焼き込まずに済む」という利点で (a) の弱点をすでに消している以上、
(a′) の調査費用を払う理由が薄い。** ⛔ **不可能だから却下したのではない。**

### (b) ランタイムに「いま何を読み込んでいるか」を聞く

**⛔ 不可能である。**【実測】`onnxruntime-common@1.24.3` の `InferenceSession` が公開するのは
`inputNames` / `outputNames` / `inputMetadata` / `outputMetadata` **だけ**
（`dist/cjs/inference-session.d.ts:475-487`）。`getModelMetadata` / `producerName` 相当は
**横断 grep で0件。**

⚠ **補正**（最初の調査はここを畳んでいた）: **ランタイムに聞く道は閉じているが、
ファイルを自分で読む道は開いている。**⟹ 上の (a′) が別候補として立つ。
**「API が無い」を「その情報が取れない」と読まないこと。**

⚠ **探り棒の記録**: この判定を出す過程で、最初の grep が**在るはずの `inputNames` まで0件**を
返した。**対照を取ったから探り棒の不備と分かった。**⟹ **0件を「無い」と読む前に、
在ることが分かっているものが同じ探り棒に掛かるかを見ること。**

### (c) 推論出力そのものを指紋にする（固定入力 → ベクトル）

**最も検出力が高い**——構造ではなく中身を見る。**却下の理由は2つ。**

1. **いま測る経路が1本も無い**【受: 調査報告】——生ベクトルやその hash を出しているジョブは
   ゼロ本である。⟹ 費用ゼロなのは CI の課金時間だけで、コード変更なしには測れない。
2. 🔴 **偽陽性率に上限を置けない。**【実測】比較に使える2ジョブは**別 VM**
   （`runner_name` = `GitHub Actions 1000020516` / `1000020517`）で、**同じキャッシュ blob から
   同じ重み**を復元しており（両ジョブのログに `Cache hit for: local-embedding-ruri-v3-30m-q8-v1`）、
   **差はハードウェア／ランタイムだけに絞れる**——実験としては正しい。
   **しかし n=2・同一 run・起動時刻差1秒**である。⟹ 「一致した」は**この条件下の一致**であって
   「ランナー間で一般に再現する」の証明にはならない。**不一致でも原因の切り分けができない。**

⟹ **ADR 0088 / 0094 が繰り返し採ってきた「まず測る → 測れたら門にする」の手前で止まっている。**
**必要物は [Issue #565](https://github.com/takecchi/mnemora/issues/565) へ送った**（①固定入力の `embed()` 出力 hash を両ジョブが必ず通る経路で出す
②既存の「測定→summary→artifact」3段に載せる ③`lscpu` でハードウェアを記録する
④2ジョブの比較段。⚠ **③が無いと、不一致だったとき原因を切り分けられない**）。

### (d) HF の revision を固定して落とす

**照合ではなく予防**である。⟹ #142 が名指しした「ずれを*見つける*」には答えない。

そして**決定1 によって、(d) は (a) の前提条件ではなくなった**——期待値を HF から
その場で引く以上、revision を固定しなくても期待値は腐らない。
⟹ ⛔ **この PR には混ぜない。**[Issue #564](https://github.com/takecchi/mnemora/issues/564) に
「**(a) とは別の価値（repo 消失・ミラー汚染への予防）が在る。未判断**」として残した。

### (e) 入出力の名前・形だけ見る

低費用・低偽陽性だが、**同じ形の別モデルを通す。**既存の次元検査
（`local-embedding-provider.ts` の `embed()` 内）の焼き直しに近く、
**#142 が名指しした穴の中心（重みの中身）には届かない。**

### (う) 何もしない（穴として記録だけ）

#142 本文が自分で挙げている選択肢である【現物】。**却下の理由**: 上の「文脈」で示したとおり、
**既存の歯をすり抜ける具体物が現に repo に並んでいる**（`model_uint8.onnx`）。
⟹ 「踏まれうるか」への答えが出た以上、記録だけに留める理由が消えた。

## 引き受けた負債

1. 🔴 **CI が HF API の可用性に依存するようになる。** キャッシュが温まっているとき、
   従来は HF に一切触らずに済んでいた。⟹ **HF が落ちている間、この門は `undetermined` で
   止まり、PR がマージできなくなる。**
   ⭐ **それでも緑に倒さない**のは決定3 の理由による。再試行を3回入れて一過性の失敗は
   吸収するが、**恒久的な障害は人が見るべきものである。**
   ⚠ **代わりに非ブロッキングの通知にする案は採らなかった**——
   [ADR 0251](./0251-release-follow-up-notice-not-a-gate.md) の非ブロッキング通知は
   **3回出力されて3回とも読まれなかった**【受: 依頼者の報告】。⟹ **読まれない前提で
   設計しない限り、非ブロッキングは採らない。**
2. **`dtype` を変えたときの振る舞いは、この門の射程外である。** 手元に落ちたファイルを
   起点に照合するので、`model_uint8.onnx` が落ちていれば**その hash が HF の
   `model_uint8.onnx` と一致してしまう**。⟹ **この門が捕まえるのは「HF に無いもの／HF と
   違うものが手元に在る」であって、「宣言と違う dtype を選んだ」ではない。**
   後者は ADR 0247 が負債として記録済みの別の穴である。
3. **将来の偽陽性率は、標本1本から断定できない**（下記「確かめていないこと」）。
4. **キャッシュ鍵の経路（決定6）は、気づけるようにしただけで塞いでいない。**

## これが覆るとしたら何が起きたときか

- **HF が `lfs.oid` / `oid` を API から落とす**、または意味を変えたとき
  ⟹ 期待値をその場で引く前提が崩れる。
- **HF の `main` が頻繁に動くようになったとき** ⟹ ただし決定1 の形では「HF の現値」を
  期待値にしているので、**動いても偽陽性にはならない**（手元のキャッシュが古ければ
  正しく鳴る）。覆るとすれば、それは**門が正しく鳴っているのに人が黙らせたくなる**形である。
- **repo が消えたとき** ⟹ `undetermined` で止まり続ける。ADR 0085 が別の負債として
  記録している事象であり、この門はそれを**顕在化させる**（黙って動き続けない）。
- **transformers.js がキャッシュの配置を変えたとき** ⟹ 手元のファイルを見つけられなくなる。
  `undetermined` で止まるので、黙って緑にはならない。

## 追記の決定 —— 問いを2つに割る

### 追記決定1. 「宣言が指す先が在るか」を、前段として切り出す

`checkDeclaredRepoExists()` が、tree を引く**前に** `GET /api/models/<repo>` を1回引く。
**再試行3回すべてが 404 のときだけ**「存在しない」と名乗り、**赤（exit 1）**にする。

🔴 **この問いは 404 か否かの2値に留める。⛔ ここに 429 や 5xx を混ぜない。**
それらは「在るか」に**答えていない**ので、赤の根拠にならない——答えられないときは
`undetermined` を返して**続行し、tree 側の判定（保留）に委ねる。**

⭐ **404 を再試行して確かめるのは、一過性の 404 で必須ジョブを止めないためである。**

### 追記決定2. 「中身を読めたか」の倒れ方は変えない

`fetchTreeWithRetry` 以降はそのままである。**(1) を通った時点で「repo は在る」ので、
tree だけが非2xx を返すのは HF 側の事情**（API の形の変更等）＝外部要因だからである。

### 追記決定3. 判定表に行を足す

**#586 の芯は「実装が悪い」ではなく「判定表と論拠が実装の射程を覆っていない」だった。**
⟹ 実装だけ直して表を直さなければ半分である。**行が無かった2事象**（tree の非2xx／
応答が配列でない）に明示の行を与え、**(1)/(2) の別**を表の列にした。

### 追記決定4. なぜ「再帰しない」と言えるか

「モデル情報 API 側が壊れたら、同じ構造が再帰するのでは」という問いには、**1段で底を
打つ**と答える。(1) の問いには「赤／答えない」の**2値しかなく、それ以上分ける先が無い**。
⟹ 残るのは「モデル情報 API が _404 を返すバグ_ を持ったとき」だけであり、**それは
404 を内部起因の信号として使うどの案でも同じ**——この形に固有の弱点ではない。
⭐ **この形の値打ちは、その底がどこかを表に書けることにある。**

## 追記5 (2026-09-24、Issue #597 案(a)。CI run 35953212055 で赤くなった): キャッシュの置き場所の解釈を直した

> **⚠ このコメントは、自動化された担い手（クローンのマネージャーのセッション）が書いた。**
> **⛔ オーナー本人が決めたのではない**（[ADR 0220](./0220-issue-comment-author-does-not-distinguish-owner-from-agent.md)）。
> **⚠ 状態欄も本文も書き換えていない**（追記1〜追記4 と同じ扱い）。

### 何が起きたか（【実測】）

追記4 をマージした PR（#678）の CI で、`examples/chat (本物の Postgres + pgvector、擬似
provider)` ジョブが赤くなった（run `35953212055`、head `0fc1efd`）。門の出力（逐語）:

```
不一致: 一致 4 本 / hash 食い違い 0 本 / 素性不明 4 本。

  素性不明（HF の tree に無い）: cdf9391f1ff2198daa8f63f7ccf97d7b3e7415a0/tokenizer.json
  素性不明（HF の tree に無い）: cdf9391f1ff2198daa8f63f7ccf97d7b3e7415a0/tokenizer_config.json
  素性不明（HF の tree に無い）: cdf9391f1ff2198daa8f63f7ccf97d7b3e7415a0/onnx/model_quantized.onnx
```

### なぜ起きたか（【実測】、手元で再現・特定した）

`@huggingface/transformers`（`node_modules/@huggingface/transformers/src/utils/hub.js`
の `buildResourcePaths`）は、`FileCache` のキャッシュキーをこう組み立てる（逐語）:

```js
const proposedCacheKey =
  cache instanceof FileCache
    ? revision === 'main'
      ? requestURL
      : pathJoin(path_or_repo_id, revision, filename)
    : remoteURL;
```

⟹ **`revision` が `"main"` 以外だと、ファイルは `<repo>/<revision>/<filename>` という
revision 名のサブディレクトリに置かれる。** revision が既定の `"main"` のときだけ
`<repo>/<filename>` というフラットな配置になる。

**手元で実際に確かめた**（`LocalEmbeddingProvider` に revision を渡す/渡さないで、
それぞれ一時 `cacheDir` へ本物のモデル一式を落とし、`find` で比較した）:

```
revision 無し: <cacheDir>/sirasagi62/ruri-v3-30m-ONNX/config.json
              <cacheDir>/sirasagi62/ruri-v3-30m-ONNX/onnx/model_quantized.onnx
              ...
revision 在り: <cacheDir>/sirasagi62/ruri-v3-30m-ONNX/cdf9391f.../config.json
              <cacheDir>/sirasagi62/ruri-v3-30m-ONNX/cdf9391f.../onnx/model_quantized.onnx
              ...
```

**CI のログの「素性不明」のパスと完全に一致した。** さらに、この門をこの2つの
キャッシュディレクトリそれぞれに対して手元で走らせ、CI と同じ「不一致」（revision 在り
側）・同じ「一致」（revision 無し側）を再現した。

⭐ **CI では「一致4本／素性不明4本」だった理由**: `example-chat` ジョブは
`MNEMORA_LOCAL_EMBEDDING_CACHE_DIR` を、revision を渡さない
`examples/chat/src/embedding-fingerprint.ts`（`embedding-fingerprint` サブコマンド）と、
Issue #597 で revision を渡すようになった `examples/chat/src/providers.ts`
（`test:db` が使う）とで**共有している**。⟹ 同じキャッシュディレクトリに、フラットな
配置（4本、main の tree と一致）と revision サブディレクトリの配置（4本、パスが
違うので「素性不明」）が同居していた。

### 直したこと —— 対応づけ（キャッシュの置き場所の解釈）だけを直した。照合の意味は変えていない

**⛔ この門が「何と照合するか」（`main` の tree）は変えていない。** 変えたのは
「手元のどのファイルが、tree のどのパスに対応するか」という解釈だけである
（クローンの決定どおり）。

- `scripts/check-local-embedding-fingerprint-lib.mjs` に純関数 `normalizeActualPath(relPath,
  pinnedRevision)` を追加した。`pinnedRevision` の名前のサブディレクトリで relPath が
  始まっていれば、そのプレフィックスを剥がす。`pinnedRevision` が無い（宣言が読めない）
  場合は何もしない——**この正規化は追加のフォールバックであり、無くても
  （revision=main のフラットな配置しか扱わない、この変更より前の挙動のまま）動く。**
- `scripts/check-local-embedding-fingerprint.mjs` に `readPinnedRevisionForCacheLayout()`
  を足した。**`scripts/local-embedding-pinned-revision.json`（唯一の宣言）を読む——
  ただし「キャッシュの置き場所の解釈にのみ使う」**。`collectActualFiles` がこれを
  受け取り、各ファイルの相対パスを正規化してから `expectedByPath` と突き合わせる。
  CLI の標準出力に、読んだ値（または読めなかった旨）を必ず印字する
  （黙って解釈を変えない）。
- フラット配置と revision サブディレクトリ配置が同じキャッシュディレクトリに同居する
  ケース（CI の実際の形）も扱う——両方が正規化後に同じ論理パスへ写れば、両方とも
  `matched` に数えられる（重複を「不一致」にはしない）。

### もう1箇所——`examples/chat/src/embedding-fingerprint.ts` も revision を渡していなかった

**クローンからの指摘で発覚**: 上の「同居」は、この門の直し方（キャッシュの置き場所の
解釈）だけでは対症療法だった。**根本原因は、`examples/chat` 側に `LocalEmbeddingProvider`
を作る箇所が2つあり、片方（`providers.ts` の `buildEmbedding`）だけが revision を
渡し、もう片方（`embedding-fingerprint.ts` の `runEmbeddingFingerprint`。Issue #565 の
固定入力測定が使う）が渡していなかったことである。** `example-chat` ジョブは
`MNEMORA_LOCAL_EMBEDDING_CACHE_DIR` をこの2箇所で共有しているため、フラット配置
（`embedding-fingerprint.ts` が `main` で落とす）と revision サブディレクトリ配置
（`providers.ts` が固定 revision で落とす）が同居していた——これが実際の「同居」の
発生源である。

⟹ **`embedding-fingerprint.ts` にも `localEmbeddingPinnedRevision()` を渡した**
（クローンの決定「使う側はすべて固定する」の対象に、この経路も含まれる）。

**grep で全数を確認した**（テストを除く `.ts`/`.mjs`/`.js` から
`new LocalEmbeddingProvider(` を検索）: 実物の呼び出しは
`examples/chat/src/providers.ts` と `examples/chat/src/embedding-fingerprint.ts` の
**ちょうど2箇所**であり、両方とも固定 revision を渡すようになった。この事実を固定する
歯として `examples/chat/src/__tests__/local-embedding-revision-wiring.test.ts` を
新設した——特定のファイル名を決め打ちせず、`examples/chat/src` 直下の `.ts` を
機械的に全部走査して `new LocalEmbeddingProvider(` の呼び出しを拾い、
（1）呼び出しがちょうど2箇所であること（3つ目が増えたら要更新という陽性対照）、
（2）すべてが `revision: localEmbeddingPinnedRevision()` を渡していること、の両方を
assert する。変異試験（`cp` で退避・復元）: `embedding-fingerprint.ts` 側だけ
revision を外す ⟹ 新設した歯が赤になった。戻すと緑に戻ることを確認した。

⟹ **CI では、もうこの「同居」は起きなくなる。** `example-chat` ジョブの2つの
呼び出し経路が、どちらも同じ固定 revision で重みを落とすため、キャッシュディレクトリの
中身は revision サブディレクトリ配置だけになる（フラット配置は、旧いキャッシュが
残っている場合にだけ現れうる）。

⛔ **それでも、門の「フラットと revision サブディレクトリの同居」を扱う歯・正規化は
残す。** 理由: (1) 旧いキャッシュ（この修正より前に作られたもの）が `actions/cache`
に残っている間の後方互換のため。(2) 手元で誰かが `revision` を渡さずに
`LocalEmbeddingProvider` を直接使い、同じ `cacheDir` を指す場合にも通用させるため。
——**キャッシュ鍵（ADR 0263）が変わるので、この修正のマージ後の最初の run では
どのみち温かいキャッシュを失う**（新しいキャッシュ鍵の下には、両方とも revision
サブディレクトリ配置のファイルしか入らない）。

⭐ **[Issue #565](https://github.com/takecchi/mnemora/issues/565) の測定（固定入力に
対する `embed()` 出力の sha256・次元数・lscpu）の値が、この修正で「固定 revision の
重みに対する出力」になる。** 直す前は `main` の重みに対する出力だった。sha が同じ
（固定した時点で `main` と内容が一致することを確認済み——上記「sha の出所」参照）なので
**出力される値そのものは変わらないはずである**が、`main` が将来動いても、この測定は
追随せず固定した版のままになる、という点は変わる。

### 訂正: 追記4「4. 門」は「この門は revision を読まない」と書いたが、それは誤りだった
