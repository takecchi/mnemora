# ADR 0694: `check:consumer-install` は、出荷パッケージごとに別の空のプロジェクトへ入れて確かめる

- **状態**: 採用 (2026-10)
- **日付**: 2026-10-07

> **⚠ 本文はクローン miku の委譲先が書いた。オーナー本人の執筆ではない。**
> 方針（案1を採る）はクローン miku の判断で、オーナーの判断ではない。ADR 0346 の本文は書き換えない。この ADR がその決定3の実装の姿を置き換える。

---

## 何が起きたか

[ADR 0346](./0346-consumer-install-check-before-release.md) の陽性対照3（core の `dependencies` から `zod` を消す）が、緑のまま通るようになっていた
（Issue #1890。#1872 の #1121 の確かめ直しで見つかった）。

- 原因は、あとから `@mnemora/testkit` の `peerDependencies` に `zod`（と `vitest`）が入ったこと。
  全パッケージを1つの空のプロジェクトへ入れると、npm が peer の `zod` をトップの `node_modules/zod` へ置く。
  core の dist はそこで `zod` を解決できてしまい、`--install-strategy=nested` の狙い（各パッケージが自分の `dependencies` だけで解決できること）が
  `zod` については効かなかった。core・openai・anthropic のどれから `zod` の宣言が消えても赤にならない。
- 【実測 2026-10-07、直す前】core の `dependencies` から `zod` を消して道具を走らせると、全段が緑で exit 0。
- ADR 0346 の対照3の表（「nested では ESM が赤」）は、この状態では成り立たない。

## 決めたこと

1. **install を、出荷パッケージごとに別の空のプロジェクトへ行う。**各プロジェクトで、そのパッケージの入口だけを、
   型検査2種・ESM・CommonJS で確かめる。repo の外へ、利用者と同じ形で入れる点は ADR 0346 のまま。
2. **1つのプロジェクトへ入れる tarball は、そのパッケージ自身と、`dependencies` で頼る `@mnemora/*` の tarball だけ。**
   `workspace:^` は pack で版に置き換わり、未公開の版を指しうるので、registry ではなく手元の tarball に解決させる必要がある。
   testkit のような別の出荷パッケージは、頼っていなければ入れない。
3. **`peerDependencies` は、こちらから足さない。**利用者の npm が自動で入れる姿（peer はトップへ置かれる）に任せる。
   利用者は自分で peer を入れるか、パッケージマネージャが自動で入れる。どちらでも、peer は利用者のプロジェクトのトップに在るので、
   その形で確かめる。足さずに peer を欠かせると、利用者が普通に受け取る形ではなく、使えない状態を見ることになる。
   peer の巻き上げが効くのは、peer を持つパッケージ（今は testkit）のプロジェクトの中だけで、ほかのパッケージのプロジェクトには届かない。
4. **core の `dependencies` の宣言漏れは、core 自身のプロジェクトで見る。**そこには testkit が居ない。
   ⚠ testkit のプロジェクトでは、core もトップに入るので、testkit の peer の `zod` が core の解決に効く。これは core の宣言漏れを隠すが、
   core のプロジェクトが同じ漏れを赤にするので、見逃しにはならない。
5. **既定の CI には入れない（ADR 0346 の決定5のまま）。**単体テスト（`planConsumerProjects`）だけが既定の CI で走る。
   道具を本物に走らせる歯は CI に入れない。走らせると、1パッケージずつ入れるので install が7回になる。
   【実測 2026-10-07、キャッシュ温まり】合計約49秒（ADR 0346 の26〜37秒より少し長い）。

## 採らなかった案

- **案2: dist の import と `dependencies` の静的な突き合わせ。**やり方そのものが ADR 0346 の「利用者と同じ形で入れる」から変わる。
  動的な `import()` や条件付きの解決を取りこぼす。実際に入れて解決させるほうが、利用者が見る壊れ方に近い。
- **peer を持つパッケージだけを分ける（core だけ別、など）。**どのパッケージが peer を持つかに道具が依存する。
  次に peer を足したパッケージで同じことが起きる。全部を分ければ、その判断が要らない。
- **peer を持つ testkit だけ、peer なしで入れる。**利用者の形から外れる（上の決定3）。

## 陽性対照の表の今の姿

ADR 0346 の表を置き換える。【実測 2026-10-07、main `7d6486e4` を土台に、直したあとの道具】どれも保存した元のファイルへ戻し、`cmp` で一致を確かめた。

| 変異 | 直す前 | 直したあと |
|---|---|---|
| 1. testkit の `exports` から `./fixtures` を消す | exit 1（突き合わせの段ほか） | exit 1（突き合わせの段が赤。入口の一覧から外れるので、値の名前の抜き出しでも止まる） |
| 2′. core の `files` から `.d.ts` を落とす | exit 1（型検査2種） | exit 1（core のプロジェクトの型検査2種だけが赤。ほかのパッケージの型検査は緑のまま） |
| 3. core の `dependencies` から `zod` を消す | **exit 0（全段が緑）** | **exit 1**（core のプロジェクトの ESM・CommonJS が赤。core に頼る openai・postgres・anthropic・local-embedding のプロジェクトも赤。testkit・bullmq は緑——testkit は peer の `zod` が効くため（決定4）、bullmq が緑のままの理由は追っていない） |

変異2（`types` を存在しないファイルへ向ける）が対照として不適切なことは ADR 0346 のとおりで変わらない。

## 引き受けた負債

- install が7回になり、約49秒（キャッシュ温まり）かかる。リリース前に人が打つ道具なので受け入れる。
- testkit のプロジェクトでは、peer の `zod` が core の解決を助ける（決定4）。core の宣言漏れは core のプロジェクトで見る。
- 型だけで使う依存の漏れを捕まえないこと、CommonJS の型・実行時の振る舞いを見ないこと、README の例の依存を見ないことは、ADR 0346 のまま。

## これが覆るとしたら

- 兄弟の出荷パッケージが、`dependencies` ではなく `peerDependencies` で `@mnemora/*` に頼る形になったとき。そのときは決定2の「頼る tarball」の選び方を見直す。
- 時間が利用者の基準（リリース前の手順として許せる長さ）を超えたとき。
