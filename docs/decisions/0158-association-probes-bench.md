## 文脈

**Issue #291**: 連想枠（[ADR 0151](./0151-recall-association-unprompted.md)、
`recall()` の段3.5）は実装されたが、それが**想起の質を動かすか**を測る器が無かった。
ADR 0151「引き受けた負債」2番が自ら割った宿題である。

`examples/chat` の `compare` は⭐門（[ADR 0133](./0133-compare-baseline-and-gate.md)）だが、
想起側の指標 `factStatementSurvived` は基準値の全12行で既に `true` であり
（Issue #291 本文【現物】）、**伸びる余地が無い。⟹ `compare` では測れない。**
測るべきは `hit@k` / MRR を持つ `retrieval` 系のベンチである。

## なぜ既存の probe 集合・既存の指標では測れないか（構造で決まる。実測ではない）

**PR #308 の本文が示した2点を、書き手が `packages/core/src/recall-runtime.ts` を
自分で読んで検算した【現物】。**

1. **除外集合が `withinLimit` を丸ごと含む。**

   ```
   packages/core/src/recall-runtime.ts:844-848
   // 除外集合: 既に返る集合（withinLimit + companions）とアンカー自身。
   const excludeIds = new Set<MemoryId>([
     ...withinLimit.map((c) => c.memory.id),
     ...companions.map((c) => c.memory.id),
     ...anchorIds,
   ]);
   ```

   連想枠の候補生成（段3.5）は、**クエリで `limit`（既定10）以内に既に返っている記憶を
   無条件に除外する。** ⟹ **クエリだけで `limit` 以内に返る gold は、連想枠が
   どれだけ広く探索しても絶対に拾われない。** 既存 `retrieval` の probe（`probe-set.ts`）は
   「query が直接 gold に当たる」ことを前提に設計されているため、この構造とは
   原理的に噛み合わない。

2. **連想の結果は既存の結果集合の「後ろ」に足されるだけで、順位を入れ替えない。**

   ```
   packages/core/src/recall-runtime.ts:955
   const allUnits = [...units, ...associationUnits];
   ```

   `units`（クエリで当たった単位）が先頭に来て、`associationUnits`（連想枠）は
   常にその後ろに連結される。⟹ **連想で浮上した記憶は、`limit=10` の外側
   （11位以降）にしか現れない。** 既存の `hit@k`（`k ≤ 10`）は、連想枠を on にしても
   off にしても構造上ビット単位で同じ値になる——**指標そのものが連想枠の効果を
   観測できない設計になっている。**

**⟹ 1 により「連想枠が拾うべき対象（クエリでは届かない gold）」を持つ probe が
既存集合に無く、2 により「拾えたかどうか」を見る指標（`hit@10` 等）も既存には無い。
probe とメトリクスの両方を新設する必要がある——これは実装の不備ではなく、
連想枠がそもそも「クエリに当たらないものを返す」ために作られた機構であることの
帰結である（ADR 0151「なぜ『チャンネルを1本足す』形にしなかったか」と同じ理）。**

## 決定

1. **`examples/chat` に `association-probes` サブコマンドを足す。**
   `examples/chat/src/association-probe-set.ts`（12 probe。ブリッジ語の字種3カテゴリ
   ×4件）と `association-arm.ts` / `association-json.ts` / `association-format.ts` が
   実装する。probe は「三角形」で設計する——`query ≈ anchor`（クエリで上位に当たる）／
   `anchor ≈ gold`（ブリッジ語を共有）／`query ≉ gold`（クエリでは `limit=10` の外）。
   見る指標は `hit@k` ではなく `goldReturned` / `goldRank` / `mrr` /
   `goldViaAssociationCount`（連想枠経由で返ったか）にする——上の構造上の理由による。

2. **CI に `association-probes` ジョブを1本足す**（`identifier-probes` ジョブと同じ
   体裁: `@mnemora/local-embedding` 固定、鍵・カセット不要、`continue-on-error` にせず
   bench 自体が壊れたときだけジョブを赤くする）。値は Job Summary と artifact に残す。

3. **`compare` の⭐門・`compare-baseline.json`・既存 probe 集合4ファイルには1文字も
   触らない。** 別ファイル・別 arm・別 JSON スキーマにする（ADR 0094 §3 と同じ規律）。

4. **⛔ `association-probes` ジョブを required（門）にしない。** 理由は次節。

5. **本 ADR は「連想枠が想起の質を動かしたかどうか」を主張しない。** 下の
   「確かめていないこと」に理由を書く。**器を足したことだけがこの ADR の主張である。**

## ⛔ なぜこのジョブを required（門）にしないか

**Issue #291 自身が、着手前に条件を明示している【現物】:**

> **`retrieval` ベンチは⭐門ではない**（門は `compare` 1本だけ。ADR 0133）。
> ⟹ **門にするかどうかは別の判断である。**ADR 0133 が門にした根拠は
> 「同一 commit の CI 再実行が `measuredAt` を除いて完全一致した」ことであり、
> `retrieval` について同じことを確かめた記録は無い。**確かめずに門にしないこと。**

**そして前任者が実際に確かめ、一致しなかった（Issue #316）【受・PR #308 の報告】:**

同一 commit を `gh run rerun` で3回実行したところ、`goldReturnedCount` の値自体は
一部の arm で偶然一致することがあったが、**「連想枠の構成員（どのアンカーから
どの gold が浮上したか）が3回とも完全一致した probe は 12件中 0件」**だった
（`maxCount=3` の arm でも 1/12）。⟹ **件数が同じでも、中身が毎回入れ替わっている。**
非決定性は段3.5（連想枠）に局在しており、`off` arm（連想枠なし）は
probe 別の値まで3回完全一致していた（Issue #316【受】）。原因の仮説（HNSW の近似性）は
**まだ確かめていない**（同 issue 自身が明記）。

**⟹ 「同一 commit の再実行が一致することを確かめてから門にする」という
Issue #291 の条件に対し、実際に確かめた結果は「一致しなかった」である。
確かめずに門にしないことも、確かめて分かった不一致を無視して門にすることも、
どちらも同じ理由（Issue #291 の3番）で禁じられる。⟹ 本 ADR は required にしない。**

**この判断は、値が悪かったから緩めたものではない。** 良い値が出ても悪い値が出ても、
**非決定性が解消されない限り、単発の CI run の結果を merge の可否に使ってはいけない**
——これは ADR 0088 §2.1・ADR 0094 §7 が「標本が足りない probe を閾値の門にしない」と
書いたのと同じ規律を、標本数ではなく再現性という別の軸に当てたものである。

## 🔴 この測定は、まだ信頼できる状態にない（測定結果の解釈をここに書かない理由）

**本 ADR は「連想枠が想起の質を動かしたか／動かさなかったか」を一切主張しない。**
PR #308 が実測した数字（Issue #316 / #317 に引用されている）は存在するが、
**次の2つの理由で、その数字を根拠に何かを結論しない。**

1. **Issue #316（非決定性）**: 上述のとおり、連想枠の中身は同一 commit の
   再実行でも一致しない。ある1回の実行で `goldReturned` が増えても、
   それが「連想枠が効いた」ことを示すのか「たまたま近似索引がその回だけ
   別の近傍を返した」ことを示すのか、**この観測だけでは区別できない。**

2. **Issue #317（probe の公正性が破れている）**: probe 集合の docstring
   （`association-probe-set.ts`）は「①アンカーがクエリ上位3件以内 ②gold が
   クエリ順位11位以降 ③cos(anchor, gold) ≥ 0.5 ④gold がアンカー近傍の40位以内」の
   4条件を「12/12で実測済み」と主張しているが、**新しい haystack での実測は
   これと食い違う**——**連想枠を渡さない `off` arm でも gold が 2/12 返っている**
   （本来は条件②により0/12のはずである）。⟹ **少なくとも2件の probe は、
   そもそも連想枠が無くても答えが出る設計になっている。** この2件を分子に含めた
   `goldReturnedCount` の比較は、arm 間の差を大きく見せる方向にも小さく見せる
   方向にも歪みうる。

**⟹ #316 は「同じコードで測っても値が揺れる」、#317 は「そもそも測ろうとしている
対象（12件の三角形）の一部が設計どおりに成立していない」——**性質の異なる2つの
不備であり、**どちらか一方が直っても、もう一方が残っている限り数字を解釈できない。**

**だから本 ADR は、次を「確かめていないこと」として明記するに留める** ——
「連想枠は想起の質を上げる」とも「上げない」とも書かない。書けるのは
「**この器はまだ、その問いに答えられる状態にない**」までである。

## これが覆るとしたら

1. **Issue #316 の原因（甲: ingest ごとの索引差／乙: 同じストアへの引き直しでも
   揺れる）が切り分けられたとき** ——(乙) であれば ADR 級の変更（近似探索への
   依存を外す・`ef_search` を上げる）が要り、本 ADR の「まだ器を作っただけ」という
   立ち位置ごと次の ADR に引き継がれる。
2. **Issue #317 の2件の probe が直り、`off` arm が 0/12 に戻ったことが CI で
   確認されたとき** ——「確かめていないこと」の一部が埋まる。ただし #316 が
   残っていれば、依然として結論は書けない。
3. **#316 と #317 の両方が解決し、複数回の CI 再実行で連想枠の構成員が
   安定して一致するようになったとき** ——**そこで初めて「連想枠が想起の質を
   動かしたか」を書く ADR（あるいは本 ADR への追記）が書ける。** その ADR は
   ADR 0151「これが覆るとしたら」3番（動かなかったら落とす）に対する答えを
   持つことになる。
4. **`association-probes` の母数（12件）で、CI 再実行の一致率に上限を
   置けると実測できたとき** ——ADR 0094 §7 と同じ条件が満たされたことになり、
   required にするかどうかを**改めて**判断できる。**今回の「required にしない」は
   その条件が満たされていないことの反映であり、恒久的な決定ではない。**

## 追記（Issue #317 の修正、2026-09-16）

**本節は、本 ADR が既に足すことを決めた bench の probe 集合が、自ら宣言した
条件（上の「4条件」）を破っていたことを訂正する。新しい ADR は起こしていない**
——決定（bench を足すこと自体）は変わらず、変わるのはその bench が自ら主張した
実測条件の食い違いを直したことだけだからである。

**何が破れていたか**: 条件② 「gold はクエリ単独では11位以降にしか出ない」が
`ascii-project` / `name-trip` の2件で破れていた。`off` arm（連想枠なし）の
`goldRank` がちょうど `recallLimit`（10）で、クエリ単独で `limit=10` 以内に
gold が入っていた（Issue #317 本文、CI run `35020771347`）。

**どう直したか**: `ASSOCIATION_PROBES`（`bridge`/`query`/`anchor`/`gold`/`distractor`）
は1文字も変えていない。`ASSOCIATION_HAYSTACK` に、この2 probe 専用の filler を
2文だけ足した——**話題は query に近いが、bridge 語を持たない**（Issue #317 の
コメントが名指しで推奨した方向）:

```
"担当している別件の見積もりをまだ作成していません。" // ascii-project 用
"来週、大阪への出張の日程を変更しました。"           // name-trip 用
```

**手元の素コサイン計算**（`@mnemora/local-embedding`、CI と同じ
`ruri-v3-30m/sym/256次元`）で、追加前は `ascii-project`/`name-trip` とも
`goldRank=10`（CIの実測と一致）、追加後は `goldRank=11`/`12` に下がり、
他10 probe の相対順位（`goldRank`/`anchorRank`/`distractorRank`）は変化しないことを
確認した。**素コサインは `recall()` の実ランキングと完全一致しないため、
最終判定は CI に委ねている**（PR 本文参照）。

**`name-meeting` について**: `maxCount=10` でも一度も gold を返していない事実
（旧・新 haystack のどちらでも `goldRank=null`）を、本ファイルの docstring に
「確かめていないこと」として明記した。**場を弱める方向の変更はしていない**
——Issue #317 のコメントが名指しで禁じている。

**#316（非決定性）は本追記の範囲外であり、未解決のまま。** 上の「引き受けた
負債」1・2番はそのまま残る——②の一部が直っても、①が残っている限り
`goldReturnedCount` の値を「連想枠が効いた」の証拠として読めない。
