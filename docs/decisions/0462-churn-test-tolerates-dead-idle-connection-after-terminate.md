# ADR 0462: 全接続を切る反復の歯は、切った直後に死んだ待機中の接続を掴む `57P01` を、`max` 回まで受け入れてから「新しい transaction が通る」を縛る

- **状態**: 採用 (2026-10)
- **日付**: 2026-10-01

クローン miku の委譲先（マネージャー mgr-3a4ae979）が書いた。直し方の線（テストの側の揺らぎならテストを直す）はクローン miku が決めた。オーナーの判断ではない（[ADR 0220](./0220-issue-comment-author-does-not-distinguish-owner-from-agent.md)）。
**オーナーが覆せる点は「これが覆るとしたら」にまとめてある。**
出所の区別: 【現物】は読んだコード・CI のログ、【実測】は手元（PostgreSQL 17、`initdb` で立てた自分専用のインスタンス、`--encoding=UTF8 --locale=C.UTF-8`）で走らせた結果、【判断】は担い手の判断。

- **文脈**:

  [ADR 0444](./0444-pool-begin-release-rollback-error-preserved.md) が足した `packages/postgres/src/__tests__/transaction-begin-release.postgres.test.ts` の
  「負荷の最中に全接続を切る反復をしても、pool は枯れない」が、CI で2回落ちた。

  1. **【現物】** 落ちた2回は、どちらも同じ箇所・同じ形だった。
     - PR #1567 の head `ca0b4e78`（run `36825869997`、`packages/postgres` の `server_encoding=UTF8` の脚）。落ちたジョブだけを再実行すると緑。
     - main `5e7f1c2b`（#1567 のマージ後、run `36840797222` の attempt 1、`server_encoding=SQL_ASCII` の脚）。attempt 2 は緑。
     - どちらも `transaction-begin-release.postgres.test.ts:170:7`（反復の後の「健全な transaction が通る」の `client.db.transaction`）で、
       `Failed query: begin`、cause は `57P01`（`terminating connection due to administrator command`）。その前の2つの `expect`
       （worker が終わる・借りられたままが 0）は通っていた。
  2. **【現物】** この `it` では、worker の中の失敗はすべて `catch` で握っている。テストまで上がる `begin` の失敗は、170行目の最後の transaction しかない。
  3. **【判断】筋**: 25回目の `pg_terminate_backend` は、pool で**待機中**の接続の backend も切る。pg-pool が待機中の接続の死に気づくのは、
     socket の error/end のイベントが届いてからで、非同期である。反復の直後に最後の transaction を借りると、まだ取り除かれていない死んだ接続を掴み、
     `begin` が `57P01` で落ちる。待機中の接続が死んでいることは使って初めて分かる——これは pool の一般の振る舞いで、
     `packages/postgres/README.md` の「例外の見分け方」も再起動の最中に出る例外の形として書いている。
     実装（`createPostgresClient` が `begin` の失敗で `release(err)` する）は、借りられたままが 0 に戻っているとおり枠を漏らしていない。
     ⟹ **テストが「切った直後の最初の1回は必ず通る」と仮定していたのが揺らぎの元**であり、実装の穴ではない。
  4. **【実測】再現率**: 直す前のテストで、この `it` だけを名指しして 40 回走らせると、**3 回（7.5%）**が CI と同じ形（`Failed query: begin`・`57P01`）で落ちた。

- **決めたこと**:

  1. **最後の transaction を、切断の種類の失敗だけを `max`（3）回まで受け入れる形にした。** cause の連鎖のどこかに SQLSTATE `57P01` か
     pg の切断の文面（`terminating connection`・`Connection terminated`）がある失敗だけを受け入れ、それ以外の失敗はそのまま投げる。
     死んだ待機中の接続は高々 `max` 本なので、`max` 回を超えた切断の失敗も投げる。
  2. **受け入れるたびに、借りられたままが 0 に戻ることを `expect` で縛る。** `begin` の失敗で接続を返す（ADR 0444 BG-1）ことを、この経路でも確かめる形にした。
     最後に新しい transaction が通ること、借りられたままが 0 であることは、従来どおり縛る。
  3. **実装（`packages/postgres/src`）は変えていない。** 変えたのはテストの1ファイルだけ。CHANGELOG は、利用者に見える変更が無いので足していない。

- **測ったこと**（【実測】。手元の PostgreSQL 17、ポート 56258）:

  | 形 | 回数 | 結果 |
  |---|---|---|
  | 直す前のテスト、この `it` だけ | 40 | 37 緑・**3 赤**（3 回とも `Failed query: begin`・`57P01`） |
  | 陽性対照: 直す前のテストの最後の transaction の直前に、`pg_terminate_backend` をもう1回差し込む（待たずにすぐ借りる） | 8 | 6 緑・**2 赤**（`57P01`） |
  | 同じ変異を、直したテストに入れる | 8 | **8 緑** |
  | 直したテスト、ファイル全体（4 本） | 24 | **24 緑** |

  - 陽性対照の変異は、差し込んだ切断の後に `sleep(5)` を挟むと、直す前の形でも 8 回とも緑だった（5ms の間に pool が死んだ接続を取り除く）。
    揺らぎの窓はそれより狭い。
  - **24 回緑は、それだけでは強い根拠ではない**（直す前の失敗率 7.5% のとき、24 回とも緑になる確率は約 15%）。根拠の芯は陽性対照（直す前 2/8 赤 → 直した後 0/8）に置く。
  - CI の SQL_ASCII の脚に相当する手元の形（`--encoding=SQL_ASCII --locale=C`）では走らせていない。落ちた筋はエンコーディングによらない（2回は UTF8 と SQL_ASCII の両方の脚だった）。

- **採らなかった案**:
  - **最後の transaction の前に、pool が死んだ接続を取り除くまで待つ**（`pool.totalCount` が減るのを待つ等）。反復の最後の切断の後に worker が新しく開いた
    生きた接続も残るので、「何本減れば済んだか」を決められない。待つ時間で揺らぎを薄めるだけで、窓は消えない。
  - **反復の後に `sleep` を挟む**。陽性対照で 5ms でも窓が閉じたが、CI の器の負荷では足りる長さを決められない。
  - **切断の種類を問わず、失敗をすべて受け入れる**。`begin` 以外の失敗（たとえば借りられたままが漏れて別の例外になる形）まで握りつぶし、歯が弱くなる。

- **引き受けた負債**:
  - 受け入れる切断の印（`57P01`・pg の文面）は pg 8.23.0 の現物に合わせた。pg の文面が変わると、切断の失敗を受け入れられず、この歯がまた揺れる（赤い側に倒れるので、黙って弱くはならない）。
  - 待機中の接続が死んでいることを使って初めて知る、という pool の振る舞い自体は変えていない（利用者の側でも、再起動の直後の最初の問い合わせは同じ形で落ちうる。README の「例外の見分け方」が書いている）。

- **これが覆るとしたら**:
  - 「再起動の直後でも、最初の問い合わせは落ちない」を `@mnemora/postgres` の約束にすると決めたとき（pool の手前で再試行する等）。そのときはこの歯も、受け入れずに縛る形へ戻す。
  - 直したあとも同じ `it` が CI で落ちたとき。筋の読み（死んだ待機中の接続）が足りていないので、ログから切り分け直す。
