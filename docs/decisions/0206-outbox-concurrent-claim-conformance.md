- **【実測】** — この書き手が自分の手で走らせて確かめた。

## 問い

**`@mnemora/testkit` の `OutboxStore` 適合テストは、「検査する契約」に同時 claim 安全性を
掲げながら、それを1本も検査していなかった。**

[Issue #424](https://github.com/takecchi/mnemora/issues/424) がこれを指摘し、
[PR #431](https://github.com/takecchi/mnemora/pull/431) が **docstring に「⚠ これは検査していない」を
名乗らせる**ところまでを入れた（#424 の「案C」）。**歯そのものは1本も足していない。**

**【現物】2026-09-17、`main` = `cd4d812`**:

```
$ grep -c "Promise.all" packages/testkit/src/outbox-store-conformance.ts
0
$ grep -c "^    it(" packages/testkit/src/outbox-store-conformance.ts
15        ← 15本すべて逐次 await
```

⟹ **本 ADR は、その歯を足す。**[Issue #205](https://github.com/takecchi/mnemora/issues/205) が
逐語で「**`OutboxStore.claimBatch` の同時 claim 適合テスト（これは今すぐ価値がある。独立）**」
「**`packages/bullmq` 本体（1 の後）**」と定めた、その **1本目**である。

**⚠ #424 は「決める前に測るべきこと」を2つ挙げ、どちらも未実測のまま閉じた**（逐語）:

> 1. **`Promise.all` で同一 store を叩いたとき、`pg.Pool` 上で本当に2つの文が時間的に重なるか。**
> 2. ⭐⭐ **`FOR UPDATE SKIP LOCKED` を外す変異を入れたとき、その `it` が赤くなるか。
>    赤くならないなら、その歯は飾りである。**

**本 ADR は、まずこの2つを測ってから決めている。**

## 測ったこと【実測】

器: 手元に立てた PostgreSQL 17 + pgvector（`AGENTS.md`「手元で Postgres を立てる」節の手順。
専用ポート・専用 PGDATA。共有インスタンスには触っていない）。

### 1. `Promise.all` は `pg.Pool` 上で本当に重なる

```
pool.options.max = 10          ← client.ts は max を指定しないので pg の既定値
overlap: {"a":{"pid":32195,...},"b":{"pid":32196,...},"overlap":true,"distinctPid":true}
```

**別バックエンド PID で、実行区間が重なる。**⟹ `max` は 1 ではなく、構造的に逐次化される
心配は無い。**#424 の「確かめていないこと」に挙がっていた `pg.Pool` の `max` は、ここで埋まる。**

### 2. `FOR UPDATE SKIP LOCKED` を外すと、この歯は赤くなる

本 ADR が足した歯（下の「決定」）に対して、`packages/postgres/src/outbox-store.ts` を
`cp` で退避してから2通りの変異を入れた（⛔ `git checkout` は使っていない。`AGENTS.md`）。

| 変異                                                  | 試行 | 結果                                              |
| ----------------------------------------------------- | ---- | ------------------------------------------------- |
| （変異なし）                                          | 5    | 5回とも **GREEN**。**偽陽性は観測していない**     |
| **(i) `FOR UPDATE SKIP LOCKED` を丸ごと削る**         | 3    | 3回とも **RED**（`duplicateRounds` = 9 / 10 / 9） |
| **(ii) `SKIP LOCKED` だけ外して `FOR UPDATE` にする** | 2    | 2回とも **GREEN**                                 |

⟹ 🔴 **この歯が守っているのは `FOR UPDATE` の行ロックであって、`SKIP LOCKED` ではない。**

READ COMMITTED 下では、ロック待ちで止まった側はロック解放後に行を再フェッチして `WHERE` を
再評価する。先に claim した側が書いた `claimed_at` がそこで見えるため、その行は候補から外れる。
**`SKIP LOCKED` が足しているのは「詰まらないこと」だけである。**

⚠ **「`SKIP LOCKED` は throughput 側」は、詰まりを直接観測して言っているのではない。**
上の実測が見ているのは正しさ側だけであり、**機構からの推論である。**

### 3. ラウンド数を減らすと、壊れた実装を取りこぼす

**変異 (i) を入れた状態で、ラウンド数だけを変えて撃った:**

| ラウンド数 | 試行 | 結果                                               |
| ---------- | ---- | -------------------------------------------------- |
| **1**      | 6    | 5回 RED / 🔴 **1回 GREEN（壊れた実装を見逃した）** |
| **10**     | 4    | 4回 RED（見逃し無し）                              |

⟹ **1ラウンドでは、実際に取りこぼす。**⛔ **ラウンド数を減らさないこと**——
**見逃しは赤くならないので、減らしたことが表に出ない。**

## 決定

### 1. `OutboxStoreConformanceOptions` に任意の能力フラグを足す

```ts
supportsRealConcurrency?: boolean;
```

`true` のとき並行 claim の歯が走り、**省略/false のときは `it.skip` になる。**
⟹ **測っていないことが、緑ではなく skip として見える。**

- **`packages/postgres` は `true`** ⟹ 実 DB の `postgres` ジョブ（`ci.yml` の `test:db`）で毎 PR 走る。
- **in-memory プレースホルダは渡さない** ⟹ skip。**【現物】その `claimBatch` は本体に `await` を
  1つも含まないため、`Promise.all` で並べても完全に逐次化される**——`true` を渡すと
  「何も測らずに緑」になる。呼び出し側にその旨のコメントを置いた。
- **任意フィールドなので、公開型の破壊的変更にはならない。**

### 2. 歯の判定は「返った id の和集合に重複が無い」ことだけにする

ラウンドごとに、claim 可能なジョブを**ちょうど1本**置き、`limit: 1` で **8並行**に撃つ。
これを **10ラウンド**回し、**重複が出たラウンド数が 0 であること**を検査する。

⛔ **「合計が1本である」ことは検査しない。**競合下では `SKIP LOCKED` 相当の実装が
「ロック中の行を、この呼び出しでは単に飛ばす」だけで、どれか1本が必ず拾う保証はしていない
【実測: ジョブ5本・`limit=3`・4並行で、合計が5未満になるラウンドが出た】。
**拾い残しは次の tick が拾う**——設計上の許容範囲であって故障ではない。

### 3. この歯が測っていないことを、歯の側に書く

- ⛔ **`SKIP LOCKED` を守る歯ではない**（測ったこと 2）。
- ⚠ **`duplicateRounds === 0` は「このラウンド数では出なかった」以上を主張しない。**
- ⚠ **複数プロセスが実際にネットワーク越しに撃つ状況は、いまも測っていない。**
  この歯は**単一プロセス内の複数接続まで**である。

## 採らなかった案

### 案A: 全 adapter に対して無条件に `Promise.all` を走らせる

⛔ **採らない。**in-memory で「意味なく緑」になる（上記のとおり完全に逐次化される）。
**「測っていない」を「問題なかった」に潰す。**

### 案D: in-memory 実装にわざと yield 点を作る / 案E: suite が複数プロセスを立てる

⛔ どちらも採らない。理由は #424 本文のとおり（テストのために実装を曲げる／adapter 作者全員に
プロセス監督を要求する）。本 ADR で新たに付け加える根拠は無い。

### 🔴 案F: 能力フラグではなく「加温フック」を要求する —— **一度採り、実測で崩して戻した**

**この節が、本 ADR でいちばん残す価値のある部分である。**

**当初、次の形を採ろうとした:**

```ts
prepareConcurrentClaim?: (concurrency: number) => Promise<void>;
```

**根拠はこうだった【実測、ただし後述のとおり誤り】**——`pg.Pool` は遅延接続であり、接続が
張られていないと `Promise.all` の各呼び出しが接続確立でずれて**競争の窓が閉じる。**
実際、**1ラウンドの探り棒は、変異 (i) を入れても緑だった。**
⟹ 「boolean のフラグは『測れる』と宣言させるだけで、**実際に測れる状態を作らせない**」
「adapter に**手続きを出させれば**、宣言だけの嘘は防げる」と考えた。

**🔴 歯を実装してから測り直したところ、この根拠は2箇所で崩れた。**

1. **ラウンドのループ自体が、プールを温めていた。**ラウンド1の8本同時 `claimBatch` が接続を
   張るので、**ラウンド2以降は加温済みである。**⟹ 加温フックが効くのは**1ラウンドのときだけ**
   （【実測】1ラウンド: 加温なし 5/6 検出 → 加温あり 6/6 検出）。
   **10ラウンドでは、加温の有無にかかわらず 4/4 で検出した。**
2. **空のフック（何もしない `prepareConcurrentClaim`）を渡しても、歯は赤くなった**【実測】。
   ⟹ **フックも嘘をつける。**「宣言は嘘をつけるが、動くものは嘘をつけない」は**成り立たない**
   ——**空のフックも「渡された」し「呼べる」からである。**

⟹ ⭐ **手続きを要求しただけでは、嘘は防げない。**
**「出させるもの」は、*出せたことを検証できる*形でなければ、申告と変わらない。**
本件では suite 側にその検証手段が無く、**案F が boolean に対して持つ優位は
「1ラウンド時の見逃しを消す」だけに縮んだ。**公開型に手続きを持ち込む対価として釣り合わない。

⟹ **boolean に戻した。**⛔ **次に「フックにすべきでは」と考えた人は、上の2点を測り直さなくてよい。**

## 引き受けた負債

### 1. 🔴 `supportsRealConcurrency: true` が正しいかを、suite 側は検証できない

**逐次化される adapter が `true` を渡せば、何も測らずに緑になる。**
⟹ **この歯は「嘘をつかない adapter」を前提にしている。**

⭐ **これは [ADR 0205](./0205-local-embedding-pipeline-required-interface.md) と同じ形の負債である。**

|              | 何を強制したか                                                | 消えた壊れ方                                      | ⛔ 消えていない壊れ方                                                                                          |
| ------------ | ------------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **ADR 0205** | `LocalEmbeddingPipeline` に `maxInputTokens` の**宣言**を強制 | 宣言し**忘れる**                                  | **宣言した上限を実装が守るか**は型では見えない（[Issue #449](https://github.com/takecchi/mnemora/issues/449)） |
| **本 ADR**   | 並行を測れる adapter だけに `true` を**宣言**させる           | 並行を**測っていないのに緑**になる（既定が skip） | **宣言どおり本当に並行するか**は suite では見えない                                                            |

⟹ **「宣言を強制する歯は、宣言の _中身_ までは守れない」**という同じ限界である。
⛔ **本 ADR はこれを解かない。**名指しするところまでである——**次にこの層を強くする人が、
2箇所を同じ手で解けるかもしれない。**

### 2. 単一プロセス内の複数接続までしか測っていない

**複数プロセスが実際にネットワーク越しに撃つ状況は、いまも測っていない。**
`docs/architecture.md`「確かめていないこと」節と
[ADR 0032](./0032-outbox-claim-lease.md)「確かめていないこと」節の、この部分は**残る。**
⚠ **ADR 0032 自体は当時の記録として書き換えていない。**

### 3. `SKIP LOCKED` を守る歯が無い

**測ったこと 2 のとおり、`SKIP LOCKED` だけを外しても、この歯は赤くならない。**
⟹ **`SKIP LOCKED`（詰まらないこと）を守る歯は、別に要る。**本 ADR は足していない。

## これが覆るとしたら

- **in-memory 以外に「逐次化される adapter」が現れ、`true` を渡して緑を得たとき。**
  ⟹ 負債1 が実害になる。そのときは「宣言の中身を検証する」層が要る（ADR 0205 / Issue #449 と同じ手）。
- **`packages/bullmq` が入り、複数プロセスの同時 claim が既定経路になったとき。**
  ⟹ 負債2（単一プロセス内までしか測っていない）が実害になる。
  **#424 が「`packages/bullmq` が入った日に、この判定は即座にひっくり返る」と書いたのはこの点である。**
- **ラウンド数や並行数を変えたくなったとき。**⟹ 測ったこと 3 の表を測り直すこと。
  ⛔ **測らずに減らさない。見逃しは赤くならない。**
