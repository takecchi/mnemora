# ADR 0200: `adr-renumber.mjs` は付け替えたときに PR タイトルの修正を促す警告を出す — 道具は `gh` を叩かない（Issue #405）

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-17

**⚠ 各主張の出所を分ける**（ADR 0132 / 0137 / 0179 の体裁を踏む）。

- **【現物】** — この repo のコード・文書を書き手が読んで確かめた。
- **【実測】** — この書き手が自分の手で `git`/`gh`/`vitest` 等を走らせて確かめた。
- **【受】** — 報告として受け取り、再導出していない（出所を明記する）。

## 問い

[Issue #405](https://github.com/takecchi/mnemora/issues/405)。`scripts/adr-renumber.mjs`
（[ADR 0179](./0179-adr-number-assigned-at-merge.md)）は、ADR 番号の衝突をマージ直前に
機械的に解消する——ファイル名・見出し・このブランチが追加した行の中の参照はすべて
書き換わる。**しかし PR タイトルと、squash merge が生成するコミットのタイトルだけは
書き換えられない**（GitHub 側の状態であり、リポジトリ内のファイルではないため）。

[PR #399](https://github.com/takecchi/mnemora/pull/399) で実際に踏んだ
（issue 本文に詳細）。`main` に着地したコミット:

```
e47952e fix(core,docs): ann_unreached を窓が満杯でも鳴る形に直す（ADR 0192） (#399)
```

**この変更の ADR は実際には `0193`**（`0192` は無関係な別の ADR）。`adr-renumber.mjs` が
番号を付け替えたにもかかわらず、PR タイトルは古い番号のまま残り、そのまま squash commit
のタイトルとして `main` の履歴に固定された。

issue は5案を並べ、マネージャーが着手コメント（実測つき）で **案1（手順に一手を足す）＋
案2（`adr-renumber.mjs` が警告する）** を採ると決めた。本 ADR はその実装と、
却下した案3・4・5の記録である。

## 自分の手で数え直した（マネージャーの実測の検算）

マネージャーの着手コメントは、`main` の全281 commit（`origin/main` =
`4b92134c45b2377b9f5bb501ef921ab3e8b9cee3`）について、タイトルの `ADR NNNN` と
その commit が `docs/decisions/` に対して行った変更を突き合わせ、次を報告していた:

| | マネージャーの報告 |
|---|---:|
| `main` の commit 総数 | 281 |
| タイトルに `ADR NNNN` を含む commit | 167 |
| うち、その番号の ADR ファイルを触っていない commit | 15 |
| そのうち実際の紛れ（誤った番号を名乗っている） | 2 |
| そのうち正当な参照（既存 ADR を根拠として引いているだけ） | 13 |

**【実測】自分の手で同じ `origin/main`（`4b92134c...`）に対して独立に数え直した。**
`git rev-parse origin/main` が `4b92134c45b2377b9f5bb501ef921ab3e8b9cee3` を返すことを
まず確認し（マネージャーが見た時点と同じ sha）、次の手順で検算した:

1. `git log origin/main --format=%H` で全 commit の sha を取る → **281**。
2. 各 commit について `git log -1 --format=%s <sha>` からタイトルを取り、
   `/ADR (\d{4})/g` で番号を抽出する。1つ以上ヒットした commit → **167**
   （マネージャーの数字と一致）。
3. 各 commit について `git show --name-status --format= <sha> -- docs/decisions/`
   で「その commit が touch した `docs/decisions/*.md`」のファイル名から番号を取る
   （status は問わない——追加だけでなく修正・rename も含む）。
4. タイトルの番号のどれもが touch したファイルの番号に含まれない commit を数える
   → **15**（マネージャーの数字と一致）。

**⚠ 手順3を「追加（A status）だけ」に絞ると 31 件に増える**——`docs/roadmap.md` や
`docs/autonomy.md` のような「既存 ADR への正当な言及を書き足すだけで、ADR ファイル
自体は touch しない」commit まで誤って「紛れ」に数えてしまうため
（例: `a3b756e`「§1.1 に…一手を足す（ADR 0183）」は ADR 0183 を新規追加せず、
docs 側で言及しているだけ）。**touch（追加+修正+rename）で見て初めてマネージャーの
15件と一致する。**

15件の内訳を自分で読んで分類した:

- **紛れ2件**（マネージャー報告と同じ2件）:
  - `e47952e`（`0192` と名乗るが実体は `0193`。issue 本文の現物）
  - `2840492`「examples/chat が memory_usage を報告する…（Issue #301 / ADR 0161）」
    — 実際に追加した ADR は `docs/decisions/0163-memory-usage-reporting-example-chat.md`
    （`git show --name-status 2840492 -- docs/decisions/` で `A` を確認）。
    `0161`（`Runtime.getRecall` を足す ADR）とは無関係。
- **正当な参照13件**（残りすべて）。代表例:
  - `8abfb0c`「連想枠（ADR 0151）が想起の質を動かすかを測る association-probes ベンチ」
    — 実際に追加したのは `0158-association-probes-bench.md`。`0151` は連想枠そのものの
    既存 ADR への言及であり、タイトルは「連想枠（の話）」を指しているだけで
    「この PR の ADR が 0151 だ」とは主張していない。
  - `4545d81`「CIの履歴から失敗率を数えると…§4に足す（ADR 0141 §2.1）」
    — 既存 ADR の一節を根拠として引用しているだけ。
  - `fd6ee53`「掃引(ADR 0114)をexamples/chatベンチへ配線する」
    — 実際に追加したのは `0119`。`0114` は配線対象の既存機能の ADR。
  - `a5a7667`「… / ADR 0119・0120 の後続」— 明示的に「後続」と書いてある。実際に
    追加したのは `0121`。
  - 残り9件も同様に、既存 ADR を根拠・前提として文中で引いているだけで、
    その PR 自身の ADR ではない。

**⟹ 15件中2件が紛れ、13件が正当な参照——偽陽性率 13/15 ≈ 86.7%（マネージャーの
「≒87%」と一致）。** 自分の手で独立に再現できたので、この数字を根拠として案5を
却下する（下記）。

## 決定

### 1. 案2 — `adr-renumber.mjs` が付け替えたときに警告する

`scripts/adr-renumber-lib.mjs` に純関数 `renumberedTitleWarning(renames)` を足した。
`renames` が空（付け替えが1本も起きなかった）なら `null` を返し、1本以上あれば
「どの番号がどの番号へ付け替わったか」の一覧と、「PR タイトルと squash commit の
タイトルは機械が直せない。マージ前に `gh pr edit <PR番号> --title ...` で直すこと」
という文言を含む文字列を返す。

`scripts/adr-renumber.mjs` の `performRenumber()` は、付け替え（`git mv` と参照の
書き換え）が終わったあと、この関数の戻り値が `null` でなければ `console.error` で
出力する。**付け替えが起きなかったときは何も出さない**——毎回出ると読み飛ばされる
ため（issue の案2自身が明記している懸念）。

⛔ **`gh` は呼ばない。** 出力で促すだけであり、`gh pr edit` を実行するのはマージする
側の人間（または後続の手順）である——これは案3を却下した理由（採番の道具が
GitHub API を叩くようになると、repo 内で完結している性質が壊れる）を守るための、
意図した制約である。

### 2. 案1 — `docs/autonomy.md` §4 の手順に一手を足す

§4「ADR PR をマージするとき、索引の再生成を忘れる」の行にある手順:

```
git fetch origin main && git merge origin/main
node scripts/adr-renumber.mjs
node scripts/generate-adr-index.mjs
commit → push → CI の緑を引き直す → merge
```

に、`adr-renumber.mjs` の直後・`generate-adr-index.mjs` の前に次を挿し込んだ:

> 付け替えが起きたら（`adr-renumber.mjs` が標準エラーに警告を出す）、その場で
> `gh pr edit <PR番号> --title "...（ADR <新番号>）"` を実行して PR タイトルも直す。

**この位置（`adr-renumber.mjs` の直後・マージより前）でなければならない理由**:
squash merge が作るコミットのタイトルは、マージ実行時点の **PR タイトル**から
作られる。⟹ PR タイトルを直すのが「マージの前」であれば、生成される squash commit
のタイトルも正しくなる。**しかしマージの「後」に気づいて直そうとしても、
squash commit のタイトルは `main` の履歴として既に確定しており、`gh` にも
書き換える手段が無い**（PR #399 の事故そのものがこれを示している——PR #399 の
タイトルは事後に直せたが、`main` に着地した squash commit のタイトルは直っていない
——issue 本文「今回の後始末」参照）。⟹ **「付け替えた直後・マージ前」以外の
タイミングでは、この一手は意味を持たない。**

## 検討して採らなかった案

- **案3（`adr-renumber.mjs` が `gh pr edit` まで叩く）**: **却下**——マネージャーの
  指示による。`adr-renumber.mjs`（ADR 0179）は「採番がリポジトリ内で完結する
  機械的な道具である」という性質を持つ。`gh` を呼ぶようになると、この道具は
  ネットワーク・認証・GitHub 側の API 仕様に依存するようになり、`--check` の
  ような読み取り専用の使い方（CI や他のスクリプトから呼ばれる可能性がある）にも
  副作用のリスクが波及する。案2（警告するだけ）で「忘れにくくする」という
  利益の大部分は得られる一方、「道具が GitHub API を叩く」という性質の変化は
  避けられる。
- **案4（PR タイトルに ADR 番号を書かない習慣をやめる）**: **却下**——issue 本文が
  明記する通り、ADR 番号をタイトルに書く習慣は `gh pr list` や
  `git log --oneline` で「何の PR か」を一目で分かるようにする実利があり、
  「捨てる判断は安くない」。この問題（付け替え後にタイトルが追随しない）は、
  習慣そのものをやめなくても、案1・案2で緩和できる。
- **案5（CI の歯——PR タイトルの ADR 番号と、実際に追加/変更した
  `docs/decisions/*.md` の番号が一致するかを検査する）**: **却下**。
  自分の手で `origin/main`（`4b92134c...`、281 commit）を検算し
  （上記「自分の手で数え直した」）、次を確認した:
  - 素朴な歯（「タイトルが名乗る番号の ADR ファイルを、その commit が touch して
    いるか」）は 167本中 15本を赤くする。
  - **うち13本（≈87%）は偽陽性**——既存 ADR を根拠・前提として文中で引用して
    いるだけで、その commit 自身の ADR ではない（`fd6ee53`「掃引(ADR 0114)を
    …」、`a5a7667`「… ADR 0119・0120 の後続」等）。
  - 機械には「このタイトルは**自分の** ADR を名乗っている」のか「**他人の**
    ADR を参照している」のかを区別する手段が無い——両方とも「タイトル文字列に
    `ADR NNNN` が出現する」という同じ形をしている。
  - ⟹ **この歯を required にすると、偽陽性率87%の警報を毎回人が手で見分けて
    通す運用になる。**「壊れているのに気づかない」問題を、「毎回誤検知に
    付き合う」問題に置き換えるだけであり、割に合わない。
  - **確かめていないこと**: 「タイトルが自分の ADR を名乗っている」ことを機械的に
    見分けられる、もっと精度の高いヒューリスティック（例: タイトル末尾の
    `(ADR NNNN)` という決まった位置の記法だけを対象にする、等）を検討していない
    ——今回は素朴な歯（issue が示した形そのもの）だけを検算し、それが87%の
    偽陽性を持つことを示した。より狭い記法規則を敷いた歯であれば成立する
    可能性は残る（下記「これが覆るとしたら」）。

## 引き受けた負債

1. **警告は出力されるだけであり、読み飛ばされうる。** 案2の設計そのものが
   「人が読んで `gh pr edit` を実行する」ことに依存しており、マージする側が
   出力を見落とせば、PR #399 と同じ事故が再発する。案3（道具が `gh` を叩く）を
   却下した以上、この負債は引き受けたものである——**「人が警告を読み飛ばしたら
   同じことが起きる」**。
2. **警告は `adr-renumber.mjs` の標準出力を見ている場合にしか届かない。**
   CI ジョブとしてこの CLI を自動実行する設計にはなっていない（ADR 0179 の
   「確かめていないこと」と同じ前提）ため、マージする側が手元で実行して
   出力を見ることに依存する。
3. **`docs/autonomy.md` §4 に一手足したが、それも文書であり、規律ではなく
   注意力に依存する**（`AGENTS.md` が「複製した瞬間からずれ始める」と
   同じ理由で警告している族の一種）。警告出力（案2）がこの負債を機械的な
   信号で補っているが、「信号を見て動く」のは依然として人である。

## これが覆るとしたら

- **案3（`gh` を叩く）を却下した判断が覆るとしたら**——警告の見落としが実際に
  繰り返し発生し（この ADR の「引き受けた負債」1番が顕在化し）、かつ
  「採番の道具が repo 内で完結する」という性質より「見落とし事故を無くす」
  利益が明確に上回ると判断されたときである。その場合も、`gh pr edit` を
  叩く前に PR 番号をどう特定するか（`adr-renumber.mjs` 自身は PR 番号を
  知らない——呼び出し側が渡す必要がある）を新たに設計する必要がある。
- **案5（CI の歯）を却下した判断が覆るとしたら**——タイトルの記法を
  「自分の ADR を名乗るときは末尾に `(ADR NNNN)` を置き、他人の ADR を
  参照するときは文中に置く」のように狭く定め、かつその狭い記法だけを
  対象にした歯が偽陽性を実際に消せることを検算で示せたときである。
  現状はそのような記法の取り決め自体が存在しない。
- **案1・案2の組み合わせでも事故が再発したことが実測されたら**——その時点で
  「警告を読み飛ばした」という具体的な事例が積み上がることになり、
  案3（道具が `gh` を叩く）を再検討する材料になる。

## 測ったこと

- 【実測】`git rev-parse origin/main` → `4b92134c45b2377b9f5bb501ef921ab3e8b9cee3`
  （マネージャーが着手コメントで数えた時点と同じ sha であることを確認した）。
- 【実測】上記「自分の手で数え直した」節の手順で、`main` の commit 総数281・
  タイトルに `ADR NNNN` を含む commit 167・そのうち touch していない commit 15
  ——いずれもマネージャーの報告と一致することを確認した。
- 【実測】15件を自分で読んで分類し、紛れ2件（`e47952e` / `2840492`）・
  正当な参照13件であることを確認した——マネージャーの分類と一致する。
- 【実測】`scripts/__tests__/adr-renumber-lib.test.mjs`（30 tests、既存25 +
  新規5）が全て green。新規5 tests は `renumberedTitleWarning` を検査する:
  空配列で `null`・`undefined`/`null` 入力でも `null`・1件付け替えで
  旧番号→新番号と `gh pr edit <PR番号> --title` の文言を含む・複数件で
  両方列挙する・戻り値が文字列であること。
- 【実測】変異試験: `renumberedTitleWarning` の本体を `return null;` に
  差し替えたところ（警告を出す判定そのものを壊す変異）、新規5 tests のうち
  3 tests が red になった（期待通り——非空配列を渡しても警告文字列が
  返らなくなったことを検出した）。`cp` で退避しておいた元ファイルから
  復元し、30 tests 全て green に戻ることを確認し、`git status --porcelain`
  が意図した3ファイル（`scripts/adr-renumber-lib.mjs` /
  `scripts/adr-renumber.mjs` / `scripts/__tests__/adr-renumber-lib.test.mjs`）
  の変更のみで、変異の残骸が残っていないことを確認した（`git checkout` は
  使わず `cp` で退避・復元した——`docs/autonomy.md` §4 の穴を踏まないため）。
- 【実測】`node scripts/adr-renumber.mjs --next` → `0199`
  （`origin/main` の ADR 数188、他のリモートブランチ16本、open な PR 4本の
  ADR 主張を見た上での楽観的な次の番号）。

## 確かめていないこと

- **PR #399 以降、この形の事故（付け替え後に PR タイトルが追随しない）が
  実際に再発したかどうかは、issue 提起時点までの範囲でしか調べていない。**
  本 ADR の作業中に新たな事例が発生していないかは確認していない。
- **`renumberedTitleWarning` が返す文言を、実際にマージ作業者が読んで
  `gh pr edit` を実行するかどうか**——これは運用（人の注意力）に依存する
  部分であり、道具の側では検証できない（「引き受けた負債」1番）。
- **案5で示した「素朴な歯は偽陽性87%」という数字は、この ADR で新たに
  設けた狭い記法規則（末尾の `(ADR NNNN)` だけを見る等）を対象にした場合の
  偽陽性率ではない**——そのような狭い歯を仮に実装した場合にどの程度
  偽陽性が減るかは、実装して検算していないので分からない。
- **CI（`ci.yml`）上で `adr-renumber.mjs` を自動実行する設計は、この ADR
  でも検討していない**——ADR 0179 の「確かめていないこと」と同じく、
  この CLI はマージする側が手元で実行する想定のままである。
