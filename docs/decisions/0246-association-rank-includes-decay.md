## 文脈

[Issue #402](https://github.com/takecchi/mnemora/issues/402) は、正典
`docs/north-star.md`「目指す姿」項目4「**使われない記憶が、静かに遠ざかる。——消えるのではなく、遠ざかる。**」が
連想枠（段3.5）で破れていることを実測で報告している。

**項目4 には軸が2つある。**

| 軸 | 機構 | 状態（本 ADR より前） |
|---|---|---|
| **ゲート軸** | 忘却ゲート（`decay_floor_at`） | ✅ **破れていない。**[ADR 0172](./0172-association-passes-decay-and-validity-gates.md)（Issue #347）が段3.5 にも通した。歯は `recall-association-gates.test.ts`、`recall()` まで通した一巡は `recall-usage-selection.test.ts`（`docs/roadmap.md` §7.16） |
| **順位軸** | スコア閾値による選別 | 🔴 **開いている。これが本 ADR の対象である。** |

### ⛔ 「段3.5 にも段2 の閾値を掛ける」という形では閉じない

**この形は、着手前に検討して落ちた。**落ちた根拠は2つとも repo の中に在る【現物】。

- [`docs/recall.md`](../recall.md) §9.8 が逐語で —— 「**段2で落ちた記憶こそが連想枠の主な獲物であり、
  除外すると連想枠の意味がほぼ無くなる**」。
- [ADR 0151](./0151-recall-association-unprompted.md)「採らなかった案」が、連想を候補生成チャンネルとして
  段1 に置く案を逐語で —— 「**段2で再スコアされ、クエリに当たらないのだから必ず `below_threshold` に落ちる**」。

⟹ 閾値を掛ければ連想枠は全滅し、連想枠のスコア（`affinity` が中立の 1 に退化する）へ掛ければ素通りする。
**どちらの向きでも「閾値を掛ける」は解にならない。**

### 【現物】では、順位軸の穴は実際にはどこに在るのか

**席の取り合いに、減衰が一切効いていないことである。**`recall-runtime.ts` の段3.5 は、
`maxCount` 件の席を**アンカーとの類似度だけ**で埋めていた（本 ADR より前の形、逐語）:

```ts
associationHits.sort((a, b) => b.similarity - a.similarity);
const selectedHits = associationHits.slice(0, associationQuery.maxCount);
```

`decay` / `lastReinforcedAt` / `strength` は、この選別に1つも関与していない。
スコア（`decay` を含む）が計算されるのは**選別が終わった後**であり、その使い道は
段4 の予算順（`rankScore`）だけだった。

⟹ 🔴 **連想枠の中では、使用報告された記憶と、されなかった記憶が、順位として一切分かれていなかった。**
**「静かに遠ざかる」が、この枠だけ働いていない。**

⭐ **これは Issue #402 が挙げた3根拠より1つ下の層に在り、かつ修理できる。**
#402 の根拠 (a)（段3.5 が構造上スコア閾値を通らない）は上のとおり**意図した設計**として
`docs/recall.md` §9.8 に既に記録されており、(b)（段2 が棄却した記憶が `association` で返る）は
その帰結である。**本 ADR が閉じるのは、その内側に在った「順位が付いていない」という穴である。**

### ⚠ 隣の穴（分類軸）は既に閉じている。混同しないこと

同じ段3.5 に由来する穴のうち、**同じ `memoryId` が `memories` と `omitted` の両方に載る**という
**分類軸**の破れは [ADR 0203](./0203-memories-omitted-exclusivity.md)（Issue #421）で既に塞がれている。
**本 ADR はそれとは別の軸である**（`docs/recall.md` §9.8 冒頭が、この2つを別軸として切り分けている）。

## 決定

1. **連想枠の席を、減衰を含む順位で埋める。**順位キーは

   ```
   rankKey = anchorSimilarity × decay × tagMatch × freshness × strength
   ```

   実装上は `hit.similarity * score.total` である——`score` は段3.5 が既に組んでいる
   `defaultScoringStrategy(...)` の結果であり、そこでは `similarity` / `lexicalMatch` を渡さないため
   `affinity` が中立の 1 に退化する（`strategies/scoring.ts` の doc）。⟹ 掛け合わせると
   上の式になる。**段2 の式と同じ積の形であり、新しい「似ている」の定義も新しい順位の定義も作らない**
   （`docs/recall.md` §9.3 が保留している事柄を踏まない）。

2. **順位キーは枠の内側の順序付けにだけ使い、返り値には出さない。**
   `ScoreBreakdown.similarity` は**クエリとの**類似度の枠であり、そこへアンカーとの類似度を入れない
   ——ADR 0151 が北極星の問い3・問い4 で落とした案である。**本 ADR はその決定を覆さない。**

3. **順位を付けるために、候補を過取得してから並べ替える。**
   `getMany` の対象を `maxCount` 件から `max(maxCount, round(maxCount × overFetchFactor))` 件へ広げ、
   Memory を得てからスコアを組み、`rankKey` 降順で並べ替えて `maxCount` で切る。
   ⭐ **段1 が `kPrime = limit × overFetchFactor` で過取得してから段2 で並べ替えるのと同じ形である。**
   **新しい係数を定義しない**（同じ理由で同じことをしている先例が、段3.5 の連想用 `search()` の
   `limit: kPrime` 流用である）。
   `Math.max` で下限を `maxCount` に留めているのは、呼び手が `overFetchFactor < 1` を渡したときに
   **返る件数が減る退行**を防ぐためである。

4. **同点のときの並びは、これまでどおり adapter に委ねる。**
   `Array.prototype.sort` は安定（ES2019+）であり、`rankKey` が完全に同値の候補は
   **類似度降順の前置きの順序**をそのまま保つ。⟹ [ADR 0170](./0170-association-search-tiebreak-nondeterminism.md) が
   「この段自身で再タイブレークを重ねない」と決めた形は**破れていない。**

5. 🔴 **`over_limit(stage: "association")` は数え直す。**
   ⚠ **これは着手時の想定と逆である**——「並べ替えても『候補総数 − `maxCount`』という値は変わらないから、
   式はそのままでよい」と見積もって着手し、**実装の途中で誤りに気づいた** 【実測】。

   **値は（通常は）変わらないが、その数が*指している集合*が壊れる。**
   修理前は席が類似度順で決まっていたので「類似度順で `maxCount` 位より後ろ」＝「席に着けなかった候補」だった。
   修理後は席が順位キー順で決まるので、**類似度順では後ろに居た候補が席に着くことがある**
   ⟹ その形のまま数えると、**返した記憶を「席に着けなかった」と名乗る。**
   ⭐ **これは [ADR 0203](./0203-memories-omitted-exclusivity.md) が `below_threshold` について閉じた穴と同族である。**
   ⚠ `over_limit` は memoryId を持たないので**個体単位では検出できない**（ADR 0203 自身が同じ限界を書いている）
   ——だからこそ、数え方の側で閉じる。

   ⟹ **数えるのは次の2つの和にする**: (a) 過取得の窓の外に居た候補（一度も順位付けの土俵に上がらなかった分）
   ＋ (b) 土俵に上がって席を競り負けた分。
   ⛔ **多層防御で落ちた分はどちらにも入れない**——段5 の `aggregateScope` が `filtered(...)` として数えており
   （Issue #329 / ADR 0173）、ここで足すと二重計上になる（ADR 0172 決めたこと3 と同じ線）。
   `countKind: "exact"` はそのままである（JS 側で確定するため）。

   ⚠ **観測できる差は小さい。正直に書く**: 多層防御が1件も落とさない通常の場合、
   この和は `(N − F) + (F − maxCount) = N − maxCount` となり**修理前と同じ値**である。
   ⟹ **値が変わるのは、多層防御が実際に落としたとき（＝adapter が ADR 0034 の契約を破ったとき）だけ**であり、
   そのとき修理前は**過大に**数えていた（落ちた分を段5 と二重に数えていた）。
   ⛔ **つまり、この数え直しが直したものの大半は「値」ではなく「意味」である。**
6. **多層防御（`subjectId` / `period` / `excludeProvenanceKinds` / `survivesValidityGate` /
   `survivesDecayGate`）の述語も順番も変えない。**
   [ADR 0172](./0172-association-passes-decay-and-validity-gates.md) 決めたこと3 の
   「落ちた件数はここでは数えない」もそのままである。

   ⚠ **ただし、副作用が1つある。黙って埋めない。**この防御は「席が決まった後」から「席が決まる前」へ移った
   （対象が `maxCount` 件から過取得した件数へ広がったため）。⟹ 修理前はここで落ちた候補の席が**空いたまま**返っていたが
   （「一度選んだのに落ちる」負債）、修理後は**落ちた分を別の候補が埋める。**
   ⟹ 連想枠が返す件数が、修理前より増えることがある（`maxCount` は超えない）。
   ⛔ **これを「負債を返した」とは書かない**——この防御が実際に落とすのは adapter が ADR 0034 の契約を破ったときだけであり、
   **その場合に何件増えるかは測っていない。**
7. **既定を1バイトも動かさない。**`RecallQuery.association` は任意フィールドのままで、
   渡さない呼び出しの挙動は変わらない。⟹ **[Issue #337](https://github.com/takecchi/mnemora/issues/337)
   （既定 on にするかのオーナー判断）には触れない。**

8. **公開 API の面を広げない。**新しいつまみも新しい欄も足さない。破壊的変更ではない。

## ⛔ これが閉じないもの

### 1. 段1／段2 は絶対閾値、段3.5 は相対順位のみ —— この非対称は残る

**本 ADR の修理は相対である。**競合が居なければ、古く未使用の記憶は依然として連想枠から返る。
一方、段1／段2 の `scoreThreshold` は**絶対**であり、競合の有無に関わらず落とす。
⟹ 🔴 **「なぜ段3.5 だけ絶対の線が無いのか」という非対称は、この ADR の後も残る。**

**黙って埋めない。**下の「採らなかった案」に、絶対の線を引く案の形と、
**採らなかった理由**をそのまま書いてある。

⭐ **ただし、相対で止めたのは妥協ではない。**正典の文言は「**消える**」ではなく
「**静かに遠ざかる**」である。**順位で沈み、席を競り負けて押し出される**という形は、
その文言にそのまま一致する。絶対の線のほうが正典に近い、とは言えない。

### 2. 札（`score.total`）が、棄却されたときより高く見える

連想枠が返す `score.total` は `affinity` が中立の 1 に退化しているため、
**段2 がその同じ記憶を棄却したときの `total` より高い値になりうる**（Issue #402 §4 の指摘。【現物】で正しい）。
⟹ **使う側から見ると、遠ざかったはずの記憶が、遠ざかる前より高い札を付けて戻ってくるように見える。**

⛔ **本 ADR はこれを直さない。**これは順位軸ではなく**説明可能性**（正典項目3）の軸であり、
直すには `ScoreBreakdown` に「この値は比較可能ではない」を名乗らせる欄が要る
——ADR 0151 が「アンカーとの類似度を `ScoreBreakdown.semanticSimilarity` に入れない」と決めている以上、
**入れない形での設計からやり直しになり、公開 API の破壊的変更になる。**
リリース週に破壊的変更を1件増やす判断は、この穴の実害より重い【受: 依頼元のクローン】。
⟹ **[Issue #548](https://github.com/takecchi/mnemora/issues/548) へ割り、`v1.0.0` の後に持つ。**リリースノートの「既知の弱さ」に1行で名乗らせる。

### 3. 項目4 の数え直しをしていない

`docs/roadmap.md` §7.4 の判定「在る」にも、§7.4 ⚠3 の留保にも、**手を触れていない。**
**数え直しはオーナーの領分である**（§7.16 の「確かめていないこと」1番と同じ線）。
本 ADR が動かすのは「**順位軸を測る歯が在るか無いか**」だけである。

## 引き受けた負債

1. **過取得の前置きの外に居た候補は、席に届かない。**
   `rankKey` で勝てたはずでも、アンカー類似度が `max(maxCount, round(maxCount × overFetchFactor))` 位に
   入らなければ順位付けの対象にならない。**段1 の過取得（`kPrime`）と同性質の近似である。**
   ⚠ **この近似が実際にどれだけ効くかは測っていない。**
2. **`getMany` が広がる分の費用を測っていない。**既定（`maxCount` は呼び手が必ず渡す値、
   `overFetchFactor` の既定は 4）で、DB への往復の**本数**は変わらず、**幅**だけが広がる。
   ⚠ **レイテンシは測っていない。**[Issue #337](https://github.com/takecchi/mnemora/issues/337) が
   「段3.5 の追加レイテンシは10万行級で測る」としている話と合流しうるが、**本 ADR では測っていない。**
3. **実 Postgres では走らせていない。**歯は `packages/core` の fake ストアの上だけで回る
   （§7.16 の「確かめていないこと」3番と同じ断り）。
4. **既定 off のままなので、北極星の物差しは動かない。**ADR 0151「引き受けた負債」1番がそのまま残る。

## これが覆るとしたら何が起きたときか

1. **オーナーが「連想枠にも絶対の線が要る」と決めたとき** —— 決定1 の相対順位の上に、
   下の「採らなかった案」の絶対閾値を積むことになる。⚠ **そのときは既定値を何にするかが
   製品の性格を決める判断になる**（`docs/autonomy.md` §3.1）。
2. **`retrieval` ベンチで、連想枠が想起の質を動かさないと実測されたとき** ——
   ADR 0151「これが覆るとしたら」3番により連想枠そのものが落ちる。**本 ADR は一緒に落ちる。**
3. **[Issue #337](https://github.com/takecchi/mnemora/issues/337) の10万行級の測定で、この順位キーが
   費用に見合わないと出たとき** —— 過取得の幅（決定3）を見直す。
4. **`ScoreBreakdown` に比較可能性を名乗らせる欄が入ったとき**（上の「閉じないもの」2） ——
   そのとき順位キーを返り値へ出すかを決め直す余地が生まれる。**本 ADR は決定2 でそれを禁じているが、
   禁じた理由は「クエリとの類似度の顔で別の量を出さない」であって、別の顔で出すことまでは禁じていない。**

## 誰が壊れうるか

**`RecallQuery.association` を渡している呼び手の、返る記憶の顔ぶれが変わりうる。**

- `maxCount` を超える候補が在るとき、席に座る記憶が変わる（そこが本 ADR の目的である）。
- **型は1バイトも変わらない。**新しい欄も新しいつまみも無い ⟹ **破壊的変更ではない。**
- **既定 off なので、`association` を渡していない呼び手は1バイトも影響を受けない。**
- 本リポジトリ内で `association` を渡す呼び手は `examples/chat`（`private: true`）とテストだけである【現物】。
