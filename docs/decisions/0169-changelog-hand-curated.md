# ADR 0169: CHANGELOG は手で書く。ADR 0070 は覆らない

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-16

**⚠ 各主張の出所を分ける。**「私が実行して確かめた」と「読んだだけ／受け取った前提」を混ぜない。

---

## 文脈

### なぜ CHANGELOG を作るかは、この ADR が提起する話ではない

`docs/roadmap.md` §7.3 は、v1.0 を切れる状態の条件として **README・移行ガイド・
CHANGELOG・`pack:check`** を既に名指ししている。**⟹ CHANGELOG を作ること自体は
決定済みであり、この ADR はそこを問い直さない。**この ADR が決めるのは、
**どう作るか**（手で書くか、tag/commit から自動生成するか）だけである。

### ⭐ ADR 0070 が名指しした覆る条件と、正面から向き合う

[ADR 0070](./0070-version-comes-from-the-release-tag.md)（版の権威は Release の tag に
置く）の「これが覆るとしたら」は、逐語でこう書いている:

> **オーナーが CHANGELOG を要求したとき。**tag だけからは生成できないので、Changesets か
> conventional commits の規約が要る。**決定1が覆る。**

`docs/roadmap.md` §7.3 が CHANGELOG を要求した以上、**この条件文の前半（「オーナーが
CHANGELOG を要求したとき」）は満たされた。** この ADR が答えなければならないのは
「では決定1（版は tag が決める）は本当に覆るのか」である。

**結論を先に書く: 覆らない。** 理由は「決定」節。

### 現物で確認したこと——コミットメッセージは部分的に conventional commits 風だが、規約ではない

CHANGELOG の自動生成を検討する前提として、**この repo の commit メッセージが
conventional commits に足る規約を既に持っているか**を現物で確かめた。

```
$ git log --oneline | wc -l
233
$ git log --format=%s | grep -cE "^(feat|fix|docs|test|chore|refactor|perf|style|build|ci)(\([a-zA-Z0-9,_-]+\))?!?: "
92
```

**233件中92件（約39%）が `feat(scope)!: ...` のような prefix を持つ。** 直近の commit
（例: `1021a93 feat(core,postgres,testkit,chat): 減衰の時計を2本にする…`）は概ねこの形に
揃っているが、初期の commit（例: `1cf6a60 設計フェーズの成果物: …`、`4248670 compare の
出力に…`）は prefix を持たない。**⟹ 「近ごろは概ね守られている」ことと「規約として
確立している（全 commit がこれに従う）」ことは別であり、後者は成立していない。**
この事実は「採らなかった案」節の判断に使う。

## 決定

### 決定1: CHANGELOG.md はルートに置き、手で書く（Keep a Changelog 風）

- 見出しは Release tag 単位（`## [1.0.0] - 未リリース` のように）。
- 分類は **Breaking / Added / Changed / Fixed** の4種。
- 各項目は1〜2行の要約 + ADR/Issue へのリンクのみ。**詳細は複製しない**
  （`AGENTS.md` の反重複規律——ADR 側が正、CHANGELOG は目次）。
- **内部専用の PR（docs のみ・script 修正・ADR 索引再生成・テスト追加）は載せない。**
  GitHub の自動生成 Release notes（`git log`／PR一覧をそのまま列挙するもの）との違いは
  ここにある——自動列挙は全 PR を無差別に並べるが、CHANGELOG は**利用者に関係する変更**
  だけを人が選ぶ。

### 決定2: ADR 0070 決定1（版は Release の tag が決める）は覆らない

ADR 0070 の「これが覆るとしたら」は、**「tag だけからは生成できないので」**という
前提の上に立っている——つまり、**CHANGELOG を自動生成する**ことを暗黙の前提にしていた。
`vX.Y.Z` という tag の文字列だけでは「何が変わったか」の文章は書けないので、
自動生成するなら Changesets か conventional commits の規約で「変更の粒度」を
別途記録する必要がある、という条件文である。

**この ADR はその前提を採らない。** CHANGELOG.md は**手で書く**——tag からの自動生成を
一切経由しない。⟹ 「tag だけからは生成できない」という制約そのものが、そもそも
発火しない（生成しようとしていないので、生成できないことが問題にならない）。

**⟹ 版を決める仕組みと、CHANGELOG を書く仕組みは、別の文書・別の作業のままである。**
版は引き続き Release の tag だけが決め（`package.json` の `version` は権威ではない、
ADR 0070 決定1・決定4のまま）、CHANGELOG.md は人が Release のたびに追記する、
**独立した文書**である。**ADR 0070 決定1・決定4・決定5 のいずれにも、この ADR は
1文字も触れていない。**

### 決定3: Changesets は導入しない

ADR 0070 が既に検討して「却下ではなく後回し」にした理由——

> **確かめていない道具へ、動いている経路から乗り換えない。**加えて、`changeset publish`
> が `workspace:` をどう扱うかを**この器で確かめていない**（ADR 0060 の要である
> 「`pnpm pack` が `workspace:` を置換する」を通るかどうか）。

——は、**この作業を行った時点でも未検証のままである。**この ADR の作業者はこの環境で
`changeset publish` を実行して `workspace:` の扱いを検算していない。ADR 0070 の判断を
覆すには、この未検証を埋める実測が要るが、**その実測をしてまで Changesets へ乗り換える
理由が今回は無い**——手で書く CHANGELOG が roadmap §7.3 の要求（v1.0 を切れる状態にする
ための CHANGELOG）を満たすのに、版決めの仕組みごと入れ替える必要が無いからである。
⟹ **却下ではなく、引き続き後回し。** 覆る条件は「これが覆るとしたら」節参照。

### 決定4: 過去分（v0.1.x）は遡って書き起こさない

CHANGELOG.md の冒頭に、次の方針を明記する:

> **v0.1.x までの変更は、[GitHub Release](https://github.com/takecchi/mnemora/releases) を
> 参照すること。** このファイルは v1.0.0 以降を対象とする。

**理由**: v0.1.0〜v0.1.9 の10版・233コミットを、決定1で定めた粒度（利用者に関係する
変更だけを人が選ぶ）で遡って選別し直す作業は、**v1.0 を切れる状態にする**という
roadmap §7.3 の目的に対して不釣り合いに重い。GitHub の Release ページは既に各 tag の
時点の内容を（自動列挙という粒度で）保持しており、**「無い」のではなく「別の場所に
粗い形である」**——ADR 0008「無い」の分類に倣えば、これは "存在しない" ではなく
"別の詳細度で存在する" である。⟹ 遡って書き起こさず、参照先を1行示すことで足りると
判断した。

### 決定5: v1.0.0 の項目は6件の破壊的変更＋🟡3件＋新機能5件＋利用者向けバグ修正1件を載せる

内訳の実測・出所は `docs/migration-v1.md`（本作業で別途作成）と CHANGELOG.md 本体に譲る。
この ADR は「載せる基準」（決定1の反重複・内部専用 PR 除外）だけを定める。

## 検討して採らなかった案

| 案 | 却下の理由 |
|---|---|
| **Changesets を導入し、CHANGELOG をリリース時に自動集約する** | 決定3参照。ADR 0070 が「確かめていない道具へ、動いている経路から乗り換えない」と判断した状態が変わっていない。加えて Changesets 自体も「PR ごとに変更内容を手で書く」ことを要求する道具であり（`.changeset/*.md` を人が書く）、**「自動化」ではなく「手で書くタイミングを PR 時点へ前倒しする」道具である**——この repo が抱える「手で書く負担」自体を消さない。 |
| **conventional commits の prefix（`feat`/`fix`/`docs`…）から `conventional-changelog` 等で自動生成する** | 現物で確認した通り、**233件中92件（約39%）しかこの形に従っていない**——「文脈」節参照。規約として確立していない履歴から自動生成すると、prefix を持たない141件が拾えず、逆に内部専用 PR（`test(core): …`・`docs(roadmap): …`）まで無差別に拾ってしまう。**決定1が明示的に除外するもの（内部専用 PR）を機械的には弾けない**——scope が `core`/`chat` であっても、その PR が利用者に見える変更かどうかは commit prefix からは判定できない（例: `test(core): Omission.kind の11値に…歯を足す` は internal-only だが `test(core):` という prefix だけでは自動判別できない）。 |
| **`conventional-changelog` を導入したうえで、今後の commit にだけ規約を強制する（過去は対象外）** | 「これから」を Changesets と同じ理由で却下しないなら検討の余地はあるが、**この ADR は roadmap §7.3 が要求する「v1.0 を切れる状態」を今回満たすことが目的であり**、今後の commit 規約を強制する仕組み（lint-staged の commit-msg hook 等）を新設する作業は、この ADR・この PR の射程外である。将来 CHANGELOG の手書きが実際に負担として痛んだとき（下記「これが覆るとしたら」）に再検討する。 |
| **LLM に commit ログ／diff を要約させて自動的に CHANGELOG 項目を生成する** | 北極星の問い5（LLM を呼ばずに済ませられないか）に当てて落ちる。CHANGELOG の各項目が「どの利用者に、何が起きるか」を正確に言うことは、列と索引ではなく人の判断（ADR を読んで破壊の向きを判定する）を要する仕事であり、**LLM 要約は生成後に人が全件検算する必要があり、手で書く手間を消さない**——むしろ「もっともらしいが不正確な要約」を検算する新しい仕事を足す。加えて、tag 駆動の決定性（ADR 0070 決定1・決定2）と対照的に、LLM の出力は同じ入力に対して決定的ではなく、この repo が繰り返し優先してきた「決定的な経路」の規律とも噛み合わない。 |
| **GitHub の自動生成 Release notes（`Generate release notes` ボタン）だけで済ませ、`CHANGELOG.md` を作らない** | roadmap §7.3 が CHANGELOG を README・移行ガイド・`pack:check` と並べて名指しした時点で、この案は既に射程外（「文脈」節参照）。加えて自動生成 Release notes は全 PR を無差別に列挙するため、決定1が定める「内部専用 PR を載せない」という差別化ができない——これは CHANGELOG.md を別に持つ理由そのものである。 |

## 引き受けた負債

1. 🔴 **手で書く CHANGELOG は、書き忘れうる。** 自動生成ではないため、ある Release で
   利用者に影響する変更が実際にあったのに、CHANGELOG.md への追記を忘れる、という
   失敗モードを構造的に持つ。**これを検出する歯は無い**——`compare`（ADR 0133）のような
   ⭐ 門は、CHANGELOG の鮮度には掛かっていない。
2. **「利用者に関係する変更」の線引きは、書く人の判断に依存する。** 決定1が「内部専用の
   PR は載せない」と定めたが、ある変更が内部専用か利用者向けかの判定自体は自動化されて
   いない——境界線上の PR（例: 内部スクリプトの修正だが挙動が `examples/chat` の
   出力に影響する）で書く人ごとに判断がぶれる余地が残る。
3. **CHANGELOG.md と GitHub Release 本文が、独立に更新されうる。** 両者を同期させる
   仕組みは無い——Release 作成時に CHANGELOG.md の該当節をコピーする、といった運用上の
   規律に頼っている。この規律を守らせる歯は無い。
4. **過去分（決定4）を「GitHub Release を見よ」の1行に留めたことで、v0.1.x の変更を
   横断的に検索したい利用者は、CHANGELOG.md 側では見つけられない。** GitHub Release
   ページを個別に遡る必要がある。

## これが覆るとしたら

- **手で書く負担が実際に痛みとして表面化したとき**（例: 複数の Release で連続して
  書き忘れが発生した、レビューで指摘されるまで気づかなかった等）。⟹ 「検討して
  採らなかった案」の Changesets／今後限定の conventional commits 規約を再検討する。
- **`changeset publish` の `workspace:` 解決を実際にこの器で検証し、ADR 0060 の要
  （`pnpm pack` が `workspace:` を置換する）を通ることが確認されたとき。** ADR 0070
  「これが覆るとしたら」3番目の条件と同一——検証が済めば、Changesets 導入の技術的な
  障害が1つ消える。
- **commit prefix の規約（conventional commits 風）が、今後 100% 近くまで強制される
  仕組み（commit-msg hook 等）で固まったとき。** そのとき初めて、「内部専用 PR を
  scope/prefix の組み合わせで機械的に除外する」設計が現実的になる——ただし、その場合
  でも「利用者に見える変更かどうか」の最終判断は人が要ることに変わりはない可能性が高い。

## 北極星の5つの問いに実際に当てた結果

**⚠ ただし問いが規定しない判断には、正直に「落ちる案なし」と書く。** 北極星の5つの
問いは `recall()` のパイプライン設計・プロンプトへ積む量・記憶の選定理由・AI推論と
ユーザー事実の区別を対象にしており、**CHANGELOG というリリース文書の書き方は、
そのほとんどに規定されない。**飾りとして当てはめない。

| 問い | この判断にどう当たったか | 落ちた案 |
|---|---|---|
| **1**（毎回渡す量を減らす方向に働くか） | この判断は `recall()` が積む量に一切関わらない。 | **落ちる案なし**——この問いはこの判断を規定しない。 |
| **2**（これを無効にしたとき、Memory Framework として成立するか） | CHANGELOG.md はリリース文書であり、Runtime の機能ではない。「無効にする」という概念自体が当たらない。 | **落ちる案なし**——この問いはこの判断を規定しない。 |
| **3**（選ばれた理由を、後から説明できるか） | この問いは文言上 `recall()` が返す記憶の選定理由を指しており、CHANGELOG の書き方を直接規定しない。ただし決定1（要約+ADR/Issueリンク、詳細を複製しない）は、この問いの精神（説明できることを一次資料へのリンクで担保する）と方向は揃っている——**とはいえこれは類推であり、この問いがこの案を落としたわけではない。** | **落ちる案なし**——この問いはこの判断を規定しない。 |
| **4**（AI の推論と、ユーザーが言った事実を区別しているか） | CHANGELOG.md は `provenance.kind` にもユーザー発話にも触れない。 | **落ちる案なし**——この問いはこの判断を規定しない。 |
| **5**（LLM を呼ばずに済ませられないか） | **これは実際に「LLM に diff を要約させて自動生成する」案を落とした**（「検討して採らなかった案」参照）。手で書く・tag 駆動で生成する・conventional commits から生成する、のいずれも LLM 呼び出しを必要としない——この判断全体が、LLM を必須にする設計を一つも採っていない。 | **LLM による自動要約生成**——この問いで落ちた。 |

## 確かめたこと / 確かめていないこと

- **確かめた（この器で実行）**: `git log --oneline \| wc -l` と conventional commits
  prefix の grep カウント（233件中92件）。ADR 0070 本文を読み、「これが覆るとしたら」の
  逐語を確認した。
- **確かめていない**: `changeset publish` が `workspace:` をどう扱うか（ADR 0070 が
  既に「確かめていない」と書いた点で、この ADR でも埋めていない）。
- **確かめていない**: 手で書く CHANGELOG が実際にどれくらいの頻度で書き忘れられるか
  ——運用が始まっていないため、実測できない（「引き受けた負債」1番）。
