# ADR 0052: `compare` を実 API で測ったら「答えが落ちる」は消えた — 擬似物の産物だったことの確認と、その代償

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-07

**⚠ 各主張の出所を分ける。**本 ADR の数字は、断りの無い限り**すべて私が実行して取った**ものである。

---

## 問い

[ADR 0051](./0051-recorded-provider-cassette.md) は `retrieval` だけをカセット化し、
**`compare` は範囲外として残した。**その結果、北極星の物差しの中心にある表——

> 322ターン以降、冒頭の事実は `recall()` に残らない（❌）

——は**依然として擬似埋め込みの産物のまま**だった。ADR 0051 自身が「これは未解決のまま残る」と
書いている。**この ❌ が mnemora の限界なのか、擬似物の限界なのかが分からない。**

## まず、カセットを足す前に直す必要があったもの

`compare` の「冒頭の事実が残っているか」の判定は、**`digest.includes("青")` という文字列一致**
だった。そして当時のコメント自身がこう書いていた:

> **本物の LLM を使うと、digest は要約・言い換えされるため、この文字列一致はもう成立しない**
> ——「青」という語を使わずに要約されれば偽陰性になるし、逆に無関係な記憶の要約が「青」という語を
> 含めば偽陽性になる。

**⟹ 限界を正しく書いたまま、その判定を使い続けていた。**このまま実 API で録っても ❌ 列は
無意味になる。そこで判定を **`sourceObservationId` を辿って `externalId` で照合する**形へ
置き換えた（`provenance-trace.ts`。`retrieval` 側が既に使っていた経路を共有部品として降ろした）。

- **`CompareOptions.memoryStore` は省略可能にしていない。**省略を許すと文字列一致へ倒れる経路が
  残り、「どちらの判定で出た ❌ なのか」が表から読めなくなる。
- **擬似 provider で回帰確認済み**——判定を替えても、擬似 provider では**従来と1文字も違わない表**が
  出る（322 / 642 が ❌ のまま）。**つまりこの置き換え自体は結果を動かしていない。**

## 🔴 実測: ❌ は消えた（実 API、2026-09-07）

| 2 | 2 | 2 | ✅ | 49 | 129 | 263.3% |
| 4 | 3 | 3 | ✅ | 97 | 142 | 146.4% |
| 6 | 3 | 3 | ✅ | 150 | 142 | **94.7%** |

| 10 | 4 | 4 | ✅ | 243 | 152 | 62.6% |
| 12 | 5 | 5 | ✅ | 294 | 162 | 55.1% |
| 22 | 8 | 8 | ✅ | 552 | 211 | 38.2% |

**⟹ 全12行が ✅。322 / 642 の ❌ は消えた。**642ターンでは**209件のスコープから10件だけを返して
なお冒頭の事実が残り、naive の 1.1% しか積んでいない。**

### ⚠ 「初めて本物で測った」のは量ではなく、答えが残るかの側である

**量（`mnemora chars` の列）は既に測られていた**——[ADR 0019 §7.7](./0019-real-openai-measurement-cost.md)
が 2026-09-06 に実 API の `compare` を1回走らせ、README にも載っている。**本 ADR が
新しく測ったのは「冒頭の事実が残っているか」の列である**——README 自身がその時点で
こう書いていた:

> **この表が言えるのは「積む量」までである。**「正しく引けたか」は後述の `retrieval` のほうが答える。

理由は本 ADR の冒頭のとおり、**当時の生存判定が文字列一致で、本物の LLM では成立しなかった**
からである。系譜の追跡へ置き換えて初めて、この列を本物の provider で埋められるようになった。

**⚠ 量の数字も、前回の実測とは一致しない。**642ターンで ADR 0019 §7.7 は 244 chars（1.5%）、
本 ADR の実測は 184 chars（1.1%）。**原因は後述の「代償」と同じ LLM の非決定性である**
——同じ会話を実 API で2回測れば、抽出結果が変わり、返る digest が変わる。
**⟹ 実 API の `compare` は、そもそも実行ごとに数字が動く計測である。**

### ⚠ ADR 0019 §4 の外挿は誤りだった（本 ADR で訂正する）

ADR 0019 §4 は3発話を実 API で試した結果から、こう書いていた:

> **本物の LLM では、同じ会話のスコープ内 Memory は数件にしかならない。**

**実測は 209件である**（642ターン）。「今日はいい天気ですね。」は確かに `{"memories":[]}` を返すが、
`scenario.ts` の filler には「仕事の進捗について相談したいことがあります。」のように
**本物の LLM が記憶として抽出する文が混ざっている。**3発話の標本から12種の filler 全体へ
外挿したのが誤りだった。

**⟹ これは重要である。**「干し草の山が消えたから ✅ になった」のではない。
**209件の干し草の中から、実際に引き当てている。**

## ⚠ 代償: カセットの再生は、記録時の数字を再現しない

**出所: 私が実行した。**DB を作り直し、キーを外して再生した。

| 会話ターン数 | 記録時（実 API） | 再生 | 冒頭の事実 |
|---|---|---|---|
| 42 | 15 | 14 | 両方 ✅ |
| 82 | 27 | 25 | 両方 ✅ |
| 162 | 56 | 49 | 両方 ✅ |
| 322 | 108 | 95 | 両方 ✅ |
| 642 | **209** | **189** | 両方 ✅ |

642ターンの `mnemora chars` も 184（1.1%）→ 272（1.7%）へ動く。

**原因は鍵の設計そのものである。**カセットの鍵は入力のハッシュなので、
**657回の LLM 呼び出しが13種のプロンプトに畳まれる**（`scenario.ts` の filler は12種 + 事実表明1種）。
実 API では同じ発話が呼ばれるたびに違う抽出結果を返しうるが、記録は各鍵につき1つしか持てない。
**⟹ 実行ごとの揺れが捨てられ、系統的に少なめの件数へ収束する。**

これは ADR 0051 が `retrieval` の arm C で観測した「ずれ」と同種だが、**`compare` では
その影響が桁違いに大きい**——arm C は74回の呼び出しが74種だったのに対し、`compare` は
657回が13種である。**同じ入力が繰り返される計測ほど、カセットは実行時の分散を潰す。**

**再生そのものは決定的である**（DB を作り直しても出力が1バイトも変わらないことを確認した）。
**⟹ カセットが与えるのは「実 API との一致」ではなく「測定の再現性」である**という
ADR 0051 の結論は、ここでも変わらない。**そして結論（全行 ✅）は記録・再生の両方で同じである。**

## 決めたこと

1. **`compare` もカセット化する。**対象ごとに別ファイル（`cassettes/compare.json` /
   `cassettes/retrieval.json`）。1つにまとめると片方を録り直すたびにもう片方まで
   録り直すか、`recordedAt` が中身と食い違う。
2. **`record` / `verify` は対象を明示させる**（既定値を持たせない）。`retrieval` は $0.0045、
   `compare` は $0.032 で**桁が違う**——取り違えは実害になる。
3. **`compare` は `retrieval` と同じ規律で走る**——キーがあれば実 API、無ければ記録の再生、
   どちらも無ければ落ちる。**「記録が無いなら擬似物で」とは読み替えない。**
4. **事実の生存判定は系譜の追跡のみ**（文字列一致の経路は削除した。「予約」として残さない
   ——[ADR 0024](./0024-remove-exact-counts-option.md) と同じ線）。

## 採らなかった案

- **`compare` の記録を `retrieval` と同じファイルに入れる**: 却下（上記2の理由）。
- **鍵に呼び出し回数や tenantId を混ぜて、実行ごとの揺れも記録する**: 却下。
  再生時に「何回目の呼び出しか」を一致させる必要が生じ、**取り込み順が少しでも変われば
  全部ずれる**。壊れやすさが、再現できる分散の価値を上回る。
- **`factStatementSurvived` を省略可能な `memoryStore` で分岐させる**: 却下。
  文字列一致へ倒れる経路が残ると、表の ❌ がどちらの判定で出たか読めなくなる。
- **記録時の表を README の正としてだけ載せ、再生の表は載せない**: 却下。
  **両方載せて差を明示する**——差があること自体が、この仕組みの限界の一部である。

## 引き受けた負債

1. **再生は記録時を再現しない**（上記。系統的に少なめ）。**カセットの `compare` の数字を
   「本物の compare の値」として引用してはならない。**引用してよいのは記録時の表である。
2. **カセットは 515KB 増える。**（重複排除が効いたため、事前の見積もり 3〜6MB より遥かに小さい。
   見積もりが外れたことを記録しておく。）
3. **`verify` は `compare` の LLM 記録を照合しない**（ADR 0051 と同じ理由: 応答が揺れるため）。
   埋め込み68件だけを照合する。
4. **費用の見積もりも外れた。**ADR 0019 §3 の見積もりは $0.023、実測は **$0.032075**（+39%）。
   差は output tokens——見積もりが約4,000としていたところ、実測は **18,898** だった。
5. **`compare` の CI 化はしていない。**再生は2.2秒で走るが、CI に載せるかは別の判断であり、
   本 ADR では決めていない。

## これが覆るとしたら

- **`verify compare` が閾値割れを報告したとき。**モデルが替わったか、記録が壊れたか。
- **`scenario.ts` の filler を増やしたとき。**13種という少なさが「再生が分散を潰す」度合いを
  決めている。種類を増やせば潰れ方は小さくなる——**が、それは記録の費用を上げる。**
- **`recall()` の既定 `limit`（10）や over-fetch を変えたとき。**全行 ✅ という結論は
  「209件から10件を返して残った」という条件の下での話であり、条件を変えれば変わりうる。
- **より長い会話を測ったとき。**642ターン・209件で ✅ だったことは、
  **オーナーが前提と決めた100万件級（roadmap §5.6）については何も言っていない。**
