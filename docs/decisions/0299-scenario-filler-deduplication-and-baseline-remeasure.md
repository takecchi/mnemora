## 結論（先に）

**`examples/chat/src/scenario.ts` の filler user/assistant 発話を、12文の固定配列を
`i % 12` で巡回する方式から、話題×述語の直積で `fillerIndex` ごとに一意な文を生成する
方式へ直した。** 320往復（`fillerPairs=320`）の会話でも重複が無いことを歯で固定した
（`scenario.test.ts`）。この修正に合わせて `examples/chat/cassettes/compare.json` を
実 API で録り直し、`examples/chat/compare-baseline.json` をこの PR 自身の CI artifact で
実測更新した。

| | 内容 |
|---|---|
| 実 API 呼び出し（合計） | LLM(gpt-4o-mini) 642回・embeddings(text-embedding-3-small) 281回・**約 $0.0311**（2回に分けて録音。理由は本文「2回録った理由」） |
| 触ったカセット/基準値 | `examples/chat/cassettes/compare.json`（録り直し）・`examples/chat/compare-baseline.json`（CI artifact から実測更新） |
| 12行の誤差（旧→新） | 最大誤差 2.068%→**2.061%**（両方とも許容誤差2.5%以内）。hold-in/hold-out の内訳が7行/5行→**8行/4行**に変わった |
| turnCount=322 の外れ値 | 【実測】重複の直接の原因（ADR 0170 §3 が記録した「13件重複×2種のdigest長」の tie-break構造）は消えた——filler が一意になったため同一 digest の大量重複クラスタが作れない |
| 🔴 未解決 | ADR 0201 の字数余白の歯（`recall-footprint-baseline.test.ts`）が**いま実際に赤い**——82ターン行の下側余白が6.51字とFLOOR(7.225字)を下回った。本文「残った赤」参照 |

## 背景

Issue #340 の直近のコメント（2026-09-17、自動化された担い手）が、`turnCount=322` 行の
`mnemoraChars` が非決定になる根本原因を、`scenario.ts` の filler user 発話が**12文を
`i % 12` で巡回するだけ**であることに特定していた。`fillerPairs=160`（`turnCount=322`）
では各文が約13回重複し、この重複した母集団から連想枠の `maxCount=10` に合わせて
tie-break で切り詰めるときに、長さの違う digest（17字/19字）が混ざる（ADR 0170 §3）。

同コメントは、**filler を直すには新しい文が要り、そのためにカセットの録り直し
（実 API・課金）が前提になる**——CI の `compare` は `llmMode=recorded` で走るため、
記録に無いプロンプトが来ると `RecordedLLMProvider` が例外で止まる——と特定した上で、
「これは実 API の課金を伴うのでオーナーの領分」として着手していなかった。

本 ADR は、その残件（filler の重複を無くし、カセットを録り直し、
`compare-baseline.json` を測り直す）を実行する。

## 決めたこと

### 1. filler の生成規則: 話題×述語の直積

`scenario.ts` に `FILLER_TOPICS`（20件の話題名詞句）と、user/assistant それぞれの述語
テンプレート（`FILLER_USER_PREDICATES`/`FILLER_ASSISTANT_PREDICATES`、各20件）を用意し、

```
predicateIndex = fillerIndex % predicates.length
topicIndex     = floor(fillerIndex / predicates.length) % FILLER_TOPICS.length
text           = predicates[predicateIndex](FILLER_TOPICS[topicIndex])
```

という位取りで一意な文を選ぶ（`fillerLine()`）。直積の容量は 20×20=400 で、
`DEFAULT_COMPARE_SEQUENCE`（`compare.ts`）の最大 `fillerPairs=320` を超える
——320往復まで、user・assistant それぞれ320文すべてが相異なることを
`scenario.test.ts` の歯で固定した。`fillerIndex` が容量を超えると例外を投げる
（将来ベンチが伸びたときに、静かに重複へ戻らないための機械的な検出）。

**話題・述語の選定は、1回目の録音・結果を見る前に決めた。** 話題は日常会話の一般的な
トピック（天気・仕事・趣味・買い物等）、述語は「〜について話したい/〜が気になっている/
〜しようと思っている」等の一人称の心情・意図の文型——**特定の会話長の誤差が小さくなる
ように文を選ぶ調整はしていない**（Issue #340 のコメントが却下した PR #683 の
「選んだことによる偏り」と同じ理由で避けた）。assistant 側も同じ方式で一意にした
——`ingestConversation`（`mnemora-path.ts`）は `userUtterances`（user発話のみ）しか
`observe()` しないため assistant の重複はこのバグに関与しないが、対称な規則にしておく
ほうが「なぜ片方だけ一意にしたか」を説明する負担が無い。

### 2. 2回録った理由: 列挙順序のバグ

1回目の録音を検算したところ（【実測】、DB・API キー不要、cassette を直接解析）、
`fillerIndex → (topicIndex, predicateIndex)` の分解順序（**当初は話題を速く・述語を
遅く**回していた）が原因で、`fillerPairs<=20`（i=0..19）の全域で述語インデックスが
常に0（「〜について話したいです。」——20話題すべてで抽出率0/20）に固定され、
`totalInScope` が「fillerPairs<=20 で一定のまま→ fillerPairs=40 で段差状に急増」
という不自然な形になっていた。述語ごとの抽出率は話題にほぼ依らず、術語間の差が
大きい（0/20〜20/20、20話題全部で確認）ため、**述語が20 fillerPairsごとにしか
切り替わらない列挙順序では、「同じ述語だけが並ぶ区間」がそのまま「スコープ内件数が
動かない区間」になっていた。**

これは話題・述語の**文面**の問題ではなく、**列挙順序という実装細部**の問題だったため、
文面には一切手を触れず、`fillerLine()` の軸の速さだけを入れ替えた（述語を速く・
話題を遅く）。この訂正のため、カセットを2回目の実 API 録音で録り直した。

⚠ **この判断について**: 「列挙順序を直したら誤差が小さくなった」という結果と
「列挙順序を直した」という行為は時系列として不可分だが、**選んだのは文面ではなく
列挙の位取り式であり、`FILLER_TOPICS`/述語テンプレートの中身は1文字も変えていない。**
また、この訂正は「totalInScope が階段状になる」という構造上の欠陥（`calibrateRecallFootprint`
が単一の `memoryCount` しか観測できず両係数を決められない、という較正の破綻）を直すために
行ったのであり、正確に「誤差の数値を下げるため」に個別の文を選び直したのではない
——この違いは本文「検討して採らなかった案」で敷衍する。

### 4. `compare-baseline.json` の更新手順

`examples/chat/README.md`「基準値（`compare-baseline.json`）を更新する手順」に従った:

1. 2回目の録音カセットを含む PR（#701）を push し、その PR 自身の CI
   （`example-chat` ジョブ、run `36056651196`）を実行。
2. 同一 run の同一ジョブを `gh run rerun --job` で2回実行し（attempt 1/2）、
   `compare` artifact をそれぞれ取得（Artifact ID `10833100840` / `10832593674`）。
3. `measuredAt`/`commit` を除いて `rows` が2回ともバイト単位で一致することを確認
   （node で `JSON.stringify` を比較）。
4. 一致を確認した上で、artifact を node で読み込んで `llmMode`/`embeddingMode`/
   `rowCount`/`rows` をそのまま複製（⛔ 手で数値を書いていない）。
5. `provenance.fourthUpdate` に、なぜ値が動いたか・録音を2回に分けた理由・
   一致確認の手順を記録した。

### 5. `packages/core` の `BUILTIN_RECALL_FOOTPRINT_PROFILE` も再較正した

`recall-footprint-baseline.test.ts` の「既定プロファイルの最大誤差が許容誤差以内であり、
hold-in較正済みプロファイルとほぼ同程度に当たる」歯が、`compare-baseline.json` の
更新後に赤くなった——`BUILTIN_RECALL_FOOTPRINT_PROFILE` の係数（`charsPerDigest=15.458`/
`fixedIndexChars=170.881`）は、以前の `compare-baseline.json` の hold-in 7行から
測ったものであり、新しい基準値（hold-in 8行）に対しては古い。この歯自身の
コメントが「ずれるなら既定プロファイルの係数が古いということなので、その場合は
このテストの失敗をそのまま報告すること」と明記していたが、**この既定プロファイルの
`origin.measuredFrom` は文字通り「`examples/chat/compare-baseline.json`」を指しており、
その基準値自体を本 ADR で更新した以上、既定プロファイルを再較正しないままでは
「同じファイルを指しながら値が食い違う」状態になる。** ⟹ `charsPerDigest=14.45`/
`fixedIndexChars=180.7`（新しい `compare-baseline.json` の hold-in 8行から
`calibrateRecallFootprint` で再較正した値、`recall-footprint-baseline.test.ts` が
検算する値と一致）に更新した。

⛔ **推定器の形（自由係数2つという構造・線形式・`calibrateRecallFootprint` の
アルゴリズム）は1つも変えていない。** 動いたのは係数の値だけであり、それは
「入力（`compare-baseline.json`）が変わったので再較正した」結果である
——マネージャーの委譲文「推定器の形・重みも変えない（入力が変わったことで係数が
動くのは可）」の範囲内。

## #340 本文の射程に照らした判定: 余裕は設計意図の6割に戻ったか

**戻っていない、が百分率の余裕自体はわずかに改善した。**

- 百分率で見た余裕: 旧 `(2.5−2.068)/2.5≒17.3%` → 新 `(2.5−2.061)/2.5≒17.6%`。
  **依然として「設計意図の6割」（#340 本文が言う元の水準）には遠い。**
  この PR は322行の外れ値の**構造的な原因**（重複content由来の tie-break）を
  取り除いたが、**推定器そのものを直していない**ため、百分率の余裕自体は
  ほぼ変わらない——これは #340 の一連のコメントが繰り返し確認してきたとおり
  （案(ii)「推定器を直す」は依然として v1.0.0 後の宿題のまま、`docs/roadmap.md` §7.10）。
- 字数で見た余白は、**42行が hold-in へ移ったことで「いちばん狭い行」自体が
  入れ替わり**、新しく最狭になった82行の余白（6.51字）はむしろ FLOOR を
  下回った。⟹ **字数の物差しでは、この PR は余裕を狭めている。**

⟹ **この PR がやったこと**: turnCount=322 行の**非決定性の直接原因**
（重複contentのtie-break）は取り除いた。**やっていないこと**: 推定器の精度自体の
改善——それは元々この PR の射程外（#340 の一連のコメントが v1.0.0後の宿題と
確認済み）。

## 検討して採らなかった案

## 🔴 残った赤 — オーナーの判断を仰ぐ

**`recall-footprint-baseline.test.ts` の「字数で見た誤差の余白」歯（ADR 0201由来）が、
このブランチで実際に赤い。** 82ターン行の下側余白が6.51字で、FLOOR（7.225字）を
下回っている。この PR は次のいずれも行っていない:

- `ACCURACY_TOLERANCE`（2.5%）を動かす
- `FLOOR_CHARS`（半digest分）の式を変える
- 82行付近の filler 内容・会話長を、この歯が通るように調整する

**理由**: いずれも委譲の線・ADR 0166・ADR 0201・Issue #340/#410 が既に却下している
「通すために動かす」の一種になるため。ADR 0201 自身の「これが覆るとしたら」1項
（較正標本の取り方・入力が変わって hold-out 行の誤差が動いたとき）が実際に起きた
状態であり、**この歯は意図通り「境界に近づいたら知らせる」役割を果たして赤くなっている**
——これは bug ではなく、この歯の設計上の正しい動作である。

**次にオーナーが選べる案**（この PR では決めていない）:

1. **現状を記録して受け入れる**——Issue #340 が案(iii)として既に一度採った形と同じ。
   ADR 0201 の「これが覆るとしたら」1項に対応する新しい訂正を ADR 0201 の訂正節
   （またはこの ADR）に積む。
2. **推定器を直す**（案(ii)、v1.0.0後の宿題として `docs/roadmap.md` に残す）。
3. **較正標本の取り方を見直す**（ADR 0201「引き受けた負債」1番が触れている、
   hold-in行の自己参照問題を含む、より大きな設計変更）。

この判断は、この PR の作業者（クローンの委譲で動くセッション）の権限外
（ADR 0220）——オーナーへ返す。

## 引き受けた負債

1. 🔴 **上記「残った赤」**——ADR 0201 の字数余白の歯が赤いまま、この PR は
   `recall-footprint-baseline.test.ts` を緑にしていない。
2. ⚠ **推定器の精度自体（誤差の実体）は改善していない**——322行は外れ値ではなく
   なったが、12行全体の最大誤差は2.068%→2.061%とほぼ変わらない。#340 の射程
   （「設計意図の6割」の余裕）には届いていない。
3. ⚠ **話題×述語の組み合わせが実際に GPT-4o-mini からどう判定されるかは、
   モデルが変われば変わりうる**（ADR 0051 と同じ限界——カセットは記録時点の
   API の姿の記録である）。
4. ⚠ **列挙順序の訂正は「述語を先に変える」という1つの案を採っただけである**
   ——他の順序（例: 話題と述語を交互に、あるいはより細かく織り交ぜる）を
   試していない。今回の順序で「totalInScope が階段状になる」構造上の欠陥は
   解消したが、より滑らかな成長曲線を作る余地は残っている。

## これが覆るとしたら

1. **オーナーが「残った赤」への対応（上記3案のいずれか）を選んだとき。**
2. **推定器そのものを直す作業（案(ii)）が着手されたとき**——`packages/core` の
   `recall-footprint.ts` の式・`calibrateRecallFootprint` のアルゴリズムを変える
   作業。本 ADR はその作業の対象を1つも変えていない。
3. **`DEFAULT_COMPARE_SEQUENCE` の標本点が見直されたとき**——特に82ターン行
   （最初の hold-out 標本点）付近の密度。

## 確かめていないこと

- **列挙順序を別の形（例: 話題と述語を同時に、より細かい粒度で織り交ぜる）に
  したとき、82行の余白がどう動くか**——試していない。
- **本番の会話パターンでの一般化**（ADR 0166 の負債4・ADR 0201 の負債2と同種）。
- **述語テンプレートの抽出率（0/20〜20/20の二極化）が、モデルのバージョンが
  変わっても同じ傾向を保つか**——測っていない。
