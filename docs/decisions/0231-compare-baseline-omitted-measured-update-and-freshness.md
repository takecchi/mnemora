- **状態**: 採用 (2026-09)
- **日付**: 2026-09-17

**⚠ 各主張の出所を分ける**（ADR 0133 / 0188 / 0226 の体裁を踏む）。

- **【実測】** — この ADR の作業者が自分の手で走らせて確かめた（`gh run download` で取得した
  artifact を `node` で突き合わせた／`vitest` を走らせた）。
- **【現物】** — この repo のコード・文書を自分で読んで確かめた。
- **【受】** — 委譲文・ISSUE のコメントとして受け取り、この作業者が再導出していない。

## 文脈

**[Issue #403](https://github.com/takecchi/mnemora/issues/403)**: `examples/chat/compare-baseline.json`
の `omitted` 欄が `main` 上で陳腐化している。⭐門（`scripts/compare-summary-lib.mjs` の
`evaluateCompare`）が見るのは `mnemoraShareOfNaiveChars` と `factStatementSurvived` の2つだけ
なので（[ADR 0133](./0133-compare-baseline-and-gate.md) 決定3）、`omitted` が相違しても
**CI は緑のまま**である。しかし `omitted` は `DIFF_FIELDS` に入っているので、
**Job Summary の差分節には出続ける。**⟹ 🔴 **「誰も見ていない欄」ではなく、
「出ているが、誰も直す義務を負っていない欄」である。**

**この ADR は、Issue #403 が並べた3案（A: 判定に加える / B: 欄ごと落とす / C: 更新だけする）
に対する決着である。**⚠ **判定そのものは、この ADR の作業者が出したものではない**
——【受】Issue #403 の
[issuecomment-5714096661](https://github.com/takecchi/mnemora/issues/403#issuecomment-5714096661)
（クローンによる判定。⛔ オーナー本人の判定ではない）が「**案C を採る。ただし案C 単独では
#403 が再発するので、鮮度の名乗りを一緒に入れる**」と決めている。この ADR は
**その判定を実装した記録**であり、判定をやり直してはいない。

## 2. なぜ動いたか（変更理由は2本の ADR である。⛔「実装に合わせた」ではない）

【現物】相違の原因は**2つ重なっている**。どちらも**意図した仕様変更**であり、ADR として
記録されている。

### (2-a) [ADR 0188](./0188-association-over-limit-omission.md): `over_limit` に `stage` を足した

**42 / 82 の2行は、これだけで説明が付く**——`stage` ラベルが増えただけで `count` は不変である。
322 / 642 の `over_limit(stage=association)` も 0188 が足した札であり、
**「連想枠が `maxCount` で何件捨てたか」が初めて `omitted` に現れた分**である。

⭐ **0188 自身が、このずれを予告していた。**「引き受けた負債」3番の逐語【現物】:

> **`examples/chat/compare-baseline.json` の `omitted` フィールドは、この PR の後
> 実測と食い違う**（`stage` が無い・`association` 由来のエントリが無い）。……
> **このファイルは本 PR の対象外**——⛔ 更新しない（担い手への明示的な指示）。
> **次に `compare-baseline.json` を実測更新する PR が、このずれも一緒に解消する。**

🔴 **その PR は来なかった。**0188 が当てにしていた「次の実測更新 PR」は PR #386 だったが、
それは OPEN のまま止まっている【実測: `gh pr view 386` が `state: OPEN`】。
⟹ **Issue #403 は「予定されていた解消 PR が来なかった」ことの記録である。**

### (2-b) [ADR 0193](./0193-ann-unreached-covers-full-window.md): `ann_unreached` が初めて鳴った

**162 / 322 / 642 の3行に現れた `ann_unreached` は、こちらが原因である。**

`ann_unreached` という札自体は古い（[ADR 0026](./0026-ann-unreached-omission.md)）。しかし
【現物】0193 の逐語によれば、旧条件の3つ目 `annHits.length < kPrime`（窓が埋まっていない）が
**`ann_truncated` の判定が動く場合＝窓が満杯の場合をまさに除外していた**ため、その事象は
「**一度も鳴りようがなかった**」。0193 がこの条件を落とし、**発火条件が広がって初めて鳴り始めた。**

⟹ 🔴 **相違5行のうち、2行は「`stage` が増えただけ（`count` 不変）」、3行は
「基準値に存在しない entry がまるごと増えた」である。**⛔ **どちらも退行ではない**
——⭐門が見る2欄は12行すべてで一致している（§1）。

## 3. 決めたこと

### 決定1: `compare-baseline.json` を、**この PR 自身の CI の artifact** で実測更新する（案C）

[ADR 0133](./0133-compare-baseline-and-gate.md) 決定1 の逐語【現物】:

> CI の artifact をそのまま基準値の本体にする(手で数値を書いた欄は無い)

形の実例は [ADR 0168](./0168-examples-chat-uses-association.md) 決定5【現物】:

> `examples/chat/compare-baseline.json` を、この PR 自身の CI（`example-chat` ジョブ）が
> 生成した artifact で更新する（ADR 0133 決定1と同じ手順）。

⟹ **本体（`llmMode`/`embeddingMode`/`rowCount`/`rows`）は artifact を `node` で読み込んで
差し替えた。⛔ 手で数値を書いた欄は無い。**

⛔ **手元で `compare` を回して差し替えることはしない**——[ADR 0121](./0121-bench-baselines-from-ci-artifacts.md)
の表題が逐語で「**手元では書かない**」であり、[ADR 0119](./0119-archive-sweep-cost-bench.md)
決定6 が「**実測せずに数値を書けば、それは捏造である。**」と書いている。

⭐ **基準値の実測更新は、この repo では「腐りを直す例外的な手当て」ではない。**
`examples/chat/README.md`（`identifier-probes` の節）が逐語で「**値が意図して動いたときは、
基準値ファイルを手で更新すること**（CI は自動更新しない）。⭐ **その手間は目的である**」と
書いている【現物】——**最初から指定された正規の運用である。**

### 決定2: 旧基準・新基準・変更理由・失う保証を分けて示す

`docs/autonomy.md` §2.2 の4番の逐語【現物】:

> **合格させるためにテストを削除・skip したり、閾値・期待値・基準値を実装へ合わせない。**
> 仕様変更や誤った正解の修正で基準変更が必要なら、旧基準と新基準での結果、変更理由、
> 失う保証を分けて提示し、実装とは別のレビュー対象にする。

⟹ **旧基準と新基準の結果は §1 の表、変更理由は §2、失う保証は §5（引き受けた負債）に分けた。**
PR 本文にも同じ4つを分けて書く。

⚠ **今回「失う保証」は小さい**——⭐門が見る2欄は1つも動いていないので、**この更新で
退行の検知力は1ミリも下がらない。**下がるのは「旧い `omitted` の形が diff に残っている」
という記録だけであり、それは ADR 0188 / 0193 と、この ADR の §1 の表に残る。

### 決定3: 基準値の**鮮度**を毎 run 名乗らせ、⭐門が見ない欄の食い違いを**警告**として出す。⛔ **門にはしない**

🔴 **決定1（値を直すこと）だけでは、#403 はもう一度立つ。**Issue #403 の本文が案C の代償として
自分でそう書いており【現物】、**そしてそれは既に一度起きた**（§2-a の 0188 負債3）。

形は [ADR 0214](./0214-release-candidates-lists-not-judges.md) 決定5 の逐語をそのまま当てる【現物】:

> **数字を直しても、次の commit でまた腐る。⭐ 腐らないのは「どこまで数えたか」の宣言の
> ほうである。**⟹ 道具の役目は、**その宣言と現在地の差を毎回言わせる**ことに留める。

⟹ `scripts/compare-summary-lib.mjs` に純関数 `evaluateBaselineFreshness()` を足し、
Job Summary に節「**基準値の鮮度**」を出す。毎 run 名乗るのは3つである:

1. **宣言** — 基準値の `provenance`（どの commit を、いつ、何 run で測ったと名乗っているか）。
2. **現在地** — いま実測した artifact の commit と `measuredAt`。
3. **その差** — ⭐門が見ない欄（`DIFF_FIELDS` から `mnemoraShareOfNaiveChars` と
   `factStatementSurvived` を引いたもの）が、**どの会話長で・どの欄で**食い違っているか。

⛔ **ジョブを落とさない（終了コード 0/1/2 の意味は1つも変えない）。**理由は
[ADR 0223](./0223-cross-cutting-disciplines-extracted-from-the-adr-corpus.md) 決定3 の逐語【現物】:

> **門（落とす検査）にしてよいのは、偽陽性率に上限を置けると実測できたものだけである。
> 置けないなら門にしない。**⟹ **その代わりに置いたもの（観測口・警告・候補一覧・人手監査）を、
> 同じ場所に明記する。**

🔴 **`omitted` の偽陽性率は誰も測っていない。**⟹ 門にしない。**警告は、決定3 が言う
「その代わりに置いたもの」そのものである。**

⭐ **これは案A の弱い版ではない。**案A は「退行を止める」ための門であり、これは
「**基準値が古いことに気づかせる**」ための鮮度表示である。目的が違うので、後から案A を
置くときに邪魔にならない。⟹ **「誰も直す義務を負わない」を「毎 run 名指しされる」に変える。**

### 決定4: 実装は `scripts/compare-summary-lib.mjs` ＋ `scripts/compare-summary.mjs` に置く。⛔ `ci.yml` は触らない

【現物】`example-chat` ジョブの summary ステップは、`compare-summary.mjs` の **stdout を
`$GITHUB_STEP_SUMMARY` へリダイレクト**している。⟹

- **鮮度の節は stdout（Markdown）へ** → Job Summary に出る。差分節のすぐ後に置く。
- **警告の1行は stderr へ** → ジョブログに出る。`evaluateCompare` の直後・早期 exit の**前**に
  出すので、`fail`（exit 1）でも `indeterminate`（exit 2）でも必ず出る。

⛔ **`::warning::` は使わない。**この repo に前例はある（`scripts/decide-publish-dry-run.mjs`・
`scripts/apply-release-version.mjs`）が、どちらも **stdout** へ出す形である【現物】。ここでは
stdout が Job Summary へリダイレクトされているので同じ形は使えず、**stderr のワークフロー
コマンドが注釈として解釈されるかは、この作業者は確かめていない。**⟹ 確かめていない挙動に
依存しない。

⛔ **CI のステップを増やさない。**増やせば新しい失敗面ができる。既に走っているステップの
出力に足すだけで、**毎 run 目に入る**という目的は満たせる。

### 決定5: 「**基準値を更新する前に、2回以上の run で一致を確認する**」を明文化する

[ADR 0133](./0133-compare-baseline-and-gate.md) の「これが覆るとしたら」節が、逐語で
こう書いている【現物】:

> **`examples/chat/cassettes/compare.json` が再記録され、再現性が崩れたとき。**
> そのとき負債2が実害になる——基準値を更新する前に、再度2回以上の run で一致を
> 確認する規律を明文化する必要が出る。

⚠ **「明文化する必要が出る」と将来形で書かれたまま、明文化されていなかった**【実測: `docs/` と
`AGENTS.md` を当てた範囲】。⟹ **今回がまさに「基準値を更新する」場面なので、ここで明文化する。**

⭐ **⚠ 0133 はこの規律を「カセットが再記録されたとき」に条件付けている。この ADR は、
その条件を待たずに前倒しで明文化する**——条件が満たされてから書く規律は、**満たされた瞬間に
手元に無い**からである。⛔ **0133 の本文は書き換えていない**（採用済み ADR の本文は書き換えない）。

**明文化した内容**（`examples/chat/README.md` の `compare` 節に手順として置いた）:

- artifact を **2本以上**取り、`measuredAt` と `commit` を除いて `rows` が**バイト単位で一致**
  することを確かめてから採る。**同一 commit で同じジョブを再実行した2本が最も強い**
  （前例: [ADR 0170](./0170-association-search-tiebreak-nondeterminism.md) の3本）。
- ⛔ **一致しなければ基準値を更新しない**——先に直すべきは値ではなく非決定である。
  **0170 がまさにその実例である**【現物】: ADR 0168 が採った 322 行の値は、実は run ごとに
  `4481/4555/4558` と揺れる3値のうちの1点だった。

**この ADR 自身がこの規律に従った**【実測】: §1 の通り `main` の成功 run 8本で `rows` の一致を
確かめ、**さらに更新に使う artifact そのものを、同一 commit の2 attempt で突き合わせてから採った**（下の「測ったこと」7番）。

### 決定6: `_readme` の裏付けられない指し先を直す

【実測】`compare-baseline.json` の `_readme` は逐語で「CIのジョブがこのファイルを更新する
ことはない(意図的な手作業のみ。**ADR 0133参照**)」と書いているが、**ADR 0133 の本文に
「手作業」という語は1度も出てこない**（`grep -c` が 0）。

⛔ **主張自体は誤りではない**——ADR 0121 決定1 と ADR 0119 決定6 が支えている。
⟹ ⭐ **裏付けられないのは指し先だけである。**今回 `_readme` を触る PR なので
（同じファイルの同じ欄）、**指し先を実際に支えている ADR へ差し替えた。**⛔ これは
「ついでに直す」ではない——**触っている欄の中の、触っている主張の指し先である。**

## 採らなかった案

### ⛔ 案A: `omitted` を⭐門の判定に加える

**ADR 0223 決定3**（門にしてよいのは偽陽性率に上限を置けると実測できたものだけ）に触れる。
`omitted` の偽陽性率は誰も測っていない。⟹ ⛔ **却下ではなく「測ってから」である。**

⭐ **そして、測る前に置くと実際に何も検出しない形になりうる**ことが、この ISSUE の調査で
判明している【受: issuecomment-5714096661】——「`stage` ラベルの増減は無視して、同じ `kind` の
`count` の増加だけを見る」という弱めた形は、**いま相違している5行を1行も捕まえない**
（`over_limit(rescore)` の `count` は基準値も実測も同じである。§1 の表で【実測】確認できる）。
⟹ 🔴 **ADR 0133 の却下理由（全欄一致だと無関係な変更で赤くなる）を避けようとして形を弱めると、
検出力が 0 になる。**⟹ **案A を置くときは「この形はいま在る相違を何行捕まえるか」を実数で
出すこと。**

### ⛔ 案B: `omitted` を基準値ファイルから落とす

**ADR 0133 決定1 に正面から反する。**逐語【現物】:

> `retrieval-baseline.json` の `arms`/`time-term-baseline.json` の `probes` と同じ規律で、
> **`rows` は比較の主単位そのものなので落とさず残す。**

`omitted` は `rows` の中に在る。⟹ 採るなら決定1 を覆す ADR が要る。そこまでの理由は無い。
併せて、`stage: "association"` の切り捨て記録（北極星「知らないと言える」の測定対象そのもの）
が基準値から消える。

### ⛔ 案「値を『唯一の出所への指し』に置き換える」

ADR 0223 決定9（焼き込んだ数字は腐る。唯一の出所を指すだけにする）を `rows` にも当てる案。
**採らない**——ADR 0121 / 0133 決定1 が「**CI の artifact をそのまま基準値の本体にする**」と
決めており、⭐門は**値との突き合わせ**でしか動かない。指しに置き換えると門が成立しない。
⟹ **決定9 が実際に適用されてきたのは、このファイルでは説明文（`_readme`）の層である**
（PR #508 の前例）。**決定6 はその層に留めた。**

### ⛔ `provenance` を「指し」に置き換える

**触らない。**これは日付付きの**実測の記録**であって説明文ではない。置き換えると測った事実が
消える。

## 誰が壊れうるか / 引き受けた負債

1. 🔴 **警告は無視できる。**門ではないので、鮮度が「食い違っている」と言い続けても
   誰も直さないことはありうる。⟹ **この ADR が賭けているのは「毎 run 名指しされれば、
   いつか誰かが直す」である。**⛔ **それは保証ではない。**次にこの欄が腐ったときに、
   警告が実際に効いたかどうかで検算できる（§「これが覆るとしたら」）。
2. **鮮度の「宣言」は `provenance` の自己申告である。**`repeatRuns` が本当に2以上の run で
   確かめられたかを機械が検算する仕組みは無い。⟹ **決定5 の規律は、いまは文書と人の側に在る。**
3. **commit の一致は文字列比較でしかない。**`main` は数分おきに動くので commit 相違は常態で
   あり、⛔ **commit が違うこと自体は警告にしていない**（警告にすると毎 run 鳴って意味を失う）。
   ⟹ 鮮度が警告するのは**欄の食い違い**だけである。
4. **`omitted` は引き続き⭐門の判定に使わない。**この更新のあとも、`omitted` の退行は CI を
   赤くしない。**案A は測ってからである。**
5. 🔴 **今回入れた値も、次に `omitted` の形が変わればまた古くなる。**鮮度は
   **気づかせるだけで、直しはしない。**⟹ **#403 と同じ穴が塞がったとは言っていない**
   ——塞いだのは「気づかれないまま放置される」経路だけである。

## これが覆るとしたら

- **`omitted` の偽陽性率が実測され、上限を置けたとき。**⟹ 案A（⭐門に加える）へ進める
  （ADR 0223 決定3 の条件が満たされる）。そのとき鮮度の警告は残してよい——目的が違う。

  足りないことの実測になる。**負債1が実害になり、門にするか別の形（PR の検査・ISSUE の自動起票）

- **`examples/chat/cassettes/compare.json` が再記録されたとき。**⟹ ADR 0133 が
  「これが覆るとしたら」で名指しした条件そのものである。決定5 が先に明文化されているので、
