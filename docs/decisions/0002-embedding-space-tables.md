# ADR 0002: pgvector の抽象と埋め込み空間ごとのテーブル分割

- **状態**: 採用 (2026-09)

> （上流の `CHANGELOG.md` は CVE 番号を書いておらず、GitHub advisory database でも該当0件。

- **文脈**:
  mnemora は埋め込みモデルを固定しない。モデルを変える・多言語対応で複数モデルを併用する・将来の
  再 embed 移行を行う、といった事態を core が知らずに扱えることが `docs/decisions/0003-memorystore-vs-vectorstore.md`
  の非対称契約の前提になっている。ここで技術的な壁にぶつかる。**pgvector の `vector` 型は次元を指定しない列を
  作ること自体はできるが、次元指定なしの列には索引が張れない。**（確認済み）
  索引が張れなければ recall の二段検索（`0004-decay-at-query-time.md`）の段1が成立しない。
  つまり「次元を固定しない」という要求と「索引を張る」という要求は、同じ列の上では両立しない。

- **検討した選択肢**:
  - **単一テーブル + 次元混在**: `memory_embeddings(memory_id, space_id, embedding vector)` のように
    1テーブルに全空間の埋め込みを入れる案。次元を指定しない `vector` 列になるため索引が張れない。却下。
  - **次元ごとの列**（`embedding_1536 vector(1536)`, `embedding_3072 vector(3072)`, ...）:
    列を使う空間ぶんだけ事前に用意する案。モデルを追加するたびにマイグレーションで列を足す必要があり、
    使われない列がテーブルに残り続ける。空間の数が増えるほど疎になる。却下。
  - **最初からベクトル DB を外出しする**(pgvector をやめて専用ベクトル DB を Phase 1 から採用):
    `docs/decisions/0003-memorystore-vs-vectorstore.md` の「VectorStore は再構築可能な派生索引」という
    契約自体は満たせるが、mnemora は Postgres を必須要件として運用を組んでおり（`0005-job-queue-abstraction.md`
    参照）、Phase 1 からインフラを一つ増やすコストに見合う理由が無い。将来 adapter として選べる余地は
    interface 分離（0003）で既に残している。却下（Phase 1 では）。
  - **埋め込み空間ごとにテーブルを分ける**: 採用（下記）。

- **決定**:
  埋め込み空間（モデル, 次元の組。`EmbeddingSpaceId`）ごとに専用テーブル `memory_embeddings_<space>` を
  空間登録時に作る。**core はこのテーブル分割を知らない。**core が知るのは `VectorStore` interface と
  `EmbeddingSpaceId` という値だけであり、テーブルをどう分けるかは `packages/postgres` の実装詳細に留まる。
  **Phase 1 は稼働中の空間を1つに限る。**2つ目の空間を追加するときは、既存行の移行ではなく「テーブルを
  追加する」形で済むようにしておく（`memory_embeddings_<space>` はテーブルごとに独立しているため、
  新しい空間の追加は既存テーブルへの破壊的変更を伴わない）。

- **理由**:
  1. 次元を固定した `vector(dimensions)` 列でなければ索引が張れないという pgvector 自身の制約が、
     この決定を直接に要求する。回避可能な設計上の好みではなく、技術的な必須条件。
  2. テーブルを空間単位で分けることで、モデル追加が「新しいテーブルを足す」という加算的な変更になり、
     既存空間のデータやクエリに触れない。埋め込みモデル移行のコストを局所化できる。
  3. `core` が次元を知らないという境界を保てる。次元は adapter（postgres）の実装詳細であり、
     interface 層の型に漏れない。

- **結果（この決定が招くもの）**:
  良い面: 索引が確実に効く。空間の追加・廃止がテーブル単位の操作で完結し、他の空間に影響しない。
  「モデルを変える」ことが「記憶を作り直す」ことと直結しない（0003 と同じ理由）。

  引き受ける負債: 空間が増えるほどテーブル数が増える。マイグレーション・スキーマ管理・監視対象が
  空間の数だけ増殖する。Phase 1 は空間を1つに限定してこの負債を先送りしている——Phase 2 以降で複数空間が
  実際に必要になったときに、テーブル生成・登録の運用（誰が・いつ・どうテーブルを作るか）を設計する必要がある。
  これは本 ADR の範囲外として残す。

  バージョン要件: pgvector は **`>= 0.8.0` を必須**とする（iterative index scan が入っているため、
  `0004-decay-at-query-time.md` 参照）。**`>= 0.8.2` を推奨**とする(2026-02-26 リリース。
  CVE-2026-3172 のバッファオーバーフロー修正を含む)。

- **これが覆るとしたら**:
  - pgvector が将来のバージョンで可変次元列への索引付けをサポートしたら、テーブル分割の技術的必要性が
    消える。その場合でも「空間ごとの独立性」という設計上の利点（負債の局所化）は残るため、単純に
    単一テーブルへ戻すとは限らない。
  - 空間の数が Phase 1 の想定を大きく超え（たとえば数十空間を同時運用する必要が生じ）、テーブル管理の
    負債が索引の利益を上回ると分かったら、空間のグルーピング（近い次元をまとめる等）を再検討する。

- **確かめていないこと**:
  - **マネージド Postgres 各社が実際に提供する pgvector のバージョンは特定できなかった。**
    利用環境ごとに `SELECT * FROM pg_available_extensions WHERE name='vector'` で確認する必要がある。
  - **可変次元列を Drizzle でどう表現するかの一次情報は見つからなかった。** 本 ADR の決定（空間ごとの
    テーブル分割）はこの問題自体を回避するため、mnemora の設計には影響しない。ただし調査した事実として
    記録しておく。
