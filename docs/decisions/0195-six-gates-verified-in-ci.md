# ADR 0195: 6つの門の緑は CI で確かめる——手元で全体を走らせることを止まる条件にしない（Issue #407）

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-17

**⚠ 各主張の出所を分ける**（ADR 0105 / 0106 / 0127 / 0128 / 0137 の体裁を踏む）。

- **【現物】** — この repo のコード・文書を書き手が読んで確かめた。
- **【実測】** — この書き手が自分の手で走らせて確かめた。
- **【受】** — 報告として受け取り、再導出していない（出所を明記する）。

---

## 問い

[Issue #407](https://github.com/takecchi/mnemora/issues/407)。`docs/autonomy.md` §2
「どこで止まるか」の止まる条件に、次の行が在った 【現物】:

```
- [ ] 6つの門が緑（`typecheck` / `lint` / `format:check` / `test` / `build` / `pack:check`）
```

**この行は「どこで緑を確かめるか」を書いていない。**そして同じチェックリストの別の行が
`CI が緑` を**独立の条件**として立てている。⟹ **2行が並ぶことで、上の行は
「手元で6つの門を走らせる」ことを求めている、と読める。**§2.1 の5番
（「**手元の**6つの門の緑を、CI の緑の代わりにしない」）も、手元で走らせることを
前提にした書き方だった。

**⚠ これは実態と食い違っている。**オーナー takecchi の方針（逐語、2026-09-17 に
マネージャー経由で受領 【受】）:

> GitHubで自動テストが行われるので**ローカルでテストしなくても大丈夫です**。
> 二重に時間かかっちゃうと思うので**大人しくGitHubのCIに任せてしまうのは手です**

⚠ **そして実際に事故が起きている** 【受】——2026-09-17、この器で担い手が
`pnpm run test`（全体）を背景処理で走らせたまま作業を畳み、**起こし直しの上限に当たって
委譲ごと止まった。**⟹ §2 を素直に読んだ担い手が、止まる条件を満たそうとして
手元の全体テストを走らせることが、実際に起きている。

**v1.0.0 のリリース直前であり、docs の記述が実態とずれていること自体が出荷物の欠陥である**
（[Issue #256](https://github.com/takecchi/mnemora/issues/256) と同じ族）。

## ⭐ まず「§2 が何を保証しているか」を確かめた

**書き換える前に、緩めてはならないものを特定した。**

**§2 が守ろうとしている保証は「緑を確かめずにマージしない」である** 【現物】
——**「*どこで*確かめるか」ではない。**§2 の直後の行が
「**CI が緑で差分に問題が無ければ、そのままマージする**（§3。ADR 0118）」と書いており、
止まる条件の全体が**マージの可否**に向いていることからも読める。

⟹ **確かめる場所を CI へ移しても、この保証は弱まらない。**次節でそれを現物で示す。

## 【現物】CI は6つの門をすべて走らせており、手元より強い

`main` = `0505aea` の `.github/workflows/ci.yml`。**ジョブ名
`typecheck / lint / test / build`（9-10行目）の中に、6つとも在る**:

| 門 | `ci.yml` の行 | ステップ名 |
|---|---|---|
| `typecheck` | 28 | `Typecheck` |
| `lint` | 31 | `Lint` |
| `format:check` | 34 | `Format check` |
| `test` | 37 | `Test` |
| `build` | 40 | `Build` |
| `pack:check` | 71 | 「publish 梱包の門（pack:check）を毎PRのCIでも走らせる（Issue #241）」 |

⟹ **6つの門のうち最後まで CI に無かった `pack:check` も、Issue #241 /
[ADR 0138](./0138-pack-check-in-ci.md) で既に配線済みである。**

⭐ **さらに、CI のほうが手元より強い。**手元の `pnpm run test` は `DATABASE_URL` が
無ければ DB 段を「実行していません」と告知して緑のまま通る（[ADR 0015](./0015-root-test-gate-reports-skipped-db-tests.md)・
`docs/autonomy.md` §4）。CI は DB を持つジョブを別に持つ（check run
「ルートの test 門の DB 段（DATABASE_URL 在りで順方向に実測、ADR 0015）」）。

⟹ **手元の6つの門の緑は、CI の6つの門の緑の部分集合にすぎない。**
**保証は弱まらない。強まる。**

## 決定

### 1. 6つの門の緑は、CI で確かめる

`docs/autonomy.md` §2 の止まる条件の該当行に、**確かめる場所は CI である**ことを明記する。
**止まる条件の項目そのものは消さない**——消すと「緑を確かめずにマージしない」という
保証が消える。変えるのは場所だけである。

### 2. ⭐ 「手元で走らせること」と「マージの前提として課すこと」を書き分ける

**手元の全体テストを禁じるものではない。**実際、`initdb` を要する測定などでは
手元で走らせている 【受】。**課さないのは「マージの前提として手元の全体テストを
走らせること」だけである。**

⟹ 速い手元の検査（`typecheck` / `lint` / **触ったファイルのテストだけ**）は、
**短い輪として引き続き有用である**と明記する。これは「緑の根拠」ではなく
「早く気づくための道具」であり、役割が違う。

### 3. §2.1 の5番と §4 の該当行は、消さずに向きを足す

- **§2.1 の5番**（手元の緑を CI の緑の代わりにしない）は**今も正しい**
  ——むしろ本 ADR の根拠そのものである。⟹ 消さずに、
  「**だから §2 は CI で確かめることを止まる条件にしている**」という帰結を足す。
- **§4 の表の「手元の `pnpm run test` が緑」の行**は、手元で走らせる人にとって
  今も正しい落とし穴の記述である。⟹ 消さずに、
  「そもそも手元の全体テストは止まる条件ではない」ことを足す。

### 4. §2 の「判断に迷ったら」の括弧を直す

「6つの門のどれかが微妙」→「**CI の門のどれかが微妙**」。
6つの門をどこで見るかを変えた以上、この括弧も同じ場所を指していなければ、
**同じ食い違いが1行だけ残る。**

## 検討して採らなかった案

- **止まる条件から「6つの門が緑」の行ごと消す。**
  ⟹ **採らない。**`CI が緑` の行だけが残るが、そちらは §2.1 の判定手順
  （check-runs を job 単位で読む）を指しており、**「どの門が在るべきか」を列挙していない。**
  ⟹ 門が1つ CI から落ちても誰も気づかなくなる。**列挙は保証の一部である。**
- **「手元で6つを走らせること」を残したまま、CI でも確かめると書き足す。**
  ⟹ **採らない。**オーナーの方針（「二重に時間かかっちゃう」）に正面から反する。
  ⚠ **そして、これは事故が実際に起きた形そのものである**（上記「問い」節）。
- **手元の全体テストを明示的に禁止する。**
  ⟹ **採らない。**禁止は行き過ぎである——`initdb` を要する測定のように、
  手元で走らせることに固有の用途が在る 【受】。**課さないことと禁じることは別である。**
- **`api:check`（49行目）と `check:cjs-parse`（52行目）も「門」に数え、列挙を8つにする。**
  ⟹ **採らない。**この2つが止まる条件に入るべきかは**別の判断**であり、
  本 ADR の射程（記述と実態の食い違いを消す）を超える。**Issue #407 の
  「確かめていないこと」に残した。**

## 引き受けた負債

1. **手元で速い検査すらしない担い手が現れると、CI が赤くなるまで気づかない。**
   CI は1周に数分〜十数分かかる（DB ジョブを含む）。⟹ **型エラー1つのために
   1周を捨てることが起こりうる。**本 ADR は「速い検査は短い輪として有用」と
   書くに留め、**強制はしていない**——強制すると、いま消した食い違いが
   別の形で戻るためである。
2. **「6つの門」という列挙が、`ci.yml` と `docs/autonomy.md` の2箇所に在る状態は続く。**
   片方だけが変わればずれる。⚠ **これは `AGENTS.md` が「複製した瞬間から、正文と要約は
   ずれ始める」と警告している形そのものである。**本 ADR はこれを解いていない
   ——**列挙を機械的に突き合わせる歯は足していない。**
3. **本 ADR の根拠のうち、オーナーの逐語はマネージャー（クローン）の記憶からの【受】である。**
   この書き手は一次の出所に当たっていない。

## これが覆るとしたら、何が起きたときか

- **CI から6つの門のどれかが落ちたとき。**そのとき §2 の列挙は「CI で確かめる」と
  書いてあるのに実際には確かめられていない、という**新しい食い違い**になる。
  ⟹ 負債2番の歯が要る。
- **CI の1周が、手元の検査より十分に遅くなったとき。**いまは DB ジョブを含めて
  数分〜十数分であり、「二重に走らせる」費用のほうが大きいと判断した。
  **この大小が逆転すれば、判断も変わる。**
- **オーナーの方針が変わったとき。**本 ADR の決定1と2は、上に引いた逐語に直接立っている。

## 測ったこと

- 【現物】`.github/workflows/ci.yml` に6つの門がすべて在ることを、行番号つきで確認した
  （上の表）。`grep -n "run: pnpm" .github/workflows/ci.yml` と
  `sed -n '1,75p' .github/workflows/ci.yml` で読んだ。
- 【現物】`docs/autonomy.md` の書き換え対象4箇所が、それぞれ**1箇所だけ**であることを、
  置換前に出現数を数えて確認した（0 件や2件以上なら中断する形にした）。
- 【現物】`gh issue list --state open --limit 60` を引き、**同趣旨の OPEN な issue が
  無い**ことを確認してから Issue #407 を起こした。
- 【実測】ADR 番号は `node scripts/adr-renumber.mjs --next`（[ADR 0179](./0179-adr-number-assigned-at-merge.md)）で採った
  ——`origin/main` の ADR 184 本・他のリモートブランチ14本・open な PR 4本の主張を見て
  `0195` を返した。**確定はマージ直前の既定動作が行う。**

## 確かめていないこと

- **`api:check` と `check:cjs-parse` を止まる条件にどう扱うか**は決めていない（上記）。
- **オーナーの逐語の一次の出所**には当たっていない（負債3番）。
- **「`initdb` を要する測定では手元で全体を走らせている」**は【受】であり、
  この書き手は再導出していない。
- **本 ADR の変更が、実際に担い手の振る舞いを変えるか**は測っていない
  ——文書の変更であり、効果は次にこの文書を読む担い手の行動でしか測れない。
