# ADR 0118: PR のマージを、CI 緑・差分健全を条件に担い手へ委譲する（`docs/autonomy.md` §3 の改定）

- **状態**: 採用 (2026-09)

- **⚠ 番号について**: この ADR はもともと ADR 0112 を名乗って提出された（PR #212）が、
  同時期に着地した [ADR 0112](./0112-relax-zod-dependency-range.md)（zod の依存範囲緩和、PR #213）と
  番号が衝突したため 0118 へ付け替えた。**PR #212 はオーナー takecchi のレビュー待ちで open のまま
  保留されており、いつ着地するか未定である。保留の間に 0118 が別の PR に割り当てられ、
  再び衝突する可能性がある——マージ直前に `docs/decisions/` の空き番号を必ず取り直すこと。**

- **⚠ 先に書く — この ADR が決めていないこと**:

  **§3 の他の禁止条項には一切触れない。** npm への publish・Release 作成・npm 側の設定・
  `package.json` の `version` を上げること・`docs/north-star.md` の書き換え（「やらないこと」への
  追記を含む）・公開 API の破壊的変更・ライセンス／パッケージ名／依存の追加方針の変更・
  §5 級の判断——**これらはすべて、この ADR の後もそのまま ⛔ である。**
  この ADR が変えるのは「PR のマージ」という**1行だけ**である。

  **「どの PR をマージすべきか」という技術判断も、この ADR は変えない。**
  変えるのは「誰がマージを実行するか」だけであり、
  6つの門・変異試験・ADR の要件（`AGENTS.md` / `docs/autonomy.md` §2）は一切緩めない。

- **文脈**:

  ADR 0071（Phase 2 の作業選定を自律エージェントへ委譲する）は、
  「マージも委譲する」案を検討したうえで**明示的に却下していた**（同 ADR の「採らなかった案」節、逐語）:

  > **マージも委譲する** | オーナーが「マージまでしちゃっていいよ」と言った場面は在ったが、
  > **それは特定の PR に対する許可であって、恒常的な委譲ではない。**
  > 恒常化するならオーナーが明示的に決める

  ⟹ **ADR 0071 自身が、この決定の覆る条件を名指ししていた**——「オーナーが明示的に決める」。

  そして 2026-09-15、まさにその条件が満たされた。**担い手が Issue #182 の実装を終え、
  マネージャー経由で「CI が緑ならマージまで」と伝えられた際、`docs/autonomy.md` §2/§3 の
  現行の文言（「⛔ PR を出したら止まる。マージしない」「PR のマージ：取り込む判断はオーナーのもの」）
  を根拠にマージを拒否した。**これは当時の正典に照らして正しい判断だった
  （伝聞1つで ⛔ を越えるべきではない、という規律そのものが機能した）。

  ⟹ **問題は担い手の側ではなく、正典が実際のオーナーの意向を反映していないことにあった**
  （Issue #203 に詳細な経緯が記録されている）。

  この Issue を受けて、オーナー本人がマネージャー経由で明示的に回答した（**逐語**、2026-09-15）:

  > **a-1でお願いします。というか積極的にマージをお願いします。**

  「a-1」は、Issue #203 が示した選択肢 (A)「正典を運用に合わせる」のうち、
  **条件付きで §3 の表から「PR のマージ」を外す案**（CI が緑であることを条件にする、という提示）を指す。
  後半の「積極的にマージをお願いします」は、**単発の許可ではなく恒常的な運用方針としての意思表示**であり、
  ADR 0071 が要求した「オーナーが明示的に決める」を満たす。

  **⚠ 出所について（`docs/autonomy.md` §5 の要求どおり明記する）**:
  上記オーナーの逐語は、この ADR の筆者（担い手）がオーナー本人から直接受け取ったものではなく、
  **マネージャー経由で伝達されたもの**である。筆者はこの伝達内容そのものを検証する手段を持たない。
  ⟹ **この ADR は「マネージャーが、オーナーが明示的に許可したと伝えている」という前提の上に立っている。**
  この前提が誤りだった場合、この ADR は無効であり、`docs/autonomy.md` は ADR 0071 の状態へ戻すべきである。

- **決定**:

  **1. `docs/autonomy.md` §3 の表から「PR のマージ」の行を削除する。**
  代わりに、§3 の直後（または §2）に次の条件を明記する:

  > **CI の6つの門がすべて緑で、差分に明らかな問題が無い場合に限り、担い手は自分で PR をマージしてよい。**
  > `gh pr merge <n> --squash --delete-branch` を使う。
  > **迷ったら（差分が大きい・レビューが必要だと感じる・6つの門のどれかが微妙）、マージせず止まって報告する。**
  > この条件は「PR のマージ」1点にのみ適用され、**§3 の他の禁止条項を一切緩めない。**

  **2. §2「どこで止まるか」の「⛔ PR を出したら止まる。マージしない。（§3）」を、
  実態に合わせて次のように改める。**

  > **CI が緑で差分に問題が無ければ、そのままマージする（§3）。
  > 判断に迷ったらマージせず、そこで止まって報告する。**

  **3. 境界の引き方は ADR 0071 の「取り消せるか」の基準を維持する。**
  この ADR は「マージは取り消せない操作である」という前提そのものは否定しない。
  ⟹ だからこそ、委譲の条件を**狭く**（CI 緑・差分健全）保ち、
  **迷ったら止まる**という既定を残す。「積極的にマージを」という運用指示を、
  「何でもマージしてよい」とは読まない。

- **採らなかった案**:

  | 案 | 却下の理由 |
  |---|---|
  | **現状維持（Issue #203 をオーナー未定として放置する）** | オーナーは既に明示的に決定を返している。放置すると、Issue #182 と同じ形の停止が今後も繰り返される——それこそが Issue #203 が指摘した実害である |
  | **単発の許可として扱い、PR ごとに都度確認する** | オーナーの発言（「積極的にマージをお願いします」）は継続的な運用方針を求める言い方であり、都度確認は本人の意図に反する。ADR 0071 が求めた「明示的に決める」は既に満たされている |
  | **マージ可能な規模・レビュー要否の閾値を数値で細かく決める**（Issue #203 の (A) が例示した「どの規模まで自己マージしてよいか」） | オーナーの逐語にその粒度の条件が含まれていない。**推測で線を引くと、オーナーが言っていない制約を勝手に足すことになる。**⟹ 「CI 緑・差分健全」という広い条件と「迷ったら止まる」という既定に留め、**より細かい閾値が必要になったら、そのときに新しい ADR で決める**（`docs/autonomy.md` §3.1 と同じ思想） |
  | **§3 の他の禁止条項（publish・version・north-star・破壊的変更等）も同時に見直す** | Issue #203 はマージの1点のみを問題にしており、他の条項の衝突は報告されていない。「ついでに直す」をしないという規律（`docs/autonomy.md` §2）をこの ADR 自身にも適用する |

- **引き受けた負債**:

  - **「差分に明らかな問題が無い」の判定は、依然として担い手の主観に委ねられている。**
    数値的な閾値（diff の行数・変更ファイル数など）は置いていない。
    誤ってマージすべきでない PR をマージした事例が出たら、そのときに閾値を ADR で明文化する。
  - **オーナーの許可の出所がマネージャー経由の伝聞である**（上記のとおり）。
    この ADR 自体が伝聞の上に成り立っているという事実は、意図的に消さずに残す。

- **これが覆るとしたら**:

  - オーナーが直接（伝聞を介さず）この委譲を撤回したとき。
  - マージの権限委譲によって実害（取り消せない失敗、例えば壊れた変更が `main` に入り
    利用者に届いた等）が起きたとき——そのときは委譲を狭めるか、レビューの挟み方を
    条件に足す ADR が必要になる。
