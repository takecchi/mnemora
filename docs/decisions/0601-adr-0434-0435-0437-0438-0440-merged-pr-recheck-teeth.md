## 決定【判断】

1. 実装は変えない。
2. 歯を足す（試験だけ）。
   - **#1544 (a)**: `claim-key-index-limit-unnamed-guard.postgres.test.ts`（新規）。
     - 本物の Postgres: claimKey が小さく、`extractorVersion` だけ・`contentHash` だけが1万字（`sourceObservationId` あり。`uq_memories_extraction` は partial 索引で、これがあるときだけ効く）。名前の無い 54000 が出て、`ClaimKeyIndexLimitError` に包まれず生の例外のまま出る。
     - 合成した 54000: `translateClaimKeyIndexLimit` に名前の無い形の 54000 を投げる関数を渡す。3つの項の合計が 2704 を超える入力（tenantId だけ大きい・extractorVersion だけ大きい・contentHash だけ大きい・3つとも同じ）は包まず、合計が 2704 以下なら包む。合計がちょうど 2704 なら包み、2705 なら包まない。tenantId は、本物の索引の行が 8191 バイトに届く大きさにすると `tenantId + subjectId` の項が先に断るので、本物では縛れない。合成で縛る【実測】。
   - **#1544 (b)**: 同じファイルに「全候補が落ちたら先頭の候補の例外を投げる」。`ClaimKeyIndexLimitError` になる候補と別の SQLSTATE（23514）で落ちる候補を、両方の順で渡す。例外の型は見るが、投げる型が `RangeError` かどうかは縛らない。
   - **#1545 (a)**: `packages/core/src/__tests__/purge.test.ts` に、`deleteAcrossSpaces` が失敗しても `scrubPurged` が走ること（`already_purged` の通常の分岐と、競合で `already_purged` になった分岐）、両方が失敗すれば欄が両方付くこと。
   - **#1545 (b)**: `tenant-settings-helpers-omit-params.test.ts` に、9本それぞれで、複数行の SQL の文と `params: (omitted by mnemora, N chars)` が **message** にそのまま残ること（stack ではなく message。cause の message も）。
   - **#1546 (a)**: `activity-subject-counter-tenant-qualification.postgres.test.ts` に「subject 側の修飾: 同じテナントに別の subject のカウンタ行がある」。`aggregateScope`・`archiveDecayed` それぞれで、別 subject の行が1本だけのとき（その値を使わない）と、並んでいるとき（落ちず、その subject の値だけを使う）。
   - **#1546 (b)**: `purge-memory-uppercase-id.postgres.test.ts` に、uuid の形でない大文字を含む id（3通り）が、そのままの綴りで「not found for tenant」の message に出ること。
   - **#1542**: `in-memory-nul-numeric-purged-at-postgres-alignment.test.ts` と `testkit-fixtures-nul-numeric-purged-at-alignment.postgres.test.ts` の表（2つの表は同じ内容）に、`createMemoryWithOutbox`・`createObservationWithOutbox` で SOH を含む `jobKinds` の要素は通る、を足す。
   - **#1548**: 取り直し後（attempts が 2 以上）の正当な complete・fail が終端を付ける歯を、`in-memory-outbox-terminal-exclusive.test.ts` と `outbox-complete-fail-terminal-exclusive.postgres.test.ts` に足す。
3. **縛らないもの**（クローンの判断）: 例外の型（`RangeError` かどうか）。#1544 の `cause` に pg の欄を全部写すかどうか（`code`・`schema`・`table`・`constraint` と message だけを写す、は既存の歯のとおり）。

## #1548 の追加の変異の結果【実測】

すり抜けたのは「取り直し後の正当な complete・fail の直接の歯が無い」ことだけだった。月・era・終端の検査は捕まった。

| 変異 | 結果 |
|---|---|
| `extraction.ts`: `month - 1` を `month` | `extraction-local-date.test.ts` 19本中16本が赤。赤3回・戻して緑3回（別々のコマンド） |
| `extraction.ts`: `era: "short"` を外す | 19本中5本が赤（紀元前の2本・年またぎ・範囲の端・組み直した暦日）。赤3回・緑3回 |
| `extraction.ts`: `1 - year` を `-year`（やりすぎ） | 同じ5本が赤。赤3回・緑3回 |
| `in-memory-outbox-store.ts` の complete で終端（`completedAt`/`failedAt`）の検査を外す | `in-memory-outbox-first-terminal-wins.test.ts` 8本中3本、`in-memory-outbox-terminal-exclusive.test.ts` 6本中2本が赤（捕まった）。first-terminal-wins は赤3回・緑3回。`in-memory-fixtures.conformance.test.ts` は緑のまま |
| complete で `expectedAttempts >= 2` なら黙って返す（Postgres） | `conformance.postgres.test.ts`（`-t "OutboxStore"`）の「⭐ 再現(Issue #233)」1本と `outbox-first-terminal-wins.postgres.test.ts` の「例外は直す前と同じ…」1本が赤。`outbox-complete-fail-terminal-exclusive.postgres.test.ts` の既存の3本は緑のまま |
| 同じ変異（fixture） | `in-memory-fixtures.conformance.test.ts` の「⭐ 再現(Issue #233)」1本と `in-memory-outbox-first-terminal-wins.test.ts` の1本が赤。`in-memory-outbox-terminal-exclusive.test.ts` の既存の6本は緑のまま |

「正当な2回目の complete が通る」ことを名指しで縛る歯は、Postgres・fixture とも `first-terminal-wins` 系以外では conformance の #233 の1本だけで、その it の主題は別（遅れたワーカーの fail が弾かれる）だった。そこで、新しい歯を足した。上の決定のとおり、新しい歯は complete と fail のそれぞれが赤になり（Postgres の complete・fail、fixture の complete）、戻して緑になる【実測】。

## 縛っていないもの

- 例外の型（`RangeError` かどうか）と、#1544 の `cause` に pg の欄を全部写すかどうか。クローンの判断。
- tenantId の項を本物の Postgres で赤にすること。本物の索引の行が 8191 バイトに届く tenantId は `tenantId + subjectId` の項が先に断るので、本物では作れない。合成した 54000 で縛った。
- #1548 の fixture の fail の「attempts が 2 以上なら黙って返す」変異は走らせていない【未確認】。fixture の fail の直接の歯（上の新しい1本）は complete と同じ it に入れてあるが、変異は complete 側だけ当てた。

## これが覆るとしたら

名前の無い 54000 を包む条件を変えるとき（ADR 0435）。`already_purged` の後始末の独立を変えるとき・公開ヘルパーの omit-params の範囲を変えるとき（ADR 0437）。subject カウンタの引き方・`purgeMemory` の id の扱いを変えるとき（ADR 0438）。outbox の終端の先勝ち・日付の組み方を変えるとき（ADR 0440）。`jobKinds` の検査で NUL 以外を拒むことにしたとき（ADR 0434）。
