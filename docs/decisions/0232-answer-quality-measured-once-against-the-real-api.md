# ADR 0232: 回答品質を実 API で1回測り、記録で再生できる形にする — 記録器が同じ鍵を二度録っていた穴を塞ぐ（Issue #498 / #506）

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-17

**⚠ 各主張の出所を分ける**（ADR 0146 / 0210 / 0229 と同じ体裁）。

- **【現物】** — この repo のコード・文書を書き手が読んで確かめた。
- **【実測】** — 書き手が自分の手で走らせて確かめた。
- **【受】** — 報告・判断として受け取り、自分では再導出していない。

## 文脈

[ADR 0229](./0229-answer-bench-compares-final-answers-with-a-ground-truth-bench-quality-not-yet-claimed.md)
（PR #511、Issue #506）が `answer` サブコマンドを着地させたが、**回答品質は1文字も
測られていなかった。**理由は構造的である【現物】:

- `recorded` provider は記録に無い入力で例外を投げ（[ADR 0051](./0051-recorded-provider-cassette.md)）、
  カセットの鍵は入力のハッシュである（[ADR 0052](./0052-compare-cassette-and-provenance-survival.md)）
  ⟹ **新しい評価ケースは1件も既存カセットに無い。**
- `deterministic` への置き換えは [`docs/autonomy.md` §2.2](../autonomy.md#22-品質を変える変更の評価と合格基準の扱い)
  決定3 が明示的に禁じている。
- `local` は埋め込み専用で、LLM 側に存在しない。

⟹ **鍵と課金が要り、それはオーナーの判断である**（[ADR 0184](./0184-conformance-scope-documented-not-closed.md)
決定4 / [`docs/conformance.md` §7](../conformance.md#7-実-api-に当てる手順鍵を持つ人向け)）。
**本 ADR は、オーナーから鍵を受け取って実測した回である。**

## 決めたこと

### 1. 🔴 記録器は、同じ鍵を二度録らない（memo として振る舞う）

**これが本 ADR の中心である。**カセットの鍵はプロンプトのハッシュであり、
**1つの鍵は1つの値しか持てない。**一方、実 LLM は同じプロンプトに毎回違う応答を返す。
⟹ 同じプロンプトが1回の記録の中で複数回現れると、`Map.set` の**後勝ちで先の値が消え**、
**その記録は、記録を作った実行そのものを再生できなくなる。**

**【実測】実際にこれを踏んだ。**`answer` の評価ケース12件のうち**3件が同じフィラー発話
「今日はいい天気ですね。」を含む。**実 `gpt-4o-mini` はその同一の抽出プロンプトに対して
digest を**3通り**に返した:

| 記録中に観測された digest |
|---|
| `今日はいい天気` |
| `今日はいい天気である。` |
| `今日はいい天気です。` |

カセットに残ったのは最後の1つだけである。⟹ 再生時、先の2ケースが組み立てる記憶経路の
プロンプトは記録と食い違い、`RecordedLLMProvider` が
「**このプロンプトは記録に無い**」で落ちた【実測】。

⟹ **`RecordingLLMProvider` / `RecordingEmbeddingProvider`（`packages/testkit`）を、
一度録った鍵については委譲先を呼ばず記録済みの値を返す形に変えた。**

#### 🔴 何を買い、何を捨てたか（この取引を明示する）

| | 直す前 | 直した後 |
|---|---|---|
| 同じプロンプトが N 回現れたとき | **最後の応答**が記録される | **1回目の応答**が記録され、2〜N 回目は API を叩かない |
| 記録は、記録を作った実行を再生できるか | ⛔ **できない**（先の値が消えている） | ⭕ **できる** |
| 実 API の非決定性 | 記録に**入る**（ただし最後の1サンプルだけが残る） | ⛔ **記録されない** |
| 繰り返し分の API 呼び出し | 叩く（課金される） | 叩かない |

🔴 **⟹ 「記録が自分自身と矛盾しない」を買う代わりに、「実 API の非決定性を記録する」を
捨てている。**

⚠ **ただし、捨てたものは元々ほとんど残っていなかった。**鍵が1つの値しか持てない以上、
N 回の揺れのうちカセットに残るのは常に1つだけである——直す前も「非決定性を記録して
いた」わけではなく、**「N 個のサンプルのうちどれが残るかが実行のたびに変わっていた」**
だけである。⟹ **捨てたのは「どのサンプルが残るかの偶然」であり、非決定性そのものの
記録ではない。**非決定性を測りたいなら `verify` がその役目を持つ（ADR 0051）。

- **副次的に、繰り返し分の API 呼び出しと課金が消える**【実測】——同じケース集合で
  `chat.completions.create` が **94回 → 67回**、`embeddings.create` が **50回 → 39回**、
  費用が **$0.004756 → $0.003336** に下がった。
- ⛔ **再生（`RecordedLLMProvider`）の代わりではない。**memo は1回の記録セッションの
  中でしか効かず、プロセスを跨がない。

#### 🔴 既存カセット（`retrieval` / `compare`）への影響 —— 同じ穴を持つが、再生は壊れていない

**⚠ この変更は `retrieval` / `compare` の記録経路にも掛かる。**⟹ **既存のカセットが
同じ穴を持っていないかを確かめた。**

**【実測】持っている。**`compare` のカセットは **LLM entries が13件しか無い**のに対し、
`DEFAULT_COMPARE_SEQUENCE` の実行時呼び出し回数は **657回**である
（`__tests__/cassette-coverage.test.ts` が既にこの差を歯として固定している）。
⟹ **記録中に644回ぶんの後勝ち上書きが起きていた。**

**それでも再生が壊れていないのは、次の理由による**【現物】:

1. **`compare.ts` / `retrieval-quality.ts` は `complete()` を1度も呼ばない**
   （両ファイルへの grep が0件）。LLM を使うのは `observe()` 経由の**抽出だけ**である。
2. **抽出プロンプトは、生の発話テキストだけから決まる**——`buildConversation` /
   `buildProbeSetConversation` が返す固定の入力であり、**先行する LLM 呼び出しの出力に
   依存しない。**
3. **両ベンチは `consolidate()` / `reflect()` を呼ばない**（grep 0件）——記憶の内容から
   プロンプトを組む経路が走っていない。

⟹ 🔴 **上書きされても、後続のプロンプトが変わらない。**だから「記録に無い」は起きない。
上書きが意味するのは「再生は実行時の分散を潰す」ことだけであり、それは
[ADR 0052](./0052-compare-cassette-and-provenance-survival.md) が既に代償として
引き受けている。

⭐ **`answer` は、この repo で初めて「LLM の出力から組み立てたプロンプトを、もう一度
LLM へ送る」ベンチである**（`buildMnemoraPrompt(recall)` → `complete()`。
`answer-bench.ts` が唯一の呼び出し元で、`cli.ts` の同名の使用は画面表示のみ）。
⟹ **だからこの穴は、いま初めて牙を剥いた。**

⛔ **既存のカセットは1バイトも録り直していない。**再生側（`Recorded*Provider`）は一切
変えておらず、既存の数字の意味は変わらない。⚠ **それらを録り直したときに件数・費用が
減ることは実測していない。**

**歯**: `packages/testkit/src/__tests__/cassette-recorder.test.ts`（7本）。
非決定的な偽 provider を食わせ、**記録が、記録を作った実行そのものを再生できる**ことを
固定する。**【実測】memo を外すと2本が赤くなり、戻すと緑に戻ることを確認した。**

#### 公開 API 表面の変化（ADR 0178 の門）

**`CassetteRecorder` に公開メソッドが2本増えた**——`lookupLLM` / `lookupEmbedding`。
記録用のデコレータが「もう録ったか」を問い合わせるための口である。

⛔ **破壊的変更ではない**——**追加のみで、削除も署名の変更も無い**
（`scripts/__snapshots__/public-api/testkit.d.ts` の差分が、この2本と、それに伴う
型 import 1行だけであることを確認した）。⚠ `@mnemora/testkit` は適合テストと擬似物を
提供するパッケージであり、この2本は**記録器を自作したい呼び出し側が使える口**として
意図的に公開する（`embeddingCount` / `llmCount` が既に同じ層で公開されているのと同じ扱い）。

⚠ **snapshot を更新する前に `pnpm run build` で dist を作り直した**——この歯は
`packages/<name>/dist` の `.d.ts` を読むので、dist が古いまま `--write` すると
**他人が入れた変更を snapshot から消してしまう**（歯を無効化する。ADR 0178 の注意書き）。

### 2. 二次観測（LLM 採点）は `complete()` ＋厳格パースで実装し、一次判定を上書きしない

Issue #506 の未達1件。完了条件の逐語【現物】:

> **一次判定は機械（LLM を呼ばない）**。`accept` / `reject` の包含判定。
> **二次観測（LLM 採点）は別欄で、一次を上書きしない。食い違いは `indeterminate`**

`answer-judge.ts` を新設した。設計上の必須事項は4つ:

1. **`completeStructured` を使わない。**`DeterministicLLMProvider.completeStructured` は
   未対応スキーマで**例外を投げる**【現物】⟹ judge が structured を使うと、鍵の無い
   環境での空撃ちと既存の配線検査が落ちる。`complete()` なら stub がプロンプトを
   エコーし、パースに失敗して `indeterminate` になる——これが正しい退避である。
2. **パースできない応答は必ず `indeterminate`。**⛔ 既定で `pass`/`fail` へ倒さない。
3. 🔴 **judge に `expected.accept` / `expected.reject` を渡さない。**渡すと一次判定の
   写しになり、独立した観測でなくなる（Issue #498 の逐語「LLM採点だけを無条件の正解に
   しない」/ §2.2 決定5「別の AI が採点したという理由だけで、正解の根拠や独立性が
   確保されたと見なさない」）。⟹ **`AnswerJudgeInput` が `accept`/`reject` を構造的に
   持てない形にし、規律ではなく型で塞いだ。**渡すのは質問文・`expected.kind`・
   `grounds.rationale`・`grounds.turnIndex` で引いた会話ターン・回答文だけである。
   **歯**: 実ケースで `accept`/`reject` の各文字列がプロンプト全文に現れないことを
   `__tests__/answer-judge.test.ts` が機械で固定する。
4. **食い違いは `indeterminate`**（`reconcileVerdicts`）——[ADR 0222](./0222-compare-gate-judges-only-when-turncount-sets-match.md)
   の三分割に倣う。⛔ 一致しないときにどちらか一方を勝たせない。

### 3. `answer` をカセットの対象に足し、`record answer` で記録できるようにする

`CassetteTarget` は `"retrieval" | "compare"` しか無く、`answer` は記録の対象ですら
なかった【現物】。`"answer"` を足し（`cassettes/answer.json`）、`record answer` /
`verify answer` を通した。⛔ 「対象を明示させる・既定値を持たせない」という ADR 0052 の
決定はそのまま保っている。

### 3.1 🔴 `runAnswer` は、再生の口に繋がっていなかった（PR #511 の取りこぼし）

⛔ **黙って直さず、記録に残す。**

**【実測】カセットを作った直後、`MNEMORA_LLM=recorded` で再生しようとして落ちた**——
`createProviders` の `requireCassette` が「カセットが渡されていない」と言う。
**カセットはファイルとして存在していたのに、である。**

**原因**【現物】: `runAnswer` は `createAnswerBenchRuntime(databaseUrl, process.env)` と
呼んでいた。`compare` / `retrieval` が使う `resolveCassetteForRun(target)` →
`cassette ? { cassette } : {}` という配線を、**`answer` だけが持っていなかった。**

**⚠ これは「カセットが無かったから気づけなかった」欠落である。**PR #511 は
（設計どおり）カセットを記録していないので、`MNEMORA_LLM=recorded` を指定すれば
`requireCassette` が落ちるのは**正しい挙動と見分けがつかなかった。**ADR 0229 も
「カセットが無いので `requireCassette` がそのまま落ちる（既存の挙動のまま）」と書いており、
**その文は正しかったが、その先に配線の欠落が隠れていた。**

⟹ ⭐ **次に同じ形のサブコマンドを足す人へ**: 記録の対象を足すときは、
**`record` 側だけでなく `run` 側が `resolveCassetteForRun` を呼んでいるかを必ず確かめること。**
⚠ **カセットが存在しない間は、この欠落は「正しい例外」に化けて見えない。**

### 4. ⛔ CI に実 API を配線しない。カセット被覆の歯で、録り直し忘れを検査の時点で捕まえる

[ADR 0184](./0184-conformance-scope-documented-not-closed.md) 決定4 の逐語
「⛔ **CI で実 API を叩かない。**鍵の管理と課金の判断はオーナーのものである」【現物】。
⟹ `.github/workflows/ci.yml` は1バイトも変更していない。

代わりに `__tests__/cassette-coverage.test.ts`（**DB も鍵も要らない**）へ `answer` の
被覆検査を足した。特に **naive（全文経路）のプロンプトはケースの定義だけから決まる**
（`recall()` に依らない）ので、`buildNaiveAnswerPromptSpec` を `answer-bench.ts` から
export して**テスト側で完全に組み立て直し、鍵を引く**——ケースを1文字でも変えて
録り直しを忘れたら、**実行の数分後ではなく検査の時点で**赤くなる。
⛔ プロンプトの組み立てをテスト側へ写していない（二重定義にしない）。
**【実測】ケースの質問文を1文字変えると2本が赤くなり、戻すと緑に戻ることを確認した。**

⛔ **この器を必須 CI の門にはしていない**——`gradeAnswer` の偽陽性・偽陰性率を測って
いないため（ADR 0229 決定2 / [ADR 0223](./0223-cross-cutting-disciplines-extracted-from-the-adr-corpus.md)
決定3「門にしてよいのは、偽陽性率に上限を置けると実測できたものだけである」）。
必須 CI への接続は Issue #497 の範囲である。

### 5. ⛔ 実測を見て評価ケースを書き換えていない

[`docs/autonomy.md` §2.2](../autonomy.md#22-品質を変える変更の評価と合格基準の扱い)
決定5。**held-out の `unknown-favorite-number` が `reject: ["7","3","8"]` を持ち、
正しく棄権した回答でも数字1文字が現れれば `fail` に倒れる**という脆さが事前に
把握されていた。⟹ **実測の前に書き換えず、そのまま走らせた。**

**【実測】結果は `pass` であり、この脆さは今回は現れなかった。**
⟹ ⛔ **1バイトも書き換えていない。**決定4 の基準変更の手順を踏む必要は生じなかった。

**条件**: `main` = `6851629` に本 PR の変更を当てたもの / `gpt-4o-mini` /
`text-embedding-3-small` 256次元 / 自前の Postgres 17 + pgvector 0.8.0 /

### 回答の正誤（12件 = 6類 × dev/held-out）

| mnemora（記憶経路） | pass 11 / fail 1 / indeterminate 0 | pass 11 / fail 1 / indeterminate 0 | pass 11 / fail 1 |

偽陽性・偽陰性率は依然として測っていない（決定4）。

### 記録と再生が一致すること

**【実測】記録した実行（`llmMode=openai`）と、鍵を外した再生（`llmMode=recorded`）が、
全12ケース × 両経路の `inputChars` / `inputEstimatedTokens` / `answer` / `verdict` /
`judgement.outcome` / `reconciled` のすべてでバイト単位一致した。**

**【実測】記録の前に、再生可能性を鍵無しで先行検査した**——`deterministic` で独立2回
（DB を作り直して）走らせ、全24プロンプトがバイト単位で一致することを確認した
（＝ `recall` の選択と並び順に壁時計・乱数由来の揺れが無い）。

## 🔴 見つかった欠落（⛔ 期待結果を緩めず、未達として示す）

**`schedule-change-deadline`（held-out、予定変更）で、記憶経路が撤回済みの値を答えた。**

| | 回答 |
|---|---|
| naive（全文経路） | **「25日です。」** ⟹ pass |
| mnemora（記憶経路） | **「報告書の提出期限は今月の20日です。」** ⟹ fail |

記憶経路に載っていた帯【実測】:

```
- 報告書の提出期限は今月の20日である。
- 提出期限を25日に延ばしてもらいたいという要望がある。
- 20日に間に合わないので、期限延長の理由がある。
- 週末は友達と出かける予定である。
(索引: スコープ内 5 件のうち 4 件を提示)
```

⟹ **撤回前の「20日」が事実として残り、変更は「要望がある」という形でしか載っていない**
——supersede が効いていない。⟹ **これは #498 が捕まえようとしていた欠落そのものである**
（「出典が一致しても、抽出・要約で必要な情報が欠ける可能性がある」）。

⛔ **この ADR も本 PR も、訂正機能を実装しない。**ADR 0224 決定の逐語「訂正機能は既存の
#197 / #369〜#372 / PR #366 の判断と作業を再利用し、重複実装を指示しない」に従い、
**未達として Issue #197 / #369〜#372 / PR #366 へ紐づける。**
⛔ 期待結果を緩めず、対象ケースも消していない。

## 採らなかった案

- **評価ケースのフィラー発話をケースごとに一意にして、同じプロンプトが重複しないようにする。**
  却下——それは決定1 の穴を**評価ケースの側で避ける**だけで、記録器の穴は残る。しかも
  実測を見てケースを変えることになり、§2.2 決定5 が「見て調整したケースは以後開発用として
  扱う」と定めた通り、held-out の6件が held-out でなくなる。**払う代償が大きすぎる。**
- **記録器が同じ鍵に違う値を受け取ったら例外にする。** 却下（今回は）——穴は見えるように
  なるが、記録そのものが完走しなくなる。memo にすれば**完走したうえで矛盾が消える。**
- **judge を `completeStructured` で実装する。** 却下——決定2 の1番の理由。
- **`answerQualityClaimable` に `recorded` を足して、再生でも品質を主張させない。** 却下——
  既存の契約（`deterministic` のときだけ `false`）を、実測の結果を見てから変えることに
  なる。⚠ **ただし §2.2 決定6 の逐語「記録再生はその記録条件での評価であり、現在の実 API
  や未知の会話の品質保証に広げない」は依然として掛かる**——下記「確かめていないこと」を参照。

## 引き受けた負債・確かめていないこと

- ⚠ **ケース数は12件と小さい。**母集合としての代表性は主張しない（ADR 0229 と同じ）。
- ⚠ **`gradeAnswer` の偽陽性・偽陰性率は依然として測っていない。**⟹ 門にしない理由そのもの。
- ⚠ **二次観測（LLM 採点）の偽陽性・偽陰性率も測っていない。**一次と一致したことは、
  独立に正しいことの証明ではない。
- 🔴 **この数字は「2026-09-17 の `gpt-4o-mini` の、ある1回のサンプル」である。**
  §2.2 決定6 の逐語「記録再生はその記録条件での評価であり、現在の実 API や未知の会話の
  品質保証に広げない」が掛かる。⟹ **`recorded` で緑であることを「いまの実 API でも
  11/12 である」と読まないこと。**
- ⚠ **`verify answer`（記録と実 API の乖離を測る）は実行していない。**鍵の使用を
  最小限にしたためである。
- ⚠ **記録は2回行った**（1回目は決定1 の穴を踏んで再生できなかった）。**1回目のカセットは
  repo へ入れていない。**⛔ 2回目は「気に入らない結果を録り直した」のではない
  ——**結果（11/12・同じ1件が fail）は2回とも同じであり**、録り直した理由は再生可能性
  だけである（§2.2 決定4「カセットの更新も、単なる録り直しで評価の変化を隠さない」）。
- ⚠ **`retrieval` / `compare` のカセットは録り直していない。**決定1 の変更は記録経路にのみ
  掛かり、再生側は変えていないので既存の数字の意味は変わらない——が、**それらを
  録り直したときに件数・費用が減ることは実測していない。**

## ⚠ ADR 0229 の「条件の貼り方」について

ADR 0229「引き受けた負債」は、この器が出す数字に
**「`association` 既定 off の下での値」**という条件を貼るとしている。
**【現物】これはこの器には当てはまらない**——`answer-bench.ts` は `queryRecall` を
opts 無しで呼び、`mnemora-path.ts` の `DEFAULT_MNEMORA_PATH_ASSOCIATION = { maxCount: 10 }`
が渡る ＝ **この器の記憶経路は連想枠 on で走っている。**さらに
**【現物】PR #386 の CHANGELOG 自身が、`examples/chat` について
「挙動そのものは変わらない（値は同じ `{ maxCount: 10 }`）」と書いている。**

⟹ **本 ADR が貼る条件は「`examples/chat` 呼び手側の連想枠 on（`{ maxCount: 10 }`、
ADR 0168）の下での値」である。**
⛔ **ADR 0229 の本文は書き換えていない**（この repo の作法）。0229 へ訂正の追記を打つかは、
別途の判断に委ねる。
