# ADR 0311: Issue #338 の境界を実測で確かめ直す。素の `recall()` では 3112回より先の 2392回で沈む。残るオーナー判断2点に、数値と推奨を添える

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-25

> **⚠ この ADR は、クローンの委譲で動くマネージャーのセッション（mgr-4bf05114）が書いた。
> ⛔ オーナー本人の判定ではない**（[ADR 0220](./0220-issue-comment-author-does-not-distinguish-owner-from-agent.md)）。
> 本 ADR が「決めた」のは、測定の記録と文書の訂正だけである。
> [ADR 0165](./0165-decay-activity-clock.md)「これが覆るとしたら」1 がオーナー判断と指定した
> 分岐（カウンタの単位、既定 `720` の与え方）は**決めていない**——「オーナーへ返すもの」節に
> 数値と推奨を並べるだけである。

**⚠ 各主張の出所を分ける**（ADR 0290 / 0302 の体裁を踏む）。

- **【実測】** — この作業で、作業者が自分専用の Postgres（`initdb`、AGENTS.md の手順）を立て、
  `Runtime.recall()` を通しで繰り返して確かめた。測定対象は `main` = `52113a8`。
- **【現物】** — この repo のコード・文書を読んで確かめた。
- **【算出】** — 実測した式に数値を代入しただけ。走らせていない。

## 結論（先に）

1. **09-16 の実測（3112回目まで返り、3113回目で消える）は正しい。再実測でも一致した。**
   2026-09-24 の着地報告コメントにある「3112回/日の境界は、今も逆算だけで実測していません」
   は誤りである（同じくマネージャーのセッションが書いたもの）。
2. **ただし 3112/3113 は、`scoreThreshold: 0` を明示したときの数字（段1の硬いゲート）である。**
   `scoreThreshold` を省略した**素の `recall()` では、2392回目まで返り、2393回目で消える**【実測】。
   段2の再スコアで足切りされるため（`DEFAULT_SCORE_THRESHOLD = 0.1`）で、既定の呼び方では境界は
   **約23% 手前**に来る。しかもこの 2392 は**上限**である。問いと記憶の類似度が 1 未満なら、
   さらに手前になる（下記「測ったこと」3）。
3. **`recall()` を呼ぶだけでは、記憶は強化されない。** 強化は使用報告
   （`observe({ kind: "memory_usage" })`、ADR 0009）でしか起きない【現物＋実測】。
   ⟹ 採用者が使用報告を返さない限り、表の数字は「強化が一度も起きない場合」そのものになる。
4. **サブジェクト S 個が交互に recall し、A 自身は一度も recall しなくても、A の記憶は
   テナント合計 3113回目で消える**【実測、S=10】。⟹ 効くのは「その記憶が想起を見送られた
   回数」ではなく「テナント全体の recall 回数」である。
5. ⭐ **4 は ADR 0165 決めたこと6 が定めた単位の意味と食い違っている**（下記「判断の材料」）。
   推奨は「subject を絞った recall は、その subject のカウンタだけを進める」だが、
   **migration が要るうえ、製品の性格を決める分岐なのでオーナーへ返す。**

## 文脈

[Issue #338](https://github.com/takecchi/mnemora/issues/338) は `decay_clock = 'activity'` の
テナントで recall が1日3112回を超えると「言ったことを、次の日も覚えている」
（`docs/north-star.md` 目指す姿1）が破れる、と逆算した Issue である。その後、次のものが入った。

- 2026-09-16 のコメント: 本物の Postgres で 3112/3113 を実測。カウンタがテナント単位であることも実測
- [ADR 0197](./0197-set-default-half-life-recalls.md)（PR #416）: 既定の半減期を変える本番の口
- [ADR 0290](./0290-activity-seq-read-path-documented-not-implemented.md)（PR #685）: 頻度を読む口の文書化

2026-09-24 の着地報告は、残りを「3112回の境界の実測」と「オーナー判断」の2つに整理した。
前者は上のとおり既に実測済みだった。本 ADR は、それを現行の `main` で測り直し、09-16 が
触れていなかった区別（ソフトな足切りと硬いゲート）と強化の条件を加える。そのうえで、
後者のオーナー判断を「数値を代入すれば決められる」形まで降ろす。

## 測ったこと

測定条件【実測】: `main` = `52113a8`、自分専用の Postgres 17 + pgvector、埋め込みは
`deterministic`。`decay_clock = 'activity'`、`half_life_recalls` は既定の `720`（小さくした測定では
本番の口 `setDefaultHalfLifeRecalls` を使い、SQL の直叩きはしていない）。測定用のテストは一時ファイル
として置き、単体で走らせたあと削除した（repo には残していない）。

| # | 条件 | 結果 |
|---|---|---|
| 1-hard | 1件 observe → `recall({ scoreThreshold: 0 })` を繰り返す | **3112回目まで返り、3113回目で消えた**（09-16 と一致） |
| 1-soft | 同じ。`scoreThreshold` は省略 | **2392回目まで返り、2393回目で消えた**。`omitted` は `below_threshold`、`decayGate` は `pushed_down`（候補集合には残っている） |
| 2 | S=10。A は一度も recall せず、残り9つの subject が無関係な問いで交互に recall | テナント合計 3111回の後なら A の初回 recall で見える。3112回の後（A の recall がテナント合計 3113回目）なら消えている |
| 3 | `observe()` の前後、別 subject の `recall()` の前後で `activity_seq` を読む | observe では進まない。別 subject の recall では進む（09-16 と一致） |
| 4 | `half_life_recalls = 5` で、recall → 使用報告 | 使用報告の瞬間に `decay_base_seq` 0→4、`decay_floor_seq` 22→26。recall だけでは1バイトも変わらない |
| 5 | `half_life_recalls = 5`（ソフトな足切りの位置 = `ceil(5·log2 10)` = 17）で、recall → 使用報告を一定の間隔で繰り返す | 間隔 17 なら5サイクル生き残る。間隔 18 なら1サイクルで消え、以後は recall に出ないので使用報告もできず戻らない |

### ソフトな足切りの位置（1-soft の一般形）【現物＋算出】

段2のスコアは `affinity × decay × tagMatch × freshness × strength`
（`packages/core/src/strategies/scoring.ts`）で、既定の足切りは `0.1` である。活動時計の
`decay = 2^(-(nowSeq - baseSeq) / halfLife)` なので、足切りに掛かる回数は

```
k_soft = halfLife × log2(affinity × tagMatch × freshness × strength / 0.1)
```

になる。測定 1-soft は問いと digest が同一（affinity = 1）で、`freshness`・`strength` も 1 の場合にあたる。

| affinity（他の項は 1） | 既定 720 で消える回数（`ceil`） |
|---|---|
| 1.0 | 2392（実測と一致） |
| 0.8 | 2160 |
| 0.6 | 1862 |
| 0.5 | 1672 |
| 0.3 | 1142 |

⟹ **「3112回」は、どの呼び方でも越えられない上限である。** 既定の呼び方で実際に消える位置は
問いの近さで変わり、それより手前に来る。

### 副産物（記録のみ）【実測】

`reinforce` は `last_reinforced_at < at` を条件にしている（ADR 0048、起点を巻き戻さない）。
そのため、**同じ `at` での2回目の使用報告は、例外にならずに何もしない。** 実運用では時刻が進むので
踏まない。ただし偽の時計を止めたまま使用報告を2回呼ぶテストは、これを踏む。

## 判断の材料（オーナーへ返すもの）

本番のサーバーは無く、実運用の recall 頻度は分からない（オーナー回答、2026-09-24）。
⟹ 次の表は、**テナント合計の recall 回数/日 R = S（subject 数）× r（subject あたりの回数/日）** を
代入すれば読める形にした。

### 表1: 強化されない記憶が沈むまでの日数【算出。式は実測で確認済み】

ソフト = 既定の呼び方の上限（2392）、ハード = 硬いゲート（3112）。

| R（回/日） | 現状（テナント単位）ソフト | 現状 ハード |
|---:|---:|---:|
| 24（`720` の設計想定＝1時間1回） | 99.7日 | 129.7日 |
| 100 | 23.9日 | 31.1日 |
| 1,000 | 2.39日 | 3.11日 |
| 2,392 | **1日** | 1.30日 |
| 3,112 | 0.77日 | **1日** |
| 10,000 | 0.24日 | 0.31日 |

- **現状（テナント単位）では、日数は R だけで決まる。** S が増えると、そのぶん速く沈む。
- **subject 単位のカウンタなら、日数は r だけで決まる**（S は効かない）。
  例: S=100、r=10（R=1,000）は、テナント単位なら 2.4〜3.1日で沈む。subject 単位なら 239〜311日もつ。

### 表2: 「次の日も覚えている」を満たす最小の `half_life_recalls`【算出】

ソフト（既定の呼び方、affinity=1）は `hl(R) = ceil(R / log2 10) = ceil(R / 3.3219)`、
ハードは `hl(R) = ceil(R / log2 20) = ceil(R / 4.3219)`。

| R（回/日） | ソフト | ハード |
|---:|---:|---:|
| 100 | 31 | 24 |
| 1,000 | 302 | 232 |
| 10,000 | 3,011 | 2,314 |
| 100,000 | 30,103 | 23,138 |

⟹ **既定の `720` そのものは、設計想定（R=24）より2桁大きい R まで耐える。** 問題は既定値の
大小ではない。**テナント単位のカウンタだと、subject 数 S がそのまま R に掛かること**である。

### ⭐ 単位の意味との食い違い【現物】

ADR 0165 決めたこと6 は、活動時計が測るものを逐語で「**この記憶が、想起される機会を何回見送られたか**」
と定め、「recall は機会であり」と書いている。一方で、`ctx.subjectId = B` を付けた recall は、
subject A の記憶を**候補にすら入れない**（ADR 0023 の subject filter。`vector-store.ts`・
`lexical-store.ts`・`recall-runtime.ts` の後置フィルタ。Issue #579 のコメントで全出現が確認されている）。
⟹ **B に絞った recall は、A の記憶にとって「想起される機会」ではない。それでも A の記憶の
カウンタは進む**（測定 2）。これは ADR 0165 の定義どおりの動作ではなく、
「カウンタが1本しか無い」という実装の近似から来ている。

### オーナーへの推奨（決めていない）

| 案 | 中身 | 表1の日数が依存するもの | 代償 |
|---|---|---|---|
| **P（推奨）** | subject を絞った recall は、その subject のカウンタだけを進める。絞らない recall はテナントのカウンタを進める。記憶の床は「自分の subject のカウンタ＋テナントのカウンタ」で読む | r（とテナント全体を見る recall の回数） | migration（subject ごとのカウンタ表、`decay_base_seq` の意味の変更）。ADR 0165 決めたこと8 の索引の再設計。ADR 0290 の読み口の意味も変わる |
| Q | カウンタはテナント単位のまま。案3 として、既定の `half_life_recalls` を「想定する R」から導く（表2） | R | 採用者が R（＝S×r）を見積もる必要がある。S が増えるたびに設定し直し。遡及しない（ADR 0197 の負債） |
| R0 | 何もしない。文書（本 ADR と README の表）で知らせる | R | 多数の subject を持つテナントで、`'activity'` は数日で忘れる時計になる |

**P を推す理由**: ADR 0165 自身の定義に実装を合わせる案だからである。S が効かなくなり、
「次の日も覚えている」が r（1人あたりの頻度）だけで読めるようになる。r=100/日でも 24〜31日もつ。
Q は数字合わせで、S が増えるたびに破れる。
⚠ **どれも既定（`decay_clock = 'wall'`）のテナントには影響しない。** `'activity'` を選んでいる
テナントは今日存在しない（Issue #338 本文）。⟹ 急ぐ理由は無い。

## 決めたこと

1. **測定の結果を本 ADR に記録する。** 境界は「実測済み」である。以後「逆算だけ」と書かない。
2. **採用者が読む文書の表を訂正する。** `examples/chat/README.md` の表は「逆算であって実測ではない」
   と書いていた。これを「実測で確認した」に直す。あわせて、既定の呼び方（`scoreThreshold` 省略）では
   2392回（上限）で消えること、`recall()` だけでは強化されないことを書き足す。
   `docs/memory-model.md` の該当節にも一行加える。
3. **既定値・公開 API・スキーマは何も変えない。**
4. **Issue #338 は閉じない。** 残りは P/Q/R0 のオーナー判断だけである。判断が出たら、それを実装する
   Issue を切る（P なら migration を伴う）。

## 検討した代替案

1. **`DEFAULT_SCORE_THRESHOLD` を 0.05 に揃え、ソフトとハードの境界を一致させる。**
   ⛔ 落とした。既定値の変更であり、`'wall'` のテナントを含む全ての recall の結果を変える。
   本 Issue の範囲を超える。
2. **`recall()` で返った記憶を自動で強化する。**
   ⛔ 落とした。ADR 0009 は「使った」を呼び出し側の申告に置いている。「引いた」と「使った」を
   混ぜるのは別の判断である。

## 引き受けた負債

- 表はすべて「強化が一度も起きない場合」である。使用報告が実運用でどれくらい返るかは測れない。
- 語彙チャンネル（lexical）は測っていない（ANN のみ。09-16 と同じ限界）。
- 実埋め込みでの affinity の分布は測っていない。ソフトな境界の表は affinity を振った算出である。

## これが覆るとしたら

- オーナーが P/Q/R0 のどれかを選んだとき。本 ADR の「推奨」は、その時点で役目を終える。
- `DEFAULT_SCORE_THRESHOLD` か `DEFAULT_DECAY_THRESHOLD` が変わったとき。表の数字は全て変わる。

## 確かめていないこと

- P の migration の具体形（表の形、既存の `decay_base_seq` の移し方）は設計していない。
- 09-16 のコメントが `scoreThreshold: 0` で測ったかどうかは、本文から読み取れない（数値が 3113 で
  一致したので、そうだったと推測している）。
