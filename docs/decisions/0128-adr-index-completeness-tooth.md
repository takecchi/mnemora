## この歯は何を守っているのか（先に言葉にする。ADR 0126 / 0127 と同じ順序）

**索引に載っているべき ADR が、実際に載っていること。** 技術的に必要な条件は次の1つだけ
である:

> `docs/decisions/` 配下の ADR ファイル（`NNNN-slug.md` の形。`README.md` 自身を除く）の
> 番号集合と、`docs/decisions/README.md` の索引テーブルが持つ行の番号集合が、完全に一致する。

**この条件の成立に、行数の絶対値（124, 125 …）は要らない。** ADR 0127 が pgvector
ジョブの絶対本数を「両方が着地して初めて正しい値が決まる、両者が独立に更新する対象」
として退けたのと同じ理由で、**索引の行数を固定値で持つ歯にはしない**——ADR が1本増える
たびに固定値を書き換える必要が生じ、それ自体が「複製した値を人力で同期し続ける」形
（`AGENTS.md` が退ける形）になる。**集合の一致**（差分が空であること）だけを見る。

## 設計判断（issue が名指しした5点）

### 1. 索引に載るべきでないファイルは在るか

**【現物】** `docs/decisions/` 配下を確認した。ADR ファイル124本はすべて
`^\d{4}-[a-z0-9-]+\.md$` の形（4桁の番号 + ハイフン区切りの slug + `.md`）であり、
**この形に一致しないファイルは `README.md` 1つだけ**である（テンプレートファイルや
サブディレクトリは無い。`ls -la docs/decisions/` で確認、下記「測ったこと」）。

⟹ 歯は「`README.md` を除く」ではなく、**「ファイル名が `^\d{4}-.*\.md$` にマッチする
ものだけを ADR ファイルとして数える」**という正の条件で書く。理由: 「`README.md` を
名指しで除外する」形だと、将来 `TEMPLATE.md` のような別の非 ADR ファイルが増えたときに
歯がそれも ADR として誤カウントし、赤くなる（しかも赤くなった理由が読み手に伝わらない
——「テンプレートを足しただけなのに歯が壊れた」と誤解されうる）。**正規表現で「ADR らしい
名前」だけを拾う方が、将来の非 ADR ファイル追加に対して意図が明確なまま緑を保つ。**

### 2. 索引の行から ADR 番号をどう取り出すか

**【現物】** 索引の各行は `| [0127](./0127-pgvector-job-count-tooth-drops-absolute-total.md) | … | 採用 (2026-09) |`
の形（`docs/decisions/README.md` 16行目以降、実測。ヘッダ行・区切り行は `[` を含まない）。
⟹ 行頭アンカー `^\|\s*\[(\d{4})\]\(\./([^)]+)\)` で、リンクテキストの4桁番号と
リンク先ファイル名の両方を1回の正規表現で取り出す（後述の5番の判断にそのまま使う）。

### 3. 欠番（`0080` / `0116`）をどう扱うか

**⛔ 「番号が連続していること」は検査しない。** 歯が見るのは
**「ファイルとして実在する番号の集合」と「索引に載っている番号の集合」の差分**だけであり、
**ファイルが存在しない番号（`0080` / `0116`）については歯は何も言わない**——
差分計算の対象にすら入らない（`docs/decisions/` に `0080-*.md` が無いので
「ファイル側の集合」に `0080` はそもそも入らず、索引側にも `0080` の行は無い。
両方に無ければ差分は生じない）。これは実装ではなく設計の話であり、次の集合演算
そのものが欠番を自然に無視する:

```
missing = fileNumbers - indexNumbers   // 索引に無いファイル（穴）
orphan  = indexNumbers - fileNumbers   // ファイルの無い索引行
```

**「1から採番済み最大値まで全部揃っているか」という走査は一切書かない。**

### 4. 逆向き（索引に行が在るのにファイルが無い）も検出するか

**検出する。** 理由:

- 実装コストがほぼゼロ——3番の集合演算がそのまま両方向を返す（`missing` と `orphan`）。
- 起こりうる壊れ方として、ADR ファイルをリネームしたのに索引側の行を直し忘れる、
  ADR を書きかけて索引だけ先にコミットする、といった形が考えられる
  （**実際に踏んだ実例ではない**——issue のコメントが記録しているのは「ファイルが
  在って索引に無い」方向の実例のみであり、逆方向は推測である。とはいえ実装コストが
  ゼロに近い以上、対称性のために両方見る）。
- ⚠ 確認した範囲では、**いまの `main` にはこの逆方向の穴は無い**（下記「測ったこと」）。

### 5. リンク先のファイル名が実在するかまで見るか

**見る。** 理由:

- 番号だけが一致していてもファイル名が違う、という壊れ方がありうる
  （例: ADR をリネームしたときに、索引側のリンクだけ古いファイル名のまま残る。
  `[0100](./0100-old-slug-name.md)` のように番号は合っているがリンク先が実在しない）。
  この壊れ方は「番号の集合が一致しているか」だけを見る歯では**素通りする**——
  番号の集合としては正しいまま、リンクだけが死んでいる。
- 2番の正規表現が番号とリンク先ファイル名を同時に取り出す設計なので、
  「そのファイル名が実際に `docs/decisions/` に存在するか」を追加で見るコストは低い。
- **確かめていないこと**: この壊れ方（番号は合っているがファイル名だけ違う）が
  過去に実際に起きた実例は、issue のコメントにも見当たらない。**推測に基づく予防的な
  検査**であり、issue が実測で示した「行の欠落」ほど実績のある脅威ではない。

## 決定

1. `scripts/adr-index-completeness-lib.mjs` を新設し、純関数のみを置く:
   - `parseAdrFilenames(filenames: string[]): Map<string, string>` — ADR ファイル名の
     配列から、`^\d{4}-[a-z0-9-]+\.md$` にマッチするものだけを拾い、`番号 → ファイル名`
     の Map を返す（一致しないもの——`README.md` 等——は黙って無視する）。
   - `parseIndexRows(readmeText: string): { number, linkedFile, line }[]` — 索引本文から
     `^\|\s*\[(\d{4})\]\(\./([^)]+)\)` にマッチする行を全部拾う。
   - `findMissingIndexRows(fileNumbers, indexRows)` — ファイルに在って索引に無い番号
     （＝穴）を、番号の昇順で返す。
   - `findOrphanIndexRows(fileNumbers, indexRows)` — 索引に在ってファイルの無い行を返す。
   - `findBrokenIndexLinks(fileNumbers, indexRows)` — 番号は両方に在るが、
     `linkedFile` が実際のファイル名と一致しない行を返す。
2. `scripts/__tests__/adr-index-completeness-lib.test.mjs` — 上記4関数の単体テスト
   （合成入力。欠番が挟まっていても集合演算だけで無視されることを直接検査する）。
3. `scripts/__tests__/adr-index-completeness.test.mjs` — **配線の歯**。実際の
   `docs/decisions/` ディレクトリと `docs/decisions/README.md` を読み、上記関数へ通して
   3つの差分（`missing` / `orphan` / `broken`）がすべて空配列であることを検査する。
   赤くなったときのメッセージに、該当する ADR 番号・ファイル名を含める
   （`toEqual([])` ではなく、差分の中身を `JSON.stringify` してメッセージに含める形。
   「歯が名指しで赤くなる」という変異試験の要求に応えるため）。
4. `docs/decisions/README.md` に、この ADR 自身の行を追加する
   （**この歯が自分自身の行の存在を検査することになる**——並行してこの索引を触る PR は
   本 PR の作業時点で無い）。

## 検討して採らなかった案

- **行数の絶対値を比較する**（`grep -c '^| \[' README.md === ls docs/decisions/*.md | wc -l`
  相当を1回のシェル芸で書く）。**却下**——絶対値の一致は「同じ番号が二重に載っている」
  ことと「1行足りないが別の1行が余分」なことを見分けられない（数が偶然一致して
  green になりうる）。**番号の集合そのものを比較する**（3の集合演算）方が厳密であり、
  実装コストもほぼ変わらない。
- **`docs/decisions/*.md` の front matter を解析して番号を取る**。**却下**——今の ADR
  本文に機械可読な front matter は無く（`# ADR NNNN: …` という見出しのみ）、
  ファイル名の番号で十分かつ確実（ファイル名の番号と本文見出しの番号が食い違う
  ケースは別の問題であり、本 ADR のスコープ外）。
- **YAML/Markdown パーサへの依存を足して表を厳密にパースする**。**却下**——既存の
  wiring 系の歯（`ci-yml-*-wiring.test.mjs`）が軒並み正規表現で文字列として読む方針
  を採っており（依存追加はオーナー専権、`docs/autonomy.md`）、同じ判断を踏襲する。
  ⚠ この判断の負債は下記「引き受けた負債」参照。

## 理由

issue #230 のコメント2が実測で示した通り、**この repo では ADR を伴う PR が実質的に
並行度の上限を決めている**——索引を触る PR が同時に2本を超えると、マージ側が
手作業で「どちらかに索引を触らせない」形で回避しない限り穴が空く。この回避は
`AGENTS.md` が名指しで退けている「規律ではなく注意力への依存」そのものである。
D は衝突そのものを消せないが、**「回避に失敗した」ことを機械的に、かつ番号を名指しして
検出できる**——ADR 0126・0127 と同じく「歯が実体ではなく字面に反応して黙って通る」
形を避け、**実際に守りたい主張（索引とファイルの集合が一致する）に直接反応する歯**にした。

## 結果（この決定が招くもの）

- `docs/decisions/README.md` に ADR を追加したのに索引の行を足し忘れると、
  ルートの `pnpm run test`（`vitest run` の対象、`scripts/**/*.test.mjs` を含む）が
  **その ADR 番号を名指しして**赤くなる。
- 索引の行を足したのに ADR ファイル自体を作り忘れる／誤って削除しても同様に赤くなる
  （`orphan`）。
- 索引のリンク先ファイル名が、番号は合っているが実在しない名前になっていても赤くなる
  （`broken`）。

## 引き受けた負債

1. **この歯は衝突そのものを消さない。** 索引を触る PR が同時に2本在れば、
   依然として手（マージ側の運用）で解く必要が在る。**歯が捕まえるのは
   「解き忘れた結果、穴が空いたこと」だけである。** issue #230 が指摘した
   構造的な衝突点（末尾追記が単一の位置に集中すること）自体は、A（機械生成）か
   C（1 ADR = 1 索引ファイル）を採らない限り残る。
2. **正規表現で文字列として読む**（YAML/Markdown パーサを使わない）ため、
   表の書式が変わる（例: 列を増やす、セル内に `|` をエスケープなしで書く）と、
   この歯の抽出そのものが機能しなくなる可能性がある。既存の `ci-yml-*-wiring` 系と
   同じ負債であり、同じ判断を踏襲した。
3. **「索引に行が在るのにファイルが無い」「リンク先ファイル名が違う」の2つは、
   過去に実際に起きた実例が無い予防的な検査である。** 過剰かどうかは、
   実際にこの2つが赤くなる事例が今後起きるかどうかで検証されることになる。

## これが覆るとしたら

- **A（索引の機械生成）か C（1 ADR = 1 索引ファイル）が採用されたとき。**
  そのときはこの歯の前提（索引が手編集の1テーブルであること）自体が変わる——
  A なら「生成スクリプトが実際に全 ADR を拾っているか」を検査する歯に置き換わり、
  C なら「索引ディレクトリの各ファイルに対応する ADR が在るか」に形が変わる。
  いずれの場合も、**「集合の差分を見る」という骨格そのものは転用できる**
  （issue コメントが「D は A/C と排他ではない」と述べた通り）。
- **索引の表の書式（列構成・リンクの書き方）が変わったとき。** 正規表現側の
  抽出パターンを合わせて直す必要がある。
