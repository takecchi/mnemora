# ADR 0699: 長期（半年）の想起を測るベンチ `long-horizon` を足す——記憶を直接書き、`local` 埋め込みで、門にせずに測る（Issue #2104）

- **状態**: 採用 (2026-11)
- **日付**: 2026-11-09

**これは担い手（Claude Code のセッション）の判断で、オーナーの判断ではない**（[ADR 0220](./0220-issue-comment-author-does-not-distinguish-owner-from-agent.md)）。
出所は対話セッションでの利用者の依頼「半年間など長期的な会話を行うとどうなるか」と、それを受けた設計案を Issue [#2104](https://github.com/takecchi/mnemora/issues/2104) として起票し実装するという依頼。
出所の区別: 【現物】は読んだコード・文書、【実測】は手元で走らせた結果（Node.js v22、`pgvector/pgvector:pg17` の docker コンテナを自分専用のポート 55437 で）、【判断】は担い手の判断。

**⚠ この ADR の番号は仮である。** マージの直前に `node scripts/adr-renumber.mjs` が確定する（[ADR 0179](./0179-adr-number-assigned-at-merge.md)）。

## 文脈

**「半年使い続けたとき、初期に言ったことを mnemora は思い出せるか」に答えている測定が、CI に無かった。**【現物】

- `compare` の最長は 642 ターン（合成）で、全記憶がほぼ同じ時刻に書かれる。
- `retrieval` では順位を決めているのが `similarity` だけである（[ADR 0109](./0109-which-score-terms-actually-rank.md)）。
- `time-term` / `answer-time-weighting` は時刻を動かすが、1ケースあたりの記憶は数件しかない。

一方、既定値（`DEFAULT_HALF_LIFE_HOURS` = 720、`DEFAULT_DECAY_THRESHOLD` = 0.05、`DEFAULT_SCORE_THRESHOLD` = 0.1、
`DEFAULT_TIME_WEIGHTING_POLICY` = `"legacy"`）からは、次の見立てが立つ。

- 使用報告の無い、`occurredAt` を持たない事実は、`legacy` では `decay` と `freshness` が同じ半減期で掛かる（[ADR 0300](./0300-time-weighting-policy-opt-in.md) §1）。similarity が 0.9 なら約48日で閾値を割る。
- 忘却ゲート（[ADR 0153](./0153-recall-decay-floor-gate.md)）は 720h × log2(1 / 0.05) ≈ 約130日で掛かる。

この見立ては実測されていなかった。

## 何を決めたか【判断】

1. **`examples/chat` に `long-horizon` サブコマンドを足す**（`src/long-horizon-case-set.ts`・`src/long-horizon-bench.ts`・`src/long-horizon-outcome.ts`・`src/long-horizon-format.ts`）。
2. **記憶は抽出 LLM を通さず直接書く**（`time-weighting-bench.ts` と同じ形）。`recordedAt` を模擬時刻で与え、`MutableClock` を進める。回答も生成しない。⟹ LLM を使わず、API キーも要らない。
3. **埋め込みは既定で `local`（`@mnemora/local-embedding`）にする。**`deterministic` では similarity が意味を持たず、時間項との兼ね合いを測れないため。`MNEMORA_EMBEDDING` を明示すればそれを尊重する。
4. **時間軸**: 180日。雑談を1日15件（計2,700件）、事実を22件（常用8・休眠8・訂正6）。事実ごとに、同じ話題で値が違う紛らわしい記憶を1件混ぜる。訂正は0日目に古い側、90日目に新しい側を植える。測る時点は 7/30/45/60/90/120/150/180 日目。数はすべて `long-horizon-case-set.ts` の定数が持つ。
5. **条件は4つ**（`timeWeighting` × 使用報告の有無）。
   - A: `legacy`・報告なし（入れたままの既定）
   - B: `legacy`・報告あり
   - C: `eventAwareFreshness`・報告なし
   - D: `eventAwareFreshness`・報告あり
   
   使用報告は `examples/chat` の `reportMemoryUsage` と同じ仕方で、常用の事実が7日ごとに話題に出たときに送る。
6. **テナントは3つ。**測定の `recall()` は使用報告を送らず、壁時計（既定）のテナントでは記憶の状態を変えない。⟹ A と C は同じ履歴を共有して2方針で問える。B と D は、何を報告するかがその方針の `recall()` の結果で決まるので分ける。
7. **「出なかった」を1つに潰さない。**gold が既定の `recall()` に返らなかったときは、次の4つに分ける（`classifyGoldOutcome`）。
   - `decayed`: 床を過ぎた（忘却ゲート）
   - `below_threshold`: 閾値割れ
   - `outranked`: 閾値は越えたが件数の上限の外
   - `not_reached`: 候補に上がらない
   
   判別には、閾値・忘却ゲートを外し、件数をテナントの記憶の総数まで広げた診断用の `recall()` を使う。
8. **見立てを陽性対照として並べる。**使用報告なしの arm では、最初の時点の similarity から見立てた「閾値・忘却ゲートで落ちる日」（`predictedFirstMissDay`）と、実際にそれで最初に落ちた時点を並べる。順位で先に負けた時点は別の欄に出す。
9. **門にしない。**CI の `long-horizon` ジョブは表を Job Summary に、JSON を成果物に残すだけにする（AGENTS.md「⚠ 偽陽性率に上限を置けない検査は門にしない」、[ADR 0088](./0088-retrieval-quality-measured-in-ci.md) §2）。事実は種類ごとに6〜8件しかない。
10. **配線の検査は歯にする**（`long-horizon-*.test.ts`）。分類の境界、ケース集合の不変条件、見立ての欄の分け方、忘却ゲートの日を過ぎた休眠の gold が `decayed` と名指しされること（本物の Postgres）、使用報告ありの arm で強化時刻が進むこと（本物の Postgres）を縛る。

## 測ったこと【実測】

手元の docker（`pgvector/pgvector:pg17`）で2回走らせた（所要 189秒・185秒、記憶 2,750件 × 3テナント）。
埋め込みは `local`（`ruri-v3-30m/sym`・256次元）。
2回目は、見立ての欄を分けた最終版のコードで走らせた。1回目との違いは表示だけで、測定の経路は同じである。

- **一致したもの**: 返った件数・返らなかった理由の内訳・gold の診断順位の中央値・訂正の新旧の順位関係（表示を比べて全行一致）。
- **揺れたもの**: プロンプトの平均文字数。120日目以降で、最大8字（A の180日目が 1,464字と 1,472字）。原因は調べていない。同点の雑談の並びが変わった可能性がある。
- **CI との比較**（この PR の最初の CI run 42604350108 の `long-horizon` 成果物、ジョブの所要 3分18秒）: gold・訂正の古い側の結果 800件のうち 798件が手元と一致した。違ったのは 120日目の訂正 `correction-lesson` の新しい側の2件（arm A と C）で、CI は `outranked`、手元は `returned`。similarity は CI と手元で最大 0.0021 ずれており、診断順位は 800件中 239件で違った。⟹ limit の境目にいた1件の順位が、ランナー間の数値のずれで入れ替わったと見ている（この1件の順位の入れ替わりそのものは追っていない）。

## 分かったこと【実測から言えること／言えないこと】

1. **閾値や忘却ゲートより先に、順位で負ける。**`legacy` では7日目、`eventAwareFreshness` でも30日目には、gold は既定の `limit` の外にいる。30日目の診断順位は、ほぼ全記憶の最下位に近い。
   - 機序（【実測】調査で1件ずつ確かめた）: `local` 埋め込みでは、無関係な雑談と問いの similarity が約0.75、gold は約0.9 で、差が小さい。そこに `decay × freshness` が掛け算で効く。30日目の gold は 0.9 × 0.5 × 0.5 ≈ 0.23、前日の雑談は約0.73 になり、新しい雑談に数百件抜かれる。
   - ⚠ この差の小ささは埋め込みモデルに依る。OpenAI の埋め込みでは無関係な文の similarity がもっと低いと見込むが、**このベンチでは確かめていない**。
2. **使用報告は、一度返らなかった記憶を救わない。**報告されるのは `recall()` が返したものだけなので、返らない記憶は強化されない。B は A と全く同じ結果になった。D で残ったのは、7日目に返った常用2件だけだった。
3. **訂正の新しい側も、植えてから約60日で同じように沈む**（150日目には0/6）。古い側が新しい側より上に出た時点は1つも無い。ただしそれは矛盾の検出ではなく、新しいほうが新しいからである。
4. **量の物差しは満たしている**（プロンプトは頭打ち）。ただし、その中身に gold が入っていない。⟹ 北極星の物差し「全部積むのをやめられたか」に対して、**量だけを見ると誤って「やめられる」と読める**。

⚠ この合成データ（1日15件の似た雑談・決まった問い）は実運用の分布ではない。上の結果を「実運用でも半年後に思い出せない」とは読まないこと。言えるのは、**この条件では既定値のまま思い出せない**というところまでである。

## 初版で踏んだ誤り

初版は、診断用の `recall()` の件数を固定の200にしていた。30日目以降は記憶が200件を超えるので、候補に上がっていて順位で200位の外にいた gold を、全部 `not_reached`（候補に上がらない）と数えていた。調査で1件ずつ確かめて気づき、件数をテナントの記憶の総数以上にした（`diagnosticRecallLimit`）。固定値に戻すと赤くなる歯を足してある。

## 採らなかった案

- **測る時点ごとにテナントを作り直し、その日までの履歴を書き直す。**Issue #2104 の初稿はこの形だった。測定の `recall()` が状態を変えないなら要らない（決定6）。活動時計の arm を測るときには要るので、その arm は段階1から外した。
- **全条件を1テナントで通しで測る。**B と D は使用報告の中身が方針ごとに違うので、履歴が分かれる。
- **抽出 LLM を通した E2E（Issue #2104 の段階2）。**API キーと録画が要る。段階1で「記憶が正しく書かれていても沈む」ことが分かったので、先にこちらを残す。
- **最初から門にする。**事実が種類ごとに6〜8件では、偽陽性率に上限を置けない。
- **基準値ファイルを同じ PR で足す。**基準値は CI の artifact を2回の run で一致を確かめてから採る（[ADR 0133](./0133-compare-baseline-and-gate.md) 決定1、[ADR 0231](./0231-compare-baseline-omitted-measured-update-and-freshness.md) 決定5）。CI がまだ一度も走っていないので、後続の PR に回す。

## 引き受けた負債

- **基準値が無い。**Job Summary は表を出すだけで、前回との差分を出さない。
- **事実・雑談が合成で、雑談の文型が似ている。**雑談どうしの similarity が揃いすぎている可能性がある。
- **埋め込みは `local` だけ。**分かったこと1の機序が埋め込みモデルに依るのに、他のモデルで測っていない。
- **測っているのは出典への到達だけ**（[docs/autonomy.md](../autonomy.md) §2.2 の2）。回答の正しさは測っていない。
- **ランナー間で境目の1件が入れ替わる。**基準値を作るときは、全件一致ではなく、この揺れを許す比べ方が要る（同じランナーの2回で一致するかは、まだ見ていない）。

## 確かめていないこと

- CI の run どうしの一致（CI では1回しか走らせていない）。
- プロンプトの平均文字数が揺れる原因。
- OpenAI など、他の埋め込みでの振る舞い。
- 使用報告を「返ったものだけ」ではなく「会話に出たもの」で送る使い方をしたときの振る舞い。
- 活動時計（`decay_clock = 'activity'`）、半減期を延ばした設定、`sweepArchive` を定期的に呼ぶ運用。

## これが覆るとしたら

- **CI で2回の run が一致したら**、基準値ファイルを足す（後続の PR）。
- **事実を増やし、偽陽性率に上限を置けると実測できたら**、門にすることを検討する。
- **他の埋め込みで、順位で負ける時点が大きく変わったら**、分かったこと1を「`local` 埋め込みに固有」と書き直す。
- **既定のスコア式（`decay × freshness` の掛け算、`legacy` の既定）が変わったら**、このベンチの値は大きく動く。それはこのベンチが測るために作られた変化である。
