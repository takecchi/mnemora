## 🔴 決定

1. **`.github/workflows/publish.yml` に門を1段足す。**引き金が `release` の非 prerelease のとき、
   **`origin/main` の `CHANGELOG.md` に `## [X.Y.Z]` の節が無ければ、`npm publish` の前で落とす。**
2. **述語は広げない。**[ADR 0251](./0251-release-follow-up-notice-not-a-gate.md) の通知と**同じ述語**
   （`versionFromTagName` / `findChangelogSection`）を import して使い回す。
   ⛔ **内容の推定を始めない**——それは [Issue #433](https://github.com/takecchi/mnemora/issues/433) が
   却下した側である（下の「(丙)」）。
3. **通知（ADR 0251）は消さない。**あちらは**終了コードが常に 0** のまま1バイトも変えない。
   ⟹ ⭐ **2つは役割が違う**——通知は「出した後に人へ知らせる」、門は「出す前に止める」。
4. 🔴 **手順の順序を変える。**`docs/release-v1.md` の「出した版の節が `CHANGELOG.md` に在るか」を、
   **§5（リリース後の確認）から §0（tag を切る直前の最終確認リスト）へ移す。**
   ⛔ **これは「あわせて直した」ではなく、門が成立するための条件である**（下の「なぜ (ii) か」）。
5. **除外は2つだけにする。**`release` 以外の引き金（`workflow_dispatch` の予行）と、`prerelease` の Release。
   ⛔ **3つ目を足さないこと。**足すたびに門の主張が薄まる。
6. **判定できないときは止める側へ倒す（fail-closed）。**tag が読めない・`CHANGELOG.md` が読めない・
   `prerelease` 欄が `true`/`false` のどちらでもない ⟹ **すべて門を当てる。**
   ⭐ `publish.yml` が既に採っている形と同じである【現物・逐語】:
   「**確かめていないものを publish の経路に通さない——ここで落とす。**」

## 🔴 置き場所の比較 —— **4案を、机上ではなく過去のリリースに当てて落とした**

### ⭐ すべてを決めた1つの実測

**【実測】`v0.1.9` / `v0.2.0` / `v0.3.0` / `v0.4.0` / `v0.5.0` の5つとも、tag が指す木には
出す版の節が無かった。**

```bash
for t in v0.1.9 v0.2.0 v0.3.0 v0.4.0 v0.5.0; do
  git show "$t:CHANGELOG.md" | grep -qF "## [${t#v}]" && echo "$t 在った" || echo "$t 無かった"
done
# → 5つとも「無かった」
```

⟹ 🔴 **この repo は「Release を作ってから節を書く」順序で回っている。**
⟹ ⭐ **門の置き場所をここで間違えると、正常な運用のたびに鳴る。**
⟹ ⛔ **そして「毎回鳴る門」は、ADR 0251 の通知が3回読まれなかったのと同じ末路をたどる**
——[ADR 0088](./0088-retrieval-quality-measured-in-ci.md) 逐語
「**偽陽性率を上限で抑えられない門は、いずれ無視されるか無効化される。それは門が無いより悪い。**」

### 比較表

| | 何を止めるか | 何を止めないか | 判定 |
|---|---|---|---|
| **(甲) `publish.yml` の門**（採った） | **出す版の節が無いとき、`npm publish` を止める** | ⭕ **無関係な PR は1本も止めない** | ⭕ **採用** |
| **(乙) `main` の required**（ADR 0251 案4） | 同じ欠落 | 🔴 **止めない範囲が無い**——tag 公開から節が入るまで、**無関係な PR まで赤くなる** | ⛔ 巻き添え |
| **(丙) PR 時点の門**（[#433](https://github.com/takecchi/mnemora/issues/433) 方向(B)） | 出荷面を触った PR | ⛔ 「doc コメントのみ」の PR を止めてしまう | ⛔ **偽陽性率に上限を置けない** |
| **(丁) 「ひとつ前の版の節」を要求する** | 2回連続の欠落 | 🔴 **1回目の欠落を止めない** | ⛔ **実測で死んだ** |

### ⛔ (丁) を落とした実測 —— **3回の失敗を1件も捕まえない**

**この案は「運用を変えずに済む」という理由で書き手が推していたが、当てたら死んだ。**

| | ひとつ前の版の節は、publish の時点で | 門は |
|---|---|---|
| `v0.3.0` を出すとき `[0.2.0]` | **25時間29分前に在った** | ⛔ 鳴らない |
| `v0.4.0` を出すとき `[0.3.0]` | **2時間03分前に在った** | ⛔ 鳴らない |
| `v0.5.0` を出すとき `[0.4.0]` | **39時間01分前に在った** | ⛔ 鳴らない |

⟹ 🔴 **毎回「前の版の節」は次のリリース直前に間に合っている。**⟹ **0/3。**
⭐ **これは「弱い門」ではなく「効かない門」である。**

### ⛔ (丙) を落とした理由 —— **#433 自身が書いている**

【現物・逐語】#433 の方向(B) は、提案者自身がこう書いている:

> ⛔ **「doc コメントのみ」は機械には判定できない。**⟹ **除外リストは人が書くしかない**

🔴 **⟹ 偽陽性率は「除外リストを人が書いた後」にしか決まらない ＝ 上限を*先に*置けない。**
⟹ [ADR 0223](./0223-cross-cutting-disciplines-extracted-from-the-adr-corpus.md) 決定3 に当たって落ちる。

⚠ **加えて、`[1.0.0]` 節の設計と正面衝突する。**同節は
「**`origin/main` がこれより進んでいても、この節は腐っていない——まだ数えていない範囲が増えただけである**」
という性質の上に立っており、**PR 時点で計上を強制すると、その性質が消える。**

### ⛔ (乙) を落とした理由 —— ADR 0251 が既に書いている

[ADR 0251](./0251-release-follow-up-notice-not-a-gate.md) 逐語:

> 🔴 **外したときの壊れ方**: **tag 公開〜節を書くまで `main` の required が恒常的に赤くなり、無関係な PR まで止まる** ⟹ **巻き添えが自分の外へ及ぶ**

⟹ ⭐ **本 ADR はこの指摘を否定していない。**(甲) は**同じ確実さを、巻き添え無しで**得ている

## 🔴 この門が [ADR 0223](./0223-cross-cutting-disciplines-extracted-from-the-adr-corpus.md) 決定3 を自分で満たすことの根拠

決定3 逐語: **「門（落とす検査）にしてよいのは、偽陽性率に上限を置けると実測できたものだけである。」**

### 【実測】過去4リリースへの逆測定 —— **真陽性 4/4・偽陽性 0/4**

**本物の道具**（`scripts/check-release-changelog-section-gate.mjs`）を、当時の木に当てた:

```bash
for t in v0.2.0 v0.3.0 v0.4.0 v0.5.0; do
  git show "$t:CHANGELOG.md" > /tmp/cl.md
  node scripts/check-release-changelog-section-gate.mjs \
    --tag "$t" --changelog-file /tmp/cl.md --event-name release --prerelease false
done
# → 4つとも exit 1（止める）
```

| 出した版 | 門の判定 | 正しかったか |
|---|---|---|
| `v0.2.0` | 🔴 止める | ⭕ **正しい**——節は publish の **1時間09分後**に書かれた |
| `v0.3.0` | 🔴 止める | ⭕ **正しい**——節は publish の **30時間49分後** |
| `v0.4.0` | 🔴 止める | ⭕ **正しい**——節は publish の **3時間49分後** |
| `v0.5.0` | 🔴 止める | ⭕ **正しい**——節は publish の **4時間05分後** |

⟹ **真陽性 4/4、偽陽性 0/4。**

### ⭐ 偽陽性が出うる場面は、**列挙できる**

**これが「上限を置ける」の中身である。**この門の述語は**内容の推定を一切しない**ので、
「節が無いのに止めるべきでない」場面は、**次の2つに限られる**:

| | なぜ | どう外したか |
|---|---|---|
| `workflow_dispatch` の予行 | **出す版が存在しない** | `if: github.event_name == 'release'`（既存の門と同じ条件） |
| `prerelease` の Release | **`CHANGELOG.md` は prerelease の節を持たない** | `github.event.release.prerelease == false` |

⟹ ⭐ **列挙できるのは、述語が「存在」しか見ていないからである。**
⛔ **内容を推定し始めた瞬間に、この列挙可能性が消える**——それが (丙) が落ちた理由そのものである。

## 🔴 なぜ (ii)「先に書く」で、(i)「落ちてから書く」ではないのか

**クローンの選択である。**理由（要旨）:

> **門は「止める」ためにあって「毎回鳴らす」ためではない。**
> **(i) は正常な運用のたびに門が赤くなる設計である ⟹ 赤が常態になった門は、やがて
> 「いつものやつ」として素通りされる ⟹ それは ADR 0251 の非ブロッキング通知が
> 3回読まれなかったのと、機序が同じである。**

⟹ ⭐ **正常な手順を踏めば門は鳴らず、鳴ったときだけ本当に何かが落ちている**状態にする。
⟹ **だから決定4（手順の順序の変更）は、門と一体である。**⛔ **片方だけ入れると、文書が自己矛盾する。**

### ⚠ (ii) が要求する、CHANGELOG の節の書き方の変化

**節は Release を作る*前*に起こす。**⚠ **その時点では分からない事実が3つある**【現物、`[0.5.0]` 節より】:

| 後からしか分からないもの | どうするか |
|---|---|
| `published` の UTC 時刻 | **後から埋める** |
| Release へのリンク | **後から埋める**（tag 名は先に分かるので、埋める先は決まっている） |
| 自動生成本文の行数 | **後から埋める** |

⭕ **項目そのもの（Breaking / Changed / Added の中身）は、Release の前に全部書ける。**
⟹ **門が見るのは節の存在だけなので、これで通る。**
⭐ **これは [ADR 0249](./0249-release-day-procedure-holds-no-rotting-facts.md) が `docs/release-v1.md` に
当てた規律（当日の手順書は腐る事実を本文に持たない）を、`CHANGELOG.md` の節へも当てる向きである。**

## 引き受けた負債

1. 🔴 **GitHub Release 自体は、この門が動く時点で既に公開されている。**引き金が `release: published` だからである。
   ⟹ **この門が守るのは npm であって、GitHub Release ではない。**
   ⭐ **npm のほうが取り消せないので、守る順序としてはこれでよい**——だが**「Release は出たのに npm に無い」という
   中間状態は作りうる。**⟹ 回復は「節を main へ入れて run を再実行」である（publish の段は冪等）。
2. ⚠ **`docs/migration-v1.md` の世代（ADR 0251 の (b)）は、依然として機械が見ていない。**
   ⟹ **人が `docs/release-v1.md` を読むしかない。**⛔ **「門が緑だから大丈夫」と読めてしまう**
   ——門の出力に毎回そう書かないよう明記した。
3. ⚠ **節の「中身」は見ていない。**空の `## [X.Y.Z]` でも通る。
   ⛔ **中身の検査を足すと (丙) の側へ移る**（内容の推定）⟹ **意図して足していない。**
4. ⚠ **決定4（手順の順序の変更）は、人が読む文書の変更である。**機械はそれを守らせない。
   ⟹ **門が鳴ったときに初めて気づく形は残っている。**⭐ ただし**鳴れば止まる**ので、3回目までとは違う。

## これが覆るとしたら何が起きたときか

- **門が偽陽性で止めたとき**（＝節が無いのに、止めるべきでなかったリリースが在ったとき）。
  ⟹ **除外の列挙が不完全だったことになる。**⚠ **そのときは除外を足す前に、「なぜ列挙できると思ったか」を測り直すこと。**
- **正常な手順を踏んでも門が鳴り続けるとき。**⟹ 🔴 **(ii) が運用に乗らなかったということである。**
  そのときは **(i) へ倒すのではなく**、節の形（後から埋める3つ）をもう一段減らせないかを先に見ること
  ——**(i) は「赤を常態にする」ので、この ADR が避けた側である。**
- **`CHANGELOG.md` が手書きでなくなったとき**（[ADR 0169](./0169-changelog-hand-curated.md) が覆ったとき）。
  ⟹ 節の存在は自動で保証されるので、この門は要らなくなる。

## 測ったこと

### 【実測 2026-09-21】

1. **5つの tag すべて、tag の木には出す版の節が無かった**（上の「すべてを決めた1つの実測」）。
2. **逆測定: 本物の道具を過去4リリースの木に当て、4回とも `exit 1` を返すことを確かめた**（真陽性 4/4）。
3. **(丁) の逆測定: 「ひとつ前の版の節」は3回とも publish の時点で既に在った**（0/3、見逃し）。
4. **道具の終了コードを、6通りの入力で直接測った**:
   節が在る → `0` / 節が無い → `1` / `prerelease` → `0` / `workflow_dispatch` → `0` /
   `--changelog-file` を省く → `1` / tag が空 → `1`。

### ⛔ 確かめていないこと

- 🔴 **将来の偽陽性率は測れていない。**上の 4/4・0/4 は**過去4リリースという標本**であり、
  [ADR 0094](./0094-identifier-probes-local-embedding.md) が言う「**増えた母数で偽陽性率に上限を置けると測れたこと**」とは
  **別のもの**である。⟹ ⭐ **ここで上限の根拠にしているのは標本の数ではなく、
  「述語が内容を推定しないので、偽陽性が出うる場面を*列挙*できる」という構造のほうである。**
  ⛔ **その列挙が漏れていたら、この根拠は崩れる。**
- **この門を実際の Release で走らせていない。**確かめたのは**道具の判定**と**ワークフローの配線**までである
  （ADR 0251 の歯と同じ断り）。⟹ **初回のリリースで、`RUNNER_TEMP` / `git show` の経路が本当に通るかは、その日に分かる。**
- **`prerelease` の Release を、この repo は一度も作っていない**【実測】（`gh release list` の全件が `isPrerelease: false`）。
  ⟹ **prerelease の除外は、現物で一度も踏まれていない経路である。**
- **全テストは手元で走らせていない**（判定は CI に任せる。`AGENTS.md`）。
