## 文脈

**[Issue #109](https://github.com/takecchi/mnemora/issues/109) の前半**（識別子 probe 30件・
日本語固有名詞 probe 12件・数詞・記号索引 probe 18件、PR #718 とその前の一連の PR）は、
ADR 0094「これが覆るとしたら」第1項の前半——**「標本が数十件になる」**——を満たした。
**後半——「その母数で偽陽性率に上限を置けると実測できたとき」——が未達のまま残っていた**
（ADR 0094 その後の追記「⛔ 門は置いていない。2 run では偽陽性*率*に上限を置けない」）。

**[ADR 0254](./0254-no-gate-without-a-false-positive-ceiling.md)** は「偽陽性率に上限を
置けない検査は門にしない」を `AGENTS.md` へ入れた。**[ADR 0276](./0276-retrieval-quality-shadow-verdict-stage1.md)**
（Issue #572 段1）は、既存の `retrieval` ベンチ（probe 7件）の MRR/hit@1 判定を「門ではなく
並走」で足し、**合成ノイズに対する偽陽性は 0/15（σ=0.16 まで）**と測ったが、
**「合成ノイズ」であって「実 API の揺れ」ではない**ことを明示的な限界として残していた
（同 ADR §「測定の射程」4番）。

**マネージャーの予備測定**（【受】、`/tmp/mgr-297d4d8a/probe/` に生データ）が、この2本を
つなぐ実測を先に行っていた:

- OpenAI `text-embedding-3-small`（256次元）は**完全には決定的でない**。同一入力を
  **別々の呼び出しで**投げると、まれに別のベクトルが返る（20回中、ペア190組の
  exact-match 率は文により 90〜100%、コサイン類似度の最小 0.998647）。
- **同一バッチ内の重複**は bit-identical なベクトルを返す——揺れは呼び出しをまたいだ
  ときにだけ生じる。
- 19日前に録った `cassettes/retrieval.json` との比較では、完全一致率はわずか 3.4%
  だった（最小コサイン類似度 0.998）——ただし後述のとおり、**この数字は簡易な cosine
  順位（本物の `recall()` スコープではない）で出したものであり、本 ADR の実測はこの
  誤りを踏まずに作り直した**（§5）。

**⟹ CI は決定的（同じカセットを毎回再生するだけ）なので、偽陽性は構造的に起きない。
偽陽性が起きうるのは、カセットを実 API で録り直したときである。** ⟹ 本 ADR は、
**「同じ設定で独立に録り直したとき、どれだけの頻度で無害な相違が閾値を超えるか」**を、
Issue #109 が足した6群（識別子 probe 2haystack・日本語固有名詞 probe 2haystack・
数詞・記号索引 probe 2haystack）に対して実測する。

## 決めたこと

1. **識別子・日本語固有名詞・数詞・記号索引の6群に、OpenAI 実埋め込み（`recorded`
   provider で再生）の追加 arm を足す**（`identifier-probes`/`numeral-token-probes`
   サブコマンド。既存の `local` embedding の5群には1文字も触れない）。
   専用カセット（`examples/chat/cassettes/identifier-probes.openai.json` /
   `numeral-token-probes.openai.json`）と基準値ファイル
   （`identifier-probe-baseline.openai.json` / `numeral-token-probe-baseline.openai.json`）を
   新設した。**⛔ 門にしない**——CI では基準値との差分と「並走の判定」を Job Summary へ
   出すだけで、相違しても `exit 0`（§7）。
2. **`japanese` 群（既存 `probe-set.ts` の7 probe）はこの6群に含めない**——その群は既に
   `retrieval` の arm B/C が同じ `(openai, text-embedding-3-small, 256)` 空間で測っている
   （`retrieval-baseline.json`）。同じ空間・同じ probe を二重に録らない。
3. **偽陽性率の判定を、測定前に固定する**（後出しにしない。§4）:
   - **hit@1 が基準値（round 0 の実測）の件数を1件でも下回ったら red。**
   - **MRR が基準値から 0.01 以上落ちたら red。**
   - 6群のいずれかが red ならその round は red（束ねた集計）。**加えて群ごとの
     red 件数も別に記録する**（§5 で分かる通り、束ねた集計だけでは何が上限を
     引き上げているかが読めない）。
4. **K=59（既定）で独立に録り直す。1巡=1回のバッチ embed 呼び出し**（同じバッチ内に
   同じ文字列を入れない——マネージャーの予備測定が「同一バッチ内の重複は
   bit-identical」と確認済みのため、バッチ内重複では揺れを測れない）。
   各巡・各群を、**本物の Postgres + pgvector の `recall()` パイプライン**（cosine 順位の
   簡易近似ではない）に通す。手で回す再計測の手順として
   `examples/chat/src/scripts/openai-embedding-fp-ceiling.ts` を repo に置く
   （`OPENAI_API_KEY` は環境変数から読むだけで、値をログ・生成物のどこにも出力しない）。
5. **Clopper–Pearson の片側95%上限**を自前で実装する（`examples/chat/src/openai-arm-verdict.ts`。
   正規化不完全ベータ関数を Lanczos 近似+連分数展開で計算し、二分探索で反転する）。
   K=59 を選んだ理由: **赤が0件のとき、この上限が約4.95%になる**
   （閉じた式 `1 - alpha^(1/K)` と一致することを歯で検算済み）。
6. **既存の `cassettes/retrieval.json` との1標本の乖離チェックを副産物として添える**
   （§5.1）。⛔ 既存カセットは1バイトも書き換えていない。

## 測ったこと(【実測】)

### 環境

手元の `initdb` 自製インスタンス（PostgreSQL 17 + pgvector 0.8.0、port 55911）。
本番ではない。実 API は `text-embedding-3-small`/256次元、LLM は常に
`DeterministicLLMProvider`（識別子・日本語固有名詞・数詞・記号索引の各 arm は
元々このプロバイダしか使わない設計であり、この ADR は変えていない）。

### 手順の忠実さ — 素朴な cosine 順位ではなく、本物の `recall()` を毎回通した

**最初の実装は、`retrieval.json` との1標本チェックを素朴な cosine 順位の近似で
出していた**が、既知の実測値（ADR 0276「MRR=0.738095238095238、hit@1=4/7」、
goldRank ベクトル `1,1,2,6,1,1,2`）を再現できなかった（`diet` probe の goldRank が
`13` と出た。既知値は `6`）。原因は、`retrieval` ベンチの実際の候補群が
`llmMode=recorded`（本物の LLM が書き換えた digest を埋め込む）であり、素朴な
cosine 順位が想定していた「gold の生テキストをそのまま埋め込む」という前提が
誤っていたことである。**⟹ LLM 層は録り直さず既存の記録をそのまま再生し、
embedding 層だけを新しい値に差し替えて、本物の `runRetrievalQualityArm`
（Postgres 経由）に通す形に直した。** 直した後、**2回とも既知値と完全に一致した**
（§5.1）——これが本 ADR の「陽性対照」である（本物のパイプラインを通していることの
実測による確認）。同じ理由で、6群の偽陽性率測定も**最初から**本物の
`runIdentifierProbeArm`（Postgres 経由）に通しており、簡易近似は使っていない。

### §5.1 既存カセットとの1標本の乖離チェック(⛔ 統計的主張ではない、n=1を2回)

| | 記録済み(`retrieval.json`、2026-09-06 録画) | 録り直した embedding(1巡目) | 録り直した embedding(2巡目) |
|---|---|---|---|
| hit@1 | 4/7 | 4/7 | 4/7 |
| MRR | 0.738095238095238 | 0.738095238095238 | 0.738095238095238 |
| goldRank ベクトル | 1,1,2,6,1,1,2 | 1,1,2,6,1,1,2 | 1,1,2,6,1,1,2 |
| ADR 0276 shadow verdict(`MRR>=0.65 かつ hit@1>=3`) | pass | pass | pass |

**2回とも、記録済みの値から1バイトも変わらなかった。**⚠ **標本 n=1（を2回）であり、
「19日の経年では乖離しない」を統計的に主張しない**——マネージャーの予備測定が示した

特定の候補群では、たまたま順位を1つも動かさなかった、というだけである。
**「出なかった」を根拠にしない**（`AGENTS.md`）——ここでは逆に「出た」（一致した）ことを
報告しているので、この規律には抵触しない。

強く相関している）——束ねた集計（6群のいずれかが red）を読むときはこの点を
差し引くこと。

## 偽陽性率の上限の値と、その射程

🔴 **上限が置けたもの**: `japaneseNamesSparse`/`japaneseNamesDense`/`numeralSparse`/
`numeralDense` の4群。**合算118巡で red=0件、Clopper–Pearson 片側95%上限 ≈ 2.51%。**

🔴 **上限が置けなかったもの**: `identifiersSparse`/`identifiersDense` の2群。
**合算118巡で red=33件（redRate ≈ 28.0%）、上限 ≈ 35.6%。** 個々の測定でも
上限は 29.0%〜48.8% であり、いずれも低い値ではない。**⟹ この2群を、いまの判定
（hit@1 が1件でも基準値未満、または MRR が0.01以上落ちたら red）のまま門にすると、
カセットを録り直すたびに、「品質は何も変わっていないのに落ちる」ことが数回に1回の頻度で起きる。**

### この上限が「何の揺れ」に対するものか(射程)

1. **これは「同じモデル・同じ probe 集合・同じコードでの、独立な録り直し」に対する
   上限である。**モデルの交代（`text-embedding-3-small` から別モデルへ）や、
   次元数の変更には及ばない——そのときは別空間になり、測り直しである
   （ADR 0094「これが覆るとしたら」と同じ形の限定）。
2. **日〜週単位で起きるカセットの経年変化には及ばない。**K=59回の録り直しは
   すべて同日（数時間以内）に行っている。§5.1 の1標本チェック（19日相当ではなく、
   同日内の再録画2回）は、この限界を埋め合わせるものではない——**ここは
   確かめていないこととして残る**（下の節）。
3. **この上限は、識別子・日本語固有名詞・数詞・記号索引の6群（実質3本の独立な信号）
   についてのものであり、`retrieval` ベンチの主測定7 probe については実測していない
   ——そちらは§5.1 の1標本チェック（統計的主張ではない）しか無い。**
4. **`local` embedding（`@mnemora/local-embedding`）の既存5群には、この上限は
   一切適用できない。**`local` は決定的である（ADR 0094 が2 run のビット一致で
   確認済み）ため、この ADR が測った「実 API の呼び出しをまたいだ揺れ」という
   偽陽性の原因そのものが存在しない。**ADR 0094「これが覆るとしたら」第1項が
   `identifier-probes`/`numeral-token-probes` の*既存*（local embedding）5+2群に
   ついて言っていた「母数で偽陽性率に上限を置けると実測できたとき」は、
   この ADR では閉じていない**——それはこの ADR とは異なる種類の偽陽性
   （小さい母数からくる統計的な不確実性。ADR 0033 §3 が繰り返し警告している
   もの）についての条件であり、実 API の呼び出し揺れとは別の測定が要る
   （下の「引き受けた負債」）。

## Issue #109 の閉じる条件に届いたか — 部分的にのみ

**⛔ 過大に書かない。**

- **この ADR が新設した6群の OpenAI 実埋め込み arm については、届いた**——
  「標本が数十件になり、その母数で偽陽性率に上限を置けると実測できた」の後半を、
  4群について実測で満たした（上限 ≈2.51%）。**残る2群（`identifiersSparse`/
  `identifiersDense`）については、実測した結果「上限を低く置けない」という
  結論に届いた**——これも一種の到達である（「測れなかった」ではなく
  「測って、置けないと分かった」）。
- **`identifier-probes`/`numeral-token-probes` の既存5+2群（`local` embedding）
  については、届いていない。**それらは決定的なので、この ADR の測定手法
  （実 API の呼び出し揺れ）が測る対象そのものが存在しない——**別の測定
  （合成ノイズの注入。ADR 0276 と同じ手法）が要る**（下の「引き受けた負債」）。
- **`retrieval` ベンチの主測定7 probe については、届いていない。**§5.1 の
  1標本チェックはこの ADR の副産物であり、統計的な上限を主張できる形をしていない。
- **⟹ この ADR は Issue #109 を閉じない。**新設した6群のうち4群については
  門を置く前提条件を満たしたが、**門そのものを置く判断（required への変更・
  branch protection の変更）はオーナー領分であり、この ADR は行っていない**
  （ADR 0276 の「段3」と同じ理由）。

## 検討して採らなかった案

- ⛔ **識別子・日本語固有名詞・数詞・記号索引の6群を、素朴な cosine 順位の近似で
  測る。**当初これで実装したが、既知の実測値（ADR 0276）を再現できなかった
  （§「測ったこと」）。⟹ 本物の `runIdentifierProbeArm`/`runRetrievalQualityArm`
  （Postgres 経由）を毎回通す形に直した。
- ⛔ **`retrieval` ベンチの主測定7 probe に、同じ K=59 の厳密な統計測定を行う。**
  時間予算に対して見合わないと判断し、§5.1 の1標本チェック（既存カセットとの
  差分を2回測るだけ）に留めた——これは明示的な限界として残す（下）。
- ⛔ **`identifiersSparse`/`identifiersDense` の判定基準を緩めて「上限を置けた」
  ことにする。**閾値を後から緩めるのは、測定前に固定した判定を後出しで
  変えることであり、この ADR 自身が課した規律（「決めたこと」3番）に反する。
  緩めるかどうかの判断はオーナー領分として残す。
- ⛔ **`local` embedding の5+2群についても、この手法（実 API の呼び出し揺れ）で
  偽陽性率を測る。**`local` は決定的なので、この手法が測る対象が存在しない
  （上の「射程」4番）。合成ノイズの注入という別の手法が要る——この ADR の
  範囲外とした（時間予算）。
- ⛔ **6群を「実質3本」として統合し、3本だけを測定・報告する。**sparse/dense の
  相関は実測で分かったことであり、測定前に「この2群は同じ結果になるはず」と
  決めて片方を省略するのは、値を見てから設計を変えることになる
  （ADR 0094 §6 の規律）。⟹ 6群とも測り、相関している*ことを*報告するに留めた。

## 引き受けた負債

1. **`local` embedding の既存5+2群（ADR 0094/0135/0306）の偽陽性率は、この ADR
   では測っていない。**Issue #109 の元々の「これが覆るとしたら」第1項が指していた
   のはこちらであり、**まだ閉じていない**。次に測るなら、ADR 0276 と同じ
   「合成ノイズを注入する」手法（`local` embedding は決定的なので、実 API の
   呼び出し揺れという手法は使えない）が必要になる。
2. **`identifiersSparse`/`identifiersDense` は、実測で「低い上限を置けない」と
   分かった。**⚠ CI はカセットを再生するだけなので、
   この2群の並走の判定は**毎 PR 同じ値**になり、CI 上で 🔴 が揺れることは無い。
   🔴 が出うるのは**カセットを録り直したとき**であり、実測ではその約3割
   （合算 33/118）で出た——録り直した PR で 🔴 が出ても、それだけで退行とは
   読まないこと（実際に揺れているものを、揺れていないと書かない）。次にこの2群の判定基準を
   見直す（例: margin に基づく判定、複数回の多数決）なら、それは別の ADR の
   判断である。
3. **カセットの経年変化（日〜週単位）に対する偽陽性率は、まだ測っていない。**
   §5.1 の1標本チェックは同日内の再録画であり、19日相当の経年を再現していない。
4. **6群の相関構造**（sparse/dense がほぼ同じ揺れを共有する）**は実測で発見したが、
   その原因（probe 自身の embedding 揺れが margin の小さい候補の順位を動かす）を
   確定するところまでは踏み込んでいない**——`marginStats`（各基準値ファイル）から
   推測される説明であり、個々の probe を1つずつ切り分けて確認していない。
5. **`openai-arm-verdict.ts`/`openai-arm-summary-lib.mjs` の判定閾値（hit@1低下・
   MRR低下0.01）は、二重管理である**（`.mjs` は `tsx` を通さないため TS 側の定数を
   import できない。ADR 0276 と同じ既知の負債形）。歯は両側で別々の値を検査して
   いるので、片方だけ値を変えれば数字が食い違う——検出する歯は無い。
6. **`identifier-probes`/`numeral-token-probes` の CI 配線（新設した env var・
   summary/artifact ステップ）を検査する機械の歯は新設していない**
   （ADR 0306 §4 と同じ判断——時間予算に対して見合わないと判断し、手作業と
   `scripts/__tests__` 全体の実行（1693 tests green）で確認した記録に留める）。

## これが覆るとしたら

- **`identifiersSparse`/`identifiersDense` の判定基準を見直し、低い上限を置ける
  形が見つかったとき。**（例: margin の分布に基づく判定、複数回投げて多数決を
  取る等）そのとき、この2群についても「これが覆るとしたら」の対象になる。
- **`local` embedding の5+2群に対して、合成ノイズ注入による偽陽性率測定が
  行われたとき。**そのとき Issue #109 の元々の条件が、初めてこの ADR の射程に
  入る。
- **カセットの経年変化（日〜週単位）に対する偽陽性率が別途測られたとき。**
  そのとき §5.1 の限界が解消される。
- **識別子・日本語固有名詞・数詞・記号索引のいずれかの probe 集合が変更されたとき。**
  カセット・基準値ファイルの録り直しが要る——`examples/chat/src/scripts/
  openai-embedding-fp-ceiling.ts` を再実行すること。

## 確かめていないこと

- ⛔ **CI ランナー上では走らせていない。**手元の `initdb` インスタンスのみ。
- ⛔ **カセットの経年変化に対する偽陽性率**（上の「引き受けた負債」3番）。
- ⛔ **`identifiersSparse`/`identifiersDense` の揺れが、具体的にどの probe の
  どの候補間の margin から来ているかを、1件ずつ切り分けていない。**
  `marginStats`（基準値ファイル）から推測しているだけである。
- ⛔ **3回目以降の測定を行っていない。**K=59×2回で合算118巡としたが、
  さらに多くの巡を重ねれば上限はさらに狭まる——時間・費用の両方に対して
  これ以上は今回は行わなかった（費用は1回$0.015前後で問題にならないが、
  1回あたり約10分の実行時間が掛かる）。
- ⛔ **`text-embedding-3-small` 以外のモデル・次元での挙動は測っていない。**
- ⛔ **この ADR が新設した「並走の判定」を、実際に CI 上で走らせて Job Summary の
  見え方を確認していない**（手元の `tsx` 実行でのみ確認。§「測ったこと」参照）。
