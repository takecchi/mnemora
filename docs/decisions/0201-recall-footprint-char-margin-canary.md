## 結論（先に）

**`examples/chat/src/__tests__/recall-footprint-baseline.test.ts` に、hold-out 5行（`totalInScope > DEFAULT_RECALL_LIMIT`）の許容誤差の余白を「字数」で計算し、いちばん狭い行を明示する `it` を1本足した。** `ACCURACY_TOLERANCE`（= 0.025）は動かしていない。合わせて、同ファイルの「なぜ2.5%か」docstring が持っていた古い実測値（1.56% / 1.28% / 「約6割の余裕」）を、当時の値といまの値を書き分ける形で訂正した（ADR 0166「2026-09-17 訂正」節と同じ作法）。

**⭐ 自分で数え直した結果、Issue #410 が示した「いちばん狭いのは322ターン行の20.14字」は、hold-out 5行全体で見ると正しくない。** 322ターン行より狭い行が在る——**42ターン行（`totalInScope=14`）の上側で、余白は11.15字**しかない。42行は誤差の百分率では0.635%（322行の2.068%よりずっと小さい）だが、`mnemoraChars` の絶対値が583字と小さいため、同じ2.5%という相対許容を字数に直すと322行より狭くなる。**「誤差の百分率が最大の行」と「字数の余白が最も狭い行」は一致しない**——これは Issue #410 自身の主張（百分率だけで見ると危険を見誤る）を、さらに一段強める実測である。

| 較正係数                                         | `charsPerDigest ≒ 15.4583` / `fixedIndexChars ≒ 170.8810`（hold-in 7行から） |
| 322行（Issue #410 が挙げた例）の上側余白         | 20.142857… 字                                                                |

## 背景

[Issue #410](https://github.com/takecchi/mnemora/issues/410) が、`recall-footprint-baseline.test.ts` の許容誤差（`ACCURACY_TOLERANCE = 0.025`）に対する322ターン行の余白を、百分率（(2.5-2.068)/2.5 ≒ 17%、「まだ余裕がある」ように見える）と字数（`4567.14 - 4547 = 20.1`字、「digest 1件分弱」）の両方で測り、**物差しによって危険の見え方が変わる**ことを指摘した。オーナーは同 issue のコメントで「対処候補3（境界に近づいたことを字数で検知する歯を足す）＋ 歯のコメント自身が持っている古い数字の訂正」の形で進めることを決めている。⛔ `ACCURACY_TOLERANCE` を動かす案（issue 本文・ADR 0166 双方が既に却下）は選択肢に無い。

## 決めたこと

### 1. docstring の訂正（当時の値といまの値を書き分ける）

`ACCURACY_TOLERANCE` 直上の「⚠ なぜ2.5%か」docstring は、「12行全体の最大誤差は2ターン行の1.56%」「hold-out側の最大は82ターン行の1.28%」「2.5%は実測(1.56%)に約6割の余裕」と書いていた。**この3つとも、いまの `compare-baseline.json` に対しては成立しない**（現在は322ターン行が両方の最大を兼ね2.068%、余裕は百分率で約17%）。

原因は Issue #340 が特定済み——**この1.56%/1.28%は、`queryRecall` が連想枠（ADR 0151/0168）を使うようになる前、全hold-out行の`associationCount=0`だった時点の実測**であり、ADR 0166が推定器に連想の項を足したあとも、このdocstringの数字だけが追随していなかった。

ADR 0166の「2026-09-17訂正」節が採った作法（表を消さずに当時の値といまの値を並べ、測定日とsha を添える）をそのまま踏襲し、古い文を残したまま「### ⚠ 2026-09-17訂正」節を追加した。**字数と百分率の両方を書いた**（issue #410自身の主張が「百分率だけで見ない」ことなので、訂正の書き方自体がそれを踏まえる必要がある）。

### 2. 余白を字数で見る `it` を新設

`recall-footprint-baseline.test.ts` の末尾に、次を満たす `it` を1本追加した:

- **対象は hold-out 5行のみ**（下の「検討して採らなかった案」参照。hold-in 7行は較正標本そのものであり、自己参照のため除外）。
- 各行の上限（`est / (1 - ACCURACY_TOLERANCE)`）・下限（`est / (1 + ACCURACY_TOLERANCE)`）を字数で計算し、上側余白（上限−実測）・下側余白（実測−下限）を求める。
- 5行×2方向=10値の最小をとり、`FLOOR_CHARS`（= `charsPerDigest / 2`、較正係数から導く。⛔ 固定した実測値ではない）以上であることを assert する。
- **`it` の名前自体に、いちばん余白が狭い行・方向・字数（小数2桁）・FLOOR の値を埋め込む**（`` `いちばん余白が狭いのは turnCount=${narrowest.turnCount}(${narrowest.direction}側)で ${narrowest.marginChars.toFixed(2)}字 — 半digest分(${FLOOR_CHARS.toFixed(2)}字)を上回ること` ``）。テスト名は収集時に評価されるので、緑のときも赤のときも、字数の実測がそのままテスト結果の一覧に残る——百分率だけの表示にしない、という issue #410 の要求を、レポート面でも満たす。

**新規に import した記号は無い**——既存の `calibrateRecallFootprint` / `estimateRecallFootprint` / `holdOutRows` / `associationCountForRow` / `ACCURACY_TOLERANCE` をそのまま使い回している。

### 3. CI ジョブは増やさない

既存の `example-chat` ジョブ（`.github/workflows/ci.yml`）の `pnpm --filter @mnemora/example-chat run test:db` ステップが `vitest run` で `src/__tests__/` 配下を丸ごと走らせるため、この歯は新しいジョブ・新しいステップを足さずに既存の門へそのまま乗る。

## なぜ FLOOR を「半digest分（`charsPerDigest / 2`）」にしたか

Issue #410 は自身の対処候補3で「余白が既定の下限（例: digest 2件分≒31字）を下回ったら赤くする」形を例示していた。**しかし自分で数え直すと、現在の真の最小余白（42行・上側・11.15字）は、この「2件分」を既に下回っている。** ⟹ そのまま「2件分」を閾値にすると、この歯を足した瞬間に `main` が赤くなる。

検討した3案:

**案A（採った）: FLOOR = `charsPerDigest / 2`（較正係数から動的に導く）。**
「digestの内容がわずかに変わっただけで境界に触れる」水準を、較正が変わっても追随する形で表現できる。現在値（≒7.73字）は現在の最小余白（11.15字）の下に収まり、main は緑のまま通る。較正係数（`charsPerDigest`）自体が動けば閾値も比例して動くため、「20.1字」のような特定の実測値を固定するより、将来の較正変化に対して意味を保ちやすい。

**案B（検討したが採らなかった）: 固定の字数（例: 8字、11.15字のすぐ下）を閾値にする。**
却下理由: マネージャーが名指しで警告した「余白がちょうど20.1字であることを固定すると、正当な変更で意味なく赤くなる」と同じ性質の脆さを持つ——`charsPerDigest`自体が将来較正し直されて変わっても、固定した字数は追随しない。「なぜこの数か」を将来の読み手に説明する負担も増える（案Aなら「半digest分」で説明が閉じる）。

**案C（検討したが採らなかった）: 赤にせず、境界の字数を検算して固定する形（`toBeCloseTo` で現在値を pin する）。**
却下理由: 案Cは「いまの余白がいくつか」を記録することはできるが、**「境界に近づいたことを検知する」というissue #410の対処候補3の目的そのものを果たさない**——digestが数字1つ分縮んで余白が広がっても、逆に危険なほど狭まっても、`toBeCloseTo`は両方を同じように「ズレた」として赤くする。余白が縮む方向だけを問題にしたい（issue本文「digestを数十字増やす変更でmainが赤くなる」という懸念そのもの）ので、閾値を下回ったときだけ赤くなる案Aのほうが目的に合う。

## 引き受けた負債

1. 🔴 **hold-in 7行の余白は、この歯では検知しない。** frozen calibration で計算すると2ターン行の上側余白は1.97字と、42行(11.15字)よりさらに狭く見えるが、上述の自己参照のため意味のある境界として扱えない。**hold-in行が較正標本として使われ続ける限り、「hold-in行の実測がどこまで動いても安全か」を正しく検知する歯は、この ADR の範囲では作っていない**（数値的に解くには、較正のフィードバックを含めた再帰的な感度分析が要り、この issue の対処候補3が求める単純な字数表示の範囲を超える）。
2. ⚠ **FLOOR(≒7.73字)は現在の最小余白(11.15字)にかなり近い**（差は約3.42字）。もし今後 `charsPerDigest` が較正し直されて縮めば、FLOORも比例して縮むため閾値としての意味は保たれるが、**hold-outのいずれかの行の実測が数字1つ分動けば、この歯はすぐに赤くなりうる**——これは検知の鋭敏さとして意図した設計だが、頻繁な「意図した変更」による赤で疲弊するリスクは残る。
3. ⚠ **この歯はcompare-baseline.jsonが今後更新されたとき、較正係数もFLOORも自動的に再計算される**（ハードコードされた数値が無いため）。⟹ 将来baseline全体が更新されても壊れないという利点の裏返しとして、**「FLOORが動いたこと」自体はこの歯の出力からは分からない**——テスト名に埋め込まれたFLOORの値を毎回読む必要がある。

## これが覆るとしたら

1. **Issue #410の対処候補1（推定器を直す）または2（較正標本の取り方を見直す）が採られ、hold-out行の誤差自体が縮んだとき。** そのとき、この歯が守る「境界に近づいたら知らせる」という役割の緊急度は下がるが、歯自体は引き続き正しく動く（FLOORは較正から再導出されるため）。
2. **`charsPerDigest`の較正がhold-in行の構成を変え(例: 連想昇格行も較正標本に含める設計変更)、`charsPerDigest`の値自体が大きく動いたとき。** そのときFLOOR(=`charsPerDigest/2`)も追随して動くため、閾値の絶対値の妥当性を見直す必要が出るかもしれない。
3. **hold-in行の自己参照問題(引き受けた負債1)を解く必要が出たとき**——例えば、hold-in行の実測が実際にドリフトする事例が発生し、これを検知する要求が具体化したとき。そのときは較正のフィードバックを含めた感度分析(または較正標本自体をfreezeしたsnapshotに固定する設計)を検討する必要がある。

次に`git show 9fcd47c -- packages/core/src/recall-footprint.ts`でこのcommitが`estimateRecallFootprint`本体に入れた差分を読んだ。核心部分:

```
const baseReturnedMemories = Math.min(limit, inScope);
const requestedAssociationCount = Math.max(0, shape.associationCount ?? 0);
const associationCount = Math.min(
  requestedAssociationCount,
  Math.max(0, inScope - baseReturnedMemories),
);
const returnedMemories = baseReturnedMemories + associationCount;
```

`shape.associationCount`を渡さなければ（`undefined`）、`requestedAssociationCount = 0` → `associationCount = Math.min(0, …) = 0` → `returnedMemories = baseReturnedMemories`——**`associationCount`の項が無かった旧式と完全に一致する式のまま**であることを、コード自体から確認した（分岐しているのではなく、同じ式が`associationCount=0`のとき恒等的に旧式へ潰れる）。

さらに`git show 015466c:examples/chat/compare-baseline.json`で新設時点のbaselineを取り出し、hold-out5行（`turnCount=42/82/162/322/642`）の`returnedCount`を見ると、全行`10`だった（`totalInScope`は14/25/49/95/189でいずれも`DEFAULT_RECALL_LIMIT=10`を超えるため、`baseReturned = min(10, totalInScope) = 10`）。テストファイルの`associationCountForRow`（`Math.max(0, row.returnedCount - baseReturned)`）で逆算すると**hold-out全5行が`associationCount = 0`**になる。

⟹ **現行の推定器を`015466c`版のbaselineに当てた値は、当時の実際の値と一致する。**これは反実仮想（「連想枠が無かったら」という仮定の計算）ではない——`associationCount=0`の経路は連想枠の導入前後で分岐すらしていない同じ式であり、かつ当時のhold-out行は実際に全行`associationCount=0`だったのだから、**現行コードに当時のJSONを通した出力は、当時実際に動いていた式の出力そのものである。**

最後に、`examples/chat/src/__tests__/recall-footprint-baseline.test.ts`と同じ手順（`holdInRows`から`calibrateRecallFootprint`で較正 → hold-out5行×上下2方向で`est/(1∓0.025)`の余白を計算 → 最小を取る）を、`packages/core`をbuildして`node`から`calibrateRecallFootprint`/`estimateRecallFootprint`を直接呼ぶ形で、`015466c`版と`9fcd47c`版（＝現行`main`と1バイトも違わないことを`diff`で確認済み）の両方のbaselineに対して実行した。

両時点とも`charsPerDigest = 15.458333333333334` / `fixedIndexChars = 170.88095238095235`で一致した——`015466c`と`9fcd47c`のbaselineでhold-in 7行（`totalInScope<=10`）を突き合わせると1バイトも変わっていない（`JSON.stringify`が一致することを確認）。⟹ **`charsPerDigest`は両時点で動いておらず、FLOORも動いていない。**

**⟹ 歴史上ただ1回の変更（これまでで最大の推定器の変更——連想枠を既定ONにした）で、最小余白は`12.79→11.15字`、`1.6410256410256352字`動いた。**これは当時の余裕（`5.0632631257630765字`）の**32.41%**にあたる（`1.6410256410256352 / 5.0632631257630765 ≒ 0.3241`）。

この表・比率は、マネージャーが事前に示した値（最小余白12.79字/11.15字、差1.64字、消費32%）と、私が`git`とcoreの公開関数から独立に再導出した値が一致した。

#### 判断: この実測はFLOORの置き方を変える理由になるか

**ならない、といまは判断する。**

観測された唯一の事象は、これまでで最も大きな挙動変更（連想枠を既定ONにする、ADR 0168）でありながら、当時の余裕の32%しか消費していない。もしFLOORが「頻繁な意図した変更のたびに疲弊するほど脆い」水準に置かれているなら、この最大級の変更で余裕の大半——あるいは全部——を使い切っていてもおかしくないが、実際はそうならなかった。⟹ この1件の実測は、現行のFLOOR（`charsPerDigest/2`）の置き方を積極的に否定しない。

ただし、次の理由でこれを「解決した」とは書かない:

- **標本は1件である。**歴史上、余白を動かした事象はこの1回しか無い（上の`git log`が示す通り、両ファイルとも2回目のcommitがこの1つに一致する）。1件の実測から「この歯は疲弊しない」という一般的な結論は出せない。
- **方向の保証も無い。**今回はたまたま余白が「狭まる」方向に1.64字動いたが、次の変更が同じ方向に動く保証は無い——もし次も同程度狭まる方向に動けば、残り3.42字の余裕はほぼ使い切られる。広がる方向に動く可能性も同様に未確認である。

⟹ **いまは据え置く。ただし次にbaseline（`compare-baseline.json`または`recall-footprint.ts`の推定式）が動いたときに、この節を更新し、2件目の実測として数えること。**2件そろって初めて「頻度」や「典型的な消費率」について何か言えるようになる。

#### 残る未確認

- **標本が1件であること。**上記の通り、余白を動かした事象は歴史上1回しか観測されていない。「32%程度で収まる」が典型的なのか、たまたま今回がそうだっただけなのかは、この実測だけでは分からない。
- **この測定はhold-outだけが動いた場合の話である。**hold-in 7行（較正標本そのもの）が動いた場合は`charsPerDigest`/`fixedIndexChars`自体が動くため、FLOORも同時に動く——この測定が扱ったのは「較正係数が固定されたまま、hold-out側の実測だけが動いた」ケースに限られる。hold-in行が動いたときにFLOORと最小余白がどう連動するかは、この節では測っていない（引き受けた負債1がそもそもこのケースを「意味のある境界として扱えない」と留保している範囲と同じ）。
- **今後の変更が同じ性質（構造的な項の追加）を持つとは限らない。**今回の1件は「新しい自由係数を1つも足さない、既存の2項の組み替え」（ADR 0166）だった。将来、較正式自体を作り直すような変更が入れば、余白の動き方の性質も変わりうる。

## 確かめていないこと

- **hold-in行の自己参照を含めた「真の」最小余白**（引き受けた負債1）。frozen calibrationでの参考値（2ターン行upper 1.97字）は出したが、これが実際の意味のある境界かどうかは検証していない。
- **本番の会話パターンでの一般化**（ADR 0166の負債4・引き受けた負債2と同種）。この歯は`compare-baseline.json`の12行という固定標本に対してのみ意味を持つ。
- **CIの`example-chat`ジョブでこの歯が緑になること**（この作業環境ではDB不要のこの歯自体をローカルで検証したが、CI runでの確認はPR作成後にci-green-checkで行う）。
