# ADR 0139: `consolidation-cost` の「巨大な utterance」テストの間欠タイムアウトを直す — 支配的費用は `encode()` であり、同じ壁を kana 巡回文字列で越えると解消する（Issue #258）

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-15

**⚠ 各主張の出所を分ける。**「【実測】」と書いたものは**この作業でこの器から実行して取った**ものである。
「【推論】」は**コードを読んで導いた、実行していない結論**である。「【受領】」は
Issue #258 の記述をそのまま引いたもの。

---

## 結論

**`examples/chat/src/__tests__/consolidation-cost.postgres.test.ts` の「巨大な utterance」テストが
間欠的にタイムアウトしていた主因は、入力の大きさそのものではなく、その入力の
`tokenizer.encode()` 自体の計算コストだった。** 同じ 800 件の filler sentence（約 56,700 字・
13,493 トークン）を、8192 トークンの壁を越える別の文字列（`packages/local-embedding` の
live テストが既に使っている 46 字巡回パターン、12,000 字・9,392 トークン）に差し替えると、
**この作業env で `encode()` は平均約 42 秒 → 870ms（約 48 分の1）** になった。

**⟹ 案(B)（入力を壁のすぐ上まで縮める）を、より効く形（同じ壁をより安い文字列で越える）で採用し、
テスト固有のタイムアウトも 120,000ms → 60,000ms へ下げる（案(A)を弱く併用）。**
ゼロ（ファイル既定の 30,000ms）へは寄せない——**この作業env には Postgres が無く、
DB を含むこの検査自体の総所要時間を実測できていない**ため、CI のばらつきに対する
保険を明示的に残す。

## 1. 問い（[Issue #258](https://github.com/takecchi/mnemora/issues/258)）

**【受領】** 対象テスト（`consolidation-cost: 埋め込みの入力上限(ADR 0090)への着地` >
`巨大な utterance を observe すると embeddingStatus が failed になり、kind が
input_too_long と分かる`）が、与えられた 120 秒を超えて間欠的に赤くなる。CI 実測
（`run 34949320348` / sha `805038b`）: このテスト単体 `234,066ms`——与えられている
120 秒の約2倍。

Issue が挙げた3案（どれでも技術的に成立するので選んで理由を残す、という指示）:

- (A) タイムアウトを上げる
- (B) 入力サイズを下げる（8192 トークンの壁を越える最小入力を実測して使う）
- (C) この検査を `local` 埋め込みを使わない場所へ移す

## 2. 現物

### 2.1 【実測】この env には DB が無いが、`local` embedding の tokenizer 側は測れる

`which docker podman psql postgres initdb` はどれも無く、`DATABASE_URL` も未設定——
`*.postgres.test.ts` はこの env で1度も走らせられない。**一方、`@mnemora/local-embedding`
は外部サービスに繋がないプロセス内 ONNX 推論であり、モデルの重み（Hugging Face から）は
この env からダウンロードできた**（`MNEMORA_LIVE_LOCAL_EMBEDDING=1 pnpm --filter
@mnemora/local-embedding test` が 14/14 パス、42.46秒。この env と huggingface.co の間に
ネットワーク制限は無かった）。⟹ **DB を要する `observe()`/`tick()` の側は測れないが、
`tokenizer.encode()` の重さそのものは、本物のトークナイザに対して直接測れる。**

### 2.2 【実測】旧構成（800件の filler sentence）の `encode()` は平均約42秒

対象テストが実際に使っていた生成式をそのまま抜き出し、同じ固定バージョンの
トークナイザ（`@huggingface/transformers@4.2.0` に完全固定・`sirasagi62/ruri-v3-30m-ONNX`）
に対して直接 `encode()` を呼んだ:

```js
const hugeText = Array.from(
  { length: 800 },
  (_, i) => `filler sentence number ${i} with varying words to avoid token collapse.`,
).join(" ");
// chars=56,689, tokens=13,493
```

| 試行 | encode() 所要 |
|---|---|
| 1 | 41,885ms |
| 2 | 41,365ms |
| 3 | 42,926ms |

**平均約 42.1 秒。** CI 実測 234,066ms（Issue #258）とこの env の 42 秒には約 5.6 倍の開きが
あるが、**CI と この env のハードウェア差を測る手段がこの作業には無い**（本 ADR
「確かめていないこと」参照）。それでも、**この1つの `encode()` 呼び出しがテスト全体の
支配的な費用であることは、この後の 2.4 が示す通り明確に裏付けられる。**

### 2.3 【実測】入力を壁のすぐ上まで縮めても、同じ語彙構成では大きくは速くならない

同じ filler sentence 生成式で、8192 トークンをちょうど越える最小件数を二分探索で求めた:

| n（件数） | 字数 | トークン数 | 壁からの余裕 | encode() |
|---|---|---|---|---|
| 489（最小） | 34,608 | 8,206 | +14（+0.2%、危険なほど薄い） | 12.97〜14.52秒（5試行） |
| 520 | 36,809 | 8,733 | +541（+6.6%） | 15.93秒 |
| 550 | 38,939 | 9,243 | +1,051（+12.8%） | 18.30秒 |
| 600 | 42,489 | 10,093 | +1,901（+23.2%） | 22.34秒 |
| 800（旧・現行） | 56,689 | 13,493 | +5,301（+64.7%） | 平均42.1秒 |

⟹ **単に件数を減らすだけでは、字数に対してほぼ線形〜超線形にしか縮まらない。**
n=550（字数を旧の 31% まで削っても）で `encode()` はまだ 18.3 秒——120 秒には収まるが、
CI がこの env より遅い可能性を踏まえると余裕として十分か判断が難しい。

### 2.4 🔴 【実測】同じ壁を、別の文字列で越えると劇的に速い — 46字巡回パターン

`packages/local-embedding/src/__tests__/live.local-embedding.test.ts` は、8192トークンの壁を
「同じ文字の連打では BPE に圧縮されて壁を越えない」問題を避けるため、**46字の平仮名を
巡回させる文字列（`KANA_CYCLE`）**を既に使っている（同ファイルのコメント: 「巡回させて
連続する同一文字を無くすと、実測で増分が常に0か1になる」）。同じ手法を、この作業で
直接測った:

```js
const KANA_CYCLE =
  "あいうえおかきくけこさしすせそたちつてとなにぬねのはひふへほまみむめもやゆよらりるれろわをん";
function kanaText(n) {
  return Array.from({ length: n }, (_, i) => KANA_CYCLE[i % KANA_CYCLE.length]).join("");
}
```

| n（字数） | トークン数 | 壁からの余裕 | encode() |
|---|---|---|---|
| 11,500 | 9,002 | +810（+9.9%） | 732ms |
| **12,000** | **9,392** | **+1,200（+14.6%）** | **870ms** |

**12,000字・9,392トークンという、字数だけ見れば旧構成（56,689字）よりずっと小さいだけでなく
（21%）、filler sentence の n=550（38,939字・9,243トークン、同程度の余裕）と比べても
字数は多い（12,000 > … いや実際には 12,000 < 38,939 なので字数も少ない）のに、
`encode()` は 18,300ms → 870ms、**約 21 倍速い。**** 旧構成（56,689字・平均42.1秒）と比べれば
**約 48 倍速い。**

⟹ **この差を生んでいるのは字数でもトークン数でもない。**同程度の字数・同程度の
トークン数で比べても（n=550 の filler: 38,939字/9,243トークン/18.3秒 vs kana n=12,000:
12,000字/9,392トークン/0.87秒）歴然とした差がある。**【推論】** 46字が単調に巡回するだけの
文字列は、数字・多様な英単語が混在する文字列より、tokenizer の pretokenization
（正規表現によるトークン境界の切り出し）の計算コストが低いのではないか、と考えられるが、
**この作業ではプロファイリングして原因を特定していない。**

### 2.5 【実測】production の `buildLocalEmbeddingPipeline` を実際に通した

上の数字は生の `tokenizer.encode()` を単独で呼んだものだが、実際にテストが依存するのは
`packages/local-embedding/src/pipeline.ts` の `buildLocalEmbeddingPipeline`（本 ADR は
このファイルを一切変更していない）である。この関数を**変更せずにそのまま import**し、
本 PR が採用する文字列（kana, n=12,000）を渡すと:

```
[baseline] n=12000 tokens=9392
[baseline] -> kind=input_too_long
```

**期待どおり `input_too_long` を投げた。** 続けて、意図的に壁の下まで縮めた変異
（n=9,000 → 7,043トークン、壁の下）を同じ production 関数に渡すと:

```
[mutation] n=9000 tokens=7043
[mutation] -> no error (vector returned)
```

**例外を投げず、正常な形のベクトルが返った。** ⟹ **この変異(誰かが将来 `12_000` を
誤って壁の下まで縮める)が起きれば、`consolidation-cost.postgres.test.ts` の
`expect(memory?.embeddingStatus).toBe("failed")` は赤くなるはずである**——
**【推論】** これは `packages/core` の `processEmbedJob`(例外を捕まえて
`setEmbeddingStatus(ctx, memory.id, "failed")` を書いてから再送出する)の実装を
読んで導いた結論であり、**DB を含む実際のテストを走らせてこの赤化を観測したものではない**
（4節「変異試験について」参照）。

## 3. 決定

### 決定1: 入力を、filler sentence ではなく kana 巡回文字列に差し替える(案B、より強い形)

`examples/chat/src/__tests__/consolidation-cost.postgres.test.ts` の `hugeText` を、
800件の filler sentence(56,689字・13,493トークン)から、46字巡回・12,000字
(9,392トークン、壁から+1,200トークン/+14.6%の余裕)に差し替える。

**なぜ「最小の壁越え」(n=489, +14トークン)を採らないか。** トークン数はこの env で
固定バージョンの tokenizer に対して決定的だが(実行のたびに変わらない)、
**将来 `@huggingface/transformers` や参照モデルが変わったときに、14トークンという
マージンは薄すぎる。** +1,200トークン(+14.6%)は、2.4 で実測したとおり `encode()` を
870msに保ったまま、読みやすい安全マージンを残す。

**なぜ filler sentence を縮める(n=550等)ではなく、文字列そのものを変えるか。**
2.3 と 2.4 の比較(同程度の余裕で 18.3秒 vs 0.87秒)が示すとおり、**支配的費用を
本当に消せるのは文字列の差し替えのほうである。** 件数を減らすだけの案は、
劇的な改善を捨てて中途半端な改善に留まる。

### 決定2: テスト固有のタイムアウトを 120,000ms → 60,000ms へ下げる(案Aを弱く併用)

**ゼロ(ファイル既定の 30,000ms)へは寄せない。** 理由:

1. **この env には Postgres が無く、DB を含むこの検査自体の総所要時間を
   この作業では実測できていない。** `encode()` は 870ms まで縮んだが、
   `resetTestDatabase()`・`warmupLocalEmbedding()`(実際に1回 ONNX 推論を走らせる)・
   `observe()`・`tick()`・複数回の DB 問い合わせのオーバーヘッドは未知数である。
2. **CI がこの env よりどれだけ遅いかを測る手段がこの作業には無い**
   (2.2 の「約5.6倍」という開きは、旧構成の `encode()` 単体とテスト全体の総所要を
   比べた雑な比率であり、精密な換算係数ではない)。
3. ⟹ **支配的費用(`encode()`)を約48分の1にした事実は強い証拠だが、
   それだけで「120秒は要らない」と言い切るには、DB込みの実測が要る。**
   60,000ms は、旧値を全面的に信用しない(半分にする)一方、実測していない
   総所要への保険として、ファイル既定(30,000ms)より高い値を残す、という妥協である。

### 決定3: 他の2箇所の `120_000`(CLI wiring テスト)には触れない

同ファイルには他に2箇所 `120_000` がある(サブコマンドの配線を検査するテスト、
`timeout: 120_000` と `}, 120_000);`)。**この PR ではどちらも変更しない。**

- **Issue #258 が挙げた実測(234,066ms)は、この PR が直す「巨大な utterance」テスト
  単体のものであり、CLI wiring テストの実測ではない。**
- **CLI wiring テストは、`haystackSize=60`・`groupSize=5` で実際に複数 round の
  `consolidate()` を回し、そのたびに本物の `local` embedding で複数件を推論する**
  (`json.embeddingMode === "local"` を assert している)。**これは「巨大な1入力を
  encode() する」というこの ADR の対象とは全く別の費用構造(複数件の実推論)であり、
  本 ADR の実測(2.1〜2.5)はその費用には触れていない。**
- ⟹ **証拠の無い変更をしない。**1 PR = 1 ADR の原則により、CLI wiring テストの
  タイムアウトが妥当かどうかは、必要なら別の issue・別の ADR で扱う。

### 却下した案

**案(A)単独(タイムアウトだけを 300 秒等へ上げる)。** 却下——支配的費用
(`encode()` 平均42秒)をそのまま残すと、テストが遅いという事実そのものが残り、
CI 全体の最悪所要時間が伸び続ける。Issue 自身も「最も安いが、遅いという事実は
残る」と明記している。

**案(C)(この検査を `local` 埋め込みを使わない場所へ移す)。** 却下。

- **【推論】`input_too_long` の判定は、本物のトークナイザの `model_max_length` と
  `encode()` を必要とする**(`packages/local-embedding/src/pipeline.ts` の
  `buildLocalEmbeddingPipeline` は `extractor.tokenizer.encode(text).length` を
  直接比較しており、擬似のトークンカウンタでは代替できない)。ADR 0090 §3.3 が
  既にこの代替案(`@mnemora/core` の `TokenCounter` で代用する)を「誤検出率を
  測れない門は置かない」として却下している——この PR で蒸し返さない。
- **対象テストの docstring 自身が、このテストの役割を「`local` embedding が要る。
  実物」と明記している**(ファイル冒頭のコメント「2. ADR 0090 の `input_too_long` が
  実際に `embeddingStatus:"failed"` へ着地し、`outbox.last_error` から `kind` を
  読めること」)。**擬似トークナイザで判定ロジックだけを検査する非DBテストは
  既に別に存在する**(`packages/local-embedding/src/__tests__/input-token-limit.test.ts`)。
  ⟹ **この postgres テストの独自の価値は、「本物のトークナイザ」×「本物の
  Postgres/outbox/Memory」という統合が実際に噛み合うことであり、`local` を
  外すとその価値そのものが消える。**

## 4. 変異試験について(⚠ 構造的に塞がっている)

`docs/autonomy.md` §2 は「歯が実際に噛むことを、変異試験で示した」を要求するが、
**この env には DB が無い**(`which docker podman psql postgres initdb` は全部無く、
`DATABASE_URL` も未設定)。⟹ **`consolidation-cost.postgres.test.ts` はこの作業で
1度も走らせられていない**(Issue #247 / alteroid #965 / alteroid #1015 と同じ族の穴)。

**DB を要さない層でできる分は行った**(2.5 節):

- 本 PR が採用する文字列(kana, n=12,000)を、変更していない production の
  `buildLocalEmbeddingPipeline` に**実際に**通し、`kind: "input_too_long"` が
  投げられることを確認した(【実測】)。
- 意図的に壁の下まで縮めた変異(n=9,000)を同じ関数に通すと、例外が投げられず
  正常な形のベクトルが返ることを確認した(【実測】)——これは「歯が噛まなくなる」
  条件が実際に存在することの確認である。

**しかし、この変異が `consolidation-cost.postgres.test.ts` 自体を実際に赤くすることは
確認していない。** 「`processEmbedJob` が例外を捕まえて `embeddingStatus` を `failed`
にする」という連鎖は、`packages/core/src/runtime.ts` を読んで導いた**推論**であり、
**DB を通した実験ではない。** ⛔ **論理的に自明だから不要、とは書かない**——
上の一文がその区別(導出と実験を分ける)そのものである。

**CI は draft PR でも本物の Postgres + pgvector の段を走らせる**(ADR 0132)。
⟹ **この PR に関する限り、`consolidation-cost.postgres.test.ts` の赤/緑を最初に
確認できるのは CI である。**

## 5. 結果(この決定が招くもの)

- **`encode()` の費用が、この env の実測で平均約42秒から870msへ、約48分の1になった。**
  CI がこの env と同程度に反応するなら、テスト全体の所要時間も大きく縮むはずである
  (未確認。上記「確かめていないこと」参照)。
- **テスト固有のタイムアウトが 120,000ms から 60,000ms に下がる。** DB込みの
  総所要が予想より大きければ、この値でも間欠的に赤くなる可能性が残る——
  そのときは「これが覆るとしたら」節へ。
- **CLI wiring テスト(2箇所の `120_000`)は変更していない。**

## 6. 引き受けた負債

1. **60,000ms という値は、DB を含む総所要を実測せずに選んだ妥協である。**
   支配的費用(`encode()`)の削減幅(約48分の1)は強い実測に基づくが、
   タイムアウトの具体的な数字そのものは推測を含む。
2. **なぜ kana 巡回文字列が filler sentence より `encode()` が速いのか、
   原因を特定していない**(2.4 の【推論】)。プロファイリングしていないため、
   `@huggingface/transformers` の将来のバージョンでこの差が縮む・逆転する
   可能性を排除できない。
3. **この PR の変異試験は、tokenizer/pipeline 層に閉じている**(4節)。
   `consolidation-cost.postgres.test.ts` 自体の赤→緑は CI でしか確認できない。
4. **CLI wiring テスト(120_000 が2箇所)のタイムアウトの妥当性は、この PR の
   範囲では評価していない。** 同じ族の間欠性を持つ可能性はあるが、証拠が無い。

## 7. これが覆るとしたら

- **CI が、本 PR 適用後もこのテストを 60 秒近く、またはそれ以上要すると示したとき。**
  そのときはタイムアウトをさらに引き上げるか、入力をさらに精査する必要がある。
- **CI のハードウェアがこの env より大幅に遅く、`encode()` の削減効果が
  相殺されるほどだと分かったとき。** 2.2 節の「約5.6倍」という粗い比率が、
  精密な換算として使えないことが本当に問題になる。
- **`@huggingface/transformers` や参照モデル(`sirasagi62/ruri-v3-30m-ONNX`)が
  変わり、kana 巡回文字列のトークン数・`encode()` 費用が変わったとき。**
  2.4 の数字を再測定する必要がある。
- **Issue #247(この作業環境に DB が無い構造的な穴)が解消され、この postgres
  テストをこの種の作業env で直接走らせられるようになったとき。** そのときは
  4節の変異試験を DB込みで完走し、この ADR に追記すべきである。
- **CLI wiring テストの2箇所の `120_000` が、同じ族の間欠性を示す実測が
  得られたとき。** そのときは別の issue/ADR として扱う。

## 8. 測ったこと

- **【実測】** この env から huggingface.co へのネットワーク到達性
  (`curl -sI https://huggingface.co` → `HTTP/2 200`)。
- **【実測】** `MNEMORA_LIVE_LOCAL_EMBEDDING=1 pnpm --filter @mnemora/local-embedding test`
  が 14/14 パス(42.46秒)——本物のモデルをこの env からダウンロードして推論できることの確認。
  この中で、既存の live テストが実測している「8192トークン=10,469字/8193トークン=10,470字」
