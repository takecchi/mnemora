# ADR 0305: `ts_rank_cd` の normalization に文書長のビットを足す — 語彙チャンネルの `rank` に内容由来の分解能を持たせる（Issue #394 案2）

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-25

**⚠ 各主張の出所を分ける**（ADR 0175 / ADR 0294 の体裁を踏む）。

- **【実測】** — この ADR の作業者（クローンの委譲で動くマネージャーのセッション、
  `mgr-c4687378`）が、手元に `initdb` で自前に立てた PostgreSQL 17.11 + pgvector 0.8.0
  （非特権ユーザ、AGENTS.md の手順）に対して自分の手で走らせて確かめた。
- **【現物】** — この repo のコード・文書を読んで確かめた。
- **【受】** — Issue #394 本文・コメント、ADR 0092/0175/0294 の記述を出典として引く。

## 文脈

[Issue #394](https://github.com/takecchi/mnemora/issues/394) は、語彙チャンネルの
`coverage`/`rank`（`packages/postgres/src/lexical-store.ts` の `buildLexicalSearchSelect`）
に**内容由来の分解能が無い**ことを報告した。20,000行の合成 fixture
（`lexical-store-index.test.ts` の `seedManyMemories`）で、クエリ `obsidian shards` に
ヒットする400行が全部 `coverage=1`・`rank=0.16666667` で完全同点になり、`LIMIT 50` が
その400件のタイから50件を「新しい順」（ADR 0175 の tie-break）で選んでいた。

Issue 本文「次に測るべきこと」は4案を並べ、**取り扱い**（v1.0 を止めるか・どの案を
採るか）はオーナー判断だが、**測ることは repo の中で発注できる**とクローンが整理した
（Issue #394 コメント、2026-09-17）。[ADR 0294](./0294-lexical-tie-density-bench.md)（本
ADR と同じ作業者）が案1（`retrieval` ベンチでのタイ密度測定）を実行したが、**probe 集合
が日本語のみで語彙チャンネルの候補を1件も生まないため、実データでのタイ密度は
「測れなかった」**と結論した。

**本 ADR は案2**（`ts_rank_cd` の引数を変えると分解能が上がるかを測る）**を実行する。**
案3（rank 以外の分解能項を足す。⚠ Issue 本文が「段2の再スコアが既に持っているものと
重なる可能性がある、先に見ること」と留保していた）については、下記
「案3との重なりについて」で前提確認だけ行い、実装はしない——本 ADR が案2で十分な
効果を測れたためである。

---

## 決めたこと

### 決定1: `TS_RANK_CD_NORMALIZATION` を `32` から `32 | 1`（`33`）にする

`packages/postgres/src/lexical-store.ts`:

```diff
-const TS_RANK_CD_NORMALIZATION = 32;
+const TS_RANK_CD_NORMALIZATION = 32 | 1;
```

PostgreSQL の `ts_rank_cd` normalization ビット（textsearch-controls）:

- `32`（既存）: `rank` を `rank / (rank + 1)` で割り、(0, 1) に収める。読みやすさのため。
- `1`（今回足す）: `rank` を `1 + ln(文書の長さ)` で割る。**文書が長いほど rank が下がる**
  ——`ts_rank_cd` は既定でクエリ語どうしの近接度（cover density）しか見ておらず、
  周囲にどれだけ無関係な語が続いても値が変わらない。`1` を足すことで、初めて
  「同じクエリ語を含むが、その他の内容量が違う」という差が `rank` に反映される。

**`LexicalHit.coverage` / `ScoreBreakdown.lexicalMatch` は変えていない。** `rank` は
段2のスコアに入らない値であり（下記「案3との重なりについて」）、この変更が動かすのは
`buildLexicalSearchSelect` の `ORDER BY`/`LIMIT` による**段1の切り詰め**だけである。
公開 API・`RecalledMemory`/`ScoreBreakdown` の型・契約は1バイトも変えていない。

### 決定2: 新設の歯を1本足す（`lexical-rank-resolution.test.ts`）

`packages/postgres/src/__tests__/lexical-rank-resolution.test.ts`（新設、3件）:

1. 被覆率が同じ短文（`"obsidian shards"`）と長文散漫な文（同じ2語を含む292字の英文）の
   `rank` が割れることを検査する。**直す前は赤**（両方 `rank=0.16666667` で完全同点）。
2. 内容が真に同一な行どうしは、直した後も完全に同点のままであることを検査する
   （ADR 0175 の tie-break 契約——`coverage`/`rank` が完全一致する行の順序は
   `recorded_at`/`id` が引き継ぐ——を壊していないことの確認）。
3. 20,000行 seed と同じテンプレート構造（末尾の整数だけが違う）の行が、直した後も
   同点のままであることを検査する（**「直っていない」ことを主張する歯**——後述
   「20,000行 seed のタイは今も割れない」参照）。

## 測定

### 1. 【実測】直す前（`normalization=32`）: 被覆率が同じでも内容量が違う文が完全同点だった

`obsidian shards` にヒットする4種の英文（すべて `coverage=1`、クエリ2語が本文中で
隣接して一致する）:

| label                                                                 | 文字数 | `rank`（`norm=0`） | `rank`（`norm=1`） | `rank`（`norm=2`） | `rank`（`norm=32`、直す前） | `rank`（`norm=33`、直した後） | `rank`（`norm=34`） |
| --------------------------------------------------------------------- | -----: | -----------------: | -----------------: | -----------------: | --------------------------: | ----------------------------: | ------------------: |
| `obsidian shards`                                                     |     15 |                0.2 |         0.18204784 |                0.1 |              **0.16666667** |                **0.15401056** |          0.09090909 |
| `The obsidian shards glimmer brightly.`                               |     37 |                0.2 |        0.111622125 |               0.04 |              **0.16666667** |                **0.10041373** |          0.03846154 |
| （長文散漫、292字。「obsidian shards」を1回含むが大半は無関係な内容） |    292 |                0.2 |        0.052539464 |       0.0045454544 |              **0.16666667** |                **0.04991686** |         0.004524887 |
| （長文散漫2、228字。同上）                                            |    228 |                0.2 |        0.053856503 |              0.005 |              **0.16666667** |                **0.05110421** |        0.0049751243 |

**⟹ `norm=32`（直す前）は4種すべてが完全同点（`0.16666667`）。** `norm=33`（採用）は
15字〜292字まで単調に分かれる（`0.154 → 0.100 → 0.050 → 0.051`。292字と228字は近い
長さなので順序が拮抗するが、両方とも短文2種より明確に低い）。

### 2. 【実測】`1`（対数）と `2`（線形）の比較 — `1` を選んだ理由

同じ4種の対比較で、`2` は短文とlong-diffuseの比が**約22倍**（`0.1 / 0.0045`）に開くのに
対し、`1` は**約3.5倍**（`0.182 / 0.053`）に収まる。`rank` は「同一クエリ・同一 adapter
内でのタイブレークにしか使わない値」（`LexicalHit.rank` の doc、ADR 0084 §5）であり、
段2のスコアには入らない——**極端な傾斜を持ち込む理由が無い**ため、対数（`1`）を採った。

### 3. 【実測】内容が真に同一な行は、直した後も完全同点のまま（ADR 0175 の契約を壊さない）

同一 `content`（`"widget alpha bravo tie-break resolution content"`）を持つ2行に対して
`coverage`/`rank` が完全一致することを、`lexical-rank-resolution.test.ts` の歯2で確認した
（`norm=33` でも同じ——文書長が同一なら normalization の追加は何も変えない）。

### 4. 【実測】20,000行 seed のタイは今も割れない — これは退化ではない

`lexical-store-index.test.ts` の `seedManyMemories` と同じテンプレート
（`'obsidian shards glimmer in seed content ' || i`）を、末尾の桁数が1桁（`i=0,7`）〜
5桁（`i=19950`）まで揺れる5行で作り、`norm=33` で `rank`/`coverage` を比べた——**5行とも
完全同点のまま**だった。

理由: `to_tsvector('simple', ...)` は末尾の整数を、桁数に関わらず**1語彙**として数える
（`'50'` も `'19950'` も、tsvector 上ではそれぞれ1個の lexeme）。⟹ 文書の**長さ
（lexeme 数）は5行とも同じ7語のまま変わらない**——文字数は41〜45字と揺れるが、
`ts_rank_cd` の文書長 normalization は lexeme 数を見るため、この差を検出しない。

実際に確認した数値（`psql`、`tmp_seed` に20,000行 seed の「ヒットする400行」と同じ
テンプレートを400行分入れて測定）:

```
n=400, distinct_lengths(文字数)=5, min_len=41, max_len=45
norm32: distinct_ranks=1
norm1:  distinct_ranks=1
norm33: distinct_ranks=1
norm2:  distinct_ranks=1
norm34: distinct_ranks=1
```

**⟹ Issue #394 本文が実測した20,000行 seed の400件同点は、今回の変更でも割れない。**
これは Issue 本文が既に明記していた通りである——「末尾の整数だけが違う、機械的に
複製した seed であり、どんな内容由来の項でも割れない（割れないのが正しい）」。
真に同一な内容の重複は、依然として ADR 0175 の tie-break（`recorded_at DESC, id`）が
引き受ける。

### 5. 【実測】日本語本文に埋もれた ASCII 識別子（ADR 0084 の主要ユースケース）では、効果が限定的

ADR 0084 が報告者の主目的として挙げた形——日本語の文に埋もれた1個の ASCII 識別子
（`PROJ-1234` 等）——で同じ実験をした:

| label                                            | 文字数 | lexeme 数 | `rank`（`norm=32`、直す前） | `rank`（`norm=33`、直した後） |
| ------------------------------------------------ | -----: | --------: | --------------------------: | ----------------------------: |
| 短い日本語文（33字、`PROJ-1234` を1回含む）      |     33 |         4 |                  0.09090909 |                   0.058498763 |
| 長く散漫な日本語文（159字、同じ識別子を1回含む） |    159 |         5 |                  0.16666667 |                   0.087740794 |

**⚠ ここでは「短文のほうが高くなる」効果がほとんど出ない。** `norm=32` の時点で
既に短文(0.091) < 長文(0.167)——直す前から同点ではなく、**むしろ長文のほうが高い**。
理由: 日本語はスペースを持たないため、`to_tsvector('simple', ...)` はひとまとまりの
非 ASCII の連なりを**1個の巨大な lexeme**として数える（ADR 0084 §2.1.1「日本語の残り
全体が1つの語彙になる」と同じ機序）。⟹ 短文=4 lexeme・長文=5 lexeme と、lexeme数の
差がわずか1個しか無く、文書長 normalization がほとんど効かない。

`norm=33` でも順序は変わらない（短文 0.058 < 長文 0.088。**向きは反転していない**——
`1` を足したことで両方とも値が下がるが、比率はほぼ保たれる）。

**⟹ 本 ADR の効果は、クエリ語が複数かつ内容量の差が lexeme 数として現れる場面
（ASCII の自然文どうしの比較。§1 の実験）に主に効く。ADR 0084 の主要ユースケースである
「日本語本文に埋もれた単一 ASCII 識別子」では、目立った分解能の向上にならない。**
ただしこのユースケースは、そもそも `norm=32` の時点で完全同点ではなかった
（cover density が1語だけの一致でも文書ごとに多少割れる)——Issue #394 が指した
「完全同点」の穴は、**クエリ語が複数かつ本文中の一致位置が文書間で同じ相対構造を持つ**
ときに起きる現象であり、その条件に本 ADR は直接効く。

### 6. 【実測】ADR 0294 のベンチ（`lexical-tie-density-bench`）の数字は変わらなかった

`norm=33` を入れた状態で `pnpm --filter @mnemora/example-chat run lexical-tie-density-bench`
を再実行した。**ADR 0294 に記録された数字と完全に一致した**——陽性対照
（`control:quartz-lantern`、`quartz lantern echoes near meridian gate marker <n>`、
`n=1..5`）は今回も総候補数5・タイ集団数1・`LIMIT 3` で分断、probe 7件は今回も総候補数
合計0、`ascii:TypeScript`/`ascii:Rust`/`ascii:Go`/`ascii:combined` も同じ数字だった。

理由: 陽性対照の `<n>` は`1`〜`5`の**単一桁**であり、5行とも文字数が同一——§4 と同じ
機序で、文書長 normalization を足しても影響が無い。probe/ascii 側は候補数がそもそも
0〜2件で、タイの有無を判定する母集団に達していない（ADR 0294 決定4・「分かったこと」
節がそのまま当たる）。**⟹ ADR 0294 の本文を書き換える必要は無い**
（`docs/decisions/README.md`「採用済み ADR の本文は書き換えない。訂正が要るなら、
その場に追記する」の適用——今回は訂正すら要らない。数字が実際に一致したため）。

## 案3との重なりについて（Issue 本文の留保への回答）

Issue #394「次に測るべきこと」3番には次の留保が付いていた:

> 語彙チャンネルのスコアに、`rank` 以外の分解能を持つ項（freshness 以外の、内容に依る項）
> を足すことを検討する。⚠ これは段2の再スコアが既に持っているものと重なる可能性がある
> ——先に段2で何が効いているかを見ること。

**【現物】確認した結果、`rank` は段2のスコア（`ScoreBreakdown`/`total`）に一切入らない**
（`packages/core/src/interfaces/lexical-store.ts` の `LexicalHit.rank` の doc、
`packages/core/src/recall.ts` の該当コメント、ADR 0084 §5）。段2が使うのは `coverage`
（`ScoreBreakdown.lexicalMatch` にそのまま入る、ADR 0092）だけである。`rank` は
`PostgresLexicalStore.search` 内の `ORDER BY`/`LIMIT` でしか使われず、段2に届く前に
adapter 内で消費される。

**⟹ 本 ADR（案2、`ts_rank_cd` のパラメータ調整）は、段2の再スコアと重ならない。**
案3が本当に警戒していたのは「`rank` をスコアの新しい項として足す」形の実装だったはずで
あり、それは今回行っていない——`rank` の**値そのものの分解能**を上げただけであり、
`rank` が新しくスコアへ入るようにはしていない。**⟹ 前提確認は完了し、重なりは無いと
分かった。**案3（スコアに新しい項を足す）自体は本 ADR の範囲外のままである。

## 検討した代替案

- **`2`（文書長そのもので割る、線形）を採る。** **採らない**（測定2番。短文と長文散漫の
  比が約22倍まで開き、`rank` の役割（同一 adapter 内のタイブレークのみ）に対して
  傾斜が強すぎる）。
- **`8`/`16`（一意語数で割る）を試す。** **この ADR では測っていない。** 一意語数は
  lexeme の重複（同じ語の繰り返し）を無視する点で `1`/`2` と性質が違うが、Issue #394 の
  核心（クエリ語が隣接する限り周囲の語数を見ない）には `1`/`2` と同じ理屈で効くはずで
  あり、`1` で十分な分解能が測れたため優先度を落とした。次に拾う人へ残す。
- **IDF（文書頻度の逆数）を足す。** **採らない**（ADR 0092「検討した代替案」が既に
  同じ理由で却下している——`tsvector`/`ts_rank_cd` は文書頻度の統計を持たず、別の
  索引が要る。本 ADR の範囲外）。
- **`coverage` の分解能を上げる（分母・分子の数え方を変える）。** **採らない。**
  `coverage` は `ScoreBreakdown.lexicalMatch` にそのまま入り段2のスコア・順序を直接
  動かす値であり（ADR 0092）、変えると「既定挙動が変わる」範囲が `rank`（adapter 内部の
  tie-break）よりずっと広がる。マネージャーの指示（既存利用者の既定挙動が『同点の並びが
  新しい順→関連順』を超えて変わるものは提起して止まる）に照らし、この ADR では触れない。
- **段2のスコアに `rank`（または類する内容由来の項）を新しく足す（Issue 案3）。**
  **採らない**（上記「案3との重なりについて」)。前提確認の結果、`rank` は元々スコアに
  入っておらず、本 ADR（案2）で必要な分解能が測れたため、案3に進む理由が無い。
- **何もしない（案4）。** **採らない。** Issue #394 が実測したのは「合成 seed の特殊な
  重複」だけではない——§1 の実験が示す通り、**内容が真に異なる ASCII の英文どうしでも
  `norm=32` は完全同点を作る**。これは語彙チャンネルを明示的に有効化した呼び出し側に
  対して、実際に「新しさだけで選んでいる」状態を作りうる構造的な欠陥であり、修正の
  コスト（定数1個の変更、SQL 関数呼び出しのコストは変わらない）に対して見送る理由が
  無いと判断した。

## 引き受けた負債

- **🔴 真に同一な内容の重複は、今も完全同点のまま。** ADR 0175 の tie-break
  （`recorded_at DESC, id`）がその残余を引き続き引き受ける。20,000行 seed の400件も
  今回の変更の対象外のまま（測定4番）。
- **🔴 日本語本文に埋もれた単一 ASCII 識別子（ADR 0084 の主要ユースケース）では、
  効果がほとんど無い。** 日本語が少数の巨大 lexeme に潰れるため、文書長 normalization
  の分母がほとんど動かない（測定5番）。
- **`retrieval` ベンチでの実データに対するタイ密度・`hit@1`/`MRR` への影響は、依然として
  測れていない。** [ADR 0294](./0294-lexical-tie-density-bench.md) が指摘した壁
  （probe 集合が日本語のみで語彙チャンネルの候補を生まない）は本 ADR の範囲では解消
  していない——本 ADR は「`rank` の計算自体に分解能を持たせる」ミクロな修正であり、
  `retrieval` ベンチの corpus/probe 集合という別の壁には手を付けていない。
- **`8`/`16`（一意語数 normalization）は測っていない**（検討した代替案）。
- **大規模テナント（数万行以上）での `ts_rank_cd` 呼び出しコストの変化は測っていない。**
  normalization ビットを1つ増やしても計算式自体の複雑さは大きく変わらないと見ているが、
  実測はしていない。
- **英語の自然文どうしの比較以外の言語・構成は測っていない**（例: 中国語・韓国語の
  分かち書き挙動。ADR 0084 §11 と同じ限界を引き継ぐ）。

## これが覆るとしたら

- **実運用で「長い記憶のほうが重要」という逆方向の選好が確認されたとき。** 本 ADR は
  「短く焦点が合っている方を残す」方向を選んだが、これは Issue #394 の実測（cover
  density だけでは内容量の差が一切反映されない）に対する**分解能を持たせる**ことが
  目的であり、方向そのものへの実証的な裏付けは無い。**⟹ 方向を反転させる、あるいは
  重みを調整する再検討がありうる。**
- **`retrieval` ベンチの corpus/probe 集合が拡張され、語彙チャンネルの候補が実際に
  非0件になったとき。** そのとき初めて、本 ADR の変更が `hit@1`/`MRR` にどう効くかを
  実測できる（ADR 0294「これが覆るとしたら」と同じ条件）。
- **日本語本文に埋もれた単一識別子のユースケースで、分解能不足が実害として報告された
  とき。** 測定5番の限界に対する追加の手当て（例: 一意語数 normalization、あるいは
  日本語の分かち書き導入——ADR 0084 §11 と同じ条件）を再検討すること。
- **IDF、あるいは文書頻度の統計を持つ別の索引を足す決定がされたとき。** そのときは
  `rank` の計算式そのものを見直すか、`coverage` 側の設計変更と合わせて再判断する
  （ADR 0092「これが覆るとしたら」と同じ条件）。

---

## 確かめていないこと

- **`retrieval` ベンチでの `hit@1`/`MRR` への影響。** ADR 0294 が指摘した壁が残ったまま
  であり、本 ADR も解消していない。
- **大規模データでの実行コストの変化。**
- **`8`/`16` normalization ビットとの比較。**
- **CI（GitHub Actions の Postgres service container）での再現性。** 測定はすべて
  手元の `initdb` インスタンス（PostgreSQL 17.11 + pgvector 0.8.0）で行った——
  ADR 0167/0170/0175 と同じ限界を引き継ぐ。
- **v1.0 を止めるか、Issue #394「次に測るべきこと」の他の案（1・4）をどう扱うかは、
  この ADR の範囲外である。** オーナーの判断に委ねる（Issue #394 本文・コメントの
  区分をそのまま引き継ぐ）。この ADR が閉じるのは案2だけである。
