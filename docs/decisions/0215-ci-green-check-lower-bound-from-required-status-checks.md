# ADR 0215: 「CI が緑」の下限を、branch protection の required status checks から取る（Issue #477 と同じ族）

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-17

**⚠ 各主張の出所を分ける**（[ADR 0210](./0210-root-test-gate-runs-all-stages-regardless-of-failure.md) と同じ体裁）。

- **【現物】** — この repo のコード・文書・設定を書き手が読んで確かめた。
- **【実測】** — この書き手が自分の手で走らせて確かめた。
- **【受】** — 書き手が報告として受け取っただけで、自分では確かめていない。

---

## 問い

**`scripts/ci-green-check.mjs` は、どういう条件で「緑」と答えてよいか。**

この道具は「マージしてよいか」の唯一の機械的な根拠である（[docs/autonomy.md](../autonomy.md) §2.1・[ADR 0132](./0132-ci-green-verdict-procedure.md)）。
⟹ **この道具が外れると、外れたことに誰も気づけない。**

## 🔴 この ADR は、誤った報告から始まった — それも記録する

**【受】2026-09-17 の夜、次の報告を受け取った**（逐語に近い）:

> `ci-green-check.mjs` が、push 直後に check-runs が1件も登録されていない窓で `exit=0`（緑）を返した。

**⟹ この報告は誤りだった。【実測】現物では再現しない。**

| 撃ち方 | 母集合 | 結果 |
| --- | --- | --- |
| 実在の0件 sha（CI 導入前の最初期 commit） | 3 sha | 3件とも `exit=2` |
| 偽の `gh` を `PATH` に置いて空応答を食わせる | 1 | `exit=2` |
| `verdict([])` を直接呼ぶ | 1 | `status=pending` |
| 0件 sha に `--recheck-after` / `--json` を付ける | 2 | どちらも `exit=2` |
| 存在しない sha / 壊れた JSON / 空 `--sha` / 不明な引数 | 4 | すべて `exit=3` |

**【現物】`scripts/ci-green-check-lib.mjs` の `verdict()` は、最初の分岐で `total === 0` を
`pending` にしている**（逐語）:

```js
if (summary.total === 0) {
  return {
    status: "pending",
    reason: "check-runs が0件——まだ登録されていない可能性がある（Issue #228 観測1）",
    summary,
  };
}
```

**【実測】この分岐を縛る歯も既に在り、通っている**（`scripts/__tests__/ci-green-check-lib.test.mjs`
と `ci-green-check.test.mjs` の2ファイルだけを走らせて `13 passed`）。

**⟹ 「0件で緑」は偽である。** ⛔ **この節を後から削らないこと。**
削ると、次に同じ報告を受け取った人が、同じ場所をもう一度掘る。

## ⭐ しかし、隣に本物の穴が在った — 破れていたのは *部分登録* である

**【実測】`verdict()` を直接呼んで撃った**（同じ器・同じ `main` = `798534f`）:

| 入力 | 判定 |
| --- | --- |
| 0件 | `pending` ← ガード在り |
| **1件だけ登録・それが `success`** | **`green`** |
| **13件中3件だけ登録・全部 `success`** | **`green`** |
| 2件登録・1件が `in_progress` | `pending` |

⟹ **ガードが在るのは `N = 0` のときだけで、`1 ≤ N <（本来の本数）` には無い。**
`green` の reason が言う「N件すべてが completed かつ success」の **N が、何にも縛られていない。**

### 🔴 処方が外れた形 — これも記録する

**【受】報告を受け取った側（依頼者）は、それを信じて次の処方を出した**（逐語）:

> 検査に下限を添える: 「失敗が0件」ではなく **「N ≥ 1 件あって、そのN件すべてが completed かつ success」**。

**⟹ この処方では塞がらない。** `N = 1` は `N ≥ 1` を満たすので、上の表の2行目は**処方を当てた後も緑のままである。**

**外れた形を、依頼者自身の言葉で残す**（逐語）:

> **報告されたのは「0件で緑」だった。私はそれを信じて「下限を添えよ（N≥1）」と処方した。**
> ⟹ **0件ガードは既に在り、破れているのは*部分登録*だった。**
> ⛔ **私は下限を*最小値*に置いたので、原因の形を取り違えていた。**

⭐ **症状の報告が1つ誤っていると、処方は「効かない」ではなく「効いたように見える」側へ外れる。**
N≥1 を実装して「下限を添えた」と記録すれば、**窓は開いたまま、記録だけが閉じる。**

## ⭐ 一般の形 — 3つは別の命題である

- **「失敗が0件」** — `nonSuccess.length === 0`。⚠ 対象を1件も取れていなくても真になる。
- **「成功がN件」** — `total === N && allSuccess`。⚠ N が何にも縛られていなければ、
  `N = 1` でも真になる。**0件ガードはこの命題の下端を1つ上げるだけで、上端を縛らない。**
- **「*期待する集合*が全部在る」** — 外から与えた集合 ⊆ 実際に在る集合。
  **これだけが「測り損ねていない」を言える。**

⟹ **0件ガードは3番目の代用にならない。** `Array.prototype.every` が空配列に真を返す形
（この repo では [Issue #477](https://github.com/takecchi/mnemora/issues/477) が
`compare-summary-lib.mjs` の `computeRegressions()` に同じ族を見つけている）と、
**根は同じだが、破れる場所が違う**——あちらは母集合が空、こちらは母集合が*まだ揃っていない*。

### 【実測】部分登録の窓は、理屈ではなく実在する

**【現物】`.github/workflows/ci.yml` の `postgres-regime-coverage` は `needs: postgres` を持つ。**
⟹ 依存元が終わるまで、この job の check-run は API に存在しない。

**【実測】直近の `main` 30本**について、13本目の登録時刻と他12本の最終完了時刻を突き合わせた:

- **7本で、他12本が全部 `completed` かつ `success` になった後に13本目が登録されている。**
  ⟹ その瞬間に引けば **12/12 で緑**——本来13本のうち1本を見ていない。
- **窓の幅**: その **7本すべて**について job の `created_at` まで降りて測り、**最大1秒**
  （0秒が5本・1秒が2本。秒精度なので実体は2秒未満）。

⚠ **「窓は常に1秒未満である」とは言っていない。** これは `needs:` に由来する窓を、
push トリガの run について30本の標本で測った値である。他の由来（workflow の queue 遅延、
複数 workflow の登録ずれ、API の一時的な不整合）は**測っていない。**

### ⭐ 決め手 — 遅れて登録される当の1本が、required に入っている

**【実測】`gh api repos/takecchi/mnemora/branches/main/protection`** が返す
`required_status_checks.contexts` は **6件**で、その中に
**`両方の server_encoding regime が実際に走ったことを測る (Issue #155)`**——
**`needs: postgres` を持つ、まさに遅れて登録される当の1本**——が含まれている。

⟹ **下限を required の集合に置けば、実測した窓はちょうど閉じる。**

## 検討した選択肢

### 案A: 下限を「N ≥ 1」にする（依頼者の当初の処方）

⛔ **採らない。** 上のとおり `N = 1` で素通りする。**下限を*最小値*に置くと、
「測り損ねた」と「本当に1本しか無い」を区別できない。**

### 案B: 期待する本数（13）を焼き込む

⛔ **採らない。** ジョブは増減する（【実測】今夜の着地81件のうち2件は publish の1本が乗って
14件だった）。**この repo は、出荷物に数を焼き込まない線を既に引いている**——
`PUBLISH_TARGETS` も公開 API の破壊的変更の件数も、機械が数える側に置いてある。

### 案C: `--recheck-after` を既定で有効にし、名前集合が2回一致するまで緑を出さない

⛔ **採らない。** **`compareCheckRunNameSets` の docstring 自身が「もう増えないことの証明では
ない」と明記している**【現物】。⟹ これは**窓を狭めるだけで、閉じない。**

🔴 **狭めただけの対策を「塞いだ」と記録すると、次の人は塞がっていると思って乗る。**
「回避策が*在る*」は「回避策が*効く*」ではない。
⟹ ⭐ `--recheck-after` は**残す**（Issue #228 観測1 への診断として今も有用である）が、
**下限の役は負わせない。**

### 案D（採用）: 下限を branch protection の `required_status_checks.contexts` から取る

⭐ **これだけが、下限を*外部の権威*から取る。** ハードコードでも、この道具の思い込みでもない。
⭐ そして**意味が合っている**——`required_status_checks.contexts` は
**GitHub 自身が「これが揃わないとマージさせない」と言っている集合**である。
⟹ 「マージしてよいか」を判定する道具の下限として、これ以上正しい集合は無い。

## 決定

### 1. `verdict()` は、期待する集合を**引数で受け取る**

`verdict(checkRuns, requiredContexts)` とし、**第2引数を省略可能にしない。**

🔴 **省略できる形にすると、「取れなかったから従来どおり」で歯が静かに無効化される。**
⟹ **取れていない**（配列でない）ことは、**緑でも赤でもなく「判定しない」**として表に出す。

### 2. 「含まれているか」と「含まれたものが通ったか」を、両方・独立に見る

⛔ **存在だけ見て緑にしない。** required の各 context について、

1. check-run として**登録されているか**（`missing`）
2. 登録されたものが **`completed` か**（`pending`）
3. `completed` のものが **`success` か**（`nonSuccess`）

を見る。⚠ 3 は全体の `allSuccess` が論理的に覆っているが、**独立に書く**——
将来 `allSuccess` 側が変わったときに、この保証が黙って落ちないようにするためである。

### 3. 下限が取れなかったら、止める

**branch protection が引けなかったとき**（権限不足・API 失敗・保護設定が無い・
`contexts` が空配列）は、**緑にしない。**

> **機械に任せるなら「直す」ではなく「止める」。** 分からないときは人間に渡す。

⛔ 「引けなかったから従来どおり判定する」に倒さない。**それはこの歯を静かに無効化する。**

### 4. 終了コードは足さない —— 判定不能は `2`（pending）に寄せる

**【現物】既存は `0`=green / `1`=red / `2`=pending / `3`=実行時エラー。**
「集合が不完全で判定できない」に `4` を新設することを検討し、**採らなかった。**
⛔ **「検討しなかった」と後から読まれないよう、理由をここに残す:**

1. **意味論が合っている。**「集合が不完全で判定不能」は「**まだ分からない**」であり、
   それが `pending` の意味そのものである。
   **【現物】`docs/release-v1.md` §0.1 は既に「`2`（pending）は通過ではない」と明記している**
   ⟹ 必要な性質はもう保証されている。
2. **追随先が3箇所ある**——`docs/release-v1.md` §0.1 / `docs/autonomy.md` §2.1 / ADR 0132。
   ⛔ **3箇所に散った表を増やすのは、腐りの種を撒くことである**
   （この repo では、出荷物に焼き込んだ数字が実際に腐った先例がある）。
3. **決定的**: 呼び出し側は「**`0` なら通す、それ以外は止める**」で動いている。
   ⟹ **`4` を足しても振る舞いは1つも変わらず、追随漏れの危険だけが増える。**

⭐ **ただし条件**: `reason` の文言で「**走っている最中**」と「**集合が不完全**」を
区別できるようにする。**同じ終了コードに寄せるのは機械の側の話であり、
人が読む側の情報は落とさない。**

### 5. `green` の reason 文言は1バイトも変えない

**【現物】`docs/release-v1.md` §0.1 が `status=green — N件すべてが completed かつ success`
を逐語で引いている。** ⟹ 変えると文書が腐る。下限の情報は**別の行**として印字する。

## 🔴 この下限が守らないもの —— 名指しで書く

**【実測】CI の check は13本、うち required は6本である**
（[Issue #426](https://github.com/takecchi/mnemora/issues/426) が同じことを実測している）。

> **この下限が守るのは required の6件だけである。
> 残りの7本（`retrieval-quality` などの測定ジョブ）が *登録されたか* について、
> この道具は何も保証しない。**

⟹ required でない7本がまだ1本も登録されていなくても、required の6件が揃って success なら
**緑になる。** ⛔ **「残り7本は見なくてよい」とは書かない。** ⭐ **「この道具は、残りが
揃うのを待っていない」と書く。** この2つは全く違う——前者は判断であり、後者は範囲の申告である。

⚠ **ただし「登録された check は全部 success」は、required かどうかに関わらず要求し続ける**
（`summarizeCheckRuns` の `allSuccess`。旧来の振る舞いを1つも変えていない）
——required でない check が `failure` なら、この道具は `red` を返す。
⟹ **下限に入れていないのは「揃うのを待つ」ことだけであって、「落ちても見逃す」ことではない。**

**required でない7本を下限に入れなかった理由**: それらは**定義上マージをブロックしない。**
⟹ 下限に入れると、測定ジョブの遅れだけでマージが止まる（偽陽性が構造的に出る形になる）。

## 結果（この決定が招くもの）

- **`gh api .../branches/<base>/protection` の読み取り権限が、この道具の前提になる。**
  ⟹ 権限の無い器では、この道具は緑を出さない（`2` で止まる）。**それが意図した振る舞いである。**
- **`gh` の呼び出しが1本増える**（PR 1本あたり1〜2回）。
- **branch protection の設定を変えると、この道具の下限も変わる。**
  ⟹ required を減らすと、下限も黙って下がる。**これは引き受けた負債である**——
  下限の権威を外へ出した以上、権威の側が緩めば下限も緩む。

## これが覆るとしたら

- **branch protection ではなく rulesets へ移行したとき。**
  `branches/<base>/protection` は ruleset 由来の必須チェックを返さないことがある
  ⚠（**この点は確かめていない**）。移行するなら、下限の取得先を
  `repos/{repo}/rulesets` 側へ変える必要がある。
- **required を0件にする運用に変えたとき。** この決定は「required が下限である」に
  乗っているので、required が空なら下限が消える ⟹ その場合この道具は止まる（決定3）。
- **「マージしてよいか」の権威が GitHub の外へ出たとき**（外部 CI を classic Commit Status
  API で受ける等）。⚠ **今回、classic Commit Status API は見ていない。**

## 確かめたこと・確かめていないこと

- **確かめた**【実測】: 報告された「0件で緑」が、10通りの撃ち方すべてで再現しないこと。
- **確かめた**【実測】: `verdict()` が、1件だけ・3件だけの部分集合に対して `green` を返すこと。
- **確かめた**【実測】: `needs: postgres` に由来する窓が直近 `main` 30本のうち **7本**で
  実際に開いていること、その7本すべてで幅が**最大1秒**であること。
- **確かめた**【実測】: `required_status_checks.contexts` が6件返り、その中に
  遅れて登録される `両方の server_encoding regime …` が含まれること。
- **確かめた**【実測】🔴 **直す前と直した後を、同じ入力で撃った。** 偽の `gh` を `PATH` に置き、
  required 6件のうち**5件だけが登録済み・その5件は全部 `completed` かつ `success`** という
  「部分登録の窓」を合成して CLI 全体を走らせた:

  | コード | 出力 | 終了コード |
  | --- | --- | --- |
  | 直す前（`798534f`） | `status=green — 5件すべてが completed かつ success` | **`0`** |
  | 直した後 | `status=pending — 必須チェック6件のうち1件がまだ登録されていない（集合が不完全）: c6` | **`2`** |

  **陽性対照**: 同じ器で6件すべてを登録させると、直した後のコードも
  `status=green — 6件すべてが completed かつ success` / `0` を返す
  ——⟹ **止まるようになったのは「集合が不完全なとき」だけであって、緑を出せなくなった
  わけではない。**
- **確かめた**【実測】: 実物の `gh` に対する両方向——`main` 先端 `798534f` で `exit 0`（green、
  下限6件を印字）、check-runs が0件の sha で `exit 2`、存在しない base を渡して下限が
  引けないときも `exit 2`（警告つき）。
- **確かめた**【実測】: 歯の変異試験。`missing` 分岐を `if (false && …)` に潰すと、
  「部分登録の窓」の歯**1件だけ**が `expected 'green' to be 'pending'` で落ちる
  ——⟹ **この歯は、壊したときに実際に鳴る。**
- **確かめた**【実測】: 今夜（24時間以内）`main` へ着地した **81件**すべてについて、
  **PR head sha 側の check-runs は 81/81 が 13/13 `success`** であり、0件のものは無かった。
  ⛔ **これは「だから門の判断は正しかった」を意味しない**——窓はたまたま踏まれなかっただけである。
- 🔴 **確かめていない**: 報告者が実際に何を見て「0件で緑」と報告したか。
  **別の sha・別のブランチ・別の版を見た可能性も、`pending` 全般を「0件」と読んだ可能性も、
  どちらも排除できていない。**
- 🔴 **確かめていない**: 部分登録の窓が、`needs:` 以外の由来（queue 遅延・複数 workflow の
  登録ずれ・API の一時的な不整合）でどれだけ開くか。**測っていない。**
- 🔴 **確かめていない**: 今夜の81件のうち、門が**実際にどの時点の**判定を見てマージしたか。
  引き直したのは事後の状態であり、当時の観測ではない。
- 🔴 **確かめていない**: この PR の CI が緑になること（CI 側の結果を見るまで確認できない）。
  PR 本文で報告する。
