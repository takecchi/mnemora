# ADR 0208: `SKIP LOCKED` が「詰まらないこと」を守っている、という主張に歯を足す（ADR 0206 の宿題）

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-17

**⚠ 各主張の出所を分ける**（ADR 0204 / ADR 0205 / ADR 0206 と同じ体裁）。

- **【現物】** — この repo のコード・文書を書き手が読んで確かめた。
- **【実測】** — この書き手が自分の手で走らせて確かめた。
- **【受】** — 報告として受け取り、再導出していない（出所を明記する）。

---

## 問い

**`SKIP LOCKED` が何を守っているのかを、誰も測っていなかった。**

[PR #447](https://github.com/takecchi/mnemora/pull/447)（MERGED、`91fee2e`）は、ADR 0206 の実測
（「`SKIP LOCKED` を外しても二重 claim は起きない」）を `packages/postgres/src/outbox-store.ts`
の docstring に写し、次の ⚠ を残したまま閉じた。**【現物】** 逐語:

> ⚠ **`SKIP LOCKED` が実際に詰まりを減らすことは測っていない。** 上が見ているのは正しさ側
> だけであり、「詰まらないこと」は機構からの推論である。

**本 ADR は、この ⚠ を埋める。**「詰まらないこと」を実際に測り、それを守る歯を
`packages/postgres` 側に足す。

---

## 測ったこと

### 【受】背景として渡された実測（同一セッションの別の担い手、2026-09-17、`main` = `884902a`、手元の Postgres 17）

**この書き手は以下を自分で再導出していない。** マネージャーから報告として受け取った数字である。

- **仮説A（ブロッキング）は支持された。** 外部トランザクションが対象行のロックを
  `holdMs=800` 保持している状態で `claimBatch` 相当を撃つと: `FOR UPDATE SKIP LOCKED`
  （変異なし）は **1.3〜2.7ms で 0 件**（正しくスキップ）。`SKIP LOCKED` だけ外すと
  **802〜843ms 待って 1 件**。丸ごと削ると **802〜863ms**。⟹ **2〜3桁の差。**
- **`lock_timeout` を掛けると離散的になる。** 保持側がロックを持ったまま claimer 側に
  `lock_timeout = '100ms'` を掛けると: 変異なしは**成功・0件・3.8ms**、`SKIP LOCKED` を
  外すと **エラー `55P03`（canceling statement due to lock timeout）・105ms**。
- **仮説B（`LIMIT n` の下で取りこぼす）は反証された。** `SKIP LOCKED` だけ外した構成で
  延べ **55ラウンド、取りこぼし0**。⟹ **`FOR UPDATE` だけでも取りこぼしは起きない**
  （PostgreSQL の LockRows は再評価で候補が落ちたとき下位スキャンから取り直す）。
- 🔴 **ADR 0206:119 の主張が再現しなかった。** ADR 0206 は逐語で
  「【実測: ジョブ5本・`limit=3`・4並行で、合計が5未満になるラウンドが出た】」と書いているが、
  同じパラメータ・変異なしで **50ラウンド撃って一度も5未満にならなかった**。
  ⚠ **これは「ADR 0206 が誤り」ではない**——タイミング依存の稀な事象でありうる。
  **主張できるのは「50ラウンドでは出なかった」だけである。**
  ⛔ **ADR 0206 の本文は1バイトも書き換えていない**（このリポジトリは ADR を記録として
  残す規律である。[ADR 0040](./0040-zero-vector-never-returned.md)「その後」節が
  「⛔ 上の本文は1バイトも書き換えていない。当時そう書いた経緯ごと残す」と同じ形を採っており、
  `docs/roadmap.md` §7.0 の「腐ったなら『腐った』と書いて残す」規律とも整合する）。
  ここに「再現しなかった」と記録するにとどめる。

### 【実測】この書き手が自分で走らせた変異試験

器: `docs/autonomy.md`「手元で Postgres を立てる」節の手順で立てた、専用ポート
（`57531`）・専用 PGDATA の PostgreSQL 17。共有インスタンスには触っていない。
`⛔ git checkout` は使わず、`cp` で `packages/postgres/src/outbox-store.ts` を退避・復帰した。

**歯**: `packages/postgres/src/__tests__/outbox-skip-locked-non-blocking.postgres.test.ts`
（下の「決定」参照）を、`pnpm --filter @mnemora/postgres exec vitest run <file> -t <name>`
で1本に絞って走らせた。

| 変異                                             | 試行回数 | 結果                                                                                 |
| ------------------------------------------------ | -------- | ------------------------------------------------------------------------------------ |
| （変異なし・実装時）                             | 5        | 5回とも **GREEN**                                                                    |
| **`SKIP LOCKED` だけ外して `FOR UPDATE` にする** | 3        | 3回とも **RED**（`55P03`、`where: 'while locking tuple ... in relation "outbox"'`）  |
| **`FOR UPDATE SKIP LOCKED` を丸ごと削る**        | 3        | 3回とも **RED**（`55P03`、`where: 'while updating tuple ... in relation "outbox"'`） |
| （原本に `cp` で復帰）                           | 3        | 3回とも **GREEN** に戻る                                                             |

⟹ **合計8回の緑（偽陽性なし）・6回の赤（偽陰性なし）。** 復帰後に
`git status --porcelain` を確認し、意図した差分（本ファイルの追加・
`outbox-store.ts` の docstring 追記・新規テストファイル）だけであることを確認した。

⚠ **「丸ごと削る」が RED になったのは想定どおりだが、根拠は【受】の背景実測とは別経路である**
——【受】は `holdMs=800` のブロッキング実測、ここでの `55P03` はロック待ちの相手が
`UPDATE ... FROM claimable` 側（`while updating tuple`）である点が「`SKIP LOCKED` だけ外す」
（`while locking tuple`、CTE の `SELECT ... FOR UPDATE` 側）と違う。**どちらも `lock_timeout`
を跨いで例外になる、という結論は同じだが、ロックを取ろうとしている SQL 文の場所は違う。**

## 決定

### 1. `PostgresOutboxStore.claimBatch` を直接呼ぶ肯定側の歯を `packages/postgres` に足す

`packages/postgres/src/__tests__/outbox-skip-locked-non-blocking.postgres.test.ts` を追加した。
形は次のとおり:

1. `getTestClient()` の pool から1本借り、唯一の claim 可能なジョブの行ロックを保持する
   （`BEGIN; SELECT id FROM outbox WHERE id = $1 FOR UPDATE;` コミットしない）。
2. claimer 用に `lock_timeout` を積んだ専用クライアントを作る。**`createPostgresClient`
   は第2引数の `PoolConfig` を素通しし、`options` は `pg.Pool` の startup parameter として
   実際にサーバへ渡る設計**（`client.ts` の doc コメント、`pg@8.23.0` のソースで確認済みと
   明記）:

   ```ts
   createPostgresClient(requireDatabaseUrl(), { options: "-c lock_timeout=100ms", max: 1 });
   ```

3. その db の上に本番の `PostgresOutboxStore` を作り、`claimBatch` を呼ぶ。
4. 主張: 例外を投げずに解決し、0件を返す（＝ロックされた行をスキップして詰まらなかった）。
5. `finally` で `ROLLBACK` してホルダー側のロックを解放し、claimer 側のクライアントを閉じる。

**判定は所要時間の閾値ではなく、例外が出たか出なかったかという離散的な結果である。**
ホルダーのロック保持は `finally` まで確実に続くので、`lock_timeout=100ms` を跨ぐ余裕が
構造的に在る。⛔ **`expect(elapsed).toBeLessThan(...)` のような連続値の閾値は使っていない**
——CI ランナーの負荷で「たまに赤い」を生む類の作りを避けた。

### 2. `outbox-store.ts` の docstring を「測った結果」へ更新する

PR #447 が残した ⚠（「`SKIP LOCKED` が実際に詰まりを減らすことは測っていない」）は
**そのまま残す**（記録として消さない）。その直後に、本 ADR が埋めたことを追記する形にした
——上の歯の存在と、外すと `55P03` で赤くなることを指す一文、および「実運用の throughput
そのものはまだ測っていない」という新しい ⚠ を足す。

## 採らなかった案

### 案1: 手書き SQL に対して `55P03` を確かめる形

⛔ **採らない。** 本番コードを一切通らない——`outbox-store.ts` から `SKIP LOCKED` を消しても
その歯は緑のままである。[Issue #424](https://github.com/takecchi/mnemora/issues/424) が
「赤くならないなら、その歯は飾りである」と戒めた形そのものになる。

### 案2: 所要時間の閾値（`expect(elapsed).toBeLessThan(...)`）で判定する

⛔ **採らない。** flaky になる——CI ランナーの負荷で実行時間は容易に伸び縮みする。
「例外が出たか出なかったか」という離散的な結果のほうが、閾値を選ぶ手間も揺れも無い。

### 案3: `packages/testkit` の適合 suite に置く

⛔ **置けない。** `testkit` は store 非依存で `OutboxStore` interface 越しの操作しか
受け取らず、生の接続（`BEGIN` / session レベルの `lock_timeout`）を触れない。加えて
`55P03` は PostgreSQL 固有の SQLSTATE であり、他 adapter に移植できる契約になっていない
——「適合テスト」は adapter 間で共通に要求できることだけを載せる場であり、この歯は
その条件を満たさない。

### 案4: 取りこぼし（仮説B）を歯にする

⛔ **守るべき壊れ方が無い。** 【受】の背景実測で、`SKIP LOCKED` だけを外した構成でも
延べ55ラウンド取りこぼし0だった。歯は「実際に起きうる壊れ方」を守るためのものであり、
反証済みの仮説を検査対象にする理由が無い。

## 引き受けた負債

### 1. 単一プロセス内までしか測っていない

【実測】も【受】も、同一プロセス内の複数コネクション（`pg.Pool` から借りた別々の
接続）までである。複数プロセスが実際にネットワーク越しに撃つ状況は、いまも測っていない
——ADR 0206「引き受けた負債」2番と同じ限界がここにも残る。

### 2. `lock_timeout` を本番設定に入れるべきかは判断していない

`client.ts` は現状 `lock_timeout` を設定しない——`Pool` はデフォルトで無期限に待つ。
本 ADR の歯は**歯の中の claimer 専用クライアントにだけ** `lock_timeout=100ms` を敷いて
いるのであり、`PostgresOutboxStore` が実運用で使う `Pool` の既定を変えたわけではない。
実運用に `lock_timeout` を入れるべきかどうかは、この ADR の範囲外——**判断していない。**

### 3. 仮説Bの反証は試した範囲以上を主張しない

【受】の55ラウンドは「起きなかった」だけであり、「起きない」ことの証明ではない。
ADR 0206「測ったこと 3」が「1ラウンドでは実際に取りこぼす」ことを実測で示している
ことと合わせて読むと、**ラウンド数を増やせば見え方が変わる可能性は排除できていない。**

### 4. 実運用の throughput（詰まりの量的な影響）はまだ測っていない

本 ADR の歯が測っているのは「ロックが在るときにブロックせず抜けられるか」という
*機構*であり、「`SKIP LOCKED` が無いとき、実運用でどれだけ処理が遅延するか」という
定量的な throughput の影響はいまも測っていない。【受】の `holdMs=800` の実測は
「1回の claim 呼び出しがどれだけ待つか」であって、複数ワーカー・複数ラウンドを通した
定常状態のスループット計測ではない。

## これが覆るとしたら

- **`packages/bullmq` が入り、複数プロセスの同時 claim が既定経路になったとき。**
  ⟹ 負債1（単一プロセス内までしか測っていない）が実害になる。ADR 0206 が同じ条件で
  同じ注意を残している。
- **本番の `Pool` に `lock_timeout` を設定する決定がされたとき。** ⟹ 負債2の判断が
  必要になる。本 ADR はその判断を先送りしている。
- **仮説Bの反証を、より大きなラウンド数・より高い並行数で確かめ直したくなったとき。**
  ⟹ 負債3のとおり、55ラウンドという試行数以上のことは主張していない。測り直すこと。
- **ADR 0206:119 の主張（合計が5未満になるラウンド）を再現する条件が見つかったとき。**
  ⟹ 「タイミング依存の稀な事象」という仮説が裏付けられる。逆に、今後も長期間
  再現しなければ、ADR 0206 のその実測がどのような条件（Postgres のバージョン・負荷・
  他プロセスの干渉）で起きたのかを、別途 issue で追う価値が出る。
