# ADR 0703: 矛盾検出の精度を、カテゴリごとの Precision/Recall/F1 で測る評価を足す——決定的な段を oracle 鍵で測り、アルゴリズムは変えない

- **状態**: 採用 (2026-11)
- **日付**: 2026-11-10

**これは担い手（Claude Code のセッション）の判断で、オーナーの判断ではない**（[ADR 0220](./0220-issue-comment-author-does-not-distinguish-owner-from-agent.md)）。
出所は、対話セッションの利用者の依頼「v2.0.0 で入れたい: 記憶の信頼性・整合性の改善」の課題B（矛盾検出の評価拡充）。Issue [#2112](https://github.com/takecchi/mnemora/issues/2112)。依頼の方針は「まず既存実装の精度を測定し、問題が確認された場合に限ってアルゴリズムを改善する」「評価結果を上げる目的で LLM 判定や複雑な仕組みを足さない」である。
出所の区別: 【現物】は読んだコード・文書、【実測】は手元で走らせた結果（docker の `pgvector/pgvector:pg17`）、【判断】は担い手の判断。

**⚠ この ADR の番号は仮である。** マージの直前に `node scripts/adr-renumber.mjs` が確定する（[ADR 0179](./0179-adr-number-assigned-at-merge.md)）。

## 文脈【現物】

矛盾・訂正の扱いは、互いに独立した2系統である。

1. **claim key による `contested` の検出**（opt-in）。
   - 鍵の生成は LLM（`claim-key.ts`）である。
   - 検出は決定的で、LLM を呼ばない（`runtime.ts` の `detectClaimKeyContested`）。次の条件を全部満たす相手がいると、衝突として報告する。
     - 同じテナント・同じ主語・同じ鍵
     - 有効期間が重なる（null は無期限）
     - 本文が違う（NFC + trim）
     - 同じ observation の兄弟ではない
   - 衝突を報告すると `contested` の印を付ける。統合も解決もしない。
2. **訂正の相手探し**（`findCorrectionCandidates`）。`recall()` で上位 k 件を返すだけで、判定しない（[ADR 0232](./0232-correction-candidates-returned-not-chosen.md)「mnemora は選ばない」）。

既存の評価は、系統2の検索の質（`correction-candidates` ベンチ。hit@k・MRR・誤爆）だけが CI にあった。系統1の判定は、ADR 0324・0326・0334 に一度きりの実 LLM の記録として残るだけで、カテゴリ別の P/R/F1 を出す仕組みは無かった。

## 何を決めたか【判断】

1. **系統1の決定的な段を測る `contested-detection` を `examples/chat` に足す。**
   - 抽出の結果と claim key を、理想どおりの値に固定する（oracle）。⟹ LLM の揺れを混ぜずに、アルゴリズムそのものの判定を測る。
   - 本物の Postgres で、ケースごとに新しいテナントを作り、発話を順に `observe()` する。
   - 「陽性」は、検出が衝突を報告したこと（`contested`・`contested_group`・`unresolved_conflict`）と定義する。
2. **ケースは5カテゴリ×4件の20件にする。**
   - 検出されるべき: 同時点の矛盾、明示的な訂正。
   - 検出されるべきでない: 言い換え、時間的に両立、矛盾しない別の情報（別主語・別述語・多値の属性）。
   - 依頼の「矛盾しない情報の誤検出」「矛盾を検出できないケース」は、カテゴリではなく FP・FN として数える。
3. **いまの判定を、ケースごとに DB テストで固定する**（`contested-detection.postgres.test.ts`）。既知の誤検出・見逃しも含めて固定する。「正しい表」ではなく「測った表」であり、検出のコードを変えればここが動く。
4. **CI の新しいジョブは足さない。**DB テストが `examples/chat` のジョブで走り、判定を固定している。門ではなく、変わったら気づく歯である。
5. **アルゴリズムは変えない**（下の「分かったこと」）。
6. **系統2は、分類器としては測らない。**判定しない設計（ADR 0232）なので、P/R を「分類器の数字」として並べると誤読を招く。下に、既存のベンチの数字を記録するだけにした。

## 測ったこと【実測】

`contested-detection`（2026-11-10、手元）の結果。

| カテゴリ | 検出されるべきか | 件数 | 検出した | 外れ |
|---|---|---|---|---|
| 同時点の矛盾 | される | 4 | 4 | — |
| 明示的な訂正 | される | 4 | 3 | 同じ発話の中の言い直し（FN） |
| 言い換え | されない | 4 | 3 | 「好きな色は青／青色が一番好き」など3件（FP） |
| 時間的に両立 | されない | 4 | 2 | 年が本文にだけあり、期間を構造化していない2件（FP） |
| 別の情報 | されない | 4 | 2 | 多値の属性（趣味・話せる言語）2件（FP） |

**全体: TP 7 / FP 7 / FN 1 / TN 5、Precision 0.500 / Recall 0.875 / F1 0.636。**

期待どおりだったもの:
- 空白だけの違いは、検出されなかった。
- 期間を構造化した両立する対は、検出されなかった。
- 別主語・別述語は、検出されなかった。

### 系統2（参考。既存の `correction-candidates` ベンチ、`local` 埋め込み、手元で1回）

- A群（訂正の相手が実在する、21件）: hit@1 20/21、hit@3 21/21、MRR 0.976。
- B群（相手が居ない、32件）: 深い誤爆 20/32。種類ごとの内訳は次のとおり。

  | 種類 | 深い誤爆 |
  |---|---|
  | negation | 8/8 |
  | other_period | 8/8 |
  | other_person | 4/8 |
  | vague | 0/8 |

- 整数の指標は、基準値 `correction-candidate-probe-baseline.json` と一致した。
- B群の誤爆が多いのは設計どおりである。判定は採用者に委ねる（ADR 0232）。

### 実 LLM を通した系統1（再実行していない。過去の ADR の記録）

- ADR 0324（gpt-4o-mini）: 真の訂正 5/5。無関係な話題の誤検出 9/30。原因は、別人の発話の主語を本人に誤帰属したこと。
- ADR 0326・0334（answer 経路、14ケース×6回）: 訂正4件のうち contested が成立したのは、1回あたり0〜1件（recall 約0.08）。原因は、predicate がターンをまたぐと揃わないこと。
- ⟹ 実運用の recall を下げている主因は、決定的な段ではなく LLM の鍵生成である。

## 分かったこと、アルゴリズムを変えなかった理由【判断】

決定的な段で確かめた外れは4種類だった。どれも、LLM を足さずに直す決定的な手が無い。

| 外れ | 原因 | 決定的に直せない理由 |
|---|---|---|
| 言い換えの誤検出 | 本文が違えば矛盾とみなし、意味の同一性を見ない | 意味の判定が要る。埋め込みの類似度で間引く案は、真の矛盾（「青」と「赤」）も類似度が高く、実測なしには採れない |
| 本文にだけ年がある対の誤検出 | 期間が null なら無期限として重なる | 期間の構造化は抽出（LLM）側の責務。ADR 0491 の (a)(b) がオーナー判断待ち |
| 多値の属性の誤検出 | 同じ述語に複数の値が両立する属性を区別しない | 述語の性質（多値か）の知識が要る。今回初めて測った |
| 同じ発話の中の言い直しの見逃し | 同じ observation の兄弟を検出の対象外にしている | ADR 0377 の既知の損失 |

あわせて、**誤検出の結果は `contested` の印だけである。**記憶を統合も削除もせず、解決は呼び出し側に委ねる（北極星の「矛盾を勝手に統合・解決しない」）。誤検出のコストは「解決を求める印が増える」ことで、記憶を失うことではない。⟹ 依頼の方針どおり、今回はアルゴリズムを変えない。

## 採らなかった案

- **LLM に矛盾かどうかを判定させる。** 依頼が明示的に除外している。
- **埋め込みの類似度で言い換えを間引く。** 真の矛盾も類似度が高いので、実測なしには採れない。
- **門にする。** 1カテゴリ4件では、偽陽性率に上限を置けない（AGENTS.md）。
- **系統2の B群に言い換え・時間的に両立の種類を足す。** 系統2は判定しないので、誤爆が増えるだけで新しい情報にならない。

## 引き受けた負債

- 件数が少ない（カテゴリごとに4件）。実運用の分布ではない。
- 鍵を固定しているので、実 LLM の鍵の揃い方は測っていない。実 LLM で測るなら、recorded のカセットで段2（鍵の一致率）を足すのが次の手である。
- 多値の属性の誤検出は、述語の性質を claim key に持たせる（例: 多値の印）なら直せる見込みがある。ただし LLM の出力を足すことになるので、今回の範囲の外とした。

## 追記（2026-11-10）: claim key を本物の LLM に付けさせた測定【実測】

上の「引き受けた負債」の2つ目（実 LLM の鍵の揃い方は測っていない）を測った。`MNEMORA_CONTESTED_CLAIM_KEYS=openai` で、claim key の要求だけを `gpt-4o-mini`（実 API）に回した。抽出は oracle のままで、同じ20件を3回走らせた。生の結果は `examples/chat/bench-results/contested-detection-openai-claim-keys-2026-11-10/` に置いた。

| 実行 | TP | FP | FN | TN | Precision | Recall | F1 |
|---|---|---|---|---|---|---|---|
| oracle 鍵（上の表） | 7 | 7 | 1 | 5 | 0.500 | 0.875 | 0.636 |
| 実 LLM 1 | 5 | 4 | 3 | 8 | 0.556 | 0.625 | 0.588 |
| 実 LLM 2 | 4 | 4 | 4 | 8 | 0.500 | 0.500 | 0.500 |
| 実 LLM 3 | 3 | 4 | 5 | 8 | 0.429 | 0.375 | 0.400 |

- **Recall が下がる原因は、LLM が付ける述語の名前がターンごとに揃わないこと**だった。例: 勤め先は `employment_industry` と `employment`、アレルギーは `egg_allergy` と `has_allergy_to_soba`、居住は `location` と、`location`／別の名前で揺れた。名前が違えば決定的な段は別の鍵として扱う。ADR 0326 (c) と同じ原因である。
- 同じ揺れで、言い換え（`has_pet` と `pet`）や時間的に両立する対（`living_location` と `residence_location`）が偶然見逃され、TN になった。誤検出の件数は4件で、3回とも変わらなかった（言い換え2件・年齢1件・多値の趣味1件は、述語が揃って誤検出になった）。
- 同じ入力でも、実行ごとに結果が変わった（F1 0.40〜0.59）。

**改善の候補（未実施）:** claim key を付けるときに、その主語で既に使われている述語の一覧をプロンプトに渡し、名前の再利用を促す。LLM の呼び出しは増やさず、既存の呼び出しに文脈を足す形である。依頼の制約（評価結果を上げる目的で LLM 判定や複雑な仕組みを足さない）との関係を、オーナーに確かめてから扱う。

## これが覆るとしたら

- 実運用の記録で、誤検出の印が解決の負担として問題になったとき。
- 決定的に言い換えを見分けられる手（実測で真の矛盾と分離できる指標）が見つかったとき。
- ADR 0491 のオーナー判断で、期間が null の扱いが変わったとき。表のうち時間のカテゴリが動く。
