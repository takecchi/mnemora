## 文脈 —— 「嘘をついた」のではなく「測っていない予告を、実測の口調で名乗った」

[Issue #577](https://github.com/takecchi/mnemora/issues/577) の調査で見つけた形である（[ADR 0260](./0260-answer-names-what-it-actually-runs.md) 文脈節）。**同じ画面に、予告と実測が並んでいた:**

| 行 | 出所 | 性質 |
|---|---|---|
| `[cassette] provider source: …` / `[cassette] 記録した応答を再生する: …` | `resolveRecordedRun`、**provider 構築の *前*** | **予告** |
| `[provider] LLM : …` | `printProviderMode`、**構築の *後*** ← `handle.llmMode` | **実測** |

⟹ ⭐ **[ADR 0223](./0223-cross-cutting-disciplines-extracted-from-the-adr-corpus.md) 決定5（名乗れないものを名乗らない）の「名乗れない」には、*まだ測っていない* が含まれる。**

## 🔴 測ったこと —— 両方の経路で、いま実際に食い違う

### 1. `recorded` 経路（⚠ **この ADR の書き手自身が悪化させた**）

[ADR 0260 追記](./0260-answer-names-what-it-actually-runs.md)（[PR #587](https://github.com/takecchi/mnemora/pull/587)）が「明示指定が勝つ」を入れた結果、**カセットを読んでも使わない実行が正規の道になった。** ⟹ その道で画面はこう出ていた【実測】:

```
[cassette] 記録した応答を再生する: … LLM=gpt-4o-mini(67件) 埋め込み=…/256次元(39件)
[provider] LLM       : @mnemora/testkit の決定的な擬似 provider
  ⚠ 読み込んだカセットは、この実行では使っていない
```

🔴 **「記録した応答を再生する」と名乗りながら、再生していない。Issue #577 が報告した欠陥そのものである。**
⛔ **そしてこれは CI が毎回緑で通していた**（`answer-cli.postgres.test.ts` の `deterministic` 明示の歯）。ADR 0260 決定4 の `cassetteIgnored` が2行下で否定しているだけだった。

⚠ **Issue #589 は「`openai` 経路に残っている」と書いた。⛔ 狭すぎた**——`recorded` 経路に、より直接的な形で在った。

### 2. `openai` 経路（Issue #589 が【推論・未検算】としていた主張）

**【実測】実 API を叩かずに測れた。** 鍵を置いたうえで `MNEMORA_LLM=deterministic MNEMORA_EMBEDDING=deterministic` を明示すると、`createProviders` は OpenAI provider を1つも構築せず（`usageMeter` も `llmMode`/`embeddingMode` が `"openai"` のときだけ作られる【現物】）、**鍵は一度も使われない。**

```
[cassette] provider source: openai(理由: OPENAI_API_KEY が在るため実 API)
[provider] LLM       : @mnemora/testkit の決定的な擬似 provider
```

⟹ 🔴 **画面が「実 API を叩く」と言いながら擬似 provider で走る。** これは **[ADR 0068](./0068-the-bench-must-not-lie-about-what-it-measured.md) が自分で踏んだと記録している状態そのもの**である（逐語「**画面には「実 API を叩く」と出しながら意味を持たない擬似 provider で走り、数字の表を出して EXIT=0 で終わる**」）。

### 🔴 なぜ食い違うのか【現物】

**`createProviders` は `decideProviderSource` を一度も呼ばない。** あちらが見るのは `MNEMORA_LLM`/`MNEMORA_EMBEDDING` と鍵の有無だけである。⟹ **source の判定と、実際に組まれる provider は、別の関数が別の入力から決めている。両者は原理的に食い違いうる。**

## 決めたこと

### 決定1. `[cassette] 記録した応答を再生する` → `[cassette] カセットを読んだ`

⭐ **名乗ってよいのは、その時点で実際に確かめたことだけ**——ファイルを読めたこと、中身が何件か。⛔ **「この実行が再生になる」は、まだ測っていない。**

### 決定2. `[cassette] provider source: …` → `[cassette] provider source の予定: …`

⭐ **判定そのものは真である**（`decideProviderSource` は確かにその source を選んだ）。⛔ **だが「実 API を叩く」という理由文が、結果の断定に読める。** ⟹ **「予定」と明示する。**

⛔ **`describeProviderSourceReason`（`providers.ts`）の理由文そのものは変えていない。** あれは純関数で独自の歯を持ち、**判定の理由**としては正しい。⟹ **射程の外に置き、下の「引き受けた負債」に書く。**

### 決定3. 断定の在り処を1行で指す

`[cassette]` 行の直後に、**「この行は『読めた』ことだけを言う。実際に何で走るかは下の `[provider]` 行が構築後の実測から出す」**を出す。

⛔ **これは注意書きではない。** 画面の読み方を変える**構造の一部**である——⭐ **どこが予定でどこが実測かを、画面自身が名乗る。**

### 決定4. 歯で、画面の文字列そのものを固定する

⭐ **赤の逐語が欠陥の中身を人間の言葉で残す**（ADR 0260 追記の陽性対照で得た形）。⟹ 文字列を直接 assert する:

- **既定の道**: `[cassette] カセットを読んだ` が出る ／ ⛔ **`記録した応答を再生する` が出ない** ／ `[provider] LLM : 記録した実 API 応答の再生（ADR 0051）` が出る
- **`deterministic` を明示した道**（＝再生しない実行）: ⛔ **`記録した応答を再生する` が出ない** ／ `カセットを読んだ` は出る（**読んだのは事実**）

## 検討して採らなかった案

| 案 | 落とした理由 |
|---|---|
| **(2)** 予告であることを注釈で足すだけ | ⛔ ADR 0068「**注意書きは足さない。注意書きは検査されない。形で塞ぐ。**」。⟹ 決定1・2 は**文字列そのもの**を変え、決定4 が**歯で固定**する |
| **(3)** 予告と実測の食い違いを検出して出力に焼く | ⭐ ADR 0260 決定4（`cassetteIgnored`）が既に**カセットについては**やっている。⛔ だが**予告そのものは残る** ⟹ 「名乗れないものを名乗らない」に届かない |
| `[cassette]` 行を provider 構築の**後**へ移す | ⭐ 最も筋が通る。⛔ **だがカセットを読めなければ `createProviders` が落ちる**（`requireCassette`、ADR 0051）——**読んだことを名乗る前に落ちる**と、利用者は何が起きたか分からない。⟹ **読んだ時点で名乗るのは正しい。名乗る内容を測った範囲に縮めるのが正しい** |
| `describeProviderSourceReason` の理由文を書き換える | ⛔ 純関数で独自の歯を持ち、**判定の理由としては正しい**。⟹ 射程の外（負債に記載） |

## 引き受けた負債

1. **`describeProviderSourceReason` の理由文（「実 API を叩く」「記録を再生」）は、依然として結果の断定に読める。**【現物】決定2 が「予定」と冠したので画面としては誤解を生まないが、⛔ **文字列そのものは直していない。**
2. **`examples/chat/README.md:46` の逐語「OPENAI_API_KEY があれば実 API、無ければ記録した応答を再生する」は、明示指定が在るときは真でない。**【現物】⛔ この ADR の範囲外。
3. 🔴 **「この実行が最後まで再生で通る」は、構築後にも分からない。**【実測、[Issue #583](https://github.com/takecchi/mnemora/issues/583)】`recorded` で組んでも、記録に無いプロンプトが出れば途中で例外になる。⟹ ⭐ **`[provider]` 行が名乗れるのは「何で組んだか」までであって「最後まで通るか」ではない。** ⛔ **この ADR はそこを塞いでいない。**

## これが覆るとしたら

- **`createProviders` が `decideProviderSource` を読むようになったとき。** ⟹ 予告と実測が構造的に一致し、決定2 の「予定」は要らなくなる。

## 確かめたこと

- **【実測】** `recorded` 経路・`openai` 経路の両方で、直す前の画面が食い違っていたこと（逐語を上に貼った）
- **【実測】** 直した後、両経路とも「予定」と「実測」が読み分けられること（exit 0）
- **【現物】** `createProviders` が `decideProviderSource` を呼ばないこと ／ `usageMeter` は `llmMode`/`embeddingMode` が `"openai"` のときだけ作られること

## 確かめていないこと

- 🔴 **実 API を叩く実行（鍵あり・モード無指定）は、走らせていない。** ⛔ **鍵を持っていない。** 上の `openai` 経路の測定は、**OpenAI provider が1つも構築されない条件**を作って名乗りの分岐だけを測ったものである【実測】——**実 API 側の挙動は測っていない。**
- **負債3（最後まで通るか）を名乗る形は、設計していない。**
- **`record` / `verify` サブコマンドの画面が同じ形かは当てていない**【推論・未検算】。
